# 商务标素材库与 Wiki 字段目录设计

> 本文是 [`20260604-业绩库素材库Wiki标签整合设计计划`] 的落地版正式设计文档。
> 上游计划解决「四类边界讲清楚」，本文解决「目录怎么摆、字段怎么定、Wiki 五表数据从哪来、物理移除业绩资产池要改哪些代码」。
> 本轮交付是**文档与对齐**，不在本轮直接改代码；第 6 章的改造点清单供后续实现使用。

## 0. 决策记录（本文据此展开）

| 决策点 | 选择 | 依据 |
| --- | --- | --- |
| `03-业绩资产池` 矛盾 | **物理移除，业绩库彻底独立** | 业绩库已是 `performance_*` 四表独立数据源，不再降格为通用素材普通文件夹 |
| 通用素材分类口径 | **前台六类、后台细分**：资格审查与基础证明 / 财务信用与合规声明 / 制造商与供应链材料 / 机型认证与测试报告 / 企业能力与供货业绩 / 表单模板与过程稿 | 参考「第四部分 资格审查文件」清单；前台目录服务工作人员上传和查找，不复刻资格审查清单；细分口径落到 `materialSubcategory`、`documentType` 和标签 |
| 「AI 填写」维度 | **提升为 `materialKind` 枚举值** | 处理方式是同一维度，不该 kind/tag 分裂，下游只查一个字段 |
| 目录展示与排序 | **展示名不带 `01-` 前缀**；排序交给 `sortOrder`，机器识别交给 `materialCategory` | 业务目录应便于商务标团队阅读；编号不应成为长期路径契约 |
| 字段落点 | 第一版优先落 `raw_files.ext_fields`，Wiki 从素材字段派生 | 素材库保持事实源，Wiki 只做索引和展示，不反向成为事实源 |
| 素材库构建逻辑 | **先建目录模板，再生成素材卡片** | `material_taxonomy` 承接目录骨架；`raw_files.ext_fields` 承接素材卡片字段；上传/清洗/人工修订只更新素材卡片，不让 Wiki 反写素材库 |
| Wiki 构建逻辑 | **确定性 Builder 投影五表** | Wiki 从素材卡片、业绩引用、模板映射和静态规则生成，不走自由生成；每张表有稳定键，便于覆盖更新和人工修订保留 |
| 本轮交付形态 | 正式内部设计文档（不改代码） | 与上游计划「本周重点是文档和对齐」一致 |

## 1. 背景与目标

商务标素材链路要同时处理四种东西：结构化数据（业绩）、原始/清洗文件（素材）、可检索摘要（Wiki 卡片）、检索与处理标识（标签）。本文把四者的**目录摆放**和**字段契约**钉死，避免后续实现时互相覆盖。

目标：

- 给出最终目录树（业绩资产池物理移除后，非业绩素材重分类后的形态）。
- 给「非业绩素材」定义一张统一的**素材卡片字段表**，与业绩库四表平级、独立、不混。
- 把 Wiki 五表的**数据来源**逐表标注，杜绝 Wiki 退化成文件目录镜像。
- 标签第一版收束为最小集，并把「AI 填写」收进 `materialKind`。
- 列出「物理移除业绩资产池」涉及的全部代码改造点与风险（供后续实现）。

## 2. 目录结构设计

### 2.1 最终目录树（业务展示名）

```text
商务标/
  通用素材/                       scope=standard
    资格审查与基础证明
    财务信用与合规声明
    制造商与供应链材料
    机型认证与测试报告
    企业能力与供货业绩
    表单模板与过程稿

  客户素材/{客户}/                scope=customer
    客户准入与专项证明
    客户专用响应口径
    客户模板与历史文件

  项目素材/{项目}/                scope=project
    招标要求与专项证明
    资格审查与商务响应成册
    项目过程稿与澄清文件

业绩库（独立数据源，不在素材目录树内）
  └─ performance_categories / performance_items
     performance_attachments / performance_item_attachments
     对象桶：bid-materials/performance-categories/...
```

要点：

- **业绩不再占用通用素材目录**。原 `03-业绩资产池` 删除；非业绩素材不是简单改编号，而是按真实投标材料重新归类。
- **业务目录展示名不带 `01-` 前缀**。人工界面、Wiki、文档统一展示自然名称；排序由 `sortOrder` 控制，机器识别由 `materialCategory` 控制。
- 业绩入口由 Wiki「素材总表」里的一张**引用卡片**承担（见 4.1），卡片指向业绩库 API，不复制合同本体。
- 客户素材与项目素材保留三段结构，但命名要明确区分客户级长期素材、招标文件里的项目要求、以及单项目最终成册响应，避免后续检索时把「客户通用口径」和「单项目响应」混在一起。

### 2.2 展示名、排序与路径契约

目标态采用**无编号业务展示名**。目录名称只表达业务含义，不承担排序和机器识别职责：

- `displayName`：给人看的目录名，例如 `资格审查与基础证明`。
- `sortOrder`：给界面和 Wiki 排序用，例如 10、20、30、40、50。
- `materialCategory`：给下游匹配、AI 填写、统计和自动路由用，例如 `qualification_evidence`。
- `storageKey` / `pathSlug`：如后续需要稳定对象桶路径，建议用英文 slug 或数据库 ID，不把 `01-` 写进长期契约。

实施时仍建议保留一个兼容过渡，避免历史目录、Wiki、拆分投递和对象桶路径同时震动：

| 方案 | 展示形态 | 优点 | 风险 / 代价 | 建议 |
| --- | --- | --- | --- | --- |
| A. 去编号展示名 + 字段排序 | 前端 / Wiki 展示 `资格审查与基础证明` 等自然名称；后端保留 `sortOrder` | 最终形态干净，商务标团队阅读自然，路径不被编号绑死 | 需要同步前后端目录常量、自动路由、历史路径映射 | 作为最终目标 |
| B. 路径兼容过渡 | 旧物理路径短期保留；前端 / Wiki 展示时去掉编号或映射为新名称 | 改动小，历史文件和脚本稳定 | 存储路径和展示名短期不一致，需要明确映射关系 | 若迁移窗口紧，第一阶段优先 |

本文下面的目录树按方案 A 展开；后续实现评审时可根据历史数据量和联调窗口决定是否先走方案 B。

> 风险提示：若历史数据中已有素材落在旧 `03-业绩资产池` 路径下，迁移前必须先把这些文件归位（业绩文件 → 业绩库；非业绩文件 → 对应新库），否则物理移除会留下孤儿文件。详见 6.5。

### 2.3 分类口径与真实素材映射

这版分类不是为了做一个更好看的目录，而是为了让下游标书生成能更稳定地判断：这份材料是资格审查证据、制造商/供应链证明、产品机型认证、企业能力素材，还是可填写模板。参考「第四部分 资格审查文件」后，目录设计采用**前台目录少、后台字段细**的原则：工作人员只面对六个通用目录；资格审查清单里的细项由 `materialSubcategory`、`documentType`、标签和待办清单承接。

这套分类的依据有三层：

1. **来自招标文件的资格审查清单**：第四部分要求的营业执照、资格声明、股东名单、银行资信、审计报表、生产许可、质量体系、240 小时试运行、供货协议、认证测试报告等，是目录划分的第一依据。目录不是按文件格式或部门习惯划分，而是按标书审查时的证据用途划分。
2. **来自商务标实际装订和响应动作**：有些材料是“投标人主体资格”，有些是“财务信用复核”，有些是“制造商/供应链承诺”，有些是“机型认证和测试报告”，有些只是待填写模板。它们在标书里的处理方式不同，不能全部塞进一个“资质”目录。
3. **来自后续 AI 检索和生成需要**：系统后续要判断某份材料能否整件挂载、是否需要 AI 填写、是否需要人工确认年份/有效期/完整版本。如果目录过细，工作人员难放；如果目录过粗，AI 难匹配。因此采用“前台六类、后台字段细分”的折中结构。

具体作用：

| 分类作用 | 解决的问题 | 对工作人员的价值 | 对系统 / Wiki / AI 的价值 |
| --- | --- | --- | --- |
| 降低上传认知成本 | 避免几十个资格审查细项都变成文件夹 | 只需判断材料属于六类中的哪一类 | 通过 `materialSubcategory`、`documentType`、标签继续细分 |
| 支撑资格审查成册 | 把主体资格、财务信用、制造商材料、机型报告拆开 | 更容易按招标文件补齐缺项 | Wiki 可按章节生成证据卡片和待确认清单 |
| 支撑客户 / 项目隔离 | 区分平台通用、客户长期复用、项目一次性材料 | 避免把项目过程稿误当通用素材 | 检索时可按 `standard/customer/project` 控制优先级 |
| 支撑 AI 填写与固定挂载 | 区分事实证据、模板、过程稿 | 知道哪些文件可直接引用，哪些需要填写 | `materialKind=fixed/ai_fill/other` 与目录分类配合使用 |
| 支撑风险复核 | 财务年份、信用查询时间、证书有效期、完整报告版本都需要确认 | 容易发现缺页、过期、年份口径不一致 | 自动进入 `04-待填写与待确认清单`，减少错误出稿 |

| 目录 | 收纳口径 | 样例素材 |
| --- | --- | --- |
| `资格审查与基础证明` | 资格审查章节里反复要求的投标人主体、股东关联、基础证照、开户证明和体系资质 | 营业执照、资格声明、股东名单、管理关系证明、基本户开户证明、三标体系证书、投标人基本情况证明 |
| `财务信用与合规声明` | 银行资信、审计报表、信用合规、诉讼/失信查询等需要按项目年份和查询时点复核的材料 | 银行资信证明、近三年审计报告、资产负债表、损益表、现金流量表、信用中国/国家企业信用截图、经济行为受诉情况、严重违法失信与失信被执行人查询 |
| `制造商与供应链材料` | 招标文件要求投标人和风电机组重点部件制造商分别提供或共同提供的制造商、许可、质量保证、供货协议类材料 | 重点部件制造商营业执照、制造商资格声明、生产许可证、鉴定材料、质量保证体系证明、主要部件供货协议、合作意向书、供应承诺书 |
| `机型认证与测试报告` | 与投标机型、风电机组、大部件、试运行、并网测试直接相关的认证和测试报告；虽然服务商务资格审查，但不混入投标人主体证照 | 机型设计认证、型式认证、电能质量测试报告、低电压穿越认证、高电压穿越认证、240 小时试运行证明、大部件型式认证 |
| `企业能力与供货业绩` | 用于基本情况表和正文能力陈述的公司组织、人员、设备、奖项、专利、类似供货业绩摘要等综合素材 | 公司基本情况、组织机构、人员状况、主要自有机械设备、制造基地介绍、服务能力介绍、专利奖项、国家级获奖情况、类似产品供货业绩概览 |
| `表单模板与过程稿` | 需要填写后才能进入标书的通用表单、声明、承诺函和商务响应模板；不作为事实证据本身 | 投标人基本情况表、资格声明模板、股东名单模板、三标体系认证情况表、经济行为受诉情况表、承诺函、授权书、商务偏差表、通用空表 |

后台细分不建议作为前台强制目录展示。第一版建议作为 `materialSubcategory` 推荐值，由上传路径、文件名、OCR、AI 分类或人工修订写入。

`资格审查与基础证明` 的后台细分建议：

| 后台细分 | 对应资格审查文件 |
| --- | --- |
| `投标人主体与基础证照` | 第 1 项营业执照、基本情况表里的注册信息、法定代表人、注册资本、经营范围等证明 |
| `股东关联与资格声明` | 第 2、3 项资格声明、股东名单、管理关系证明 |
| `管理体系与资质认证` | 第 7 项质量、环境、职业健康安全三标体系认证，以及投标人侧其他资质认证 |

`财务信用与合规声明` 的后台细分建议：

| 后台细分 | 对应资格审查文件 |
| --- | --- |
| `财务资信与审计报告` | 第 4、5 项银行资信证明、近三年资产负债表、损益表、现金流量表 |
| `信用合规与诉讼查询` | 经济行为受诉情况、严重违法失信企业名单、失信被执行人、信用中国等查询截图 |

`制造商与供应链材料` 的后台细分建议，用于解决「投标人和重点部件制造商应分别提供」的问题：

| 后台细分 | 对应资格审查文件 |
| --- | --- |
| `重点部件制造商主体资料` | 制造商营业执照、制造商资格声明、制造商基础信息 |
| `生产许可与鉴定材料` | 第 6 项投标人和制造商的生产许可证、有关鉴定材料 |
| `质量保证体系证明` | 制造商质量保证体系及质量认证证明 |
| `供货协议与供应承诺` | 第 9 项主要部件制造商与投标人的供货协议、合作意向、协议或供应承诺书 |

边界原则：

- 投标人自身的营业执照、资格声明、股东名单、基本户开户证明、三标体系证书优先放 `资格审查与基础证明`。
- 银行资信、审计报告、财务报表、信用查询、诉讼/失信说明优先放 `财务信用与合规声明`。
- 制造商或重点部件供应商提供的营业执照、资格声明、生产许可、鉴定材料、质量保证体系、供货协议和供应承诺，放 `制造商与供应链材料`；不要混入投标人主体证照。
- 机型、大部件、240 小时试运行、电能质量、低/高电压穿越等与产品或并网能力相关的报告，放 `机型认证与测试报告`；它们通常要求完整版本，`riskNotes` 必须提示「完整报告内容需复核」。
- 财务报表年份不要固化到通用目录名里。通用库只维护可复用的审计报告和财务报表素材；具体要求近三年是哪三年，应由项目素材里的招标要求或项目事实表驱动，例如同一文档中可能出现 `2022-2024` 与 `2023-2025` 两种口径，生成前必须进入待确认清单。
- 类似产品供货业绩资料如果只是概览、证明截图或能力陈述，可放 `企业能力与供货业绩`；合同、验收、项目明细等结构化业绩事实仍进入独立业绩库。
- 「公司介绍、制造基地、服务能力、质量专题、专利、获奖、装机图」归入 `企业能力与供货业绩`，它服务正文生成和能力陈述，不只是附件引用。
- 模板类材料即使文件名里带「承诺函」「授权书」，只要它是待填写底稿，优先归入 `表单模板与过程稿`，并通过 `materialKind=ai_fill` 或 `fixed` 标注处理方式。
- 客户素材 / 项目素材不再重复拆成上述六类；它们先按客户级、项目级三段收纳，具体类型用 `documentType`、`materialCategory`、`tags` 表达。

### 2.4 素材库构建逻辑（目录模板 + 素材卡片）

素材库第一版不要直接把「文件夹树」当成全部数据模型。建议拆成两层构建：

```text
目录模板 material_taxonomy
  └─ 定义 bidType / tier / displayName / sortOrder / materialCategory / pathSlug
      ↓
原始文件 raw_files
  └─ 挂到目录节点，保存原件 bucket/key 和基础身份字段
      ↓
清洗与分类
  └─ 回写 ext_fields：materialKind / documentType / summary / sourceRef / riskNotes
      ↓
素材卡片 material card
  └─ 由 raw_files + ext_fields 投影给 Wiki、匹配、AI 填写和人工审核
```

构建原则：

- **目录模板只负责收纳骨架**：哪些目录存在、展示叫什么、怎么排序、属于哪个 `materialCategory`。
- **素材卡片负责语义事实**：一份文件是什么、能做什么、是否可直接引用、是否要 AI 填写、有哪些风险。
- **上传时先落最小卡片**：创建 `raw_files`，写入 `tier / libraryPath / materialCategory / materialKind=other / tags=[] / reviewStatus=draft`。
- **清洗后补齐卡片字段**：清洗任务只补 `documentType / summary / applicableScene / sourceRef / riskNotes / clean*` 等字段；不把摘要写成唯一事实源。
- **人工修订只修卡片字段**：人工改分类、标签、处理方式、审核状态时，更新 `raw_files.ext_fields`；Wiki 后续重新生成时读取新值。
- **Wiki 不反写素材库**：Wiki 可保留人工备注，但不作为素材库字段事实源。需要回写的内容必须走素材卡片编辑接口。

### 2.5 目录模板字段

目录模板建议由后端 `material_taxonomy` 统一种子化，前端只读取展示，避免两端各维护一份不一致的常量。

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `taxonomyId` | 目录节点稳定 ID；可用数据库 ID 或稳定 slug | `qualification_evidence` |
| `bidType` | 标类 | `商务标` |
| `tier` | `standard` / `customer` / `project` | `standard` |
| `displayName` | 展示名，不带编号 | `资格审查与基础证明` |
| `parentPath` | 父级路径 | `商务标/通用素材` |
| `pathSlug` | 稳定存储或路由标识；不使用中文编号作为长期契约 | `qualification-evidence` |
| `materialCategory` | 目录对应的结构化分类枚举 | `qualification_evidence` |
| `sortOrder` | 展示排序 | `10` |
| `protected` | 是否为系统保护目录，不允许普通删除 | `true` |
| `children` | 第一版不建议在前台强制展示；后台细分由 `materialSubcategory` 承接 | `[]` |

第一版目录模板示例：

```json
{
  "bidType": "商务标",
  "tier": "standard",
  "displayName": "资格审查与基础证明",
  "parentPath": "商务标/通用素材",
  "pathSlug": "qualification-evidence",
  "materialCategory": "qualification_evidence",
  "sortOrder": 10,
  "protected": true
}
```

客户 / 项目素材的 `{客户}`、`{项目}` 是业务实例节点，不是固定模板节点；模板只定义实例节点下面的三段子目录。创建客户或项目素材根目录时，再把三段子目录实例化进去。

## 3. 字段层设计（本文核心）

目录只解决「文件放哪」。真正服务后续素材匹配 / AI 填写 / 正文生成的是**字段**。现状是：业绩库字段体系完整（四表 + JSONB），但**非业绩素材**只有 `tier`、`businessMaterialKind`、`tags` 三个弱字段。本章补齐。

### 3.1 处理方式维度：materialKind 扩枚举

**现状**：`materialKind` 只有 `fixed`（固定素材）/ `other`（其他）两值。「AI 填写」散落在标签里。

**改为**：

| 值 | 标签 | 含义 | 下游用途 |
| --- | --- | --- | --- |
| `fixed` | 固定素材 | 可直接引用、无需修改 | 素材匹配、正文生成、人工审核直接引用 |
| `ai_fill` | AI 填写 | 需按项目事实表填写的 Word/表格模板 | AI 填写 → 人工复核 |
| `other` | 其他 | 暂未归类 | 兜底 |

这样「处理方式」收束到**单一字段**：下游判断一份素材该直接引用还是该走 AI 填写，只看 `materialKind`，不再 kind/tag 两处都查。标签则专注「检索维度」（见 3.3）。

`materialKind` 只回答「这份素材是否需要填写」。不要把它扩成下游动作字段。下游动作建议交给 `usageMode`：

| 字段 | 回答的问题 | 例子 |
| --- | --- | --- |
| `materialKind` | 这份素材处理前是否需要填写 | `fixed`、`ai_fill`、`other` |
| `usageMode` | 生成标书时怎么使用这份素材 | `attach_whole`、`fill_table`、`extract_fields`、`reference_only` |

例如：一张营业执照通常是 `materialKind=fixed` + `usageMode=attach_whole`；一份报价表空表通常是 `materialKind=ai_fill` + `usageMode=fill_table`；一条业绩引用通常是 `sourceType=performance` + `usageMode=reference_only`。

### 3.2 素材卡片字段表（非业绩素材的统一契约）

作为 Wiki「素材总表」的数据契约，与业绩库四表平级、独立。下表写的是**对下游暴露的素材卡片字段**，内部第一版仍可落在 `raw_files.ext_fields`。

| 字段 | 建议落点 | 写入 / 更新时机 | 主要消费者 |

### 3.3 标签第一版（检索维度）

`materialKind` 接管「处理方式」、`materialCategory` 接管「目录分类」后，标签只做**检索维度**，第一版预置最小集：

- 处理方式标签（与 `materialKind` 镜像，仅用于检索展示）：`固定素材`、`AI填写`
- 检索维度标签（设计预留，不强制）：`资格审查`、`投标人`、`制造商`、`重点部件`、`供货协议`、`供应承诺`、`240小时试运行`、`穿越测试`、`资质`、`承诺函`、`证书`、`财务`、`信用`、`合规声明`、`企业介绍`、`制造基地`、`服务能力`、`专利奖项`、`有效期`、`客户`、`项目`、`权限范围`

「人工补充」是否作为标签留待下次讨论，本版先写成处理结果，不进预置集（沿用上游 §4.5）。

### 3.4 与业绩库字段的关系

素材卡片字段表与业绩库四表**独立但对齐**：

- 独立：两套数据模型不混，素材走素材卡片，业绩走 `performance_*` 四表。
- 对齐：`reviewStatus`、`tags`、`scope/tier` 命名口径一致，方便下游统一处理。
- 汇合点：仅在「素材匹配」阶段汇合——匹配候选既可来自素材卡片，也可来自业绩库 `performance_items`（候选 `sourceType` 区分，见上游 Handoff §7.4）。

## 4. Wiki 五表设计（确定性 Builder + 人工备注层）

Wiki 定位是卡片 / 摘要 / 索引 / 检索辅助，**不是文件目录镜像**。商务 Wiki 第一版建议走确定性 Builder：从素材卡片、业绩引用、模板模块种子和静态规则投影五表；AI 只允许在骨架上补「判断/描述」，不能补不存在的价格、日期、证书编号、承诺或合同事实。

### 4.1 生成输入

| 输入 | 来源 | 用途 |
| --- | --- | --- |
| `materialCards` | 第 3.2 章素材卡片 API 投影，第一版来自 `raw_files + ext_fields` | 生成 `01-素材总表`、`03-证据卡片`、`04-待填写与待确认清单` |
| `performanceRefs` | `performance_*` 四表投影出的引用卡片 | 进入素材总表和证据卡片，但只引用业绩库，不复制合同本体 |
| `moduleSeeds` | 商务标模板模块清单；当前 builder 已有 BM-01 至 BM-13 | 生成 `02-模板模块映射表` 的固定模块骨架 |
| `templateCards` | `materialCategory=template_draft` 或客户 / 项目模板过程类素材 | 绑定模板模块、形成 AI 填写入口 |
| `staticRules` | 代码内置或配置化规则 | 生成 `05-使用规则` |
| `manualWikiNotes` | 旧 Wiki 人工备注、人工审核状态、人工置顶候选 | 重新生成时保留，不反写素材库事实字段 |

生成边界：

- 素材事实以素材卡片为准；Wiki 只读 `materialId/sourceType/sourceRef/reviewStatus/riskNotes` 等字段。
- 业绩事实以业绩库为准；Wiki 只生成 `sourceType=performance` 的引用行和证据摘要。
- 模板模块以 `moduleCode` 为准；模板文件只是候选素材，不反向决定模块是否存在。
- 人工在 Wiki 里写的备注只作为 `manualNote`、`manualOverride`、`reviewStatus` 保留；需要改素材分类、标签、处理方式时必须回素材卡片。

### 4.2 五表目标命名与迁移口径

目标五表如下：

| 顺序 | 目标节点 | 当前/历史命名 | 迁移要求 |
| --- | --- | --- | --- |
| 01 | `01-素材总表` | 同名 | 继续保留 |
| 02 | `02-模板模块映射表` | `02-章节映射表` | Builder 输出新名；消费侧短期兼容旧名 |
| 03 | `03-证据卡片` | `03-素材卡片` | Builder 输出新名；旧卡片节点迁移或兼容读取 |
| 04 | `04-待填写与待确认清单` | `04-待填写清单` | Builder 输出新名；旧名作为别名 |
| 05 | `05-使用规则` | 同名 | 继续保留 |

当前代码状态需要特别注意：`material_wiki_scope.py` 的五表常量仍是旧技术标式命名；商务缺口规划侧已经在识别 `02-模板模块映射表` 和 `03-证据卡片`。后续实现要统一到目标命名，并保留一段兼容期，避免已有 Wiki 数据和新生成数据互相不可见。

### 4.3 稳定键与覆盖策略

Wiki 重建必须是可重复、可覆盖的，不允许每次生成一批新节点。建议每张表定义稳定键：

| Wiki 表 | 稳定键 | 覆盖策略 |
| --- | --- | --- |
| `01-素材总表` | `sourceType + materialId` | 由素材卡片和业绩引用全量覆盖；人工备注字段保留 |
| `02-模板模块映射表` | `moduleCode`，多模板时用 `moduleCode + templateMaterialId` | 模块种子全量覆盖；候选素材按规则重算；人工置顶候选保留 |
| `03-证据卡片` | `sourceType + materialId + segmentId/main` | 身份、路径、来源、摘要和风险覆盖；人工确认状态、人工备注保留 |
| `04-待填写与待确认清单` | `blockerType + sourceType + materialId + requiredFact/riskCode` | 未解决项重算；已解决项仅在来源仍存在时保留状态 |
| `05-使用规则` | `ruleCode` | 静态规则覆盖；人工补充规则用 `manual-*` 前缀保留 |

建议把字段分成两类：

- **生成字段**：`title`、`materialCategory`、`materialSubcategory`、`materialKind`、`usageMode`、`candidateMaterialIds`、`sourceRef`、`summary`、`riskNotes`，每次 Builder 重算。
- **人工字段**：`manualNote`、`manualOverride`、`reviewStatus`、`owner`、`resolvedAt`、`pinnedCandidateIds`，重建时按稳定键合并保留。

### 4.4 五表字段模板

#### 01-素材总表

作用：给下游先快速知道「有什么素材、来自哪里、怎么用、是否有风险」。它不是目录树，也不展开原文。

| --- | --- | --- |
| `materialId` | 素材卡片或业绩引用 | `RAW-xxxx` / `PERF-ITEM-xxxx` |
| `sourceType` | Builder 投影 | `raw_file` / `performance` |
| `displayName` | 素材卡片 `displayName` 或业绩标题 | 展示名 |
| `tier` | 素材卡片或业绩 scope | `standard/customer/project` |
| `materialCategory` | 素材卡片或业绩引用分类 | 目录分类枚举 |
| `materialSubcategory` | 素材卡片细分分类 | 后台细分或资格审查细分口径 |
| `documentType` | 素材卡片 | 营业执照、授权书、报价表、证书等 |
| `materialKind` | 素材卡片 | `fixed/ai_fill/other` |
| `usageMode` | 素材卡片或模块规则 | `attach_whole/fill_table/extract_fields/reference_only` |

#### 02-模板模块映射表

作用：回答「标书某个模块应该先找哪些模板和证据」。这是 AI 填写、素材匹配和正文装配的共同索引。

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `moduleCode` | `moduleSeeds` | 稳定模块编码，如 `BM-08` |
| `moduleName` | `moduleSeeds` | 模块名称，如 `资格证明文件模块（附件7）` |
| `bidSection` | `moduleSeeds` 或招标目录映射 | 对应标书章节 / 附件 |
| `templateMaterialId` | 模板素材卡片 | 主模板素材；没有则留空 |
| `candidateMaterialIds` | Builder 规则匹配 | 候选素材卡片或业绩引用 ID |
| `fillStrategy` | `materialKind + usageMode` 派生 | `fixed/ai_fill/reference` |
| `usageMode` | 模块规则或素材卡片 | 下游动作 |
| `requiredFacts` | 模块规则 | 填写所需事实字段，如投标人、报价、机型、台数、投运年 |
| `outputType` | 模块规则 | 正文、表格、附件、证明材料 |
| `sourcePriority` | 使用规则 | `project > customer > standard > performance reference` |
| `needsHumanConfirm` | 风险规则 | 是否必须人工确认 |
| `missingHint` | 模块规则 | 找不到素材或事实时的补料提示 |

第一版模块种子可沿用现有 BM-01 至 BM-13，但路径匹配要从旧目录字符串升级为 `materialCategory / materialSubcategory / documentType / tags / sourceType` 组合判断。尤其 BM-09「业绩情况表模块」应优先引用业绩库，不再搜索 `通用素材/03-业绩资产池`。

#### 03-证据卡片

作用：给下游按需加载证据，不承载完整原文。证据卡片可以来自普通素材，也可以来自业绩引用。

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `cardId` | Builder 稳定生成 | `evidence:raw_file:RAW-0001:main` |
| `materialId` | 素材卡片或业绩引用 | 来源 ID |
| `sourceType` | Builder 投影 | `raw_file/performance` |
| `title` | 素材卡片 / 业绩标题 | 卡片标题 |
| `materialCategory` | 素材卡片 | 分类 |
| `materialSubcategory` | 素材卡片 | 细分分类 |
| `documentType` | 素材卡片 | 文件类型 |
| `evidenceTopic` | 规则/OCR/人工 | 资质、证书、财务、承诺、业绩引用等 |
| `applicableModules` | 映射规则 | 可用于哪些模块 |
| `evidenceFields` | OCR/抽取/人工确认 | 证书编号、有效期、投标人名称等 |
| `sourceQuote` | 原文摘录，可选 | 只摘录可回溯原文，不补事实 |
| `sourceRef` | 素材卡片或业绩引用 | 原件/清洗稿/API |
| `riskNotes` | 素材卡片和 Builder 风险规则 | 过期、OCR 低置信、版本不确定等 |
| `reviewStatus` | 素材卡片 / 人工备注层 | `draft/reviewed/rejected` |

高风险事实红线继续适用：金额、承诺、证书编号、合同事实必须能回到 `sourceRef` 和人工复核入口；`summary` 只能辅助检索，不能作为唯一依据。

#### 04-待填写与待确认清单

作用：把生成前必须处理的空白、低置信和风险集中成任务清单。

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `todoId` | Builder 稳定生成 | `todo:ai_fill:RAW-0001:报价` |
| `blockerType` | Builder 规则 | `ai_fill/low_confidence/missing_fact/risk_review/manual_confirm` |
| `moduleCode` | 模板模块映射 | 关联模块 |
| `sourceType` | 素材卡片 / 业绩引用 | `raw_file/performance` |
| `materialId` | 素材卡片 / 业绩引用 | 来源 ID |
| `requiredFact` | 模块规则或证据字段 | 待填写事实 |
| `reason` | Builder 规则 | 为什么阻塞 |
| `confidence` | 清洗/OCR/业绩匹配 | 置信度 |
| `matchMethod` | 业绩匹配或素材匹配 | 如 `row_order` 低置信 |
| `expectedAction` | 使用规则 | 填写、补料、确认、驳回、替换素材 |
| `status` | 人工备注层 | `open/resolved/ignored` |
| `owner` | 人工备注层 | 负责人 |
| `sourceRef` | 素材卡片 / 业绩引用 | 复核入口 |

进入清单的典型条件：

- `materialKind=ai_fill`，且绑定到模板模块。
- `riskNotes` 非空或 `evidenceFields.reviewStatus=draft`。
- OCR 置信度低、证照有效期未确认、清洗失败或仅有图片扫描件。
- 业绩匹配出现 `matchMethod=row_order`、`matchConfidence` 低于阈值，或缺少投运时间、容量、客户等关键事实。

#### 05-使用规则

作用：给下游 Agent 和人工审核写清楚裁决规则，避免生成时各自理解。

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `ruleCode` | 静态规则 | 稳定编码 |
| `scope` | 静态规则 | 适用范围 |
| `priority` | 静态规则 | 规则优先级 |
| `decision` | 静态规则 | `allow/block/require_confirm/prefer` |
| `description` | 静态规则 | 规则说明 |
| `appliesTo` | 静态规则 | 适用字段或模块 |
| `action` | 静态规则 | 下游动作 |

第一版必须包含的规则：

- 身份隔离：项目素材 > 客户素材 > 通用素材；不得跨项目、跨客户读取。
- 业绩引用：业绩库是独立事实源，Wiki 只引用，不复制合同本体。
- 高风险事实：金额、证书编号、承诺、合同事实必须 `sourceRef + 人工复核`。
- 处理方式：是否需要填写看 `materialKind`，生成动作看 `usageMode`。
- 裁决方式：模板模块匹配优先 `manualOverride`，其次 `project/customer/standard` 分层候选，最后才全文检索。

## 5. 业务调用链（字段视角）

```text

  ├─ 业绩：结构化解析 → performance_* 四表
  └─ 素材：素材清洗 → 素材卡片字段 + summary

        ↓

        ↓
素材匹配（素材卡片 + 业绩 performance_items 汇合，sourceType 区分）

        ↓

        ↓
正文生成
```
