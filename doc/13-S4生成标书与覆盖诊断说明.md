# S4 生成标书与覆盖诊断说明

> 用途：记录当前 `S4 生成标书` 和覆盖诊断的真实实现口径，避免继续沿用旧的独立拼装/校验阶段理解。
> 更新日期：2026-05-03

## 1. 当前结论

生成标书已替换为 `bid-tech-assembler` 技术标正文拼装链路。

核心逻辑是：

```text
S1 目录 JSON
  -> S1 Wiki 卡片
  -> S3 缺口处理计划与补料/AI 填写产物
  -> 当前素材库清洗后 Word
  -> bid-tech-assembler 拼装正文 docx
  -> 覆盖诊断校验未拼上的素材和未匹配目录项
```

旧的“初稿生成”和旧独立校验阶段不再作为主链路。`/coverage` 和 `coverage` 状态仍保留为诊断/导出检查能力，但不再是主流程独立节点。

## 2. 生成标书输入

后端准备一个历史内部工作目录 `s7_assembly_workdir`。这个名字为兼容旧脚本保留，业务语义是当前 `S4 生成标书`。

核心输入包括：

| 输入 | 来源 | 说明 |
|---|---|---|
| 目录 JSON | `S1 模板与目录` 输出 | 文件路径由后端 manifest 指定，当前支持 `bid-toc-json-v1` 的 `items[]` 结构 |
| `wiki/卡片/*.md` | S1 Wiki 导出 | 卡片承载 `skeleton_section`、`material_id`、`path`、`scope/category` 等素材定位信息 |
| `gap_plan.json` | `S3 缺口处理` 确认结果 | 记录匹配素材、人工上传、选择已有素材、AI 填写产物和完整性校验结果 |
| `素材库/技术标/通用素材` | 后端运行前导出 | 技术标通用素材中的清洗后 Word |
| `素材库/技术标/客户素材/{客户}` | 后端运行前导出 | 当前项目绑定客户的技术标客户素材 |
| `素材库/技术标/项目素材/{素材项目ID}` | 后端运行前导出 | 当前项目绑定素材项目的技术标项目素材 |
| `project_params.json` | 后端项目状态 + 目录 JSON + 投标机型 | 缺失字段以 `[待填写：xx]` 占位；技术标投标机型来自项目信息补全页已确认的 `turbineModel` |
| 有效正文模板 | 项目上传模板或设置侧系统默认模板 | 没有可用模板时应给出明确提示，不再静默读取第二层旧兜底模板 |

## 3. 后端执行流程

1. 校验目录已确认、缺口处理已确认。
2. 读取 `S1` 目录 JSON；如果文件缺失，回退使用 `outline_state.nodes` 生成兼容 JSON。
3. 读取 `S3` 的 `gap_plan.json`，并把缺口处理产物补充成可供拼装读取的素材卡片。
4. 复制 S1 `wiki/` 目录，或从素材库接口导出 Wiki。
5. 遍历 Wiki 卡片，按 `material_id` 优先下载清洗后 Word；没有清洗稿时尝试原始 Word。
6. 按项目身份过滤后，将技术标通用、客户、项目三档素材导出成 skill 能读取的文件系统结构。
7. 重写 Wiki 卡片 `path`，让卡片指向导出的相对路径。
8. 写入历史 manifest `s7_assembly_input.json`。
9. 调用：

```bash
python opencode/skill/bid-tech-assembler/scripts/run_from_manifest.py \
  --manifest <s7_assembly_input.json> \
  --response summary
```

10. 生成正文 Word，并复制到项目文档路径，供 `S5 共创` 和 `S6 导出` 继续使用。

## 4. 主要输出

| 输出 | 说明 |
|---|---|
| `投标文件-正文_*.docx` | `S4` 拼装出的技术标正文 |
| `assembly_plan.json` | 每个目录项的匹配状态、素材路径、占位状态 |
| `assembly_report.md` | 拼装审计报告 |
| `needs_review.md` | 人工确认清单，包括占位符、未匹配章节、适配项 |
| `fill_state.assembly` | 后端保存的拼装路径和报告索引 |
| `fill_state.coverage` | 覆盖诊断使用的素材拼装覆盖结果 |

## 5. 覆盖诊断当前逻辑

覆盖诊断当前不再按章节 `generationMode` 做 mock 覆盖。

它以 `S4` 的 `assembly_plan.json` 和导出的素材卡片为依据：

- `fullCover`：已经被拼装计划使用的素材数量。
- `noCover`：素材库中可用但没有出现在目录 JSON 或拼装计划中的素材数量。
- `partialCover`：目录中未匹配素材或需要人工确认的项数量。
- `tree`：按 `scope/category` 分组的素材拼装覆盖树。
- `partialItems`：未匹配目录项。
- `noCoverItems`：未拼装素材清单。

边界：

- 当前覆盖诊断是“素材拼装覆盖校验”。
- 正式版评分点覆盖审计还需要继续把招标评分点、正文段落、素材证据建立细粒度追溯。

## 7. 当前仍需后续完善

- 缺口处理产物当前已作为项目级真实文件参与拼装；是否沉淀为全局可复用素材库，需要单独补齐入库、版本和复用策略。
- 覆盖诊断从“素材拼装覆盖”升级到“评分点/证据/段落覆盖”。
- `needs_review.md` 的人工确认项可以进一步映射到前端可操作列表。
- 对素材 Word 的格式异常、横竖版错误、空章节等问题增加更明确的前端提示。
