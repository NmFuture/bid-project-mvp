> 方案依据：[23-商务标S3缺口处理预计方案计划.md](./23-商务标S3缺口处理预计方案计划.md)

## 1. 总体执行原则

### 1.1 核心路线

商务标 S3 第一版直接采用 Skill 路线：

```text
商务目录 + 商务解析结果 + 商务 Wiki + 商务素材索引 + 商务所用机型
  -> bid-business-gap-planner
  -> business_gap_plan.v1
  -> 商务标 S3 页面
  -> 人工确认/补料/选材
  -> S4 商务标生成消费
```

不做后端确定性 planner。

后端职责：

- 准备 manifest
- 调用 `bid-business-gap-planner`
- 校验 `business_gap_plan.v1`
- 落盘 `business_gap_plan.json`
- 合并用户状态 `state.json`
- 提供商务标专用 API

Skill 职责：

- 目录点到任务映射
- 未命中目录兜底
- 承诺函回挂
- 同一解析承诺函产物防重复挂载
- 解析承诺函回挂边界提示
- 证书候选推荐
- 业绩候选推荐
- 模板底稿候选推荐
- 状态与风险判断

说明：

- 技术承诺过滤的主逻辑已在商务标解析 Skill 中完成，S3 不再实现技术承诺识别、过滤或重新分类。
- 承诺函主题去重的主逻辑也已在商务标解析 Skill 中完成，S3 不再重新生成/重新去重承诺函，只防止同一个解析产物被重复挂载到同一个任务。
- 如果解析阶段异常产出了明显不属于商务标的承诺函，S3 只标记 `parser_artifact_boundary_warning`，不自动转成商务正式任务。

### 1.2 技术标隔离原则

必须遵守：

- 不修改 `bid-tech-gap-planner`
- 不复用技术标 `gap_plan` schema
- 不写入 `technical-workspace`
- 不读取技术标 Wiki 作为商务标判断依据
- 不把商务标 API 接到技术标 `/gaps` 原接口上
- 技术标回归测试必须保留

允许参考：

- 技术标 Skill 的目录结构
- 技术标 manifest 调用方式
- 技术标 runner 的输入输出模式
- 技术标前端缺口页面的局部交互经验

### 1.3 每一步执行方式

每一步都按以下格式推进：

1. 明确本步目标。
2. 修改最小必要文件。
3. 本地验证。
4. 更新本文档状态。
5. 如遇业务判断不清，暂停讨论，不继续硬写。

### 7.4 API 第一版

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/projects/{project_id}/business-gaps` | 获取当前商务 S3 plan |

- `PATCH task` 可以保存状态。
- 重建 plan 不覆盖用户已确认内容。
- Skill 失败不会产生半成品 plan。
- 技术标 `/gaps` 接口行为不变。

## 11. 风险控制清单

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 技术标被误改 | 技术标 S3 行为变化 | 技术标回归测试、独立文件命名 |
| 商务/技术素材混用 | 商务任务读到技术 Wiki 或技术素材 | manifest 只传商务范围 |
| 承诺函数量失控 | 解析阶段异常产物被重复挂载或误挂载 | S3 只做回挂校验和风险提示，主过滤/去重仍由解析 Skill 负责 |
| 证书匹配错误 | 旧证书或不适配机型证书被推荐 | 机型适配、有效期、人工确认 |
| 未命中目录被丢弃 | 目录项没有任务 | 目录覆盖铁律和 `manual_mapping_required` |
| 用户确认被重建覆盖 | 重新运行后状态丢失 | `state.json` 合并策略 |
| 后端和 Skill 双轨判断 | 规则分散难维护 | 后端不实现商务缺口判断引擎 |
