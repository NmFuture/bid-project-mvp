# 评测体系建设计划

> 日期：2026-05-06
> 范围：仅技术标。商务标不在本计划内。
> 目的：把"自动结果达到人工版本至少 85%"从一个口号变成可信、可复测、可定位错因的评测体系。

## 1. 现在的问题

当前 S3 三率（覆盖率、正确率、完整率）里的"正确率"实际是"是否带了证据链"，不是"答案对不对"。这等于让学生自己改自己卷子。

加上人工 gold 只有 `PRJ-0003` 一个项目，并且这个项目已经被反复用来调 Skill prompt，等于练习卷和考试卷是同一张。换个新项目大概率立刻掉分。

要让 85% 这个门槛变得可信，必须做两件事：

1. 把评测从"文档级"降到"字段级"，逐格对答案。
2. 把开发用的项目和验收用的项目分开，绝不混用。

## 2. 总体思路（用考试做比喻）

- 找几份完整人工填好的项目，**逐字段拆成标准答案册**。
- 让自动 Skill 也填一遍，**一格一格对答案**。
- 题目分难度，不同难度有不同合格线。
- 不同题型用不同对法（数字、选择、段落各一套）。
- 平时调 prompt 用"练习卷"，最终验收用"考试卷"，二者绝不互通。
- 跑完出一张错题分类清单，能定位到底是哪类错。

## 3. Gold 集结构

每个 gold 项目落成一张机器可读表（CSV 或 JSON），一行一个字段：

| 列名 | 含义 |
|---|---|
| `project_id` | 项目编号 |
| `doc_type` | `appendix`（附表）/ `body`（正文章节） |
| `locator` | 表名 + 行号，或章节路径 + 占位符标识 |
| `field_name` | 字段名 |
| `human_answer` | 人工填写的答案；人工也没填的留空 |
| `field_type` | `numeric / enum / phrase / paragraph / list / not_fillable` |
| `difficulty_tier` | `T1 / T2 / T3 / T4 / T5` |
| `evidence_source` | 人工答案的出处（招标文件章节、素材文件名等），可选 |

难度分档：

| 档位 | 含义 | 示例 |
|---|---|---|
| T1 | 直接抄招标文件 | 项目名称、招标编号 |
| T2 | 项目核心事实 | 投标机型、单机容量、台数 |
| T3 | 素材库调取 | 客户定制服务承诺、通用资质段落 |
| T4 | 跨章节推理 | 总容量 = 单机容量 × 台数；交货里程碑组合 |
| T5 | 不可判断 | 人工版本本身留空、必须人工补 |

## 4. 评测指标重定义

替换现在的"覆盖率/正确率/完整率"，新指标如下：

- **填写率** = 自动尝试填写的字段 ÷ 应填字段（T5 不计入分母）
- **准确率** = 与 gold 语义等价的字段 ÷ 自动尝试填写的字段
- **黄标精确率** = 自动标黄字段中 gold 也是 T5 的比例
- **黄标召回率** = gold 是 T5 的字段中自动也合理标黄的比例
- **关键事实一致率** = 机型、项目名称、容量、台数等核心字段在所有附表和正文出现位置完全一致的比例
- **证据链有效率** = 抽样 N 个填写字段，证据链中的引文确实出现在源文件里的比例

注意两点：

1. **证据链有效率单独列，不并入准确率**。这是另一个维度。
2. 准确率分母是"自动尝试填的字段"，所以不能靠"啥都不填"刷分；同时配合黄标精确率，也不能靠"啥都标黄"刷分。

## 5. 字段级匹配规则

不同字段类型用不同对法，避免暴力字符串相等：

| 类型 | 匹配方式 |
|---|---|
| `numeric` | 设 tolerance（绝对或相对）；容量、米数、百分比各设一档 |
| `enum` | normalize 后 exact，附同义词表（机型、安全等级、是/否） |
| `phrase` | normalize 后 exact + 同义词表 |
| `paragraph` | LLM-as-judge 按 rubric 给 0 / 0.5 / 1.0 三档 |
| `list` | 集合 IoU |
| `not_fillable` | 看是否合理标黄 |

LLM-as-judge 纪律：

- 用与填写 Skill 不同的模型 + 不同 prompt 链。
- 上线前先用 100 字段做人工双标校准，judge 与人工一致率 ≥ 90% 才能信。
- judge 只用于 `paragraph` 字段，其他类型不允许。

## 6. 分档合格线

不要"一刀切 85%"，按难度分档：

| 难度 | 合格线 |
|---|---|
| T1 直接抄 | 准确率 ≥ 95% |
| T2 项目事实 | 准确率 ≥ 85% |
| T3 素材调取 | 准确率 ≥ 80% |
| T4 跨章节推理 | 准确率 ≥ 65% |
| T5 不可判断 | 黄标精确率 ≥ 90%、召回率 ≥ 85% |
| 关键事实 | 一致率 = 100% |

加权汇总后回归到 85% 综合门槛。如果 T1 都没到 95%，没必要看后面。

## 7. 训练集 / 验收集 隔离

- `PRJ-0003` 已经被反复用于调 Skill prompt，事实上是 dev 集。**不再当作验收依据**。
- 至少再准备 1 个新项目作为 hold-out test 集；调 prompt、改 Skill、改 manifest 期间**禁止跑这个项目**。
- 长期目标是 dev 集 ≥ 2 个项目、test 集 ≥ 2 个项目。

## 8. 防作弊纪律

- 评测代码和填写 Skill 物理隔离：独立目录、独立依赖、不共享 prompt 或词典。
- Skill 在执行期间不允许读取 `human_answer` 以外的任何 gold 元数据。
- Skill 代码不允许出现项目编号、表名、字段名等业务字面量；CI 里加 lint 检查。
- 标黄行为必须同时考核精确率和召回率，避免"全标黄"刷分。
- 任何针对单表 / 单字段的硬编码视为作弊。

## 9. 失败归因

每次评测产物里带一份 `failure_breakdown.json`，按以下维度聚合：

- 误填（填了但与 gold 不等）
- 漏填（应填没填）
- 错标黄（标黄了但 gold 有答案）
- 漏标黄（没标黄但 gold 是 T5）
- 证据链假阳性（引文在源文件里找不到）

每类再按 `field_type / difficulty_tier / skill_name / project_id` 切片。否则"准确率 75%"是死信号，定位不到改哪儿。

## 10. 产物清单

每轮评测必须产出：

- `gold/{project_id}.csv`：人工答案册
- `runs/{run_id}/predictions.csv`：本轮 Skill 输出（与 gold 一一对应）
- `runs/{run_id}/metrics.json`：六项核心指标 + 分档准确率
- `runs/{run_id}/failure_breakdown.json`：错题分类清单
- `runs/{run_id}/evidence_audit.csv`：证据链抽样审计
- `runs/{run_id}/report.md`：人读摘要

跑完一轮花费控制在 30 分钟以内（含 LLM-as-judge），否则迭代成本过高。

## 11. 冷启动路线（两周）

### 第 1 周：建立基线

- 选定 PRJ-0003 作为 dev 集。
- 把人工版附表（`/Users/wlb/Downloads/技术标模板/投标文件-附表.docx`）和人工版正文（`/Users/wlb/Downloads/技术标模板/投标文件-正文.docx`）逐字段拆成 gold CSV。预估 300-500 字段。
- 写 `eval/` 目录脚手架：gold 加载、predictions 加载、字段级 diff、分档汇总、失败归因。
- 跑一次当前 Skill，得到第一份真实基线数据。这一步**几乎一定**会比现在自评分低很多，目的就是看清差距。

### 第 2 周：盲测泛化

- 选第二个项目（人工版完整、与 PRJ-0003 不同客户/不同机型）作为 test 集，照样拆 gold。
- **不调任何 prompt**，直接跑当前 Skill，对比 dev 与 test 的指标差。
- 如果 test 比 dev 掉超过 10 个百分点，证明在过拟合 PRJ-0003，回到 Skill 层排查。
- 输出第一版完整评测报告，作为后续 Skill 迭代的回归基线。

## 12. 后续节奏

- 每次 Skill 改动跑全量 dev 评测，metrics.json 入 git 跟踪回归。
- test 集每月跑一次，平时不动。
- 字段级 gold 持续扩充：每接入一个新人工版项目就新增一份 gold CSV。
- judge 模型每季度重新校准一次。

## 13. 主要 tradeoff

人工切 gold 是真贵：每个项目约 1-2 人天，2-3 个项目就是 4-6 人天。

但要达到合同级 85%，这一步省不掉——现在的"证据链 = 正确率"本质上测不出真实差距。先花 1-2 天把 PRJ-0003 的字段级 gold 拉出来，是性价比最高的第一步。

## 14. 与现有文档的关系

- 本文件聚焦"怎么测"。验收什么由 `doc/16-目标一与目标二最终目标.md` 定义。
- Skill 边界、待办优先级仍以 `doc/14-甲方新增需求待办.md` 为准；本文件的产物用于支撑待办 14、16 的真实验收。
- 所有评测代码、gold 数据、运行产物建议放在新目录 `code/sewpg-bid-backend/eval/`,不与 Skill 代码混放。
