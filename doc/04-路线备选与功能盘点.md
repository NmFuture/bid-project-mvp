## 二、编辑器技术路线备选

### 2.1 对比矩阵

| 方案 | 类 Word 还原 | 国产化 | License | 一次性成本 | 适配度 |
|---|---|---|---|---|---|
| **OnlyOffice Developer (推荐)** | ★★★★★ | ✗ | 商业授权 | ¥25,000 | 高 |
| **WPS Web Office SDK** | ★★★★★ | **✓** | 商业授权 (谈) | 面议 | **极高** |
| **Collabora Online** | ★★★★ | ✗ | MPL-2.0 社区版免费 / 企业版付费 | 社区版免费 | 中 |
| **永中 Office 云端** | ★★★★ | **✓** | 商业授权 | 面议 | 信创场景 |
| **福昕 PDF/文档 SDK** | ★★★ | 半国产 | 商业授权 | 面议 | 偏 PDF |
| **自研 (Tiptap/ProseMirror + docx.js)** | ★★ | - | MIT | 研发成本 5-8 人月 | 低 |

### 2.2 重点备选：WPS Web Office（值得认真考虑）

**为什么值得**：
- 国企大客户对 WPS 的"亲和度"明显高于 OnlyOffice
- 金山是国产软件，信创合规背书更硬
- 中文排版、字体兼容、本地化支持天然更好
- 国企采购走 WPS 比走俄罗斯公司 OnlyOffice 流程更顺

**劣势**：
- 不开源（但 OnlyOffice Developer 也是 proprietary，本质都是商业授权）
- 定制能力可能不如 OnlyOffice 灵活（有插件机制但生态小）
- 价格需议价，不透明

**行动建议**：
> **在采购 OnlyOffice 前，先问业务方一句："WPS 是否更容易走采购流程？"**
> 如果答"是" → 优先走 WPS；否则 OnlyOffice。

### 2.3 Collabora Online（开源备选）

- 基于 LibreOffice 的 Web 版本
- MPL-2.0 社区版免费（比 AGPL 友好）
- **弱点**：中文支持不如 OnlyOffice/WPS；插件生态小；UI/UX 更粗糙
- 适用：**极度预算受限** + 可接受稍差体验

### 2.4 自研路线（不推荐，但记录）

- Tiptap（基于 ProseMirror）或 Lexical 做编辑器
- 服务端用 `docx.js` / `python-docx` 生成 .docx
- **致命伤**：.docx 往返必丢格式（OOXML 复杂度远超 HTML）
- 只适合"标书格式简单、不需要 Word 还原度"的场景 —— 不是我们

## 三、Agent Runtime 路线备选

### 3.1 对比矩阵

| 方案 | 语言 | License | 对话/Session | Desktop | 实现成本 | 适配度 |
|---|---|---|---|---|---|---|
| **opencode (推荐)** | Bun/TS | MIT | ✓ 开箱 | ✓ 官方 Electron | 低 | 高 |
| **LangGraph + LangServe** | Python | MIT | 需自研对话 UI | ✗ | **中** | 中 |
| **自研 agent loop** | Python | - | 需自研全部 | ✗ | **高** (2-3 人月) | 不推荐 |
| **AutoGen / CrewAI** | Python | MIT | 有 | ✗ | 中 | **不适配**（多 agent 协作哲学 ≠ 我们场景） |

### 3.2 值得对比：LangGraph（全 Python 方案）

**优势**：
- **单语言栈**（全 Python）— 少一个 Bun 服务，开发/运维统一
- 节点式编排 workflow，state 显式，debug 更友好
- LangChain 生态大

**劣势**：
- 对话 UI 要自研（或用 Chainlit 凑合）
- Session 持久化要自己管
- Desktop 客户端完全没有
- 对比 opencode 多 2-3 人月工作量

**适用场景**：**团队强烈希望单 Python 栈，且不需要 Desktop 客户端**。

## 四、整体架构路线备选

| 路线 | 组成 | 服务数 | 开发成本 | 合规 | 推荐度 |
|---|---|---|---|---|---|
| **A（当前推荐）** | Web 前端（当前为 React + Vite） + FastAPI + opencode + OnlyOffice Developer | 8+Bun | 基线 | 良 | ✅ |
| **B（全 Python）** | Web 前端 + FastAPI + LangGraph + OnlyOffice | 7 | +2-3 人月 | 良 | 可选 |
| **C（Markdown 流派）** | Web 前端 + FastAPI + opencode + Markdown 编辑 + Pandoc | 7 | 基线 | **差**（业务方不接受） | ❌ |
| **D（全国产信创）** | Web 前端 + FastAPI + LangGraph + WPS Web Office | 7 | +2-3 人月 | **最好** | **若信创强约束必选** |

### 4.1 路线 A vs 路线 D 决策点

| 维度 | A (opencode + OnlyOffice) | D (LangGraph + WPS) |
|---|---|---|
| 采购友好度 | 中（俄罗斯公司 + 开源 Bun） | **高**（国产 + Python） |
| 开发速度 | **快**（opencode 免费省 2-3 人月） | 慢 |
| 合规背书 | 良 | **信创友好** |
| 技术栈复杂度 | 高（双语言） | **低**（单 Python） |
| Desktop 客户端 | **有**（opencode） | 无 |
| 投标甲方政治 | 中性 | **更顺** |

**抉择依据**：
- 项目**是否有信创强约束**（甲方明文要求国产化率）？是 → D；否 → A
- 团队**是否有 TS/Bun 熟练开发**？是 → A；否 → D 更稳
- **是否需要桌面端**？需要 → A（opencode 送）；不需要 → 无所谓

## 五、UI 前后端联调复杂度评估

### 5.1 总体结论

**可实现，但复杂度显著高于普通 CRUD 系统**，需有经验的全栈工程师，首期要留足联调预算和 spike 时间。

### 5.2 难点清单与缓解

| # | 难点 | 复杂度 | 缓解方案 |
|---|---|---|---|
| 1 | 三进程协作（Next / FastAPI / opencode） | 中高 | 统一 trace id；OpenAPI 自动生成 TS/Python 类型；本地 docker-compose 开发 |
| 2 | OnlyOffice iframe 通信 | 中 | `postMessage` + Callback URL 有官方文档；OO 官方 `example-node` 可直接抄 |
| 3 | opencode SDK 集成 | **中高** | opencode 较新，文档不完整；P0 必做 spike |
| 4 | 目录树 ↔ 文档双向同步 | **高** | WebSocket + debounce；段落级 hash；竞态要测透 |
| 5 | 覆盖热力图实时刷新 | 中 | 段落 hash diff；覆盖计算后台跑，前端定期拉 |
| 6 | AI 动作审计 + 撤销 | 中 | 所有 AI diff 存 `audit_log`；"撤销栈"单独建模 |
| 7 | OnlyOffice 自定义菜单 | 中 | 社区有 plugin 模板，但定制"AI 改写"类菜单仍有坑 |
| 8 | 竞态保护（用户输入 vs AI 自动） | **高** | typing 状态锁 + 操作队列 + 粒度到段落 |
| 9 | 大文档（几百页）性能 | 中 | OnlyOffice 能扛，但目录树/热力图刷新要分段渲染 |
| 10 | PDF 解析准确率（OCR） | 中 | 建评测集持续追踪；扫描件关键字段二次人工确认 |

### 5.3 P0 强制 Spike 清单（不跑通则推翻方案）

1. **OnlyOffice iframe + FastAPI Callback**：前端打开文档，编辑后触发 Callback，后端能拿到 .docx
2. **opencode session from FastAPI**：Python 代码发 task 给 opencode server，agent 调一个 dummy tool 回调 FastAPI 成功
3. **FastAPI 调 skill**：后端可稳定调用目录生成与正文拼装能力，并完成结构化结果回收
4. **OnlyOffice 自定义菜单**：右键菜单加"AI 改写"项，点击触发前端事件
5. **跨进程 trace id**：一次用户动作能在 Next / FastAPI / opencode 三份日志中串联

**这 5 个 spike 跑通 = 方案技术可行性 90% 落地**。跑不通要立即重新评估。

### 5.4 人力建议

| 角色 | 人数 | 技能要求 |
|---|---|---|
| 前端 | 2 | 至少 1 人有 iframe / WebSocket / OT 经验 |
| 后端 (Python) | 2 | 至少 1 人有 FastAPI / Celery 经验 |
| 全栈 (TS) | 1 | 主要做 opencode plugin + 联调 |
| 算法/LLM | 1 | prompt 工程 + 评测集维护 |
| 运维 | 0.5 | Docker Compose + 内网部署 |
| PM/设计 | 0.5-1 | |
| **合计** | **7-8** | **首期 4-6 个月** |
