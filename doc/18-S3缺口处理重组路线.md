# S3 缺口处理重组路线

> 日期:2026-05-06
> 范围:仅技术标 S3。S0/S1/S2/S4 不动。
> 关联文档:`doc/14-甲方新增需求待办.md` 第 14 条、`doc/16-目标一与目标二最终目标.md`、`doc/17-评测体系建设计划.md`。
> 执行口径:本路线在 doc/17 评测体系建好后启动;没有评测就动架构,等于凭手感。

## 1. 判断

当前 S3 "先维护项目事实表 → 再 AI 填写"的方向**对了一半**:把项目核心事实独立成强一致来源,这是必须的;但**让人工开填前一次性确认 50 字段**是反模式,把不确定性甩给人却拿不到人的判断质量。

总评:**事实表保留,机制重组**;不推翻 Skill 分支(`bid-tech-table-filler` / `bid-tech-word-placeholder-filler`)。

## 2. 当前做法的功过

### 对的部分

- 项目核心事实独立成强一致来源,避免 70 张附表里机型/容量/台数各填各的。
- 人工确认门禁——合同级风险下,核心字段宁可慢也不能错。
- Skill 按产物类型分支,比一个万能 Skill 健壮。

### 错的部分

- **维护时机**:开填前让人工把 50 字段确认完,大多数字段当下不知道用在哪、为啥要,人只能瞎点"确认"。
- **粒度**:扁平 `字段 → 值` 太薄。同一个"机型"在容量计算时要数字、在合同条款里要中文全称、在功率曲线表里要型号代码,一格答案撑不住。
- **职责边界**:事实表来自 S0 解析 + 用户 + 占位符抽取;Skill 内还有自己的 RAG。两路独立无真相源,冲突时靠 prompt 写规则——脆。
- **三率假**:`correctnessRate = 是否带证据链`,自评分。已有 doc/17 替代方案。

## 3. 重组目标:四层架构

```
Layer 1  项目知识库(证据卡片集,边填边沉淀)
   ↓
Layer 2  填写规划器(决定每个空格走哪条路径)
   ↓
Layer 3  执行器(thinking 与 placement 分离)
   ↓
Layer 4  复查器(结构化规则 + 字段级评测)
```

### 3.1 Layer 1 · 项目知识库

形态:**证据卡片集**,不是扁平字典。

```json
{
  "field": "投标机型",
  "value": "SE-15530",
  "variants": {
    "数字代号": "15530",
    "中文全称": "三一重能 SE-15530-..."
  },
  "sources": [
    { "doc": "招标文件第3章", "quote": "...", "confidence": 0.95 }
  ],
  "lock_status": "locked_by_user"
}
```

`lock_status` 取值:`locked_by_user / system_high_conf / unconfirmed / conflict`。
锁定字段后续所有 Skill 必须用锁定值,不允许自由发挥。

写入触发(自动累积,非人工一次性):

| 时机 | 写入内容 |
|---|---|
| S0 解析完成 | 招标文件直接声明字段(项目名、招标编号、招标人) |
| S1 选机型 | 机型及关联参数(容量、叶轮直径、轮毂高度选项) |
| S3 首次遇到某字段且高置信抽取 | 自动写入 `system_high_conf` 态 |
| Skill 检测到冲突或必填核心字段缺失 | 暂停填写,弹问题给人,不预列 50 条 |

人工只在三种情况下被打断:**冲突 / 高风险字段缺失 / 系统置信度低于阈值**。

### 3.2 Layer 2 · 填写规划器

对每个空格先决定路径,再决定值:

| 路径 | 行为 |
|---|---|
| `direct_quote` | 招标文件直接抄,带引文 |
| `kb_lookup` | 查知识库;`locked` 值直接用;`unconfirmed` 用了带告警 |
| `material_rag` | 在素材库 `通用/客户/项目` 三档检索段落 |
| `derive` | 跨字段推理走**确定性计算函数**,不交给 LLM 算数学 |
| `mark_yellow` | 找不到 + 推不出 → 标黄,理由入报告 |

每条填写打路径标签,直接对接 doc/17 的 `difficulty_tier`,评测分档天然成立。

### 3.3 Layer 3 · 执行器

当前 table-filler / word-placeholder-filler 同时做"想答案 + 塞 docx",必须拆开:

- **思考层**:输出 `fill_instructions.json`(每条含定位、值、置信度、证据、路径)
- **放置层**:纯函数,消费 JSON 塞进 docx + 标黄 + 生成填写报告

好处:思考层可反复迭代跑评测,不污染 docx;放置层稳定,不会因为 LLM 心情不好把表格结构搞乱。

### 3.4 Layer 4 · 复查器

不是"再让 LLM 看一眼打个分",是**结构化规则检查**:

- **强一致检查**:机型/项目名/容量在所有附表 + 正文里完全一致
- **数值闭合检查**:容量 × 台数 ≈ 总容量;年发电量 / 装机容量 ≈ 等效小时数
- **交叉引用检查**:附表 C 的机型 vs 正文承诺函里的机型
- **T5 合理性**:每个标黄项是否真的检索过且未找到

输出**必须人工处理的问题清单**,不是一个分数。

## 4. 与现状的关键差异

| 维度 | 现在 | 重组后 |
|---|---|---|
| 事实维护时机 | 开填前一次性 50 字段 | 边填边沉淀,冲突/缺失/低置信才打扰人 |
| 事实形态 | 扁平 `字段:值` | 证据卡片(多变体 + 源 + 置信度 + 锁状态) |
| 思考与放置 | 同一个 Skill 内混 | 分两层,可独立迭代 |
| 跨字段推理 | LLM 自由算 | 确定性函数,LLM 不算数学 |
| 复查 | 自评分三率 | 结构化规则 + 外部字段级评测 |

## 5. 实施路径(两选一)

### 路径 A · 轻量外科手术(推荐先走)

预计 1.5-2 周,在现有架构上做最小改动消化 80% 痛点。

- **A1 按需弹窗替代 50 字段一次性确认**:事实表前端改为"系统检测到必须确认时才弹",其他时候默默累积。
- **A2 加 `fill_instructions.json` 中间层**:Skill 输出从直接 docx 改为 JSON + 放置脚本两步,docx 由确定性脚本生成。
- **A3 结构化复查器初版**:实现强一致检查 + 数值闭合检查 + 交叉引用检查三类规则。

适合场景:doc/17 评测建好后跑一次,如果 PRJ-0003 综合分能到 60-70 分,先走 A 路径,把分数往 85% 推。

### 路径 B · 完整四层重组

预计 3-4 周。

适合场景:doc/17 评测出来分数很低(< 50)且 A 路径试过仍卡住,说明现有架构有结构性问题,这时再上完整重组才划算。

**决策点**:doc/17 §11 第 1 周 baseline 跑完后,看分数选 A 或 B。

## 8. 主要 tradeoff

- **复杂度上升**:四层架构对开发心智负担更高。但当前两层(事实表 + 填写 Skill)其实已经在偷偷做这四件事,只是边界混乱;显式分层不是新增复杂度,是把隐藏复杂度搬到台面。
- **前期工程成本**:路径 A 1.5-2 周、路径 B 3-4 周。在评测没建好之前,不要启动 H 系列待办。
- **可能的退路**:如果 doc/17 评测出来 PRJ-0003 已经超过 75-80 分,可能只做 H7-H9(结构化复查器)就够,H1-H6 不必上。这个判断点放在 doc/17 baseline 出来之后。

## 9. 关于 Wiki 与 RAG 的选型判断

> 这一节是一次决策反转的留档。讨论时第一反应是"上 RAG",深入推演后判定**当前规模下不上**。留下推理过程,避免后续工程师再被术语带偏一次。

### 9.1 现状澄清

当前项目**没有真 RAG**:`requirements.txt` 里没有 `faiss / chroma / qdrant / pgvector / sentence-transformer / elasticsearch / BM25` 任何一项,也没有 embedding/检索代码。

实际机制是:

```
素材原文件
  → material_store 建扁平 inventory
  → bid-tech-wiki-material-builder Skill 让 LLM 离线读全部素材并生成 Wiki
  → 后续 Skill 把 Wiki + 清单塞进 prompt,LLM 自己挑
```

`bid-tech-wiki-material-builder/SKILL.md` 自我定位为 "AI-facing retrieval index",名字贴近 RAG,但本质是"**LLM 离线建语义索引,在线在 prompt 上下文里现挑**",不是向量检索。

### 9.2 维度对比

| 维度 | Wiki(当前) | RAG(向量+关键词) | 谁更优 |
|---|---|---|---|
| 召回粒度 | 卡片级 ≈ 文件/章节 | chunk 级 ≈ 段落 | **打平**——招标素材段落语义完整,粒度优势不明显 |
| 检索质量 | LLM 离线一次性预计算映射 | 现场召回 top-k | **Wiki 更稳**——招标 query 高度重复,预计算 > 现场 |
| 一致性 | 全局一份卡片,所有 Skill 共享 | 每次召回可能微变 | **Wiki 显著占优**——合同级场景一致性 > 创造性 |
| 可观测性 | 卡片有 reason 字段,人可读 | 召回分数,机器友好 | **Wiki 更易 audit** |
| 失效模式 | 偏"陈旧"(忘重建) | 偏"漂移"(query 微差敏感) | **Wiki 更安全**——错了能发现,漂了难察觉 |
| 规模上限 | 几百份素材,LLM 一次能读完 | 几乎无上限 | **RAG 占优,但目前不构成约束** |
| 工程成本 | 已在跑,零改动 | 选库 + chunking + 召回调参 + 索引同步 | **Wiki 占优** |

### 9.3 决策结论

**当前规模下保留 Wiki 作为主路。RAG 不上。**

S3 选材质量不稳,根本原因不在召回层,而是:

1. Wiki 重建触发机制不严:素材库改动后未自动重建 → 用旧映射
2. 选材决策层无兜底:Wiki 卡片如果漏挂或挂错,Skill 没有第二条路

### 9.4 推荐方案:Wiki 主路 + BM25 兜底

| 优先级 | 动作 |
|---|---|
| 高 | 保留 Wiki 主路;锁定 Wiki 重建触发(素材新增/修改/删除 → 自动入队重建) |
| 中 | 加 **BM25 兜底召回**:用 Postgres `tsvector` 即可,不引入新依赖。Wiki 卡片缺失或置信低时,在素材原文里关键词召回兜底 |
| 低 | RAG 列入预案,**当前不做** |

**doc/18 §3.2 的 `material_rag` 路径名字保留**,但实现为"Wiki 卡片 + BM25 兜底",不是向量检索。这样路径标签语义不变,实施成本骤降。

### 9.5 启动 RAG 的临界条件

满足以下任一条件时,重新评估上 RAG:

- 素材库文件数 ≥ 500
- 素材库段落数 ≥ 5000
- Wiki 单次重建 token 超过 LLM 上下文窗口
- 素材实时性需求出现(例如素材入库后必须秒级可用)

到达临界条件时,优先选 **pgvector**(已有 Postgres,改动最小),双路混排(BM25 + 向量)。不必引入独立向量服务。

|---:|---|---|---|---|---|---|

| H13 | [ ] | 中 | BM25 兜底召回(Postgres tsvector) | 现有素材清洗后 Word/段落表 | `app/services/material_search.py` + tsvector 索引迁移 | 给 query 能返回 top-k 段落,含原文、得分;有单测 |

## 10. Wiki 现状审计与对齐

> 这一节回答"现在的 Wiki 是否合理、够不够用"。结论:**设计大方向对,落地不彻底——目前实际只有 50% 的下游 Skill 在用 Wiki,投入产出比打折。**

### 10.1 消费链路审计

| Skill / 阶段 | 是否读 Wiki | 程度 | 实际入口 |
|---|---|---|---|
| `bid-tech-gap-planner`(S3 缺口识别) | ✅ 读 | 当线索,可回退到 manifest 的 `materialIndex` | `manifest.wikiDir` |
| `bid-tech-assembler`(S4 正文拼装) | ✅ **强依赖** | 找不到 Wiki 直接中止,声明"结构性必需" | `wiki/rules.md` 三件套 + `wiki/卡片/*.md` |
| `bid-tech-table-filler`(S3 副表填写) | ❌ **不读** | 只读 manifest 的 `materialIndex` | `manifest.materialIndex` |
| `bid-tech-word-placeholder-filler`(S3 Word 填写) | ❌ **不读** | 只读 manifest 的 `materialIndex` | `manifest.materialIndex` |

S3 真正"动手填字"的两个 Skill 全程绕过 Wiki。Wiki 里 02 章节映射表 + 03 素材卡片做的预计算,对最痛的填写环节没生效——填写 Skill 拿到的是后端预先按 identity 切好的扁平 `materialIndex`。

### 10.2 设计合理 vs 落地不合理

合理的部分:

- **离线 LLM 建索引**优于 RAG(§9 已论证)
- **5 节结构**覆盖五个查询场景
- **identity 字段**(`identity_scope / material_scope / customer_id / project_id`)支持跨项目复用 + 使用时身份过滤
- `material_id` 作为统一引用单位,Skill 传 id、Wiki 是规范源

不合理的部分:

| 问题 | 影响 |
|---|---|
| 消费不统一,Wiki 不是真相源 | 02/03 节预计算白做一半 |
| 04 待填写清单 vs 重组后的 KB 职责重叠 | 04 节生成时静态、运行期不更新,等于死叶子;KB 上线后定位更尴尬 |
| 02 章节映射只有自然语言 confidence + reason,无 score 阈值 | 下游 Skill 还要 LLM 重判一次,决策成本省不下 |
| 05 使用规则是 prompt 里的自然语言指令 | LLM 实际遵守与否不可观测、不可强制 |
| Wiki 是 LLM 一次性产物,无刚性自检 | 卡片 id 完整率、章节映射覆盖率、必需字段完整率全凭运气 |
| 重建触发不严(已并入 §9.6 H12) | 素材库变了 Wiki 不会自动跟,容易陈旧 |

### 10.3 "够用吗"的真实回答

| 维度 | 现状 | 判断 |
|---|---|---|
| S3 缺口识别 | gap-planner 用了,但只当线索 | 够用,边际收益不高 |
| S3 副表/Word 填写 | 完全没用 Wiki | **不够用**——Wiki 投入这里没回收 |
| S4 正文拼装 | 强依赖 | 够用,Wiki 在这里发挥最大 |
| 跨项目复用 | identity 字段健全 | 够用 |
| 实时性 | 重建靠手动 | 不够用 |
| 自检 | 几乎没有 | 不够用 |

### 10.4 修复方向
