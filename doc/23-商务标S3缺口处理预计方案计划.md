# 商务标 S3 缺口处理预计方案计划

> 用途：作为商务标 `S3 缺口处理` 的讨论底稿，先明确设计方向、数据结构、页面结构和实施路径，再逐步收口。  
> 状态：执行计划补充稿，待逐项审核。  
> 更新日期：2026-05-09  
> 范围：仅讨论商务标 `S3 缺口处理`；不修改技术标现有实现，不在本稿中直接推进代码改造。

## 1. 背景

当前技术标主链路已经具备完整的 `S3 缺口处理` 机制：

- 以 `S2 审核目录` 为全集
- 由后端准备 manifest，并调用 `bid-tech-gap-planner` Skill 生成 `gap_plan`
- 前端工作台围绕 `gap_plan` 进行补料、选材、AI 填写、复核与确认
- `S4 生成标书` 再消费 `gap_plan` 的结果

商务标即将具备或已经具备：

- 商务标解析模块
- 商务标模板与目录模块
- 商务标素材库与 Wiki 库

因此下一步需要设计商务标自己的 `S3 缺口处理` 方案。

商务标不能简单照搬技术标 `S3`，原因是两者的“缺口单元”不同。

## 2. 技术标 S3 当前处理思路

### 2.1 技术标 S3 的核心原则

技术标 `S3` 的核心原则是：

> 以 `S2 已确认目录` 为全集，以“目录项是否已有可用内容”为判断对象，生成统一的缺口处理计划。

它的最小处理单元，本质上是：

- 一个目录项
- 一个附表/空表任务
- 一个需要填 Word/表格的章节型任务

### 2.2 技术标 S3 的后端流程

后端主流程大致如下：

1. 读取 `S2` 已确认目录 JSON
2. 读取项目解析结果 `parse_result.json`
3. 读取项目身份、投标机型、可读素材范围
4. 读取技术标 Wiki 目录
5. 汇总生成 `materialIndex`
6. 调用 `bid-tech-gap-planner` Skill 或本地 runner
7. 输出 `gap_plan.json`
8. 前端读取 `gapPlan`，进入缺口处理工作台

### 2.3 技术标 gap_plan 的特点

技术标 `gap_plan` 具备以下特点：

- `items` 基本和目录项一一对应
- 每个 item 会判断当前目录项属于：
  - `ready`
  - `fill_required`
  - `material_required`
  - `review_required`
- 每个 item 会附带：
  - `matchedMaterials`
  - `fillTasks`
  - `appendixTasks`
  - `resolvedArtifacts`
- 最终 `S4` 可以直接消费这个 `gap_plan`

### 2.4 技术标页面的特点

技术标前端工作台本质上是“目录项工作台”：

- 按缺口 item 展示
- 目录项是主线
- 补料、选择素材、AI 填写都围绕目录项进行

这对技术标是合理的，因为技术标的核心任务就是：

- 某一章有没有内容
- 某一节是否有覆盖素材
- 某个附表是否需要填写

### 2.5 技术标 S3 vs 商务标 S3 差异对照表

| 维度 | 技术标 S3 | 商务标 S3 |
|---|---|---|
| 输入基线 | `S2` 已确认目录 + 技术标解析结果 + 技术标 Wiki + 投标机型 + 素材范围 | `S2` 已确认商务目录 + 商务标解析结果 + 商务标 Wiki + 素材范围 + 已有正式响应件 |
| 最小缺口单元 | 更接近“目录项/章节项/附表项” | 更接近“响应件任务” |
| 目录与任务关系 | `gap_plan.items` 基本与目录项一一对应 | 目录点生成任务，目录是主视图骨架，任务是执行单元 |
| 核心处理对象 | 章节内容、附表、待填写 Word、空表 | 投标函、承诺书、价格表、证书、回单、协议、支撑材料 |
| 材料消费方式 | 章节摘取、整章拼装、附表填写、Word 占位符替换 | 整件挂载、整表填写、固定模板生成、证书/扫描件选择与校验 |
| Wiki 主要作用 | 服务章节映射、素材卡片选择、正文拼装 | 服务模板模块映射、证据卡片检索、材料可用性判断、待确认项提示 |
| 缺口识别关注点 | 某章节有没有覆盖素材、某附表是否需要填写 | 某响应件有没有正式材料、有没有模板、是否需要生成、是否需人工复核 |
| 页面主视图 | 目录项工作台 | 目录缺口视图 |
| 页面辅助组织 | 围绕目录项直接处理 `fillTasks/appendixTasks` | 模块筛选 + `topicGroup` 局部分组 |
| 任务类型重要性 | 以章节项和 `fillTasks/appendixTasks` 为主，`taskType` 不是核心抽象 | `document/table/attachment/certificate/bundle` 明显影响处理策略和完成标准 |
| 缺口判定方式 | 更偏“章节内容是否可生成/可覆盖” | 更偏“响应件是否可交付/可挂载/可生成” |
| 与 S4 的交接 | `gap_plan` 更直接服务正文拼装和附表填充 | `business_gap_plan` 更直接服务响应件装配和目录落位 |
| 可复用部分 | `gap_state -> plan -> review -> confirm` 生命周期、预览/确认机制、基础 API 组织 | 同左，可复用底层框架 |
| 不可直接照搬部分 | 章节覆盖型判断、`gap_plan.items=toc items` 语义、技术标 Wiki 用法 | 需要改成响应件任务型判断、商务标 Wiki 用法、目录主视图 |

结论：

- 技术标和商务标 `S3` 不是完全相同的链路。
- 可以复用的是“缺口处理框架”。
- 不能直接照搬的是“缺口单元、任务模型、Wiki 用法、页面组织方式”。

## 3. 商务标为什么不能直接照搬技术标 S3

### 3.1 商务标的缺口单元不同

商务标的核心缺口单元，不是“章节内容段落”，而更像：

- 一份响应件
- 一份承诺书
- 一张报价表
- 一类资质证明
- 一张证书扫描件
- 一份保证金回单/保函
- 一项否决项响应
- 一份客户专项证明

这些对象的处理方式通常是：

- 整件挂载
- 整表填写
- 固定模板生成
- 证书/扫描件上传或选择
- 少量变量替换

而不是技术标常见的：

- 按章节摘取一段素材
- 多段拼接成正文
- 章节型内容填充

### 3.2 只按“商务响应件清单”也不够

曾经考虑过一种思路：

> 商务标 `S3` 不再按章节树，而是只按“商务响应件清单”展示。

这个思路有一半是对的，因为商务标确实更适合按“任务件”来处理。

但如果完全不考虑章节目录，也会带来问题：

- 用户不知道这个响应件最终要放进投标文件哪个章节
- 无法判断目录是否完整、是否漏件
- 难以校验“招标文件目录”和“实际商务响应件”之间是否对齐
- 后续生成商务标时，材料落位关系不清晰

因此，商务标 `S3` 不能做成：

- 纯章节树模式
- 纯商务响应件清单模式

而应该做成：

> 以“目录缺口视图”作为主视角，以“商务响应件任务”作为执行单元。

## 4. 当前推荐方向

### 4.1 一句话定义

建议将商务标 `S3` 定义为：

> 商务标缺口处理以“商务响应件任务”作为执行单元，以“目录章节”作为落位和审核单元。

### 4.2 三层结构

当前推荐将商务标 `S3` 的核心结构拆成三层：

1. `task`
2. `tocRef`
3. `moduleGroup`

三者关系如下：

- `task`：真正的执行对象，是一个待处理响应件/表单件/证据件
- `tocRef`：任务最终落位的章节参考，也是页面主视图的组织骨架
- `moduleGroup`：任务的辅助处理分组，用于筛选、批处理和规则复用

### 4.3 推荐原则

- 页面默认以 `tocRef` 目录视图处理
- 页面保留 `moduleGroup` 作为辅助筛选与批处理入口
- 后端 `business_gap_plan` 必须同时描述：
  - “我现在要处理什么任务”
  - “这个任务最终属于哪个目录节点”

## 5. 商务标 business_gap_plan 预计结构

### 5.1 顶层结构

```json
{
  "schemaVersion": "bid-business-gap-plan-v1",
  "projectId": "PRJ-XXXX",
  "projectName": "某商务标项目",
  "bidType": "商务标",
  "generatedAt": "2026-05-09T00:00:00Z",
  "views": {
    "default": "toc",
    "available": ["toc", "module"]
  },
  "summary": {},
  "moduleGroups": [],
  "tocRefs": [],
  "tasks": []
}
```

### 5.2 moduleGroups（辅助处理分组）

结合商务投标目录讨论结果，当前建议第一版固定为 `6` 个一级模块。

这里的分组原则不是按文件后缀，而是按“用户处理动作 + 响应件性质 + 最终落位习惯”组织辅助筛选和批处理入口。

| key | label | 覆盖目录 | 主要内容 |
|---|---|---|---|
| `base_documents_guarantees` | `01-基础响应文书与担保文件` | `一、五、六` | 投标函、法定代表人身份证明、授权委托书、廉洁承诺、投标专用章效力说明、投标保证金承诺函、电汇凭证、履约保证函格式承诺书 |
| `structured_response_tables` | `02-报价与结构化响应表` | `二、三、四、八、7.1` | 投标价格表、货物规格一览表、商务条款偏差表、开标价格表、商务部分摘要表 |
| `qualification_compliance_certificates` | `03-主体资格、合规信用与专题证书` | `7.1.1-7.1.5、7.2、7.6、7.7、7.8` | 营业执照、企业资质、体系认证、基本账户、股权结构、诉讼仲裁、企业声明、信用截图，以及机型认证证书、大部件型式认证证书 |
| `enterprise_finance_supply` | `04-企业能力、财务与供货保障` | `供货保障专题、7.3、7.4、7.5` | 公司/工厂简介、集团优势、整体能力、生产能力、纳税信用等级、质量管理、奖项专利、财务数据、资信证明、感谢信 |
| `performance_cooperation_support` | `05-业绩、合作与专项支撑` | `7.9、7.10、9.19` | 业绩表、合同业绩、240h 试运行、在供项目、技术来源与合作协议、战略协议、框架协议、示范应用证明、供应链协同证明 |
| `commitments_and_notes` | `06-承诺函与其他说明` | `9.1-9.18` | 不存在下列情形之一承诺、保密承诺书、无重大质量问题声明、无行贿声明、实质性响应声明、否决项相关响应等 |

说明：

- 页面可按这 `6` 组进行筛选、统计和批处理
- 一个任务只能有一个主 `moduleKey`
- 同一个目录节点允许关联多个任务
- 第一版可以支持可选的 `subModuleKey`，但仅在少量强需求模块中使用

### 5.2.1 二级分组建议

一级模块已经尽量克制，不建议继续把所有模块都拆得太细。

但 `03-主体资格、合规信用与专题证书` 中，`机型认证证书` 和 `大部件型式认证证书` 的重要性较高，建议在该模块内部显式保留二级分组：

| moduleKey | subModuleKey | label | 放置内容 |
|---|---|---|---|
| `qualification_compliance_certificates` | `subject_qualification` | `03-1 主体资质` | 营业执照、企业资质、体系认证、基本存款账户、股权结构等 |
| `qualification_compliance_certificates` | `compliance_credit` | `03-2 合规与信用` | 诉讼仲裁情况、企业状况声明、经营异常/失信/信用中国截图等 |
| `qualification_compliance_certificates` | `special_certificates` | `03-3 专题证书` | 机型认证证书、大部件型式认证证书、其他专项型式或认证类证书 |

说明：

- 二级分组主要用于局部筛选展示和规则强化
- `task` 仍然先以一级 `moduleKey` 为主键归类
- `subModuleKey` 作为可选字段，不要求所有模块都具备
- 后续如果 `05-业绩、合作与专项支撑` 也出现强需求，再考虑新增二级分组

### 5.3 tocRefs（目录参考层）

`tocRefs` 不是主执行对象，而是“任务与目录”的映射关系。

建议结构：

```json
{
  "nodeId": "TOC-14",
  "number": "九",
  "title": "投标人需要说明的其他内容",
  "taskIds": ["TASK-006", "TASK-007"],
  "status": "partial"
}
```

建议状态：

- `empty`：该目录节点尚未绑定任务
- `partial`：该目录节点只绑定了部分任务
- `ready`：该目录节点下任务均齐备
- `review_required`：该目录节点下仍存在待确认任务

### 5.4 tasks（真正执行单元）

任务是商务标 `S3` 的核心。

建议字段示例：

```json
{
  "id": "TASK-006",
  "taskKey": "commitment_confidentiality",
  "moduleKey": "commitments_and_notes",
  "title": "保密承诺书",
  "taskType": "document",
  "status": "needs_input",
  "decision": "fill_required",
  "sourceType": "parser_explicit",
  "sourceRequirement": {
    "triggerText": "投标人应出具保密承诺书",
    "triggerContext": "......"
  },
  "tocTarget": {
    "nodeId": "TOC-9-2",
    "number": "9.2",
    "title": "保密承诺书"
  },
  "candidateMaterials": [],
  "fillTasks": [],
  "resolvedArtifacts": [],
  "riskFlags": []
}
```

### 5.4.1 task 最终字段清单

1. 身份字段
2. 目录落位字段
3. 来源字段
4. 素材推荐字段
5. 处理结果字段

#### 5.4.1.3 `tocTarget` 子结构

```json
{
  "nodeId": "TOC-9-2",
  "number": "9.2",
  "title": "保密承诺书",
  "required": true
}
```

建议规则：

- 商务标默认 `1 个任务 = 1 个 tocTarget`
- 一个任务至少要有 `1` 个 `tocTarget`
- 第一版不建议引入“一个任务多目录落位”
- 若目录表述相似但细节不同，应拆成多个独立任务，并通过 `topicGroupKey` 归组

#### 5.4.1.4 `sourceRequirement` 子结构

```json
{
  "triggerText": "投标人应出具保密承诺书",
  "triggerContext": "......",
  "normalizedTopic": "保密",
  "fromSection": "9.2",
  "extractionMethod": "parser_explicit"
}
```

作用：

- 保留“为什么生成这个任务”的证据
- 便于用户复核系统是否误判
- 便于后续重跑解析时做增量比对

#### 5.4.1.5 `candidateMaterials` 子结构

```json
[
  {
    "materialId": "MAT-102",
    "materialName": "保密承诺书空白模板.docx",
    "libraryScope": "common",
    "score": 0.93,
    "reason": "模板模块映射表命中 + 文件名语义命中",
    "path": "...",
    "fileType": "docx",
    "previewable": true
  }
]
```

建议字段：

- `materialId`
- `materialName`
- `libraryScope`
- `score`
- `reason`
- `path`
- `fileType`
- `previewable`

#### 5.4.1.6 `resolvedArtifacts` 子结构

```json
[
  {
    "artifactId": "ART-301",
    "artifactType": "generated_docx",
    "fileName": "保密承诺书.docx",
    "filePath": "...",
    "sourceMode": "generated_from_template",
    "version": 1,
    "previewable": true,
    "confirmed": false
  }
]
```

说明：

- 对商务标 `document` 类任务，`resolvedArtifacts` 不应只理解为“外部已经存在的正式响应件”。
- 很多正式响应件本来就是在 `S3` 阶段由“模板 + 招标文件要求 + 项目变量”生成出来的待盖章正式稿。
- 因此 `resolvedArtifacts` 可以包含：
  - 已上传的外部正式件
  - 系统生成的待盖章正式稿
  - 解析阶段生成但尚待人工复核的承诺函/承诺书草稿
  - 经人工复核确认后可进入盖章流转的正式输出稿

建议字段：

- `artifactId`
- `artifactType`
- `fileName`
- `filePath`
- `sourceMode`
- `version`
- `previewable`
- `confirmed`

#### 5.4.1.7 `riskFlags` 建议枚举

| riskFlag | 含义 |
|---|---|
| `missing_material` | 还没有可用正式材料 |
| `expiry_check_required` | 需要检查证书有效期 |
| `semantic_match_only` | 仅通过语义命中生成，需人工确认 |
| `customer_specific` | 仅对特定客户适用 |
| `project_specific` | 项目专属，不能复用通用件 |
| `duplicate_candidate` | 存在疑似重复任务 |
| `technical_boundary_risk` | 可能误入技术标边界内容 |
| `parser_generated_unconfirmed` | 解析阶段已生成草稿，但尚未人工确认 |
| `manual_placement_required` | 需要人工确认目录落位 |
| `section_module_conflict` | 章节号默认模块与标题/解析/Wiki 判断不一致 |
| `parser_inferred_mapping` | 任务模块主要由解析证据推断 |
| `model_mismatch` | 候选证书与项目所用机型不匹配 |
| `model_fit_review_required` | 候选证书适配范围不明确，需要人工确认 |
| `manual_model_input` | 项目机型由人工录入，无法直接关联 Wiki 证书卡片 |

### 5.5 taskType（任务类型）

建议第一版只定义少量明确类型：

| taskType | 含义 | 典型例子 |
|---|---|---|
| `document` | 一份独立文书/响应件 | 投标函、授权书、承诺书 |
| `table` | 一张待填写表格 | 投标价格表、开标价格表、偏差表 |
| `attachment` | 一份附件/证明件 | 保证金回单、保函、评价信 |
| `certificate` | 一类证书扫描件 | 机型认证证书、部件型式认证 |
| `bundle` | 一组需成套挂载的材料 | 合格投标人证明文件集合 |

### 5.6 decision（动作判断）

建议商务标仍保留技术标类似的动作语义，但含义应重新解释：

| decision | 商务标含义 |
|---|---|
| `ready` | 已存在可直接挂载/使用的正式响应件 |
| `fill_required` | 需要基于模板、变量或解析结果生成/填写 |
| `material_required` | 缺正式材料，需上传或选择已有素材 |
| `review_required` | 系统识别到候选，但仍需人工确认 |

### 5.7 status（执行状态）

建议状态不宜过多，第一版先保留：

- `ready`
- `needs_input`
- `filling`
- `resolved`
- `ignored`
- `review_required`

## 6. 商务标任务来源预计方案

商务标 `task` 的来源，建议定为 `4` 大来源、`1` 条统一生成流水线。

### 6.1 统一生成流水线

建议后端在构建 `business_gap_plan` 时，按以下顺序生成任务：

1. 读取已确认目录模板，生成固定骨架任务
2. 读取商务标解析结果，补充动态任务与证据
3. 吸收解析阶段已生成的承诺函/承诺书产物，回挂到对应任务
4. 按规则做判重、主题归组、边界过滤
5. 根据目录映射规则补齐 `tocTarget`
6. 根据 Wiki / 素材库补充 `candidateMaterials`
7. 根据现有正式产物回填 `resolvedArtifacts`
8. 计算 `decision / status / riskFlags`

说明：

- 这条流水线比“先全量 AI 生成，再人工收拾”更稳
- 第一版优先保证任务可控、可追溯、可复核
- 其中“解析阶段已生成的承诺函/承诺书”不应被当成普通缺失件重新起炉灶，而应先作为 `S3` 的既有候选产物参与判断

### 6.2 来源一：来自目录模板的固定任务

这类任务是“目录里天然就应该有的响应件”。

例如：

- 投标函
- 法定代表人授权委托书
- 商务偏差表
- 规格表
- 开标价格表

特点：

- 不依赖全文搜索
- 可由模板目录直接枚举
- 适合预先生成基础任务骨架

建议规则：

- 固定任务必须优先生成，作为任务主骨架
- 固定任务应直接带默认 `moduleKey`、`taskType`、`tocTarget`
- 如果后续解析命中同主题内容，应补充证据，而不是重复新建任务

### 6.3 来源二：来自解析结果的动态任务

这类任务来自商务标解析模块的专门结果。

例如：

- 承诺书线索
- “投标人不得存在下列情形之一”承诺书
- 商务评分表映射出的证明件需求

特点：

- 动态性强
- 同一招标文件项目差异大
- 必须保留解析证据上下文

建议细分为两类：

| sourceType | 含义 | 默认处理 |
|---|---|---|
| `parser_explicit` | 目录或正文明确写有“承诺函/承诺书/另附承诺函/须提供承诺函”等 | 可以直接建任务 |
| `parser_semantic` | 文本未必直接写模板名，但语义上明确要求提供一份声明或响应文书 | 先建候选任务，加 `semantic_match_only` |

建议规则：

- `parser_explicit` 可以直接建任务
- `parser_semantic` 先建候选任务，但默认加 `semantic_match_only`
- 涉及技术边界的承诺项，不进入商务标任务池

### 6.3.1 解析阶段已生成的承诺函，如何进入 S3

这一点对商务标非常重要。

因为当前商务标解析阶段，并不只是“识别出哪里需要承诺函”，而是已经会：

- 全文搜索“承诺 / 承诺函 / 承诺书”等关键词
- 结合上下文识别部分承诺事项
- 直接生成部分承诺函/承诺书 Word 产物
- 默认将其放入“投标人需要说明的其他内容”这一章节语义下

所以商务标 `S3` 不能假设：

- 所有承诺类任务都还没有产物
- 所有承诺类任务都必须从模板重新生成

而应改为如下处理：

1. 解析结果中的 `fieldGroups.commitmentRequirements`
   - 负责回答“为什么会有这个承诺任务”
   - 作为 `sourceRequirement` 和 `sourceEvidenceRefs` 的来源
2. 解析结果中的 `structured.commitmentLetters`
   - 负责回答“解析阶段已经产出了什么承诺件草稿”
   - 作为 `resolvedArtifacts` 或至少“预生成候选产物”的来源
3. `S3` 构建任务时，先看固定骨架里是否已有对应目录任务
   - 如果已有，如 `9.2 保密承诺书`
   - 则把解析阶段产出的 Word 回挂到该任务，不重复新建第二个同主题任务
4. 若目录中没有精确子节点，但解析阶段已经生成了承诺书
   - 先落到 `06-承诺函与其他说明`
   - `tocTarget` 可先挂到“投标人需要说明的其他内容”父节点或最接近的子节点
   - 再由人工做最终落位确认

建议把解析阶段产出的承诺件分成两种身份：

| 身份 | 写入位置 | 默认 decision/status | 说明 |
|---|---|---|---|
| 已生成草稿，但尚未人工确认 | `resolvedArtifacts` | `review_required / review_required` | 可预览，但需复核标题、主题、项目名称、招标人、落位章节 |
| 已生成草稿，且人工确认可采用 | `resolvedArtifacts` | `ready / ready` | 可作为已存在的商务响应件待盖章正式稿 |

### 6.3.2 解析阶段承诺函与目录节点的关系

建议明确一条商务标专属规则：

> 解析阶段生成的承诺函，不是脱离目录存在的自由文书，而是 `06-承诺函与其他说明` 模块下各目录点的候选正式稿来源。

优先落位顺序建议如下：

1. 先按 `commitmentLetters.title / normalizedTopic / placementHint` 命中具体子节点
2. 命中不到时，挂到“投标人需要说明的其他内容”父节点
3. 仍无法判断时，进入该章节下的“待人工落位”状态

这样做的好处是：

- 不会把解析阶段承诺函和 `S3` 承诺任务做成两套平行体系
- 前端能直接在目录视图中看到“这一项已经有解析生成稿”
- 后续 `S4` 装配时，也知道这些 Word 最终应放在哪个目录点

### 6.4 来源三：来自素材/Wiki 映射的推荐

这类任务不是“新增任务”，而是对既有任务补充推荐素材。

例如：

- 某个资格证明任务可直接推荐 `01-资质合规库` 中的营业执照
- 某个证书任务推荐 `05-专题证书库` 中的对应证书
- 某个客户专项证明任务推荐客户素材中的战略协议

建议规则：

- 素材/Wiki 推荐默认不直接新建任务
- 其作用是为已有任务补充 `candidateMaterials`
- 仅在极少数“目录没有单列、但招标要求明确存在”的场景，可由映射规则补建任务

### 6.5 来源四：来自人工补充的临时任务

第一版建议允许存在人工新增任务，但先限制在少量场景。

例如：

- 用户发现目录里应有某项“其他说明”但系统未识别
- 用户手动补一个专项承诺件

说明：

- 第一版不建议开放完全自由新增复杂任务树
- 可先支持“新增一个响应件任务”即可

### 6.6 任务生成规则表

| 规则编号 | 规则名称 | 输入 | 输出 | 说明 |
|---|---|---|---|---|
| `R1` | 固定骨架生成 | 已确认商务目录 | 固定任务 | 先把目录中天然存在的响应件生成出来 |
| `R2` | 显式要求补建 | 解析结果中的明确承诺函/承诺书要求 | 新任务或补证据 | 明确写“应出具/须提供/另附”的，优先采纳 |
| `R2A` | 解析生成稿回挂 | `structured.commitmentLetters` | 补 `resolvedArtifacts` / 补落位 | 解析阶段已生成 Word 时，优先回挂到既有任务，不重复建同主题任务 |
| `R3` | 语义要求补建 | 解析结果中的语义要求 | 候选任务 | 需加人工复核标记 |
| `R4` | 目录落位映射 | 任务 + 目录映射规则 | `tocTarget` | 保证任务最终有落位 |
| `R5` | 素材候选推荐 | 任务 + Wiki/素材库 | `candidateMaterials` | 不直接生成正式结果 |
| `R6` | 正式产物回填 | 已存在项目文件、解析生成稿、人工确认稿 | `resolvedArtifacts` | 有现成成果时可直达 `ready` 或进入待复核 |
| `R7` | 判重与主题归组 | 全部任务池 | 去重后的任务池 | 防止重复生成，同时保留相似任务分组 |
| `R8` | 边界过滤 | 任务池 + 规则 | 过滤后的任务池 | 防止技术类任务误入商务标 |

### 6.7 判重与主题归组规则

商务标 `S3` 的重点不是“多生成”，而是“生成得稳”。

建议按以下优先级做判重：

1. `taskKey` 完全相同：直接视为同一任务
2. `moduleKey + tocTarget.nodeId + normalizedTopic` 相同：优先视为同一任务
3. 文件标题不同但指向同一目录点、同一主题：保留一个任务，别名写入 `titleAlias`
4. 一个任务命中多个解析片段：补进 `sourceEvidenceRefs`，不重复建任务

建议判重示例：

- `保密承诺函`
- `保密承诺书`
- `投标保密承诺`

三者若语义一致，且都指向 `9.2 保密承诺书`，应归并为同一个任务：

- `title = 保密承诺书`
- `titleAlias = ["保密承诺函", "投标保密承诺"]`

建议主题归组示例：

- `9.4 投标资格未受限声明`
- `9.12 未处于禁止投标处罚期间声明`

两者不合并任务，但可归入同一主题组：

- `topicGroupKey = bid_eligibility_commitments`
- `topicGroupLabel = 投标资格类承诺`

### 6.8 商务标边界过滤规则

建议在商务标 `S3` 中增加显式过滤规则。

以下主题默认不进入商务标承诺件任务池：

- 发电量承诺
- 功率曲线或功率偏差承诺
- 可利用率承诺
- 性能保证指标承诺
- 环境适应性承诺
- 技术方案、设备配置、控制策略类承诺

建议处理方式：

- 若解析命中这些主题，标记为 `technical_boundary_risk`
- 不自动进入商务标正式任务池
- 仅在需要时进入“待人工确认”候选区

### 6.9 目录落位规则

建议采用以下原则：

1. 先判断任务是什么，再决定它放到哪里。
2. 同一目录点可以拆成多个任务。
3. 商务标默认一个任务只映射一个目录点。
4. 若目录中存在节点，但没有任何任务命中，必须在 `tocRefs` 中显式展示为空缺。

建议落位顺序：

1. 优先命中固定模板映射
2. 再命中同名/近义名目录项
3. 再退化到所在大章节的“其他说明”节点
4. 仍无法落位时，挂到“待人工落位”

### 6.10 哪些场景允许归并，哪些只允许主题归组

#### 可以归并为同一任务

- 同一组信用截图的多个明细文件，可合并为 `bundle`
- 同一类客户合作协议的多份支撑件，可合并为一个支撑任务
- 同一目录点下、同一主题的重复解析命中，可归并为同一任务

#### 只允许主题归组，不建议合并任务

- 不同目录点但主题相近的承诺类任务
- `9.4` 与 `9.12` 这类表述相近但细节不同的资格声明
- `9.6` 与 `9.7` 这类同属信用类、但检查对象不同的声明
- `9.13` 与 `9.14` 这类处罚/事故主题相近但对象不同的声明

#### 明确不建议合并

- 投标函、授权书、廉洁承诺书这类独立法定文书
- 投标价格表、开标价格表、商务偏差表、规格表等独立表单
- 机型认证证书和大部件型式认证证书
- 保证金电汇凭证与履约保证函承诺书

### 6.11 任务生成后的默认状态判定

建议按如下顺序判定：

1. 若已有正式产物且可预览，置为：
   - `decision = ready`
   - `status = ready`
2. 若已有候选素材但未选定，置为：
   - `decision = review_required`
   - `status = review_required`
3. 若需要上传材料，置为：
   - `decision = material_required`
   - `status = needs_input`
4. 若需要根据模板或变量生成，置为：
   - `decision = fill_required`
   - `status = needs_input`

补充说明：

- 这里的“正式产物”对商务标要按更宽口径理解：
  - 可以是外部已有正式响应件
  - 也可以是系统在 `S3` 阶段生成的待盖章正式稿
  - 也可以是解析阶段已经生成、但尚待人工确认采用的承诺函/承诺书草稿
- 因此对 `document/table` 类任务，不应要求“必须先存在人工做好的正式件”才可进入后续流转
- 但解析阶段已生成的承诺函草稿，默认仍应先进入 `review_required`，而不是直接无条件判成 `ready`

### 6.12 缺口判定规则表（按 taskType）

这一节的目标，是把“系统为什么判成待补料/待填写/待复核/已就绪”写清楚，避免后端落地时只靠经验判断。

建议默认采用：

- 先按 `taskType` 进入对应规则
- 再按“是否已有正式产物 -> 是否已有合格候选 -> 是否仍需人工确认”顺序判断

#### 6.12.1 `document` 类任务

典型对象：

- 投标函
- 授权委托书
- 各类承诺书、声明函
- 合同生效条件说明

| 条件 | 建议 `decision` | 建议 `status` | 说明 |
|---|---|---|---|
| 已有正式 `docx/pdf` 产物，且标题、内容、版本可确认 | `ready` | `ready` | 可直接进入后续装配或盖章流转 |
| 解析阶段已生成承诺书草稿，且主题、标题、落位基本明确，但尚未人工确认 | `review_required` | `review_required` | 这是商务标特有场景，允许先预览再决定是否采用 |
| 已有可用模板、变量齐全，但尚未生成正式稿 | `fill_required` | `needs_input` | 典型“待生成文书” |
| 已有模板，但关键变量缺失或来源未确认 | `review_required` | `review_required` | 例如项目名称、招标编号、主体称谓仍待确认 |
| 仅语义命中到“可能需要声明”，但未找到明确模板或正文依据较弱 | `review_required` | `review_required` | 防止误生承诺函 |
| 完全没有模板、没有现成正式稿、也没有可复用项目文书 | `material_required` | `needs_input` | 需要补模板或补正式文书来源 |

额外规则：

- `document` 类若命中 `technical_boundary_risk`，默认不能直接进入 `fill_required`
- 承诺书/声明函命中但标题不稳定时，可通过 `titleAlias` 保留别名，不影响 `task` 独立性
- `document` 类生成出的“待盖章正式稿”一旦通过人工复核，也应计入 `resolvedArtifacts`

#### 6.12.2 `table` 类任务

典型对象：

- 投标价格表
- 开标价格表
- 商务偏差表
- 规格表
- 业绩表

| 条件 | 建议 `decision` | 建议 `status` | 说明 |
|---|---|---|---|
| 已有完成版表格，字段完整且版本确认 | `ready` | `ready` | 可直接用于后续生成或盖章流转 |
| 已有空表/模板，也有明确数据源，但尚未填充 | `fill_required` | `needs_input` | 典型表格填充任务 |
| 已有空表，但数据源不完整或字段映射未确认 | `review_required` | `review_required` | 例如价格口径、规格字段来源未定 |
| 缺空表模板，或模板版本不对 | `material_required` | `needs_input` | 需要补空表/模板 |
| 已填写部分内容，但仍存在关键空单元或金额/型号待确认 | `review_required` | `filling` | 处于处理中但不能判完成 |

额外规则：

- `table` 类更适合触发结构化填表链，而不是文书生成链
- 只要关键字段缺失，不应直接进入 `ready`
- `table` 类在商务标里很多也属于“系统先生成待盖章稿，人工后续盖章”的对象

#### 6.12.3 `attachment` 类任务

典型对象：

- 保证金回单
- 保函
- 授权附件
- 客户评价信
- 战略协议扫描件

| 条件 | 建议 `decision` | 建议 `status` | 说明 |
|---|---|---|---|
| 已有明确可用附件，且项目/客户适用性确认 | `ready` | `ready` | 可直接挂载 |
| 有多个候选附件，需人工选择版本 | `review_required` | `review_required` | 例如同一客户多份协议 |
| 缺项目专属附件 | `material_required` | `needs_input` | 例如本次保证金回单 |
| 有通用附件，但本项目是否适用不确定 | `review_required` | `review_required` | 例如评价信、框架协议 |

额外规则：

- 项目专属附件不能因为素材库有同类文件就判 `ready`
- 客户专项附件需要校验 `customerName`

#### 6.12.4 `certificate` 类任务

典型对象：

- 机型认证证书
- 大部件型式认证证书
- 行业资质证书
- 体系认证证书

| 条件 | 建议 `decision` | 建议 `status` | 说明 |
|---|---|---|---|
| 已有证书，且机型/部件/有效期匹配 | `ready` | `ready` | 可直接挂载 |
| 已有证书，但有效期、适配机型或部件关系需确认 | `review_required` | `review_required` | 商务标证书类高频风险 |
| 找到多份相近证书，需人工选择 | `review_required` | `review_required` | 例如不同机型认证版本 |
| 缺证书扫描件 | `material_required` | `needs_input` | 需要上传或补证 |

额外规则：

- 证书类必须考虑有效期
- 机型认证证书和大部件型式认证证书建议显式建任务，不依赖目录是否单列

##### 6.12.4.1 机型认证证书专项判定

机型认证证书是商务标专题证书中的高频关键材料，建议独立判定。

候选来源：

- 项目素材中的机型认证证书
- 客户素材中的专属机型认证证书
- 通用素材库 `05-专题证书库/01-机型认证证书`
- 商务标 Wiki `03-证据卡片` 中的机型认证证书卡片

判定字段：

| 字段 | 说明 |
|---|---|
| `certificateName` | 证书名称 |
| `certificateNo` | 证书编号 |
| `issuer` | 发证机构 |
| `applicableModels` | 证书覆盖机型 |
| `modelAliases` | 机型别名 |
| `platform` | 平台/系列 |
| `ratedPowerKw` | 容量等级 |
| `validFrom` | 有效期开始 |
| `validTo` | 有效期结束 |
| `sourceFilePath` | 原始证书路径 |

判定规则：

| 条件 | decision | status | 风险标记 |
|---|---|---|---|
| 证书明确覆盖 `selectedBusinessTurbineModel.model`，且有效期满足要求 | `ready` | `ready` | 无 |
| 证书覆盖项目机型别名，且有效期满足要求 | `review_required` | `review_required` | `model_fit_review_required` |
| 证书覆盖同平台/同容量，但未明确列出项目机型 | `review_required` | `review_required` | `model_fit_review_required` |
| 证书机型与项目机型冲突 | `review_required` | `review_required` | `model_mismatch` |
| 证书有效期缺失或过期 | `review_required` 或 `material_required` | `review_required` 或 `needs_input` | `expiry_check_required` |
| 未找到任何候选证书 | `material_required` | `needs_input` | `missing_material` |

说明：

- 第一版不建议系统自动忽略 `model_mismatch` 证书，而是降级为低优先级候选并提示风险
- 若用户人工确认某张证书适用，应写入 `selectedMaterialRefs` 并记录确认备注
- 若项目机型由人工录入，所有候选机型证书默认 `review_required`

##### 6.12.4.2 大部件型式认证证书专项判定

大部件型式认证证书不一定直接写项目机型，可能按部件型号、平台、容量等级或适用范围表达，因此比机型认证证书更容易进入人工复核。

建议第一版重点关注以下大部件：

- 叶片
- 齿轮箱
- 发电机
- 变流器
- 主轴承
- 轮毂/主机架
- 塔筒或其他招标文件明确要求的部件

候选来源：

- 通用素材库 `05-专题证书库/02-大部件型式认证证书`
- 商务标 Wiki `03-证据卡片`
- 项目素材中的专项部件证书

判定字段：

| 字段 | 说明 |
|---|---|
| `componentName` | 部件名称 |
| `componentModel` | 部件型号 |
| `certificateName` | 证书名称 |
| `certificateNo` | 证书编号 |
| `issuer` | 发证机构 |
| `applicableModels` | 适用整机机型 |
| `applicablePlatforms` | 适用平台 |
| `ratedPowerRange` | 适用容量范围 |
| `validFrom` | 有效期开始 |
| `validTo` | 有效期结束 |
| `sourceFilePath` | 原始证书路径 |

判定规则：

| 条件 | decision | status | 风险标记 |
|---|---|---|---|
| 部件证书明确覆盖项目机型和对应部件，且有效期满足要求 | `ready` | `ready` | 无 |
| 部件证书覆盖同平台或容量范围，但未明确写项目机型 | `review_required` | `review_required` | `model_fit_review_required` |
| 部件名称匹配，但部件型号缺失 | `review_required` | `review_required` | `model_fit_review_required` |
| 证书有效期缺失或过期 | `review_required` 或 `material_required` | `review_required` 或 `needs_input` | `expiry_check_required` |
| 缺少招标文件明确要求的大部件证书 | `material_required` | `needs_input` | `missing_material` |

说明：

- 大部件证书可能是一组材料，不一定只有一个文件
- 如果招标文件明确要求多个部件证书，建议每个部件生成独立 `certificate` 子任务或在 `bundle` 中列出子项
- 第一版可以先以 `大部件型式认证证书` 为总任务，详情中展示子项齐备情况

#### 6.12.5 `bundle` 类任务

典型对象：

- 信用截图包
- 获奖和专利包
- 财务资料包
- 合同业绩支撑包

| 条件 | 建议 `decision` | 建议 `status` | 说明 |
|---|---|---|---|
| 子项全部齐备且版本确认 | `ready` | `ready` | 可以作为完整包进入装配 |
| 子项部分齐备，关键子项缺失 | `material_required` | `needs_input` | 需要补关键文件 |
| 子项齐备但年份、客户、项目范围需确认 | `review_required` | `review_required` | 例如财务年度、业绩范围 |
| 完全没有可用素材 | `material_required` | `needs_input` | 需要补料 |

额外规则：

- `bundle` 的完成标准不是“有一个文件”，而是“关键子项是否齐备”
- `bundle` 最容易出现“素材明明有一些，但还不能判 ready”的情况

##### 6.12.5.1 业绩支撑材料专项判定

业绩支撑材料是商务标中典型的 `table + bundle` 组合任务。

它通常不是“有一份文件就完成”，而是需要同时判断：

- 业绩表是否可填写
- 业绩条目是否满足容量等级、机型、时间、客户等要求
- 每条业绩是否有支撑材料
- 支撑材料是否成套

建议把 `7.9` 拆成两类任务：

| 任务类别 | taskType | 说明 |
|---|---|---|
| 业绩表填写 | `table` | 生成或填写各类容量等级业绩表 |
| 业绩支撑材料 | `bundle` | 挂载合同、中标通知书、240h、验收报告等支撑材料 |

常见业绩支撑子项：

| 子项 | 说明 | 是否关键 |
|---|---|---|
| `contract_scan` | 合同扫描件 | 是 |
| `award_notice` | 中标通知书 | 条件性 |
| `trial_240h_report` | 240 小时试运行报告 | 条件性 |
| `acceptance_report` | 验收报告 | 条件性 |
| `operation_certificate` | 运行证明/并网证明 | 条件性 |
| `capacity_model_evidence` | 容量等级/机型证明 | 是 |

判定规则：

| 条件 | decision | status | 说明 |
|---|---|---|---|
| 业绩表模板存在，且筛选出满足要求的业绩数据 | `fill_required` | `needs_input` | 可进入表格填充 |
| 业绩表模板存在，但容量等级/机型/时间范围未确认 | `review_required` | `review_required` | 需要人工确认筛选口径 |
| 缺业绩表模板 | `material_required` | `needs_input` | 需要补空表或模板 |
| 每条入表业绩均有关键支撑材料 | `ready` | `ready` | 支撑包可用于装配 |
| 部分入表业绩缺合同或容量证明 | `material_required` | `needs_input` | 关键材料缺失 |
| 支撑材料存在但无法对应具体业绩 | `review_required` | `review_required` | 需要人工匹配 |

额外规则：

- 业绩表和业绩支撑包应相互引用，避免表里列了业绩但支撑材料缺失
- 若招标文件要求 `240h`，则 `trial_240h_report` 是关键子项
- 若招标文件只要求合同业绩，则合同扫描件和容量/机型证明优先
- 若业绩支撑材料数量较多，第一版可以先按“业绩条目”分组展示，不必拆成复杂父子任务树

#### 6.12.6 一般优先级规则

为避免不同类型之间判定口径漂移，建议统一采用以下优先级：

1. `ready`
   - 已有正式可用产物
2. `review_required`
   - 有候选，但仍存在版本、适用性、变量、语义边界等不确定性
3. `material_required`
   - 缺关键原件/模板/子项
4. `fill_required`
   - 具备模板和来源，只差生成或填写

补充说明：

- `fill_required` 主要适用于 `document/table`
- `material_required` 主要适用于 `attachment/certificate/bundle`
- `review_required` 是所有类型都可能进入的中间态

#### 6.12.7 缺口判定示例

| 任务 | `taskType` | 当前情况 | 预期判定 |
|---|---|---|---|
| 保密承诺书 | `document` | 有空白模板，项目变量待带入 | `fill_required` |
| 投标人不存在下列情形之一承诺函 | `document` | 解析阶段已生成 Word 草稿，但未确认 | `review_required` |
| 投标价格表 | `table` | 有空表，价格数据尚未确认 | `review_required` |
| 营业执照 | `attachment` | 已找到并选定最新营业执照扫描件 | `ready` |
| 机型认证证书 | `certificate` | 找到两份相近证书，机型适配关系待确认 | `review_required` |
| 信用截图包 | `bundle` | 仅有信用中国截图，缺经营异常截图 | `material_required` |

## 7. 页面预计方案

### 7.1 页面总体原则

页面不应完全照搬技术标 `GapRecognition`。

推荐原则：

- 默认主视角：目录缺口视图
- 辅助入口：模块筛选与批处理
- 两个视图消费同一份 `business_gap_plan`

### 7.2 视图一：目录缺口视图（主视角）

默认按 `tocRefs` 展示。

每个目录节点展示：

- 章节编号
- 章节标题
- 该目录节点下任务数
- 已完成数 / 待处理数
- 风险数

展开目录节点后，展示该节点下的任务卡片。

每个任务卡片展示：

- 任务名称
- `taskType`
- `status`
- `decision`
- 所属模块标签
- 来源说明
- 推荐素材
- 当前已解决产物
- 可执行动作

可执行动作建议包括：

- 查看任务详情
- 查看目录原文要求
- 查看来源证据
- 预览解析生成稿
- 选择候选素材
- 上传补充材料
- 生成/重新生成待盖章稿
- 标记已确认
- 标记忽略

此视图主要用于：

- 按目录顺序检查缺口
- 按用户习惯核对“这一节到底齐不齐”
- 为后续 `S4` 生成提供一致的目录心智

### 7.3 视图二：模块筛选视图（辅助入口）

该视图不是主骨架，而是辅助入口。

默认提供模块筛选：

- `01-基础响应文书与担保文件`
- `02-报价与结构化响应表`
- `03-主体资格、合规信用与专题证书`
- `04-企业能力、财务与供货保障`
- `05-业绩、合作与专项支撑`
- `06-承诺函与其他说明`

建议用途：

- 只看某一类任务
- 对同类任务做连续处理
- 快速进入专题证书或承诺类任务
- 进行模块级完成度统计

在 `06-承诺函与其他说明` 这类任务较多的模块内，可进一步使用 `topicGroup` 做局部分组展示。

### 7.4 推荐的页面信息结构

建议页面上方统一展示：

- `总任务数`
- `已就绪`
- `待填写`
- `待补料`
- `待复核`

建议页面中部：

- 左侧：目录列表
- 顶部或侧边：模块筛选器、状态筛选器
- 右侧：当前任务详情面板

建议任务详情面板展示：

- 基础信息
- 目录落位
- 所属模块 / 主题组
- 来源证据
- 解析生成稿
- 推荐素材
- 已解决产物
- 操作区

其中对 `06-承诺函与其他说明` 模块，建议显式展示：

- 该任务是否来自解析阶段关键词识别
- 是否已有解析生成的承诺书草稿
- 草稿标题与当前目录点标题是否一致
- 是否已人工确认采用该草稿

## 8. 与技术标复用的边界

### 8.1 可以复用的部分

以下能力可优先复用技术标现有基础设施：

- `gaps` 路由族整体模式
- `store.py` 中 gap_state 的基本组织方式
- `review document` 的提交/确认机制
- 上传补料、选择已有素材、产物回挂的基本能力
- OnlyOffice 预览机制

### 8.2 不应直接照搬的部分

以下部分不应直接照搬技术标：

- `gap_plan.items = toc items` 的一一对应关系
- 技术标那种“以章节内容覆盖为核心”的页面语义
- 以章节覆盖/整章拼装为核心判断逻辑
- 技术标的 `fillTasks / appendixTasks` 语义原样迁移

### 8.3 推荐复用策略

建议商务标 `S3` 采用：

- 底层框架复用技术标
- 任务模型和页面视角重做

也就是：

- 后端仍可以保留 `gap_state -> plan -> review -> confirm` 这套生命周期
- 但 `plan` 的结构换成 `business_gap_plan`
- 前端新建商务标 `S3` 页面，不直接复用技术标页面组件主结构

## 9. 商务标 S3 与后续 S4 的关系

商务标 `S3` 的输出，不只是给页面看，还必须能服务后续商务标生成。

因此 `business_gap_plan` 至少要满足后续两个需求：

1. 能告诉生成模块：哪些任务已经有正式产物
2. 能告诉生成模块：这些产物最终应落到哪个目录节点

换句话说，`resolvedArtifacts` 不只是“任务完成记录”，也应是后续商务标装配/挂载的输入。

## 10. 当前仍需继续确认的问题

后续建议继续收口以下事项：

1. `目录点 -> 标准任务` 的固定映射表
2. `06-承诺函与其他说明` 中哪些承诺书由解析阶段生成，哪些由 S3 生成
3. `resolvedArtifacts.confirmed` 的人工确认交互
4. `bid-business-gap-planner` Skill 的 manifest、输出 schema、运行命令和验收口径
5. 页面是否复用技术标 `GapRecognition` 的局部组件，还是完全新建商务标页面
6. S4 生成商务标时如何消费 `business_gap_plan`

## 11. 执行阶段拆分

本节把前文方案拆成可以逐步开发、逐步验收的实施阶段。

第一版直接建设商务标专用 gap planner Skill，不先做后端确定性 planner。

建议第一版按 `7` 个阶段推进：

| 阶段 | 名称 | 目标 | 主要产出 | 是否阻塞后续 |
|---|---|---|---|---|
| `P0` | 现状对齐与边界确认 | 确认技术标 S3、商务标解析、商务标目录、素材库/Wiki 当前代码位置 | 代码位置清单、复用边界说明 | 是 |
| `P1` | Contract 与 Skill 契约定稿 | 固化 `business_gap_plan` JSON 结构、manifest 结构、状态枚举 | Contract 文档、类型定义或 schema、Skill 输入输出约定 | 是 |
| `P2` | `bid-business-gap-planner` Skill 建设 | 由 Skill 根据目录、解析结果、Wiki/素材生成 `business_gap_plan` | Skill 目录、`SKILL.md`、runner、references、样例 manifest | 是 |
| `P3` | 后端 Skill 接入 | 后端准备 manifest、调用 Skill、校验覆盖率、落盘 plan | service、落盘文件、基础接口、错误处理 | 是 |
| `P4` | 承诺函与素材/Wiki 逻辑纳入 Skill | 把解析承诺函回挂、同一解析产物防重复挂载、边界提示、候选素材推荐放入 Skill | 承诺函回挂、证书有效期风险、模板候选、业绩候选 | 是 |
| `P5` | 前端商务标 S3 工作台 | 建立目录主视图、任务卡片、详情面板和操作区 | 页面、交互、状态持久化 | 是 |
| `P6` | S4 对接与验收 | 让后续商务标生成能消费 S3 结果 | S4 输入 contract、端到端样例、测试 | 是 |

推荐执行顺序：

1. 先完成 `P0-P2`，让 `bid-business-gap-planner` 能用样例 manifest 生成真实 `business_gap_plan`
2. 再做 `P3`，让后端以技术标相同方式调用 Skill，而不是在后端重写判断逻辑
3. 再做 `P4-P5`，补齐承诺函、素材推荐和前端处理闭环
4. 最后做 `P6`，将已确认产物交给商务标生成链路

说明：

- 后端不承担商务缺口核心判断，只负责 manifest 准备、Skill 调用、schema 校验、目录覆盖校验、状态持久化和接口输出。
- 映射表、兜底规则、语义判断、承诺函回挂、证书/业绩候选推荐都应放入 `bid-business-gap-planner` Skill。
- 技术承诺过滤和承诺函主题去重的主逻辑仍归商务标解析 Skill；S3 不再重复识别、过滤或去重承诺函，只做解析产物回挂、防重复挂载和边界提示。
- 第 `15` 节中的规则仍然保留，但定位调整为 Skill 的参考规则和测试基线，而不是后端确定性 planner 的实现依据。

与解析阶段现有目录的关系：

| 来源 | 典型路径 | S3 处理 |
|---|---|---|
| 解析附表 | `parsed/{project_id}/s1_appendices/` 或 `documents/{project_id}/technical-workspace/appendices/` | 商务标需另设商务 workspace，不与技术标 appendices 混放 |

第一版建议：

- `business_gap_plan.json` 由后端可重复生成
- `state.json` 保存用户操作，重建 plan 时尽量合并保留
- 解析生成的承诺函默认不移动原文件，可先引用；人工确认后再复制到 `artifacts/parser-generated/`

## 13.1 `bid-business-gap-planner` Skill 设计草案

商务标 S3 第一版直接建设专用 Skill：

```text
code/sewpg-bid-backend/opencode/skill/bid-business-gap-planner/
  SKILL.md
  scripts/
    run_from_manifest.py
  references/
    business_gap_plan_schema.json
    task_mapping_table.json
    commitment_rules.json
    certificate_rules.json
    performance_rules.json
    risk_flags.json
```

### 13.1.1 Skill 定位

`bid-business-gap-planner` 的职责：

- 读取 S2 已确认商务目录
- 读取商务解析结果
- 读取商务 Wiki 与素材索引
- 读取商务项目所用机型
- 判断每个目录点对应的商务响应任务
- 回挂解析阶段生成的承诺函/承诺书
- 防止同一解析承诺函产物重复挂载
- 对解析产物中的非商务边界风险做提示
- 推荐证书、业绩、模板底稿等候选素材
- 输出 `business_gap_plan.v1`

`bid-business-gap-planner` 不负责：

- 不生成最终商务标 Word
- 不执行盖章
- 不自动决定最终业绩项目
- 不修改原始素材库
- 不读取技术标 Wiki、技术标素材或技术标 gap plan
- 不替代后续 S4 装配

### 13.1.2 后端与 Skill 分工

| 事项 | 后端负责 | Skill 负责 |
|---|---|---|
| 读取项目 | 是 | 否 |
| 准备 manifest | 是 | 否 |
| 限定商务素材读取范围 | 是 | 否 |
| 调用 runner | 是 | 否 |
| 目录点语义判断 | 否 | 是 |
| 承诺函回挂 | 否 | 是 |
| 同一解析承诺函产物防重复挂载 | 否 | 是 |
| 解析产物边界提示 | 否 | 是 |
| 证书有效期和机型适配判断 | 否 | 是 |
| 业绩候选排序 | 否 | 是 |
| 输出 plan | 否 | 是 |
| schema 校验 | 是 | 可自检 |
| 目录覆盖校验 | 是 | 是 |
| 状态持久化 | 是 | 否 |
| 用户人工修改合并 | 是 | 否 |

核心原则：

> 后端是 Skill 的运行容器和状态管理层，商务缺口识别逻辑归 `bid-business-gap-planner`。

### 13.1.3 运行命令

参考技术标 `bid-tech-gap-planner` 的 `s4gap <manifest>` 模式。

商务标建议命令：

```bash
businessgap /data/documents/<projectId>/business-workspace/gaps/manifests/business_gap_input.json
```

执行要求：

- 命令只接收一个 manifest 路径
- 完整 plan 写入 manifest 的 `outputFile`
- stdout 只输出小摘要 JSON
- 失败时非零退出，不输出半成品 plan

stdout 建议结构：

```json
{
  "schemaVersion": "business_gap_plan.v1",
  "outputFile": "/data/documents/PRJ/business-workspace/gaps/business_gap_plan.json",
  "tocRefCount": 42,
  "taskCount": 58,
  "coverageStatus": "passed"
}
```

| `outputFile` | 是 | Skill 输出完整 plan 的路径 |

### 13.1.5 输入边界铁律

Skill 只能读取 manifest 中声明的路径和索引：

- 只能读取 `tocJsonPath`
- 只能读取 `parseResultPath`
- 只能读取 `businessWikiDir`
- 只能读取 `materialIndex` 中列出的素材
- 只能读取 `materialScope` 允许的商务标原始素材
- 不得读取技术标素材库
- 不得读取技术标 Wiki
- 不得读取其他客户或其他项目素材
- 不得因为文件名相似跨越素材边界

### 13.1.6 输出铁律

`business_gap_plan` 必须满足：

- `schemaVersion = business_gap_plan.v1`
- `bidType = business`
- `tocRefs` 覆盖 S2 已确认商务目录
- 不能只输出缺口项
- 不能只输出有素材匹配的任务
- 每个 `task` 必须有 `tocTarget`
- 每个 `task` 必须有 `taskType / decision / status`
- 未命中映射的目录点必须进入 `manual_mapping_required`
- 解析生成承诺函只能回挂或生成候选，不得无确认地直接 `ready`
- `coverageStatus` 必须为 `passed`，否则后端视为失败

### 13.1.7 Skill references 建议

| 文件 | 作用 |
|---|---|
| `business_gap_plan_schema.json` | 固化输出字段、枚举和必填项 |
| `task_mapping_table.json` | 对应第 15 节目录点到任务映射表 |
| `commitment_rules.json` | 承诺函/承诺书回挂、同一解析产物防重复挂载、边界提示规则 |
| `certificate_rules.json` | 机型认证、大部件证书、有效期、机型适配规则 |
| `performance_rules.json` | 业绩资产池筛选和业绩包完整性规则 |
| `risk_flags.json` | 风险标记枚举和触发条件 |

这些 references 是 Skill 的规则底座。后端不重复维护同一套商务判断规则。

### 13.1.8 与技术标 `bid-tech-gap-planner` 的差异

| 维度 | 技术标 `bid-tech-gap-planner` | 商务标 `bid-business-gap-planner` |
|---|---|---|
| 主对象 | 技术目录项、整章素材、附表、待填写 Word | 商务响应件任务、证书/附件、承诺函、价格/规格/偏差表 |
| 输出 schema | `bid-tech-gap-plan-v1` | `business_gap_plan.v1` |
| 主数组 | `items` | `tocRefs + tasks` |
| 机型字段 | `projectTurbineModel` | `selectedBusinessTurbineModel` |
| Wiki 来源 | 技术标 Wiki | 商务标 Wiki |
| 素材范围 | 技术标素材 | 商务标素材 |
| 承诺函 | 技术承诺为主 | 商务承诺、声明、其他说明为主 |
| 表格任务 | 技术附表/空表 | 价格表、开标价格表、规格表、商务偏差表、业绩表 |
| 证书任务 | 非核心 | 核心，必须关注有效期和机型适配 |
| 后续消费 | 技术标正文拼装 | 商务标响应件装配和附件挂载 |

### 13.1.9 第一版验收口径

第一版 Skill 跑通的最低标准：

- 样例 manifest 可独立运行
- 输出合法 `business_gap_plan.v1`
- `tocRefs` 覆盖全部商务目录
- 至少覆盖投标函、价格表、规格表、偏差表、保证金、资格证明、机型证书、业绩、承诺函这些核心任务
- 解析生成的承诺函能进入 `resolvedArtifacts`
- 机型证书候选能读取 `selectedBusinessTurbineModel`
- 未命中目录能进入人工确认
- stdout 摘要能被后端稳定解析
- 技术标 `bid-tech-gap-planner` 不受影响

## 14. 输入输出关系

### 14.1 输入

商务标 S3 的输入建议固定为：

| 输入 | 来源 | 用途 |
|---|---|---|
| 已确认商务目录 | 商务标模板与目录模块 | 生成 `tocRefs` 和固定任务骨架 |
| 商务解析结果 | 商务标解析模块 | 补充动态任务、证据、承诺函草稿 |
| 商务素材库 | 原始素材库 | 推荐候选材料、补料 |
| 商务 Wiki | Wiki 库 | 模板模块映射、证据卡片、待确认项 |
| 项目变量 | 项目信息、解析结果、人工录入 | 生成投标函、承诺书、表格 |
| 所用机型 | 创建商务标项目时选择 | 匹配机型认证证书、大部件证书、规格表、业绩资产 |
| 已有正式响应件 | 项目素材/上传文件 | 回填 `resolvedArtifacts` |

### 14.1.1 商务标项目创建阶段的所用机型选择

商务标也需要在创建项目时提供“所用机型”选择框。

原因：

- 机型认证证书需要按本次投标机型匹配
- 大部件型式认证证书需要按机型或部件适配范围匹配
- 货物规格一览表、商务摘要表、业绩资产筛选也可能依赖机型
- 若没有项目级机型输入，S3 只能在证书候选中做模糊匹配，容易进入大量 `review_required`

建议交互参考技术标投标机型选择，但数据来源应改为商务标 Wiki/素材库：

| 字段 | 说明 |
|---|---|
| `selectedBusinessTurbineModel.id` | 机型候选 ID |
| `selectedBusinessTurbineModel.model` | 机型名称 |
| `selectedBusinessTurbineModel.platform` | 平台或系列 |
| `selectedBusinessTurbineModel.ratedPowerKw` | 额定功率 |
| `selectedBusinessTurbineModel.rotorDiameterM` | 叶轮直径 |
| `selectedBusinessTurbineModel.aliases` | 机型别名 |
| `selectedBusinessTurbineModel.source` | `business_wiki_certificate` / `manual` |
| `selectedBusinessTurbineModel.certificateRefs` | 对应机型认证证书候选 |

候选来源建议：

1. 商务标 Wiki 中 `03-证据卡片` 的机型认证证书解析结果
2. 原始素材库 `通用素材库/05-专题证书库/01-机型认证证书`
3. Wiki 附件或证据卡片中的 `applicable_model / turbineModel / aliases`
4. 人工指定机型

如果候选为空：

- 允许人工录入机型
- `source = manual`
- 后续证书匹配默认进入 `review_required`

项目创建后，该机型应进入 `business_gap_plan` 顶层：

```json
{
  "selectedBusinessTurbineModel": {
    "model": "EW10.0-220",
    "platform": "EW10MW",
    "source": "business_wiki_certificate",
    "certificateRefs": ["CERT-001"]
  }
}
```

S3 使用方式：

- `certificate` 类任务优先匹配该机型
- `candidateMaterials` 按机型适配度排序
- 若证书机型不匹配，标记 `model_mismatch`
- 若证书机型覆盖范围不明确，标记 `model_fit_review_required`
- 若项目机型为空，证书类任务默认不直接 `ready`

### 14.2 输出

商务标 S3 的输出建议固定为：

| 输出 | 用途 |
|---|---|
| `business_gap_plan.json` | 页面展示、状态判断、S4 输入 |
| `state.json` | 保存人工操作与确认结果 |
| `resolvedArtifacts[]` | 后续商务标生成/装配的直接输入 |
| `selectedMaterialRefs[]` | 已选素材引用，供 S4 挂载 |
| `riskFlags[]` | 提醒用户复核证书有效期、语义误判、落位不确定 |
| 生成稿文件 | 待盖章正式稿或中间草稿 |

### 14.3 下游消费

S4 商务标生成模块至少应读取：

- `tocRefs[]`
- `tasks[]`
- `resolvedArtifacts[]`
- `selectedMaterialRefs[]`
- `status / decision / confirmed`

S4 不应重新判断“某个响应件是否缺失”，而应以 S3 已确认结果为准。若 S3 仍存在 `needs_input` 或 `review_required`，S4 应阻断生成或进入带风险提示的生成模式。

## 15. 目录点到任务映射表（第一版）

本表是 `bid-business-gap-planner` Skill 的基础规则和验收基线。

### 15.0.1 关于章节默认模块的适用边界

第 `15` 节的映射表不应理解为“某个章节号只能属于某个模块”。

它的真实作用是：

- 提供第一版 planner 的默认识别线索
- 让常见商务目录能快速生成稳定任务
- 在目录命名不规范或缺少上下文时提供兜底判断

但商务标目录在不同招标文件、不同模板、不同客户下可能发生变化，例如：

- `机型认证证书` 可能出现在 `7.1.2`，也可能单独列在附件证明材料中
- `供应链协同证明` 可能在 `9.19`，也可能放在资格证明或其他说明中
- `保密承诺书` 可能在 `9.2`，也可能作为附件单独列项
- `投标保证金保函` 可能在 `五`，也可能放入单独的保证金附件章节

因此第一版 planner 应采用“多信号判断”，不能只按章节号硬编码。

这里的 `planner` 指 `bid-business-gap-planner` Skill，而不是后端服务内的确定性 planner。

建议优先级如下：

| 优先级 | 信号 | 说明 |
|---|---|---|
| `1` | 人工确认目录节点 | 用户在 S2 审核过的目录结构优先 |
| `2` | 目录标题关键词 | 例如“保密承诺书”“机型认证证书”“开标价格表” |
| `3` | 解析结果证据 | 来自招标文件上下文、评分表、承诺要求 |
| `4` | Wiki 模板模块映射 | 商务 Wiki 中的模块映射关系 |
| `5` | 素材路径/素材类型 | 文件位于专题证书库、业绩资产池等 |
| `6` | 章节号兜底 | 仅在其他信号不足时参考章节号 |

换句话说：

> 模块归属应以“任务是什么”为主，以“目录在哪里”为辅。

如果目录标题与章节默认模块冲突，应按以下方式处理：

| 情况 | 处理方式 |
|---|---|
| 标题语义明确，章节号不匹配 | 按标题语义归模块，保留原 `tocTarget` |
| 标题语义不明确，但解析证据明确 | 按解析证据归模块，标记 `parser_inferred_mapping` |
| 标题和解析证据都不明确 | 按章节号兜底，标记 `manual_mapping_required` |
| Wiki 推荐与章节号冲突 | 进入 `review_required`，由人工确认 |

建议新增风险标记：

| riskFlag | 含义 |
|---|---|
| `section_module_conflict` | 章节号默认模块与标题/解析/Wiki 判断不一致 |
| `parser_inferred_mapping` | 任务模块主要由解析证据推断 |

前端展示时，应让用户看到：

- 任务最终落在哪个目录节点
- 系统为什么把它归到当前模块
- 是否存在章节与模块冲突
- 是否需要人工确认

| `9.18` | 不存在其他投标无效或否决情形声明 | `declaration_no_other_invalid_or_rejection_condition` | `bid_eligibility_commitments` | `fill_required` | 是 | 是 | `parser_generated_unconfirmed` |

说明：

- `9.3` 更像合同/响应说明，不一定是标准承诺函，因此默认 `review_required`
- `9.6` 和 `9.7` 通常需要信用查询截图或实时查询结果支撑，因此额外关注时效性
- `9.15` 涉及实质性响应，可能同时包含商务和技术边界，默认保留 `semantic_match_only`
- `9.17` 是否需要生成声明与招标文件具体要求强相关，默认 `review_required`
- 以上标题为第一版标准标题，实际文件名可根据招标文件措辞通过 `titleAlias` 保留别名

#### 15.1.1 承诺/声明任务生成模式

`9.1-9.18` 任务可由三种模式产生：

| 生成模式 | sourceType | 说明 | 默认状态 |
|---|---|---|---|
| 目录固定生成 | `toc_template` | 已确认目录中存在对应 `9.x` 节点 | 按映射表 decision |
| 解析显式生成 | `parser_explicit` | 招标文件明确要求提供承诺函/承诺书/声明 | `fill_required` 或 `review_required` |
| 解析草稿回挂 | `parser_generated` | 解析阶段已经生成 Word 草稿 | `review_required` |

同一个 `taskKey` 命中多个来源时：

- 保留一个任务
- `sourceEvidenceRefs` 追加多个证据
- `resolvedArtifacts` 回挂解析生成稿
- `sourceType` 可记录为 `merged`

#### 15.1.2 承诺/声明 topicGroup 定义

| topicGroupKey | topicGroupLabel | 包含任务 |
|---|---|---|
| `bid_eligibility_commitments` | 投标资格类承诺 | `9.1`、`9.4`、`9.9`、`9.10`、`9.12`、`9.17`、`9.18` |
| `compliance_commitments` | 合规承诺 | `9.2` |
| `contract_response_notes` | 合同响应说明 | `9.3` |
| `quality_and_safety_commitments` | 质量与安全类声明 | `9.5`、`9.14` |
| `credit_and_integrity_commitments` | 信用与廉洁类声明 | `9.6`、`9.7`、`9.8`、`9.11`、`9.13` |
| `substantive_response_commitments` | 实质性响应说明 | `9.15`、`9.16` |

`topicGroup` 仅用于页面局部分组和批量筛选，不用于合并任务。

#### 15.1.3 承诺/声明文件命名规则

默认文件名按任务标题生成：

```text
{默认任务标题}.docx
```

若招标文件原文使用不同说法：

- 原始说法进入 `titleAlias`
- 文件名优先使用用户确认后的标题
- 未确认时使用标准标题

示例：

```json
{
  "title": "保密承诺书",
  "titleAlias": ["保密承诺函", "投标保密承诺"],
  "fileName": "保密承诺书.docx"
}
```

#### 15.1.4 承诺/声明回挂与防重复挂载规则

说明：

- 承诺函去重的主逻辑由商务标解析 Skill 完成。
- S3 不重新解析全文、不重新批量生成承诺函。
- S3 只负责把解析阶段已经确认输出的承诺函草稿回挂到任务，并防止同一个解析产物重复挂载。

防重复挂载时建议使用：

```text
moduleKey + tocTarget.number + taskKey
```

解析生成稿回挂时建议使用：

```text
taskKey > normalizedTopic > title/titleAlias > placementHint
```

若多个解析生成稿命中同一任务：

- 默认只保留最高置信度或最新生成稿为主产物
- 其他稿件进入 `resolvedArtifacts`，但标记 `duplicate_candidate`
- 前端提示用户选择采用哪一版

若一个解析生成稿无法命中具体 `9.x`：

- 先挂到“投标人需要说明的其他内容”父节点
- 标记 `manual_placement_required`
- 人工确认后再转入具体 `9.x` 任务

#### 15.1.5 解析产物边界提示

说明：

- 技术承诺过滤的主逻辑由商务标解析 Skill 完成。
- S3 不重复执行全文搜索、语义过滤、主题去重或重新分类。
- S3 只在回挂解析产物时做边界提示：如果解析结果明显不属于商务标，只标记 `parser_artifact_boundary_warning`，不自动生成商务正式任务。

如解析命中以下主题：

- 发电量
- 功率曲线
- 可利用率
- 性能保证
- 环境适应性
- 机组技术方案
- 设备配置
- 控制策略

默认处理：

- 不生成 `9.1-9.18` 正式任务
- 记录为候选或日志
- 标记 `technical_boundary_risk`
- 需要人工确认后才能进入商务 S3

### 15.2 未命中映射表的兜底规则

第 `15` 节的映射表不是“唯一允许的任务清单”，而是 `bid-business-gap-planner` Skill 的默认骨架规则。

因此如果商务目录中出现了映射表未覆盖的目录项，系统不应丢弃该目录项，而应进入兜底处理。

兜底处理目标：

- 保证目录项不丢
- 保证用户能看到系统没有把握的内容
- 保证后续可以通过人工确认继续处理
- 保证高频未命中项可以沉淀为新的映射规则

#### 15.2.1 兜底处理顺序

建议按以下顺序处理未命中目录项：

1. 名称精确匹配
   - 与映射表中的目录/任务名称完全一致时，直接命中
2. 名称近义匹配
   - 例如“投标保证金银行保函”可近义命中“保证金电汇凭证/保函”
3. 大章节归类
   - 根据目录所在大章推断 `moduleKey`
4. 解析结果辅助判断
   - 使用商务解析结果中的上下文、评分要求、承诺要求辅助判断
5. Wiki/素材库辅助判断
   - 使用模板模块映射表、证据卡片、素材路径辅助判断
6. 人工确认
   - 仍无法判断时，生成待人工确认任务

#### 15.2.2 大章节默认归类

当目录项没有命中固定映射表时，可按大章节进行初步归类：

| 目录位置 | 默认 moduleKey | 默认 taskType | 默认 decision |
|---|---|---|---|
| `一` | `base_documents_guarantees` | `document` | `review_required` |
| `二` | `structured_response_tables` | `table` | `review_required` |
| `三` | `structured_response_tables` | `table` | `review_required` |
| `四` | `structured_response_tables` | `table` | `review_required` |
| `五` | `base_documents_guarantees` | `attachment` | `review_required` |
| `六` | `base_documents_guarantees` | `document` | `review_required` |
| `七` | `qualification_compliance_certificates` | `attachment` | `review_required` |
| `八` | `structured_response_tables` | `table` | `review_required` |
| `九` | `commitments_and_notes` | `document` | `review_required` |
| `供货保障专题` | `enterprise_finance_supply` | `document` | `review_required` |
| 无法识别 | `unmapped` | `document` | `review_required` |

说明：

- 大章节归类只是初步归类，不代表最终确认
- 所有通过兜底生成的任务默认进入 `review_required`
- 前端应提示“该任务由兜底规则生成，需要人工确认”

#### 15.2.3 兜底任务结构

未命中映射表时，建议生成如下任务：

```json
{
  "id": "TASK-UNMAPPED-001",
  "taskKey": "toc_unmapped_9_x_x",
  "title": "目录原始标题",
  "moduleKey": "commitments_and_notes",
  "taskType": "document",
  "decision": "review_required",
  "status": "review_required",
  "sourceType": "toc_unmapped",
  "tocTarget": {
    "nodeId": "TOC-9-X",
    "number": "9.X",
    "title": "目录原始标题",
    "required": true
  },
  "sourceRequirement": {
    "triggerText": "目录原始标题",
    "triggerContext": "",
    "normalizedTopic": "",
    "fromSection": "9.X",
    "extractionMethod": "toc_fallback"
  },
  "candidateMaterials": [],
  "resolvedArtifacts": [],
  "riskFlags": ["manual_mapping_required"]
}
```

#### 15.2.4 人工确认后如何处理

前端应允许用户对兜底任务做以下确认：

- 确认所属模块
- 确认 `taskType`
- 确认 `decision`
- 确认是否需要上传材料
- 确认是否需要系统生成稿
- 确认是否忽略该任务

人工确认后：

- 更新任务 `moduleKey / taskType / decision / status`
- 移除或保留 `manual_mapping_required`
- 写入 `state.json`
- 后续重建 `business_gap_plan` 时应优先保留人工确认结果

#### 15.2.5 规则沉淀

如果某类未命中任务频繁出现，应沉淀为新的固定映射规则。

建议沉淀条件：

- 同类目录项在多个项目中重复出现
- 人工确认结果高度一致
- 已明确默认 `moduleKey / taskType / decision`
- 已明确是否允许系统生成稿

沉淀后：

- 补充到第 `15` 节固定映射表
- 或写入商务标 Wiki 的 `02-模板模块映射表`
- 后续 planner 可直接命中，不再进入兜底状态

## 16. 承诺函专项执行规则

承诺函是商务标 S3 的关键专项，不建议只靠通用 `document` 规则处理。

### 16.1 来源优先级

承诺函任务来源优先级：

1. 已确认商务目录中的明确承诺节点
2. 商务解析结果中的 `structured.commitmentLetters[]`
3. 商务解析结果中的 `fieldGroups.commitmentRequirements[]`
4. 用户人工新增承诺任务
5. Wiki/素材库中的承诺模板候选

### 16.2 必须生成或进入任务池的情况

以下情况默认进入商务标 S3 任务池：

- 明确写有“承诺函”
- 明确写有“承诺书”
- 明确写有“另附承诺函/另附承诺书”
- 明确写有“须提供承诺函/须提供承诺书”
- 明确写有“应出具承诺函/应出具承诺书”
- 命中“投标人不得存在下列情形之一”

### 16.3 默认待复核的情况

以下情况只进入候选，不直接生成正式任务：

- 仅正文中出现“承诺”二字，但未明确要求单独出具文件
- 语义上像声明义务，但缺少明确文件名称
- 标题含“承诺”但正文无法判断是否需要独立文件
- 解析模型置信度低

默认处理：

- `decision = review_required`
- `status = review_required`
- `riskFlags` 包含 `semantic_match_only`

### 16.4 技术类承诺边界复核

以下内容若异常出现在解析承诺函结果中，S3 默认不进入商务标正式任务池：

- 发电量承诺
- 功率曲线承诺
- 可利用率承诺
- 性能保证指标承诺
- 环境适应性承诺
- 控制策略、设备配置、技术方案类承诺

默认处理：

- 进入候选区或日志
- 标记 `technical_boundary_risk`
- 不自动生成商务承诺书

### 16.5 防重复挂载规则

承诺函去重的主逻辑由商务解析阶段完成。S3 只做防重复挂载，建议按以下顺序：

1. `taskKey` 相同，合并
2. `tocTarget.nodeId + normalizedTopic` 相同，合并
3. 标题近义且证据上下文指向同一要求，合并
4. 同一解析生成稿多次被命中，只回挂一次

标题别名进入：

```json
{
  "title": "保密承诺书",
  "titleAlias": ["保密承诺函", "投标保密承诺"]
}
```

### 16.6 命名规则

承诺函文件名不应全部叫“承诺函”。

建议命名规则：

```text
{主题}{承诺书/承诺函}.docx
```

示例：

- `保密承诺书.docx`
- `投标人不存在下列情形之一承诺函.docx`
- `无行贿犯罪行为声明.docx`
- `未列入失信被执行人名单声明.docx`

### 16.7 确认规则

解析阶段生成的承诺函草稿默认不直接 `ready`。

确认前：

- `sourceMode = parser_generated`
- `confirmed = false`
- `decision = review_required`
- `status = review_required`

人工确认后：

- `confirmed = true`
- `decision = ready`
- `status = ready`
- 可进入 S4 装配或盖章流转

## 17. Wiki/素材库命中规则

商务标 S3 使用 Wiki/素材库的目标不是“新建大量任务”，而是给既有任务补充候选材料和风险判断。

### 17.1 素材优先级

建议候选素材优先级：

1. 项目素材
2. 客户素材
3. 通用素材
4. 模板底稿库
5. 解析阶段产物

说明：

- 项目素材优先，因为它最贴近本次投标
- 客户素材优先于通用素材，因为重点客户可能有专属协议和评价证明
- 通用素材可作为资质、能力、财务、业绩资产池的基础来源

### 17.2 Wiki 节点使用方式

| Wiki 节点 | 在 S3 中的作用 |
|---|---|
| `01-素材目录索引` | 帮助列出可用素材范围 |
| `02-模板模块映射表` | 判断某个任务优先找哪些素材或模板 |
| `03-证据卡片` | 提供证书、资质、业绩、协议等证据候选 |
| `04-待填写清单` | 提醒哪些任务需要变量填充 |
| `05-生成规则与风险提示` | 提供有效期、适用范围、人工确认要求 |

### 17.2.1 商务标机型候选来源

商务标创建项目时的“所用机型”候选，建议优先从商务标 Wiki 和专题证书库生成。

候选来源：

| 来源 | 说明 | 优先级 |
|---|---|---|
| Wiki `03-证据卡片` | 从机型认证证书证据卡片中读取 `applicable_model / turbineModel / aliases` | 高 |
| 原始素材库 `05-专题证书库/01-机型认证证书` | 从证书文件名、OCR、清洗摘要中提取机型 | 高 |
| Wiki 附件元数据 | 从附件关联的证书卡片和摘要中读取机型 | 中 |
| 人工录入 | 候选为空或项目使用新机型时手动输入 | 兜底 |

候选项建议字段：

```json
{
  "id": "BTM-001",
  "model": "EW10.0-220",
  "platform": "EW10MW",
  "ratedPowerKw": 10000,
  "rotorDiameterM": 220,
  "aliases": ["10MW-220", "EW10.0"],
  "source": "business_wiki_certificate",
  "certificateRefs": ["CERT-001", "CERT-002"]
}
```

如果同一机型存在多张证书：

- 创建项目时只选择机型，不要求用户立即选择具体证书
- S3 的 `certificate` 任务再根据有效期、认证范围、证书类型推荐候选证书
- 若多张证书都可用，任务进入 `review_required`，由用户选择

### 17.2.2 机型选择对 S3 的影响

`selectedBusinessTurbineModel` 应参与以下任务判断：

| 任务 | 使用方式 |
|---|---|
| 机型认证证书 | 判断证书适用机型是否覆盖项目机型 |
| 大部件型式认证证书 | 判断部件证书适用机型、平台或容量等级是否覆盖项目机型 |
| 货物规格一览表 | 默认带入机型基础参数 |
| 商务部分摘要表 | 默认带入机型/容量等摘要字段 |
| 业绩资产池 | 可按容量等级、机型平台筛选业绩 |

判定规则：

| 条件 | 建议处理 |
|---|---|
| 证书明确覆盖所用机型，且有效期满足要求 | `ready` 或候选优先 |
| 证书覆盖同平台/同容量，但未明确写当前机型 | `review_required` + `model_fit_review_required` |
| 证书机型与项目机型冲突 | 不作为默认候选，标记 `model_mismatch` |
| 项目未选择机型 | 证书类任务不直接 `ready`，进入 `review_required` |
| 项目机型人工录入 | 标记 `manual_model_input`，证书匹配需人工确认 |

### 17.3 证书有效期规则

证书类任务必须检查：

- 证书名称
- 适用机型/部件
- 项目所用机型
- 发证机构
- 有效期开始日期
- 有效期结束日期
- 是否覆盖投标截止日期或合同要求日期

若缺有效期信息：

- 不直接判 `ready`
- 标记 `expiry_check_required`
- 进入 `review_required`

若缺项目所用机型：

- 机型认证证书不直接判 `ready`
- 大部件型式认证证书不直接判 `ready`
- 标记 `model_fit_review_required`

### 17.3.1 专题证书证据卡片字段要求

为支持项目创建阶段机型选择和 S3 证书匹配，商务标 Wiki 的证据卡片需要对专题证书提取结构化字段。

机型认证证书证据卡片建议字段：

| 字段 | 说明 | 是否关键 |
|---|---|---|
| `evidenceType` | 固定为 `turbine_model_certificate` | 是 |
| `title` | 证据卡片标题 | 是 |
| `documentType` | `机型认证证书` | 是 |
| `certificateName` | 证书名称 | 是 |
| `certificateNo` | 证书编号 | 否 |
| `issuer` | 发证机构 | 是 |
| `applicableModels` | 适用机型列表 | 是 |
| `modelAliases` | 机型别名 | 否 |
| `platform` | 平台/系列 | 否 |
| `ratedPowerKw` | 额定功率 | 否 |
| `rotorDiameterM` | 叶轮直径 | 否 |
| `validFrom` | 有效期开始 | 否 |
| `validTo` | 有效期结束 | 是 |
| `sourceMaterialId` | 原始素材 ID | 是 |
| `sourcePath` | 原始素材路径 | 是 |

大部件型式认证证书证据卡片建议字段：

| 字段 | 说明 | 是否关键 |
|---|---|---|
| `evidenceType` | 固定为 `component_type_certificate` | 是 |
| `title` | 证据卡片标题 | 是 |
| `documentType` | `大部件型式认证证书` | 是 |
| `componentName` | 部件名称 | 是 |
| `componentModel` | 部件型号 | 否 |
| `certificateName` | 证书名称 | 是 |
| `certificateNo` | 证书编号 | 否 |
| `issuer` | 发证机构 | 是 |
| `applicableModels` | 适用整机机型 | 否 |
| `applicablePlatforms` | 适用平台 | 否 |
| `ratedPowerRange` | 适用容量范围 | 否 |
| `validFrom` | 有效期开始 | 否 |
| `validTo` | 有效期结束 | 是 |
| `sourceMaterialId` | 原始素材 ID | 是 |
| `sourcePath` | 原始素材路径 | 是 |

字段缺失处理：

| 缺失字段 | 处理方式 |
|---|---|
| 缺 `applicableModels` | 不能直接用于机型精确匹配，进入 `review_required` |
| 缺 `validTo` | 标记 `expiry_check_required` |
| 缺 `componentName` | 大部件证书不能自动归到具体部件，进入 `review_required` |
| 缺 `sourcePath` | 不可作为最终挂载材料，只能作为线索 |

### 17.3.2 证书候选排序规则

S3 推荐证书候选时，建议按以下优先级排序：

1. 项目素材中已上传且明确适配当前机型的证书
2. 客户素材中明确适配当前机型的证书
3. 通用素材中明确适配当前机型的证书
4. 覆盖同平台/同容量的证书
5. 标题近似但适用范围不明的证书
6. 机型不匹配但同属专题证书库的低优先级候选

推荐分数建议参考：

| 匹配情况 | score 建议 |
|---|---|
| 精确机型匹配 + 有效期满足 | `0.95-1.00` |
| 机型别名匹配 + 有效期满足 | `0.85-0.94` |
| 同平台/同容量匹配 | `0.65-0.84` |
| 仅标题或路径命中 | `0.40-0.64` |
| 机型冲突 | `<0.40` |

说明：

- `score` 只用于候选排序，不直接决定 `ready`
- 是否 `ready` 仍需满足机型/部件/有效期等关键条件
- 人工确认结果应优先于自动评分

### 17.3.3 业绩证据卡片字段要求

为支持 `7.9` 业绩表和业绩支撑材料判断，商务标 Wiki 应为业绩资产生成结构化证据卡片。

业绩主卡片建议字段：

| 字段 | 说明 | 是否关键 |
|---|---|---|
| `evidenceType` | 固定为 `performance_record` | 是 |
| `performanceId` | 业绩唯一 ID | 是 |
| `projectName` | 项目名称 | 是 |
| `customerName` | 客户/业主 | 是 |
| `contractName` | 合同名称 | 否 |
| `contractNo` | 合同编号 | 否 |
| `contractDate` | 合同签订日期 | 否 |
| `turbineModel` | 机型 | 是 |
| `turbinePlatform` | 平台/系列 | 否 |
| `ratedPowerKw` | 单机容量 | 是 |
| `quantity` | 台数 | 否 |
| `totalCapacityMw` | 总容量 | 否 |
| `deliveryStatus` | 供货状态 | 否 |
| `operationStatus` | 运行/并网状态 | 否 |
| `has240hTrial` | 是否有 240h 试运行 | 条件性 |
| `hasAcceptance` | 是否有验收证明 | 条件性 |
| `supportingFileRefs` | 支撑材料引用 | 是 |

业绩支撑材料卡片建议字段：

| 字段 | 说明 | 是否关键 |
|---|---|---|
| `evidenceType` | `contract_scan` / `award_notice` / `trial_240h_report` / `acceptance_report` / `operation_certificate` | 是 |
| `performanceId` | 对应业绩 ID | 是 |
| `fileName` | 文件名 | 是 |

| `matchedBy` | `exact_id` / `project_name` / `contract_no` / `manual` | 是 |

字段缺失处理：

| 缺失字段 | 处理方式 |
|---|---|
| 缺 `ratedPowerKw` | 不能自动用于容量等级筛选，进入 `review_required` |
| 缺 `performanceId` | 支撑材料不能自动归属业绩，进入 `review_required` |
| 缺 `sourcePath` | 不可作为最终挂载材料 |
| 240h 要求下缺 `trial_240h_report` | 对应支撑任务进入 `material_required` |

### 17.3.4 业绩候选排序规则

业绩候选排序建议按任务类型分别处理。

业绩表候选排序：

| 匹配情况 | score 建议 |
|---|---|
| 容量等级满足 + 机型/平台匹配 + 支撑材料齐备 | `0.90-1.00` |
| 容量等级满足 + 支撑材料基本齐备 | `0.75-0.89` |
| 容量等级满足但支撑材料缺项 | `0.55-0.74` |
| 容量等级不明确但标题/合同疑似匹配 | `0.35-0.54` |
| 容量等级不满足 | `<0.35` |

业绩支撑材料候选排序：

| 匹配情况 | score 建议 |
|---|---|
| `performanceId` 精确匹配 | `0.95-1.00` |
| 项目名称 + 合同编号匹配 | `0.85-0.94` |
| 项目名称匹配 | `0.70-0.84` |
| 客户名称匹配但项目不明确 | `0.45-0.69` |
| 无法归属具体业绩 | `<0.45` |

说明：

- 业绩表排序关注“能不能入表”
- 支撑材料排序关注“能不能对应到具体业绩”
- 人工确认后的业绩和支撑材料关联应优先于自动匹配
- 若同一业绩被多个表复用，支撑材料不复制多份，只保留引用关系

### 17.4 图片/扫描件处理规则

图片和扫描件可直接作为 `attachment/certificate/bundle` 候选材料。

原则：

- 图片/扫描件不要求清洗成 Word
- 可预览即可作为候选
- OCR 信息只用于辅助识别证书名称、有效期、主体名称
- 最终装配时通常按原件图片/PDF 挂载，而不是按清洗稿挂载

### 17.5 模板底稿处理规则

模板底稿主要用于 `fill_required`。

若任务命中模板底稿，且项目变量齐全：

- `decision = fill_required`
- `status = needs_input`

若模板存在但变量缺失：

- `decision = review_required`
- `status = review_required`

## 18. 前端验收标准

第一版商务标 S3 页面做到以下能力，即可认为功能闭环成立。

### 18.1 页面打开

- 能从商务标项目流程进入 S3 页面
- 页面标题和导航明确是“商务标缺口处理”
- 不进入技术标 S3 页面
- 没有复用导致的技术标字段残留

- 左侧或主区按商务目录展示 `tocRefs`

- 点击目录节点能看到该节点任务卡片

### 18.3 任务卡片

任务卡片至少展示：

- 任务标题
- `taskType`
- `decision`
- `status`
- 所属模块

- 是否有候选素材
- 是否有风险标记

- 目录落位
- 来源证据
- 解析生成稿预览入口
- 推荐素材列表

- 已解决产物
- 人工备注
- 操作按钮

- 上传补充材料

- 标记任务忽略

## 20. 风险与暂缓项

### 20.1 第一版明确不做

- 不做复杂父子任务树
- 不做一个任务多目录落位
- 不自动发布最终盖章件
- 不让 Wiki 直接批量新建大量任务
- 不让 AI 无人工确认地生成全部承诺件
- 不将图片/扫描件强制清洗成 Word

### 20.2 主要风险

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 承诺函误生成 | 标题或普通语句被误判为独立承诺书 | `parser_semantic` 默认待复核 |
| 技术承诺混入商务标 | 发电量、功率等技术承诺进入商务 S3 | `technical_boundary_risk` 过滤 |
| 证书版本错误 | 找到旧证书或不适配机型证书 | 证书有效期和机型适配检查 |
| 目录落位不准 | 任务挂到错误章节 | `manual_placement_required` + 人工确认 |
| Wiki 推荐不准 | 素材存在但映射不完整 | 支持搜索兜底和人工选择 |
| 与技术标混用 | 商务 S3 修改影响技术标 S3 | 独立接口、独立路径、独立 plan schema |

### 20.3 后续增强方向

- 引入 AI 语义辅助落位
- 承诺函草稿自动合并与重命名
- 证书 OCR 自动抽取有效期
- 表格字段自动填充和校验
- S3 与 S4 的一键装配闭环

说明：商务标专用 `bid-business-gap-planner` Skill 不再作为后续增强项，而是第一阶段必做项。

|---|---|

### 22.2 必填字段的最低可用标准

每个任务至少必须具备以下字段，前端才可以稳定展示：

- `id`
- `taskKey`
- `title`
- `moduleKey`
- `taskType`
- `decision`
- `status`
- `sourceType`
- `tocTarget`
- `fingerprint`
- `updatedAt`

每个任务至少必须具备以下字段，S4 才能稳定消费：

- `taskKey`
- `title`
- `taskType`
- `status`
- `tocTarget`
- `selectedMaterialRefs`
- `resolvedArtifacts`

### 22.3 状态判定优先级

后端计算 `status` 时建议按以下顺序执行：

1. `decision = not_applicable` 时，`status = not_applicable`。
2. 存在 `riskFlags` 中的强人工确认风险时，`status = review_required`。
3. 存在未确认的解析生成稿时，`status = review_required`。
4. `taskType = document/table` 且缺少必要项目数据时，`status = needs_input`。
5. `taskType = certificate/attachment/bundle` 且未选择素材时，`status = needs_input`。
6. 存在已确认 `resolvedArtifacts` 或已选 `selectedMaterialRefs` 且无阻断风险时，`status = ready`。
7. 其他情况默认为 `review_required`。

### 22.4 `taskType` 对前端操作的影响

| `taskType` | 默认操作 | 预览方式 | 完成标准 |
|---|---|---|---|
| `document` | 生成草稿、上传 Word、选择模板 | Word 预览或下载 | 有确认稿或已选正式文件 |
| `table` | 上传/填写表格、选择底稿 | Excel/Word 表格预览 | 表格数据完整且人工确认 |
| `attachment` | 上传附件、选择素材 | 原件预览 | 附件已选择且无明显风险 |
| `certificate` | 选择证书、检查有效期和适配性 | PDF/图片/Word 预览 | 证书有效、适配项目或已人工确认 |
| `bundle` | 多材料组合选择 | 包内文件逐个预览 | 必要子项齐全且人工确认 |

### 22.5 `decision` 对前端提示的影响

| `decision` | 含义 | 前端提示 |
|---|---|---|
| `material_required` | 必须提供外部材料或证书 | 显示上传/选择素材入口 |
| `fill_required` | 必须填写或生成响应件 | 显示生成草稿、上传定稿或选择模板入口 |
| `review_required` | 系统无法自动确定 | 显示人工确认入口 |
| `optional` | 可能需要，取决于项目要求 | 显示低优先级提示 |
| `not_applicable` | 当前项目不适用 | 显示为已忽略，可恢复 |

### 22.6 重建 plan 时的保留规则

`business_gap_plan` 允许重新生成，但不能覆盖用户已做的关键选择。

| 内容 | 重建时处理方式 |
|---|---|
| 人工确认的 `moduleKey/taskType/decision` | 保留 |
| 已选择的 `selectedMaterialRefs` | 保留 |
| 已确认的 `resolvedArtifacts.confirmed = true` | 保留 |
| 人工备注 `notes` | 保留 |
| 新解析出的承诺函草稿 | 尝试按 `fingerprint/topicGroup/title` 回挂 |
| 已不在目录中的任务 | 标记 `orphaned_by_template_change`，不直接删除 |
| 映射规则变化导致的任务变更 | 加 `mapping_changed_review_required` |

### 23.6 第一阶段不建议做的事项

| 事项 | 暂缓原因 |
|---|---|
| 一开始就做复杂多目录复用 | 当前已明确商务标默认不允许一个任务多处落位 |
| 自动决定最终业绩项目 | 业绩选择强业务判断，必须人工确认 |
| 自动盖章或发布最终件 | 盖章流程属于后续正式文件管控 |
| 图片/扫描件强制清洗成 Word | 证书和扫描件应保留原件，必要时只做 OCR 元数据 |
| 直接复用技术标 S3 接口 | 容易混淆路径、状态和后续装配逻辑 |
| 后端实现一套商务缺口判断引擎 | 会和 Skill 双轨冲突，后续难维护 |

### 23.7 推荐下一步

下一步建议先做 `P0` 到 `P3`：

1. 固化 `business_gap_plan.v1` schema。
2. 新增 `bid-business-gap-planner` Skill 目录和 `SKILL.md`。
3. 按技术标 `bid-tech-gap-planner` 的方式实现 `run_from_manifest.py`。
4. 新增商务标独立落盘路径、manifest 构建和 Skill 调用接口。
5. 用样例 manifest 先跑通 `business_gap_plan.json`。
6. 再接解析承诺函回挂、机型证书候选和素材推荐。

这样做的好处是边界清晰、可测试、不会影响技术标链路。
