# 27 — 双轨开发协作规范与权限加固计划

> 用途：固化"商务标 / 技术标"双轨开发的协作边界，沉淀后端权限隔离的整改路线。
>
> 适用对象：技术标前端、商务标前端、后端、参与 AI 协作的所有人。
>
> 维护规则：每次跨双线的大改动前补充/更新本文；PR Review 时引用对应章节作为对照。
>
> 2026-05-25 补充：本文保留协作和权限思想。当前前端页面目录已按 `src/workspaces/business` / `src/workspaces/technical` 拆分，旧 `pages/*` 示例只作为历史问题背景，不作为当前代码路径。

---

## 0. 背景

当前痛点两条：

1. **前端组件归属混乱**：商务标和技术标由两位同学分头维护，但代码层把两套页面塞进同一个组件用 `if (bidType==='商务标')` 分支，导致一方 polish 时常误改另一方视觉。
2. **后端权限完全裸奔**：164 个业务端点中有 143 个连"必须登录"都没有，更没有"角色 × 标书类型"隔离。前端 `WorkspaceGuard` 只是浏览器层的提示，绕过即失效。

本文给出两件事的整改方案与团队协作规则。

## 2. 前端协作铁律：分层 + 分叉

### 2.1 五层架构

| 层 | 路径 | 是否按 bidType 分叉 | 谁动谁负责 |
|---|---|---|---|
| 视觉原子 | `components/shared/*`、`components/states/*` | **共享**，禁止出现 `bidType` 判断 | 任意，需双方 review |
| 布局/壳 | `components/layout/AppShell` 及侧栏 | **共享**，菜单可见性由 `user.role` 决定 | 任意，需双方 review |
| 数据/逻辑 | `api/*`、`utils/workspace.js`、`utils/permissions.js`、`utils/stageFlow.js` | **共享** | 任意，需双方 review |
| 业务页面 | `src/workspaces/technical/pages/*` vs `src/workspaces/business/pages/*` | **分叉**：两条独立目录 | 各自维护 |
| 路由 | `App.jsx` | 显式 import 两套页面，**不再运行时 dispatch** | 双方 review |

### 2.2 铁律

1. **`components/shared/*` 内禁止出现 `bidType === '商务标'` 这类判断**。任何 bidType 分支必须发生在 `pages/*` 里。违反即视为破坏边界，PR 不予合并。
2. **路由层不做运行时 dispatch**。当前以 `src/workspaces/business/routes.jsx` 和 `src/workspaces/technical/routes.jsx` 显式挂载对应页面。
3. **每个共用组件必须有"参数化的扩展点"而非"内部分支"**。例如共享壳只接收配置和 slot，由两个 workspace 页面注入业务差异，而不是组件内部判断。

### 2.3 目录结构（建议）

```
src/
  components/
    layout/        # AppShell, Sidebar  —— 共享
    shared/        # Button/Modal/Table/...  —— 共享，禁 bidType
    states/        # PageLoading/PageError  —— 共享
  pages/
    Dashboard.jsx  # 真正的共用页
  workspaces/
    technical/
      pages/       # 技术标专属页（owner: 技术标同学）
      components/
      routes.jsx
    business/
      pages/       # 商务标专属页（owner: 商务标同学）
      components/
      routes.jsx
  api/             # 共享
  utils/           # 共享
```

### 2.4 协作流程

1. **CODEOWNERS**（仓库根加 `.github/CODEOWNERS`）

   ```
   /code/sewpg-bid-frontend/src/workspaces/business/   @<商务标同学 GitHub 用户名>
   /code/sewpg-bid-frontend/src/workspaces/technical/  @<技术标同学 GitHub 用户名>
   /code/sewpg-bid-frontend/src/components/shared/  @<双方>
   /code/sewpg-bid-backend/                       @<后端>
   ```

2. **PR 模板**（仓库根加 `.github/pull_request_template.md`）

   ```
   ## 影响范围
   - [ ] 仅技术标 (src/workspaces/technical/*)
   - [ ] 仅商务标 (src/workspaces/business/*)
   - [ ] 共享层 (components/shared/*, components/layout/*, utils/*, api/*)

   ## 共享层改动 checklist
   - [ ] 无新增 bidType 判断
   - [ ] 已通知双线 owner review
   - [ ] 同时验证了 tech 和 business 路由
   ```

3. **PR 标题约定**：`feat(tech): ...`、`feat(business): ...`、`refactor(shared): ...` 三类强制前缀。

## 3. 商务标 UI 解耦现状

本节最初记录的是商务标 UI 被共享页面影响后的恢复路线。当前口径已经更新：

- 商务标页面已进入 `code/sewpg-bid-frontend/src/workspaces/business/pages/`。
- 技术标页面已进入 `code/sewpg-bid-frontend/src/workspaces/technical/pages/`。
- `BusinessTenderReview.jsx` 是商务标 workspace 内的正式页面，不再是旧根 `src/pages` 下的薄壳。
- `GapEntry` 这类运行时分发入口不再作为当前路线，双轨路由由各自 `routes.jsx` 显式挂载。

后续不再按旧 R1/R2/R3 恢复路线推进。新的检查口径是：业务页面留在各自 workspace，只有无业务语义的 UI 原子、布局壳、请求底座和权限工具可以共享；共享层出现 `bidType` 分支时，优先下沉到业务 workspace。

## 4. 后端权限隔离加固方案

详见对照排查记录（本节为方案凝练版）。

### 4.1 现状一句话

164 业务端点中只有 21 个端点要求登录，**0 个端点**校验"角色 × 项目 bidType"匹配。前端 `WorkspaceGuard` 仅是 UI 层。

### 4.2 四阶段整改路线

| 阶段 | 内容 | 工期 | 风险 | 验证 |
|---|---|---|---|---|
| **A 全局登录兜底** | 在 `main.py:58` 给 `api_router` 挂全局 `Depends(require_login_unless_public)`；白名单仅 `/healthz`、登录、OnlyOffice 回调 | 0.5 天 | 低 | 匿名访问 business/technical 业务接口必须 401 |
| **D 设置/审计仅 TB** | `settings.py` / `audit.py` 全部端点替换为 `Depends(require_role("TB"))` | 0.5 天 | 低 | T/B token 调 `/api/settings/users` 必 403 |
| **B 项目级 scope** | 新建 `app/services/access_control.py::require_project_access(project_id, user)`；business/technical 项目端点签名注入；列表强制按 `user.role` 注入标类过滤 | 1.5 天 | 中（OnlyOffice/解析回调要排除） | T token 访问 B 项目必 403，反之亦然 |
| **C1 素材库路径守卫** | 在 `material_store` 入口判断：T 用户读写路径必须 `技术标/*`，B 必须 `商务标/*`，TB 不限 | 1 天 | 中 | T 上传到 `商务标/*` 必 403 |

### 4.3 实施顺序与封板节奏

- **第一波（1 天）**：A + D。封板"匿名访问全开"和"低权改全局配置"两个 P0 风险。
- **第二波（1 sprint）**：B + C1。每端点签名改造需要回归测试覆盖。

### 4.4 关键代码草案（落地时落到 `app/services/access_control.py`）

```python
from fastapi import Depends, HTTPException
from app.services.auth_service import current_user
from app.services.store import store
from app.services.parse_profiles import normalize_bid_type

async def require_project_access(project_id: str, user: dict) -> dict:
    project = store.get_project(project_id)
    role = (user or {}).get("role")
    if role == "TB":
        return project
    bid_type = normalize_bid_type(str(project.get("bidType") or ""))
    if role == "T" and bid_type == "技术标":
        return project
    if role == "B" and bid_type == "商务标":
        return project
    raise HTTPException(status_code=403, detail="无权访问该标书")

def require_role(*allowed: str):
    async def dep(user: dict = Depends(current_user)) -> dict:
        if (user or {}).get("role") not in allowed:
            raise HTTPException(status_code=403, detail="无权执行此操作")
        return user
    return dep
```

## 6. 借鉴 OpenSpec：轻量 Spec-Driven

参考桌面文档 `OpenSpec：规范驱动的 AI 编程新范式.md`。**不引入 OpenSpec CLI**（过重），但借鉴其"规范先于代码"理念，落地为：

### 6.1 本项目的轻量化做法

1. **`doc/specs/<feature>.md`**：每个跨 workspace 或动共享层的功能写一份 spec，Given/When/Then 描述。
2. **AI 协作约束**：要 AI 改代码前，先让它阅读对应 spec；spec 缺失则先补 spec。
3. **PR Review**：评审 spec 与代码是否一致，spec 改动单独记录。

### 6.2 Spec 模板

```markdown
# Spec: <功能名>

## 适用范围
- workspace: tech / business / both
- 涉及层: pages / shared / api / ...

## Requirement: <一句话需求>
The system SHALL ...

### Scenario: <场景 1>
- GIVEN ...
- WHEN ...
- THEN ...

## 验收
- [ ] tech workspace 表现：...
- [ ] business workspace 表现：...
- [ ] 共享层变更：...（或"无"）
```

### 6.3 渐进采用

- 第一阶段：仅"动共享层"的功能强制写 spec
- 第二阶段：核心模块补历史 spec
- 第三阶段：评估是否上 OpenSpec CLI
