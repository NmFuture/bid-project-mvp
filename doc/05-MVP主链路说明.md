# 标书智能体 MVP 主链路说明

> 用途：统一当前 MVP 和后续开发的主链路口径。
> 更新日期：2026-05-03

## 1. 当前唯一阶段口径

当前技术标主链路统一为 `S0-S6`：

```text
S0 解析
  -> S1 模板与目录
  -> S2 审核目录
  -> S3 缺口处理
  -> S4 生成标书
  -> S5 共创
  -> S6 导出
```

其中：

- `S0 解析` 是全局解析/审核模块，负责上传招标文件、结构化解析、投标决策和项目信息补全。
- `S1-S6` 是项目模块阶段条，只展示六个节点。
- 旧 `S7/S8/S9/S10` 不再作为当前用户流程、接口文档或验收基线使用。
- 后端仍兼容旧阶段请求，例如旧客户端请求 stage `9` 会映射到当前 `S5 共创`，但返回值和页面展示按 `S1-S6`。

一句话：

> **S0 先把项目解析清楚并决定是否参与，S1-S6 再完成技术标生成、共创和导出。**

## 2. 成品思路

成品流程的核心不是“大模型直接写完整标书”，而是：

- `模板与目录`：用投标模板、招标文件和 Wiki/素材线索形成可审核目录。
- `审核目录`：由人确认最终目录。
- `缺口处理`：按已确认目录检索素材库，识别缺口，支持上传资料、选择已有素材和调用 AI 填写。
- `生成标书`：根据最终目录和缺口处理计划，从素材库与补料产物中拼接正文，不做自由发挥式生成。
- `覆盖诊断`：作为生成/导出前的检查能力，暴露未匹配目录项、未拼上的素材和需要人工确认的占位内容。
- `共创 / 导出`：在 OnlyOffice 中人机共创，最终导出 Word。

## 3. 当前 MVP 落地

当前真实打通的主链路：

- `S0 解析`：支持多个招标文件、PDF/图片型文件无感识别、结构化解析、附表线索识别、投标决策和项目信息补全；技术标项目信息补全时确认投标机型。
- `S1 模板与目录`：上传项目模板；项目未上传时读取设置侧启用的系统默认模板；调用 futurecode/opencode 执行 `bid-tech-outline-generator` 的 `s2toc` 命令生成目录；调用失败时本地运行同一 Skill 脚本降级。
- `S2 审核目录`：人工审核并确认目录，右侧支持招标文件 OnlyOffice 预览。
- `S3 缺口处理`：调用缺口识别 Skill，读取素材库 Wiki、真实素材、解析结果和已有补料记录；支持上传、选择素材、AI 填写、重新检查和确认。
- `S4 生成标书`：调用 `bid-tech-assembler`，按目录 JSON、Wiki、素材库、缺口处理计划和补料/AI 填写产物拼装正文。
- `S5 共创`：OnlyOffice 共创编辑。
- `S6 导出`：下载最新版 Word；格式刷新、PDF 导出和评分点级审计按后续待办继续推进。

## 4. 历史内部文件名说明

代码和已有数据卷里仍保留若干历史命名。它们是兼容路径，不代表当前用户阶段：

| 历史内部名 | 当前业务语义 | 说明 |
|---|---|---|
| `s1_parse_manifest.json` | `S0 解析` | 解析 Skill manifest 历史文件名 |
| `s2_toc_workdir/` | `S1 模板与目录` | 目录生成工作区，保留 `s2toc` 命令名 |
| `s4_gap_workdir/` | `S3 缺口处理` | 缺口计划、人工补料、AI 填写产物工作区 |
| `s7_assembly_workdir/` | `S4 生成标书` | 正文拼装 manifest、素材导出、拼装计划和报告 |
| `s7_assembly_input.json` | `S4 生成标书` | `bid-tech-assembler` manifest 历史文件名 |
| `fill-generation` 接口 | `S4 生成标书` | 兼容旧前端接口名 |
| `coverage` 接口/页面 | `S4/S6 诊断能力` | 保留为覆盖诊断和导出检查能力，不是独立主流程节点 |

后续新增文档、接口说明和页面文案必须使用 `S0-S6`，不要再用旧阶段号描述当前流程。

## 5. S4 生成标书实现口径

`S4 生成标书` 的输入是：

- 最新成功目录 JSON，默认位于 `documents/{project_id}/technical-workspace/s2_toc_workdir/toc.json`
- S1 导出的 `wiki/卡片/*.md`
- 当前素材库中的清洗后 Word 文件
- `S3 缺口处理` 产出的 `gap_plan.json`
- 人工上传补料和 AI 填写产物
- 项目参数、已确认投标机型和有效模板

处理方式：

1. 后端准备历史内部目录 `s7_assembly_workdir`。
2. 将当前素材库中的清洗后 Word 导出为 Skill 可读取的文件系统素材库。
3. 将缺口处理产物补充成可供拼装读取的素材卡片。
4. 重写 Wiki 卡片 `path`，让卡片指向导出的素材 Word。
5. 调用 `opencode/skill/bid-tech-assembler/scripts/run_from_manifest.py`。
6. 输出正文 `.docx`、`assembly_plan.json`、`assembly_report.md` 和 `needs_review.md`。
7. 将最终正文复制到项目文档路径，供 `S5/S6` 继续使用。

## 6. 覆盖诊断当前实现

覆盖诊断使用 `S4` 的 `assembly_plan.json` 和素材卡片结果计算：

- 已拼上的素材数量
- 素材库中存在但未出现在目录 JSON 或拼装计划里的材料
- 目录项中未匹配素材、需要人工确认的项
- 按 `scope/category` 分组的素材拼装覆盖树

边界：

- 当前覆盖诊断是“素材拼装覆盖校验”，不是最终正式版的评分点覆盖审计。
- 正式版仍需要把招标评分点、正文段落、素材来源和最终正文段落建立更细的追溯关系。

## 7. 一句话总结

> **当前 MVP 的主线已经收敛为 S0-S6：S0 解析决策，S1 生成目录，S2 审核目录，S3 补齐缺口，S4 拼装正文，S5 共创，S6 导出。**
