# 标书智能体 MVP 与成品思路

> 用途：作为后续开发的统一口径。  
> 只讲两件事：**成品怎么做，当前 MVP 怎么落地**。

## 1. 成品思路

成品流程的核心不是“大模型直接写完整标书”，而是：

```text
S2 生成目录 -> 按目录检索素材库 -> S5 对缺失素材补料并入库 -> S7 按目录拼接成稿 -> S9 共创 -> S10 导出
```

其中：

- `S5`：调用 `opencode skill` 补充缺失素材，补完后回写素材库
- `S7`：只负责从素材库检索并拼接，不负责自由生成

一句话：

> **成品里，S5 负责补料，S7 负责拼接。**

## 2. 当前 MVP 落地

当前 MVP 不重排前端展示流，页面仍按 `S0-S10` 走；实现上只把关键阶段做真，其余阶段先 mock。

```text
前端展示流：S0 -> S1 -> S2 -> S3 -> S4 -> S5 -> S6 -> S7 -> S8 -> S9 -> S10
```

当前真实打通的主链路：

- `S0`：项目列表 / 新建项目
- `S1`：真实解析招标文件
- `S2`：调用 `opencode skill` 生成目录
- `S3`：审核目录
- `S7`：调用 `opencode` 生成初稿
- `S9`：OnlyOffice 共创编辑
- `S10`：下载最新版 Word

当前先 mock 的阶段：

- `S4`
- `S5`
- `S6`
- `S8`

## 3. 为什么这样做

这样做的目的有两个：

- 复用现有前端第一版，尽量少改页面和跳转
- 先把真正有风险的链路跑通：`解析 -> opencode -> docx -> OnlyOffice -> 下载`

这里要特别区分：

- **产品语义**：正式版还是 `S5` 补料、`S7` 拼接
- **当前实现**：为了最小改动，先借现有 `S7` 页面承接“生成初稿”

一句话：

> **当前 MVP 的 S7 是实现借位，不代表正式版最终语义。**

## 4. 开发指导

后续开发统一按下面这条线理解：

- 成品目标不变：`S5` 补料入库，`S7` 拼接成稿
- 当前 MVP：前端保留 `S0-S10`，FastAPI 统一承接 `/api`
- 关键阶段真实执行，其他阶段由 FastAPI mock

一句话总结：

> **MVP 先用最小改动跑通主链路；成品再回到“素材库 + 补料 + 拼接”的完整形态。**
