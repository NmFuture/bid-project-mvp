# 标书智能体 MVP 主链路说明

> 用途：统一当前 MVP 和最终成品的主链路口径。
> 当前实现已经从“生成初稿”调整为“按目录和素材库拼装技术标正文”。

## 1. 成品思路

成品流程的核心不是“大模型直接写完整标书”，而是：

```text
S2 生成目录 -> 按目录检索素材库 -> S5 对缺失素材补料并入库 -> S7 按目录拼接成稿 -> S8 校验未覆盖/未拼装项 -> S9 共创 -> S10 导出
```

其中：

- `S5`：补齐缺失素材，并沉淀回素材库。
- `S7`：只负责根据 S2 最终目录，从素材库检索并拼接正文，不做自由发挥式生成。
- `S8`：检查目录项和素材拼装关系，暴露未匹配目录项、未拼上的素材和需要人工确认的占位内容。

一句话：

> **S5 负责补料，S7 负责拼接，S8 负责把没有拼上的问题显性化。**

## 2. 当前 MVP 落地

当前 MVP 保留前端 `S0-S10` 展示流：

```text
S0 -> S1 -> S2 -> S3 -> S4 -> S5 -> S6 -> S7 -> S8 -> S9 -> S10
```

当前真实打通的主链路：

- `S0`：项目列表 / 新建项目
- `S1`：真实解析招标文件
- `S2`：调用目录生成 skill，输出当前 S2 目录 JSON 和 Wiki 卡片
- `S3`：审核目录
- `S7`：调用 `bid-tech-assembler`，按 S2 目录 JSON + Wiki 卡片 + 素材库清洗后 Word 拼装正文
- `S8`：基于 S7 拼装计划校验未拼上的素材和未匹配目录项
- `S9`：OnlyOffice 共创编辑
- `S10`：下载最新版 Word

当前仍由 FastAPI 承接或轻量 mock 的阶段：

- `S4`
- `S5`
- `S6`

## 3. S7 当前实现口径

S7 的输入是：

- S2 生成的 `投标文件-总目录.json`
- S2 导出的 `wiki/卡片/*.md`
- 当前素材库中的清洗后 Word 文件
- 项目参数和可选模板

S7 的处理方式是：

1. 后端准备 `s7_assembly_workdir`。
2. 将当前素材库中的清洗后 Word 导出为 skill 可读取的文件系统素材库。
3. 重写 Wiki 卡片 `path`，让卡片指向导出的素材 Word。
4. 调用 `opencode/skill/bid-tech-assembler/scripts/run_from_manifest.py`。
5. 输出正文 `.docx`、`assembly_plan.json`、`assembly_report.md` 和 `needs_review.md`。
6. 将最终正文复制到项目文档路径，供 S9/S10 继续使用。

## 4. S8 当前实现口径

S8 不再只按章节 `generationMode` 做 mock 覆盖。

当前 S8 使用 S7 的 `assembly_plan.json` 和素材卡片结果计算：

- 已拼上的素材数量
- 素材库中存在但未出现在 S2 目录 JSON 或拼装计划里的材料
- S2 目录项中未匹配素材、需要人工确认的项
- 按 `scope/category` 分组的素材拼装覆盖树

边界：

- 当前 S8 是“素材拼装覆盖校验”，不是最终正式版的评分点覆盖审计。
- 正式版仍需要把招标评分点、段落证据、素材来源和最终正文段落建立更细的追溯关系。

## 5. 一句话总结

> **当前 MVP 已经把 S7 拉回正式产品语义：按照 S2 目录 JSON 去素材库找材料并拼装 Word；S8 用来暴露没有拼上的素材和目录项。**
