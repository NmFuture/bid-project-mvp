# 标书智能体 MVP 主链路说明

> 用途：统一当前 MVP 和最终成品的主链路口径。
> 当前实现已经从“生成初稿”调整为“按目录和素材库拼装技术标正文”。

> 2026-05-02 更新：前端主进度已经收敛为 6 个节点：模板与目录、审核目录、缺口处理、生成标书、共创、导出。内部 S1-S10 状态号和接口名仍保留用于兼容；本文中 S4/S5/S6/S8 的历史表述应按“缺口处理”和“生成标书/覆盖诊断”理解。

## 1. 成品思路

成品流程的核心不是“大模型直接写完整标书”，而是：

```text
模板与目录 -> 审核目录 -> 缺口处理 -> 生成标书 -> 共创 -> 导出
```

其中：

- `缺口处理`：按已确认目录检索素材库，识别缺口，支持上传资料、选择已有素材和调用 AI 填写。
- `生成标书`：根据最终目录和缺口处理计划，从素材库与补料产物中拼接正文，不做自由发挥式生成。
- `覆盖诊断`：作为生成/导出前的检查能力，暴露未匹配目录项、未拼上的素材和需要人工确认的占位内容。

一句话：

> **缺口处理负责补齐输入，生成标书负责拼接，覆盖诊断负责把没有拼上的问题显性化。**

## 2. 当前 MVP 落地

当前 MVP 内部保留 `S1-S10` 状态号，但前端主进度展示为 6 个合并节点：

```text
模板与目录 -> 审核目录 -> 缺口处理 -> 生成标书 -> 共创 -> 导出
```

当前真实打通的主链路：

- `模板与目录`：上传/回退模板，解析招标文件，由 FastAPI 调 futurecode/opencode 执行 S2 Skill 的 `s2toc` 命令，输出目录 JSON 和证据决策；futurecode/opencode 不可用时，本地运行同一 Skill 脚本降级生成。
- `审核目录`：人工审核并确认目录。
- `缺口处理`：调用缺口识别 skill，读取素材库 Wiki、真实素材、解析结果和已有补料记录；支持上传、选择素材、AI 填写、重新检查和确认。
- `生成标书`：调用 `bid-tech-assembler`，按目录 JSON、Wiki、素材库、缺口处理计划和补料产物拼装正文。
- `共创`：OnlyOffice 共创编辑。
- `导出`：下载最新版 Word，并继续补齐格式、检查和 PDF 能力。

## 3. S7 当前实现口径

S7 的输入是：

- S2 最新成功工作区中的目录 JSON，默认在 `documents/{project_id}/technical-workspace/s2_toc_workdir/toc.json`
- S2 导出的 `wiki/卡片/*.md`
- 当前素材库中的清洗后 Word 文件
- 项目参数和可选模板

S7 的处理方式是：

1. 后端准备 `s7_assembly_workdir`。
2. 将当前素材库中的清洗后 Word 导出为 skill 可读取的文件系统素材库。
3. 重写 Wiki 卡片 `path`，让卡片指向导出的素材 Word。
4. 调用 `opencode/skill/bid-tech-assembler/scripts/run_from_manifest.py`。
5. 输出正文 `.docx`、`assembly_plan.json`、`assembly_report.md` 和 `needs_review.md`。
6. 将最终正文复制到项目文档路径，供 S9/S10 继续使用。

## 4. S8 当前实现口径

S8 不再只按章节 `generationMode` 做 mock 覆盖。

当前 S8 使用 S7 的 `assembly_plan.json` 和素材卡片结果计算：

- 已拼上的素材数量
- 素材库中存在但未出现在 S2 目录 JSON 或拼装计划里的材料
- S2 目录项中未匹配素材、需要人工确认的项
- 按 `scope/category` 分组的素材拼装覆盖树

边界：

- 当前 S8 是“素材拼装覆盖校验”，不是最终正式版的评分点覆盖审计。
- 正式版仍需要把招标评分点、段落证据、素材来源和最终正文段落建立更细的追溯关系。

## 5. 一句话总结

> **当前 MVP 已经把 S7 拉回正式产品语义：按照 S2 目录 JSON 去素材库找材料并拼装 Word；S8 用来暴露没有拼上的素材和目录项。**
