# 商务标解析模块执行计划

> 用途：作为“商务标专用解析模块”落地的实施清单，指导需求确认、后端实现、前端接入、联调验收按阶段推进。  
> 状态：执行计划稿  
> 更新日期：2026-05-07

## 1. 目标与原则

本阶段目标不是泛化地“改解析”，而是明确完成：

1. 在现有解析体系外，补充一条商务标专用解析链路。
2. 商务标解析结果不再沿用技术标解析语义，避免被技术标字段污染。
3. 商务标解析结果可直接服务后续商务标项目模块。
4. 商务标解析产出的附表与承诺函可与现有预览机制兼容。

执行过程中坚持五个原则：

1. 商务标与技术标严格区分，不能在解析目标、结果结构、页面表达上混用。
2. 解析流程骨架尽量复用现有实现，但解析 contract 必须按商务标重定义。
3. 先定输出结构，再改 skill、后端、前端，不先写散代码。
4. 商务标新增能力必须兼容现有附表预览机制，但不能强行把所有新产物都叫“附表”。
5. 技术标现有解析能力必须保持稳定，不能因为商务标改造被误伤。

## 2. 当前现状结论

基于当前代码链路，先确认三个事实：

1. 现有解析会调用 skill。
2. 现有解析不是通过 Redis worker 调 skill，而是解析接口直接调用后端解析服务。
3. 现有解析 skill、本地 fallback、前端展示结构都明显偏技术标。

当前关键实现位置：

1. 解析路由：
   - `code/sewpg-bid-backend/app/api/routes/parse.py`
2. 解析服务：
   - `code/sewpg-bid-backend/app/services/parsing.py`
3. 当前解析 skill：
   - `code/sewpg-bid-backend/opencode/skill/bid-tender-structured-parser/`
4. 当前前端解析页：
   - `code/sewpg-bid-frontend/src/pages/TenderReview.jsx`

因此，本期不建议只修改技术标 skill，而应建设一条“商务标专用解析 profile / skill / 展示”的独立分流。

## 3. 本期范围

### 3.1 纳入本期

1. 补充商务标专用解析模块入口。
2. 补充商务标专用解析结果 contract。
3. 新建商务标专用解析 skill。
4. 新建商务标专用本地 fallback 解析逻辑。
5. 新增“承诺”全文检索并生成承诺函。
6. 新增“投标人不得存在下列情形之一”承诺函生成。
7. 让商务标解析产物可在页面上预览。

### 3.2 暂不纳入本期

1. 商务标后续自动生成全链路与解析结果的深度耦合。
2. 所有承诺函正文的高度智能化润色与风格优化。
3. 承诺函模板多版本治理、自动选版。
4. 商务标解析产物自动入原始素材库或自动入 Wiki。

## 4. 与技术标解析的边界

### 4.1 必须严格区分的内容

| 项目 | 技术标解析 | 商务标解析 |
|---|---|---|
| 页面入口 | 现有解析页面 | 商务标专用解析页面/入口 |
| skill | `bid-tender-structured-parser` | 新建商务标专用 skill |
| 重点字段 | 技术评分、风机参数、性能保证、环境适应性 | 商务评分、商务响应、承诺函、合规声明、商务附表 |
| 结果分组 | 偏技术字段组 | 偏商务字段组 |
| 派生产物 | 附表空表 | 附表空表 + 承诺函 |

### 4.2 可以复用但不能混淆的能力

以下能力可以复用当前解析体系，但必须保留 `bidType=商务标` 的独立分流：

1. 文件上传与保存。
2. PDF / DOCX / 图片 OCR 文本提取。
3. 解析进度条与 opencode 输出展示。
4. 附表产物保存目录与预览能力。
5. 结构化结果持久化与项目解析状态维护。

### 4.3 实施红线

1. 不能直接在技术标解析结果里“塞几个商务字段”了事。
2. 不能只改 skill，不改本地 fallback。
3. 不能让商务标页面继续展示技术标字段表格。
4. 不能把承诺函错误命名成普通附表，导致后续语义混乱。
5. 不能破坏当前技术标解析、附表预览、目录生成等已有能力。

## 5. 商务标解析结果目标结构

在正式编码前，应先冻结商务标解析结果 contract。

建议商务标解析结果至少包括以下模块：

1. `sourceDocuments`
   - 记录参与解析的源文件。
2. `scoringCriteria`
   - 仅保留 `business / price / compliance` 等与商务标相关内容。
3. `fieldGroups.projectBasics`
   - 保留项目名称、招标编号、招标人、交货期、质保期等共用基础信息。
4. `fieldGroups.businessResponse`
   - 记录商务偏差、保证金、履约承诺、开标价格表、报价相关识别结果。
5. `fieldGroups.qualificationSupport`
   - 记录资格证明、业绩证明、合规类要求。
6. `commitmentLetters`
   - 承诺函清单，每个承诺函一条记录，并产出对应 Word。
7. `appendices`
   - 商务附表、空表、模板化附件等可预览产物。
8. `requirementPresence`
   - 对专项商务响应、附件要求、否决项等做 presence 判断。
9. `coverage`
   - 汇总解析覆盖情况。

明确删除或不再作为商务标核心输出的内容：

1. 技术评分标准模块。
2. 环境适应性模块。
3. 性能保证指标模块。

## 6. 承诺函生成口径

### 6.1 生成规则

本期明确新增两类承诺函生成能力：

1. 全文搜索“承诺”：
   - 根据“承诺”所在上下文，判断是否应生成承诺函。
   - 原则上“一类独立承诺事项，对应一个承诺函 Word”。
2. 全文搜索“投标人不得存在下列情形之一”：
   - 无论是否命中普通承诺规则，均强制生成一份
   - `投标人不存在下列情形之一承诺函`

### 6.2 产物口径

承诺函建议作为“解析派生产物”保存，和附表一起可预览，但元数据中应区分类型：

1. `artifactType = appendix`
2. `artifactType = commitment_letter`

建议统一进入项目解析工作区，例如：

```text
parsed/{project_id}/s1_appendices/
```

后续进入正式项目工作区后，再按商务标语义发布到对应目录。

### 6.3 本期不解决的难点

1. 承诺函最终法律文本的绝对最佳措辞。
2. 所有承诺句都自动精确聚类成最优数量。
3. 不同客户/项目承诺函模板自动选版。

本期先做到：

1. 可识别。
2. 可生成。
3. 可预览。
4. 可进入后续商务标编制流程。

## 7. 总体实施顺序

建议按七个阶段推进，并在每个阶段结束后暂停评审，不一次性改到底。

1. 先冻结商务标解析 contract。
2. 再补后端解析分流骨架。
3. 再新建商务标 skill 与 fallback。
4. 再补承诺函派生产物。
5. 再补前端商务标解析入口与展示。
6. 再做联调与测试。
7. 最后再决定如何接入后续商务标自动生成流程。

## 8. 分阶段执行步骤

### 8.1 步骤一：冻结商务标解析结果 contract

目标：

把商务标解析模块最终要输出什么，先定义清楚。

主要工作：

1. 梳理商务标解析结果字段树。
2. 明确保留字段、删除字段、新增字段。
3. 明确 `appendices` 与 `commitmentLetters` 的元数据结构。
4. 明确前端展示模块如何对应这些字段。

产出物：

1. 商务标解析结果 JSON contract 文档。
2. 承诺函 artifact 字段清单。

验收标准：

1. 不再使用技术标字段集合直接套商务标。
2. 商务标新增需求都能在 contract 中找到落点。

### 8.2 步骤二：补商务标解析后端分流骨架

目标：

在不影响技术标解析的前提下，为商务标建立独立分流。

主要工作：

1. 为解析服务增加 `bidType/profile` 分流。
2. 区分技术标解析 skill 名与商务标解析 skill 名。
3. 区分技术标 prompt 与商务标 prompt。
4. 区分技术标 fallback 与商务标 fallback。

重点关注文件：

1. `code/sewpg-bid-backend/app/services/parsing.py`
2. `code/sewpg-bid-backend/app/api/routes/parse.py`

验收标准：

1. 技术标仍走原解析链路。
2. 商务标可走新的解析 profile。
3. 两类项目互不串解析结果。

### 8.3 步骤三：新建商务标专用解析 skill

目标：

让 opencode 调用时真正按商务标目标解析，而不是沿用技术标 skill。

主要工作：

1. 新建商务标 skill 目录。
2. 编写商务标版 `SKILL.md`。
3. 编写商务标版 `run_from_manifest.py`。
4. 如有必要，复制并裁剪 `parser_core`，形成商务标专用核心规则。

重点关注目录：

1. `code/sewpg-bid-backend/opencode/skill/`

验收标准：

1. 商务标 skill 能输出独立 JSON。
2. 输出中不再强制要求技术标模块。
3. 可识别商务评分、价格、合规、承诺等内容。

### 8.4 步骤四：实现商务标本地 fallback 解析

目标：

确保即使 skill 不可用，商务标解析也不会回退到技术标结果结构。

主要工作：

1. 新增商务标本地规则集。
2. 新增商务标字段组提取逻辑。
3. 新增商务标评分表识别逻辑。
4. 新增承诺上下文扫描逻辑。

验收标准：

1. skill 失败时，仍可输出商务标格式结果。
2. 不会因为 fallback 而重新出现技术评分、环境适应性、性能保证等模块。

### 8.5 步骤五：实现承诺函派生产物生成与预览

目标：

让承诺函像附表一样可生成、可预览、可进入后续流程。

主要工作：

1. 定义承诺函 artifact 结构。
2. 基于上下文生成承诺函 Word。
3. 接入现有 OnlyOffice / 文件预览能力。
4. 页面上与附表一并展示，但用不同标签标识。

重点关注文件：

1. `code/sewpg-bid-backend/app/services/parsing.py`
2. `code/sewpg-bid-backend/app/api/routes/parse.py`
3. 前端解析页相关组件

验收标准：

1. 可看到承诺函列表。
2. 每个承诺函可预览。
3. “不得存在下列情形之一承诺函”必定生成。

### 8.6 步骤六：补前端商务标解析模块入口与结果页

目标：

在左侧导航中补充商务标解析模块，并按商务标语义展示结果。

主要工作：

1. 新增商务标解析入口或页面分支。
2. 根据项目 `bidType` 切换技术标/商务标展示。
3. 删除商务标页面里的技术标专属展示板块。
4. 新增承诺函、商务评分、商务响应、资格支撑等板块。

重点关注文件：

1. `code/sewpg-bid-frontend/src/components/layout/AppShell.jsx`
2. `code/sewpg-bid-frontend/src/pages/TenderReview.jsx`
3. `code/sewpg-bid-frontend/src/api/index.js`

验收标准：

1. 左侧导航可进入商务标解析模块。
2. 商务标解析页展示结构与技术标明显区分。
3. 用户可查看附表与承诺函预览。

### 8.7 步骤七：联调、测试与验收

目标：

确保商务标解析链路稳定可用，且不影响技术标。

主要工作：

1. 补单测：商务标 contract、承诺函生成、artifact 预览。
2. 补集成测试：商务标项目上传并解析。
3. 做人工验收：真实商务招标文件样例验证。
4. 回归技术标解析链路。

验收标准：

1. 技术标解析通过回归。
2. 商务标解析输出符合新 contract。
3. 商务评分、附表、承诺函均可查看。
4. 无“技术标字段误入商务标结果”的混淆现象。

## 9. 风险与应对

| 风险 | 说明 | 应对策略 |
|---|---|---|
| 只改 skill，不改 fallback | skill 失败时仍回到技术标结果 | 商务标 fallback 必须同步建设 |
| 前端继续沿用技术标展示 | 即使后端正确，页面仍看起来是技术标解析 | 前端展示 contract 必须同步调整 |
| 承诺函数量失控 | 全文“承诺”命中过多，产生大量低质量函件 | 先做上下文聚类与去重，再生成 |
| 承诺函语义不稳 | 自动生成的法律措辞不够严谨 | 先按模板化生成，保留人工复核 |
| 技术标回归受影响 | 共用解析服务修改后误伤技术标 | 全程保留 bidType 分流并补回归测试 |

## 10. 建议的沟通节奏

为了方便中间沟通和改进，建议按以下节奏推进：

1. 先执行步骤一：冻结 contract。
2. 你审核 contract 后，再执行步骤二、三。
3. skill 与 fallback 跑通后，再做步骤五、六。
4. 每完成一个大步骤，就暂停一次做你这边验证。

## 11. 下一步建议

下一步不建议直接开改代码，建议先执行：

1. 步骤一：冻结商务标解析结果 contract。
2. 重点先确定：
   - 商务评分表保留哪些字段；
   - `appendices` 与 `commitmentLetters` 每条记录长什么样；
   - 页面上商务标解析结果分几块展示。

只有这一步定稳，后面 skill、后端、前端改造才不会反复返工。
