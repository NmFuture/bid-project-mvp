# 上海电气风电投标智能体 — 需求梳理与预期功能

> 版本：v1.0（基于《AI 数智化投标平台-技术标需求说明》整理）
> 目标读者：业务方、项目经理、开发团队、审阅领导
>
> 当前口径说明：
> 本文主要保留业务目标、完整产品流程和能力边界，作为背景资料使用。
> 当前开发与部署请以 `05-08` 文档为准。
> 其中当前 MVP 的实现方式是：前端展示流仍保留 `S0-S10`，但只把 `S0/S1/S2/S3/S7/S9/S10` 做成真实能力，其余阶段先由 FastAPI mock。

## 一、项目背景与目标

### 1.1 业务痛点

| # | 痛点 | 典型表现 |
|---|---|---|
| 1 | 效率低 | 标书编制依赖人工复制粘贴，一份标书动辄数十小时 |
| 2 | 易出错 | 跨部门文件格式混乱，字体字号页边距不一致 |
| 3 | 附表负担重 | 华能等大客户附表数量巨大，人工填数工作量集中在最后几天 |
| 4 | 漏项、错项 | 评分细则多达数十条，人工对照易漏；偏差识别靠经验 |
| 5 | 格式返工多 | 排版耗时占标书总工时的 30–50% |

### 1.2 项目目标

- **自动解析招标文件**：评分细则、项目信息、技术参数、附表模板
- **自动生成投标骨架**：目录结构与招标文件一致、带要点提示
- **逐条响应**：招标条款 → 投标段落的可追溯映射，杜绝漏项
- **格式 100% 标准化**：五级标题、表格、图片、页眉页脚、页码全套规范由系统统一应用
- **附表自动填充**：业主附表原样保留，系统只填数据
- **本地化部署**：数据不外泄，符合国企合规要求

---

## 二、核心原则

1. **严格响应招标文件** — 目录、条款、评分点，一字不落
2. **格式统一** — 自动清洗、自动排版、不靠人工刷格式
3. **数据准确** — 关键数字（项目名、业主、机型、容量、金额、日期、证书编号）必须来自权威源，不允许 LLM "创作"
4. **安全可控** — 全链路内网、审计可查
5. **AI 减负而非替代** — 关键内容（盖章、签字、特殊承诺、涉密、方案最终决策）**必须人工终审**

## 三、端到端业务流程

```
┌─────┐  ┌─────┐  ┌──────┐  ┌──────┐  ┌─────┐  ┌──────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
│S1   │→│S2   │→│ S3   │→│ S4   │→│S5   │→│ S6   │→│S7   │→│S8   │→│S9   │→│S10  │
│解析 │  │目录 │  │审核  │  │缺口  │  │备料 │  │审核  │  │填充 │  │校验 │  │共创 │  │导出 │
│     │  │     │  │目录  │  │识别  │  │     │  │备料  │  │     │  │     │  │     │  │     │
└─────┘  └─────┘  └──────┘  └──────┘  └─────┘  └──────┘  └─────┘  └─────┘  └─────┘  └─────┘
                    ▲                            ▲                            ▲
                    │                            │                            │
                 人工审核                     人工审核                       人机共创
                 (目录)                      (仅新增内容)                 (AI 辅助改稿)
```

| 阶段 | 输入 | 输出 | 人工介入 |
|---|---|---|---|
| S1 解析 | 招标文件（docx/PDF/扫描件）、项目定制文件 | 评分细则 / 项目信息 / 技术参数 / 附表模板（结构化） | 可选抽检 |
| S2 目录生成 | S1 结构化结果 + (可选)投标模板 + 标书类型（技术/商务） | 二级标题 + 每节要点提示的目录草案 | 无 |
| S3 目录审核 | 目录草案 | 已确认目录 | **强制** |
| **S4 素材缺口识别** | 已确认目录 + 两库现状 | 缺失清单（哪些节点缺哪些数据/段落，建议来源） | 无 |
| **S5 备料** | 缺失清单 | 数据库补录 + Wiki 节点补全 | **强制**（补录） |
| **S6 审核备料** | 新增的数据/Wiki 段落/附表 | 审核通过标记 | **强制**（仅审核新增） |
| S7 填充 / 正文拼装 | 目录 + 备齐的两库 | 正文草稿（正文 + 附表，每段带证据链与覆盖评分点） | 无 |
| S8 校验 | 初稿 | 覆盖率报告 / 一致性报告 / 清洗后稿 | 处理未覆盖项 |
| **S9 人机共创** | 清洗后稿 | 定稿（AI 辅助实时编辑，加章节/改内容/刷格式） | **主要工作阶段** |
| S10 导出 | 定稿 | .docx + PDF | 最终确认 |

**S4/S5/S6 设计理由**：避免填充阶段才发现缺素材只能让 LLM 编造。**素材缺口识别 → 人工补料 → 新增内容审核**三步前置，把所有空缺摸清、补齐、核对之后再进入填充，保障"精度优先"。
**S6 审核范围**：**仅审核本项目新增的内容**（例如新录的机型参数、新建的 Wiki 节点、新填的附表数据），已有素材库内容不重复审核，避免人工负担过重。

## 四、功能模块清单

### 4.1 招标文件解析模块

**输入**：招标文件（.docx / PDF / 扫描件混合）
**处理**：
- 自动路由到 docx / PDF 文本 / OCR 三条管线
- 结构化抽取：**评分细则**（每条含得分点、证明材料要求、权重）、**项目信息**（名称、招标编号、招标人/管理单位、标段规模、交货周期、质保期、技术承诺）、**技术参数**（风机核心参数、性能保证指标、环境适应性、专题方案要求）、**附表**（原样保留模板）、**考核条款**（发电量、可利用率、功率曲线、部件、认证）

**输出**：结构化数据（用于后续阶段）+ 解析报告（给人工抽检用）

**关键能力**：
- 扫描件 OCR（PaddleOCR，MinerU，中文）
- 附表自动识别与切片，结构完整保留
- 评分细则结构化是整个系统的基础（后续所有响应都绑定到评分项）

**对应 KPI**：招标解析成功率 ≥ 90%

---

### 4.2 目录生成与审核模块

**输入**：S1 结构化结果 + (可选)投标模板
**处理**：
- 基于招标文件"投标文件组成"章节 + 评分细则 + 客户专属结构（如华能模板）生成目录
- 目录细化到**二级标题 + 每节要点提示**（要点提示是给后续填充 agent 的导向）
- 支持一/二/三级目录与招标文件严格对齐
- 前端提供**大纲编辑器**：拖拽排序、增删节点、调整层级、改标题

**输出**：已确认的目录（冻结版本，后续填充基于此版本）

**关键能力**：
- 支持华能等大客户专属结构开箱即用
- 目录节点可关联到对应评分条款（显示右侧"本节回应的招标要求原文"）
- 支持多版本管理（审核通过后冻结）

---

### 4.3 素材库（两库体系）

素材分为两个**性质不同、管理方式不同**的库：

#### 4.3.1 数据库（结构化，客户 Excel → 系统 JSON）

**性质**：客户提供或维护的结构化数据，数字/名称/日期/编号精确。
**来源**：客户用 Excel 维护（熟悉的工作方式） → 系统导入为 JSON/表存储。
**用途**：附表填充、项目信息全局一致、标题/正文中的精确字段替换。

**典型内容**：
- 机型参数表（单机容量、叶轮直径、轮毂高度、塔筒型式、功率曲线...）
- 项目业绩表（项目名、业主、机型、容量、年份、合同额...）
- 人员清单（姓名、职称、年限、证书）
- 资质证书（证书名、编号、发证机关、有效期、扫描件路径）
- 设备清单（供货范围、规格、数量）

**管理能力**：
- **Excel 模板下载**：系统提供标准模板，客户填入后上传
- **Excel 导入**：按模板校验字段 → 存入数据库（JSON 存储 + 关键字段列式索引）
- **Web 表单编辑**：支持在 UI 里直接改
- **扩展字段**：允许自定义字段（某客户特有要求） 
- **版本快照**：每次导入保留版本，可回滚

#### 4.3.2 文档库 / Wiki（非结构化，三层组织）

**性质**：文字性素材、方案描述、专题内容 — 段落级别的可复用内容。
**来源**：内部积累，按业务域分层维护。
**用途**：章节填充时，Agent 根据目录节点的要点提示，在 Wiki 上导航找到合适段落改写融合。

**三层结构**（对应需求文档）：

| 层 | 变更频率 | 内容 |
|---|---|---|
| **标准模板层** | 季度 | 公司简介（集团概况/资质荣誉/研发实力/生产基地）、技术方案描述（主机/叶片/变桨/齿轮箱/塔筒）、专题方案（抗低温/抗覆冰/防雷/防风沙/抗高温）、机型技术描述 |
| **客户定制层** | 中 | 按客户分子树（华能/华电/大唐/国家能源/...）：合作协议描述、战略关系、合作历史叙事、客户重点关注的承诺话术 |
| **项目定制层** | 高（每项目） | 风资源计算报告、发电量担保函、载荷计算报告、塔筒工程量、部件校核报告、历次投标回收的有价值段落 |

**管理能力**：
- Wiki 树形编辑器：增删改节点、拖拽调整层级
- 每节点带摘要（LLM 生成，辅助 Agent 决策）
- 文档上传自动切片 + 挂到叶子节点
- 支持"另存为模板"：把已完成项目的段落升级为标准素材
- **标书类型标签**：每节点可标 `技术标 / 商务标 / 通用`，不同标书类型引用不同子树

#### 4.3.3 两库协作的典型场景

- 目录节点"机型技术参数表"：→ **数据库**查机型参数 → 直接填表
- 目录节点"公司简介"：→ **Wiki** `标准模板/公司简介/集团概况` 取段落
- 目录节点"与华能合作情况"：→ **Wiki** `客户定制/华能/合作历史` + **数据库**查华能历史项目清单 → 组合
- 目录节点"发电量担保函"：→ **项目定制层** 找本项目已算好的担保函 → 直接套用；若没有 → 标记缺失（由 S5 备料阶段补录）

### 4.4 素材缺口识别与备料审核（S4 + S5 + S6）

这是**目录确认后、章节填充前**的三步前置步骤，确保填充阶段每一节都有**经过审核的**可用素材，不让 LLM 编造。

#### 4.4.1 缺口识别（S4，系统自动）

**输入**：已确认的目录（带要点提示） + 数据库现状 + Wiki 现状 + 本次标书类型（技术/商务）

**处理**：
- Agent 遍历每个目录节点，分析该节点需要：
  - 哪些**结构化字段**（→ 查数据库）
  - 哪些**文字段落**（→ 查 Wiki）
  - 哪些**附表**（→ 业主附表 + 数据库填数）
- 对每项需求检查两库现状：
  - **✓ 就绪**：数据库有 / Wiki 有对应段落
  - **⚠ 缺失**：需要补录
  - **? 待确认**：有相似但不完全匹配，需人工决策

**输出**：缺失清单（分三类）
1. **数据库缺失**：如"缺少机型 SE-8.0-200 的功率曲线" → 下载 Excel 模板补录
2. **Wiki 缺失**：如"客户定制/华能/甘肃风电 无项目介绍段落" → 新建 Wiki 节点或上传文档
3. **项目定制缺失**：如"本项目的发电量担保函尚未生成" → 上传/计算后上传

#### 4.4.2 备料（S5，人工补录）

**UI 能力**：
- 缺失清单按优先级排序，点击直接跳到对应补录界面
- Excel 补录：下载预填模板 → 填完上传 → 自动校验入库
- Wiki 补录：直接在 Web 编辑器里写 / 上传现有文档
- 支持"跳过"：显式标记"本项目无此素材，填充时用占位说明或忽略"
- 所有缺失项处理完成（补齐或显式跳过）后才能进入填充阶段

**好处**：
- 避免填充时"用 LLM 凑"的幻觉风险
- 人工补录可一次性做完，避免返工
- 补录的数据沉淀到素材库，下次项目直接可用

#### 4.4.3 审核备料（S6，人工强制 — 仅审核新增内容）

**为什么要独立审核**：备料阶段新录入的数据直接进数据库、新建的 Wiki 节点直接可用于填充，若有错，错误会被放大到整份标书。必须有一道审核关卡。

**审核范围**（严格限定为新增，避免负担）：
- S5 新导入的 Excel 行（仅新行，不含已有行）
- S5 新建/修改的 Wiki 节点
- S5 新填的附表数据
- S5 显式标记"跳过"的缺口项（审核跳过理由是否合理）

**审核 UI**：
- 按"新增项"分类列出，每项附带"来源/填写人/内容预览"
- 审核人操作：✓ 通过 / ✗ 驳回（回到 S5 重填）/ ✎ 修改后通过
- 驳回项高亮原因，便于填写人修正
- 全部通过后解锁 S7 填充

**审核人角色**：
- 可与备料填写人不同（建议"双人原则"）
- 项目负责人或资深标书撰写人承担

**对应 KPI**：新增内容错误率在审核后 ≤ 1%

---

### 4.5 章节填充模块（S7）

**输入**：目录节点（含要点提示）+ 备齐的两库
**处理**：

- 每个章节独立任务，章节间可并行
- 系统按章节要求自动去两库找内容：
  - **数据库**（结构化）：精确查询后填入（项目业绩、机型参数、人员/证书）
  - **Wiki**（非结构化）：Agent 导航找最合适的段落 → 改写融合
- 每段产出必须携带：**证据链**（引用了哪些素材） + **覆盖评分点**（本段回应了哪些评分条款）

**输出**：章节初稿

**关键能力**：
- 章节级并行，长标书 30 分钟内完成初稿
- 失败章节可独立重跑
- 支持用户指定"本节必须引用的素材"

---

### 4.6 附表填充模块（专项，对应 ≥95% 准确率）

**输入**：业主附表模板（原样保留）+ 项目/机型/人员数据
**处理**：

- 附表**结构不改**、**表头不动**、**仅填数据**
- 无法填充的单元格：**高亮标记 + 原因说明**，不静默跳过
- 保持原表可编辑状态

**输出**：填充后的附表

**关键能力**：
- 支持横版/竖版附表
- 单元格级证据链（数据来自哪条记录）
- 必填项校验（业主要求的必填列全部填上才算合格）

**对应 KPI**：附表填充准确率 ≥ 95%

---

### 4.7 评分点覆盖校验模块（反向追溯）

这是对应"评分细则全部条目必须在投标文件中可追溯"硬需求的独立模块。

**输入**：全部评分细则（来自 S1） + 初稿的段落与其声明覆盖的评分项
**处理**：
- 反向统计每个评分项的覆盖情况：**完整覆盖 / 弱覆盖 / 未覆盖**
- 未覆盖/弱覆盖项：系统建议"最相关的现有段落"或"建议新增章节"
- 生成**覆盖热力图**（绿/黄/红）

**输出**：覆盖率报告 + 热力图
**人工决策**：红项必须解决（补内容/显式忽略+理由） 才允许进入下一阶段

---

### 4.8 项目信息全局一致校验

针对"项目信息全局统一"硬需求。

**校验内容**：项目名称、业主单位、机型、容量、保证率、交货周期、质保期 等关键字段是否全文一致。

**实现要点**：
- 关键字段只从**统一的项目信息表**取值
- 禁止正文硬写数字（强制用占位符 `{{project.name}}`）
- 校验阶段全文扫描，发现不一致告警

---

### 4.9 格式统一模块（5 级标题 / 表格 / 图片 / 页眉页脚）

按需求文档规范硬性落地：

**页面整体**：
- A4 纵向
- 页边距：上/下 2.54cm，左/右 3.18cm
- 装订线：左 0cm
- 页码：底部居中；封皮无页码；目录页罗马数字
- 目录：自动生成、3 级、带页码（右对齐）、超链接、可更新

**标题五级规范**：

| 级别 | 字体（中文/西文） | 字号 | 对齐 | 段落 |
|---|---|---|---|---|
| 1 级 | 宋体 / Times New Roman 加粗 | 小三 | 居中 | 段前后 6 磅 / 1.75 倍行距 / 段前缩进 1.75cm |
| 2 级 | 宋体 / Times New Roman 加粗 | 四号 | 左对齐 | 1.75 倍行距 / 无缩进 |
| 3 级 | 宋体 / Times New Roman 加粗 | 小四 | 左对齐 | 段前后 6 磅 / 1.75 倍 / 段前缩进 0.25cm |

### 4.10 人机共创模块（S9，AI 辅助实时编辑）

这是生成之后最重要的工作阶段：客户期望的不是"AI 生成完就结束"，而是**AI 继续当助手，人来主导改稿**。

#### 4.10.1 基础编辑体验

- 类 Word 富文本（所见即所得），最大还原 Word 操作手感
- **实时渲染**：输入即显示最终效果，所见即导出
- 快捷键、样式下拉、表格/图片插入与 Word 一致

#### 4.10.2 AI 辅助能力（实时 / 准实时触发）

| 触发动作 | AI 自动行为 | 触发时机 |
|---|---|---|
| 改动标题文字 | 检测样式是否为 Heading N；不是则自动套正确级别样式 | 编辑 debounce 2 秒 |
| **新增章节** | 自动重算多级编号（1.1/1.2/2.1...） + 刷新目录页 + 刷新页码 | 实时 |
| **新增章节后选"AI 填充"** | 触发 fill_section skill → 从两库找素材 → 生成正文草稿供审 | 显式触发 |
| 删除章节 | 自动刷新编号、目录、覆盖热力图 | 实时 |
| 粘贴外部内容 | 自动清理多余 `*`/`#`/空行 → 套 Normal 样式 | 粘贴时 |
| 改动正文段落 | 刷新覆盖热力图（原覆盖的评分项可能失效） | 编辑 debounce |
| 改动项目信息字段 | 全局一致性扫描 + 告警 | 保存时 |
| 字体/字号混乱 | 一键"刷格式"按钮，应用标准样式 | 显式触发 |
| 用户选中段落 → "AI 改写" | 按指定风格改写（更正式/更简洁/加强表述） | 显式触发 |

#### 4.10.3 联动能力

- **正文 ↔ 目录树**：改正文，左侧目录 3 秒内刷新；点目录节点跳到正文
- **正文 ↔ 覆盖热力图**：改段落，热力图实时刷新；点评分项跳到覆盖段落
- **段落 ↔ 元信息面板**：点段落显示证据链 / 覆盖评分项 / 人工是否已确认
- **锁定机制**：人工"锁定"某段后，后续 AI 不再覆盖该段

#### 4.10.4 协同边界（防止 AI 与人打架）

- AI 只做**格式/编号/目录/样式**等确定性动作 → 实时触发
- AI 做**内容改写/新增**等语义动作 → 必须用户显式触发
- 用户正在输入时，AI 不动（输入停止 debounce 后再检查）
- 所有 AI 动作都写审计日志，可回滚

### 4.12 标书类型支持（技术标 / 商务标）

系统支持两种标书类型，**业务流水线完全一致**，差异仅在素材库引用范围：

| 项 | 技术标 | 商务标 |
|---|---|---|
| 重点内容 | 技术方案、机型参数、专题方案、功率曲线 | 报价、商务条款、付款方式、资质证明、承诺函 |
| 主要素材 | Wiki 标准模板层的"技术方案/专题方案/机型技术" + 数据库机型参数 | Wiki 标准模板层的"商务条款模板" + 数据库财务/资质数据 |
| 附表重点 | 技术参数表、性能指标表 | 报价清单、商务承诺表 |
| 格式规范 | 同一套（本文档第 4.9 节） | 同一套 |

**实现方式**：
- 新建项目时选择标书类型（技术/商务/综合）
- Wiki 节点可标注 "适用类型" 标签（技术标/商务标/通用）
- 目录生成 + 填充时，只从适用类型的 Wiki 分支取素材
- 技术标通常更复杂，但系统无需为两种标书开发不同流程

**综合标**：同一项目可同时生成技术标和商务标两套文档，项目信息共享，互不干扰。

## 八、用户角色与典型场景

### 场景 1：新建项目 → 完稿导出（标书撰写人）

1. 登录 → 新建投标项目，填写项目名、业主、机型，**选标书类型（技术标/商务标/综合）**
2. 上传招标文件（可能是 docx + PDF 附件）
3. 等待解析完成（几分钟），查看解析报告，抽检
4. **审核系统生成的目录**，拖拽调整，确认
5. **查看素材缺口清单**：系统提示"缺 3 项数据、2 个 Wiki 段落"
6. 下载 Excel 模板补录数据 → 上传；在 Wiki 补 2 个段落（或显式跳过）
7. **提交项目负责人审核备料内容**（仅审核新增的 3 项 + 2 段） → 通过
8. 点击"开始填充"，等待章节并行完成（10–30 分钟）
9. 查看**覆盖热力图**，解决红项（补内容或显式忽略）
10. 在 Web 编辑器中**人机共创**改稿：
    - 新增一个"抗台风专题"章节 → 右键"AI 填充本节" → 审阅
    - 改某段文字 → 系统自动刷格式、更新目录、刷新热力图
    - 发现字体乱了 → 点"刷格式"一键应用标准样式
11. 导出 .docx，用 Word 最终检查
12. 导出 PDF，提交

### 场景 2：素材库维护（管理员/资料员）

- 季度更新公司业绩：导入 Excel → 自动入结构化库
- 新签客户：在客户定制树下新建节点 → 上传协议/历史项目
- 项目完成：把本项目的报告归档到项目定制树，标为"可复用"

### 场景 3：历史项目复用（项目负责人）

- 新项目与历史某项目高度相似 → 基于历史项目"另存为新项目"
- 系统保留结构与素材引用，只需替换招标文件与项目信息
- 大幅缩短新项目初稿时间

### 场景 4：审阅与批注（审阅人）

- 只读打开项目 → 查看目录 / 覆盖热力图 / 正文
- 在编辑器中添加批注（不修改正文）
- 批注汇总给标书撰写人处理

### 场景 5：审计回溯（管理员）

- 某次投标失败 → 回查操作记录：谁在何时做了什么修改
- 审计页按时间/人/项目筛选，导出报告

## 十、待确认事项

1. **投标文件通用固定顺序**（需求文档"待定"部分）—— 需要业务方提供一版通用目录模板
2. **客户专属结构**除华能外还有哪些需要开箱即用（华电/大唐/国能/...）
3. **技术标 vs 商务标** —— 首期两种都上，还是先上技术标验证闭环再做商务标
4. **风机机型清单** —— 首期要覆盖哪些机型的参数（用于数据库初始化）
5. **Excel 模板** —— 数据库各表的 Excel 导入模板由业务方确认字段清单
6. **历史标书数据源** —— 现有素材是文件夹形式还是已有系统可对接
7. **用户角色划分**是否沿用上述 4 类 / 有无更细粒度需求
8. **与现有 OA / ERP / 客户系统是否要集成**（项目信息、客户信息是否从外部系统同步）
9. **交付文档"客户端"** —— 是否确实需要 Electron 桌面端，或 Web 端就够
