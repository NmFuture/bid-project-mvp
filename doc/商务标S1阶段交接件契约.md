# 商务标 S1 阶段交接件契约

版本日期：2026-06-05

本文定义商务标 S1 阶段的交接件边界、文件布局和消费规则。目标是让 S1 解析结果、商务模板提取结果、承诺函与附件产物在后续 S2、S3、AI 填写和 S4 阶段中可追踪、可复用、可重跑。

## 1. 契约目标

S1 阶段负责把招标文件转化为稳定的商务工作区。后续阶段不应重复猜测文件位置、解析状态或模板边界，而应通过统一的 `stageArtifacts.s1` 读取已发布的阶段交接件。

交接件必须满足以下目标：

- 解析结果可被后续阶段直接消费。
- 模板切片、承诺函、附录目录和结构化 JSON 保持同一版本。
- 重跑 S1 时能生成新版本，不破坏已发布版本的引用。
- 前端和后端都能通过同一状态字段判断当前 S1 是否可继续流转。

## 2. 生命周期

S1 交接件按状态流转：

| 状态 | 含义 | 后续阶段处理 |
| --- | --- | --- |
| `running` | 正在解析或提取模板，产物可能不完整。 | 不允许 S2、S3、AI 填写或 S4 消费。 |
| `readyForReview` | 已生成候选产物，等待人工审阅确认。 | 允许前端展示和修订，不作为正式交接件。 |
| `published` | 产物已确认并发布为正式版本。 | 后续阶段只能消费该状态下的交接件。 |
| `abandoned` | 当前版本已废弃。 | 不允许继续消费，只保留审计追踪。 |

后端接口应避免把 `readyForReview` 当作最终结果。只有 `published` 状态才表示 S1 已完成阶段交接。

## 3. 存储位置

容器内默认路径如下：

| 环境变量 | 默认路径 | 用途 |
| --- | --- | --- |
| `UPLOADS_DIR` | `/data/uploads` | 原始上传文件。 |
| `PARSED_DIR` | `/data/parsed` | 解析结果、阶段发布快照和兼容索引。 |
| `DOCUMENTS_DIR` | `/data/documents` | 业务工作区、模板切片、承诺函和可编辑文档。 |

S1 工作区根目录：

```text
${DOCUMENTS_DIR}/{project_id}/business-workspace/
```

推荐目录结构：

```text
${DOCUMENTS_DIR}/{project_id}/business-workspace/
  parse/
    combined.txt
    s1_structured_result.json
    s1_parse_manifest.json
    manifest.json
    parse-result.workspace.json
    business_template_extraction/
      business_template_extraction.json
  appendices/
    APPX-*.docx
  commitment-letters/
    CL-*.docx
```

发布后的兼容索引可同步写入：

```text
${PARSED_DIR}/{project_id}/stage-artifacts.json
${PARSED_DIR}/{project_id}/s1/latest.json
```

## 5. 核心产物

S1 发布版本至少应包含以下产物：

| 产物 | 文件 | 必填 | 说明 |
| --- | --- | --- | --- |
| 合并文本 | `combined.txt` | 是 | 招标文件抽取后的全文文本。 |
| 结构化结果 | `s1_structured_result.json` | 是 | 商务 S1 主结构化结果，包含 `items` 和 `structured`。 |
| 解析清单 | `s1_parse_manifest.json` | 是 | skill 执行输入、输出路径、源文件和运行上下文。 |
| 工作区解析结果 | `parse-result.workspace.json` | 是 | 前端工作区使用的兼容解析结果。 |
| 模板提取结果 | `business_template_extraction.json` | 是 | 模板候选、边界、正式模板和审阅信息。 |
| 附件切片 | `appendices/APPX-*.docx` | 按需 | 可直接进入后续填写流程的商务模板。 |
| 承诺函 | `commitment-letters/CL-*.docx` | 按需 | 从 S1 识别出的承诺书、声明函、保证函等。 |

当 `appendices` 或 `commitmentLetters` 为空时，必须在结构化结果中保留空数组，不能省略字段。

## 6. 后续阶段消费方式

S2、S3、AI 填写和 S4 阶段应按以下顺序读取 S1：

1. 读取项目级 `stageArtifacts.s1`。
2. 校验 `status == "published"`。
3. 校验 `schemaVersion` 是否在当前代码支持范围内。
4. 通过 `paths` 获取工作区文件，不自行拼接历史路径。
5. 使用 `version`、`publishedAt` 和源文件摘要记录消费来源。

后续阶段不得直接消费 `running` 或 `readyForReview` 的产物。确需预览时，应明确标记为预览数据，不能写入正式成果。

## 7. 当前代码兼容读法

为了兼容已有项目数据，读取方可以按以下顺序查找：

1. `stageArtifacts.s1.paths.structuredResultPath`
2. `${DOCUMENTS_DIR}/{project_id}/business-workspace/parse/s1_structured_result.json`
3. `${PARSED_DIR}/{project_id}/s1/latest.json`
4. 历史 `parse-result.workspace.json`

兼容读取只解决旧项目迁移问题。新发布的 S1 必须写入 `stageArtifacts.s1`，并把 `status` 标为 `published` 后才允许后续阶段正式消费。

## 8. 重跑和版本规则

S1 每次重新解析都应创建新的版本号：

- `version` 从 1 开始递增。
- 同一项目只允许一个 `published` 最新版本。
- 新版本发布前，旧版本仍保持可读。
- 新版本发布成功后，`latest.json` 指向最新发布版本。
- 人工审阅未通过的版本可以标记为 `abandoned`。

重跑时不得覆盖已发布版本中的原始文件。需要节省空间时，可通过后续清理任务处理废弃版本。

## 9. 接口和代码边界

后端解析服务负责：

- 生成 S1 工作区。
- 执行商务解析 skill。
- 执行业务模板提取 skill。
- 组装 `stageArtifacts.s1`。
- 返回前端可审阅的结构化数据和路径。

前端工作区负责：

- 展示解析字段、模板、附件和承诺函。
- 标记审阅状态。
- 触发发布或重跑。
- 明确区分预览结果和已发布结果。

后续阶段负责：

- 只读取 `published` 的 S1 交接件。
- 保留消费版本信息。
- 不修改 S1 原始发布文件。

## 10. 验收清单

发布 S1 前至少确认：

- `s1_structured_result.json` 存在且包含 `items` 和 `structured`。
- `business_template_extraction.json` 存在，模板边界可追踪。
- `appendices`、`commitmentLetters`、`warnings` 等字段即使为空也有明确值。
- `stageArtifacts.s1.status` 为 `published`。
- `stageArtifacts.s1.version`、`publishedAt`、`schemaVersion` 已写入。
- 所有 `paths` 指向容器内实际可读文件或目录。
- 前端审阅页能展示同一版本的解析结果和模板结果。
- 后续阶段只通过交接件索引读取 S1。
