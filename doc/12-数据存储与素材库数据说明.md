# 数据存储与素材库数据说明

本文说明当前 MVP 中项目数据、docx 等文件、素材库数据的实际存储方式，以及前端获取素材库信息的数据链路。本文以当前代码实现为准，不等同于后续正式版设计。

## 一、总体结论

当前系统不是把 `docx`、`pdf`、图片、Excel 等文件二进制直接存入数据库。

实际采用的是“数据库存元数据和状态，文件系统或对象存储存文件本体”的方式：

| 数据类型 | 当前存储位置 | 说明 |
| --- | --- | --- |
| 项目状态、阶段状态、解析结果摘要 | PostgreSQL | 存在 `projects.payload` JSONB 中 |
| 招标文件、模板上传原件 | 本地文件目录 `uploads` | PostgreSQL 只保存文件路径、名称、大小等记录 |
| 解析后的文本 | 本地文件目录 `parsed` | PostgreSQL 保存解析产物路径和摘要 |
| 初稿、终稿、OnlyOffice 回写文档 | 本地文件目录 `documents`，并尝试同步 MinIO | PostgreSQL 保存文档状态、文件名、版本等 |
| 原始素材库文件 | MinIO | PostgreSQL 保存 `minio_key`、目录、文件名、大小等 |
| 结构化素材 | PostgreSQL | `structured_rows.row_data` 使用 JSONB |
| Wiki 节点正文 | PostgreSQL | `wiki_docs.markdown_content` 保存 Markdown |
| Wiki 附件 | MinIO | PostgreSQL 保存附件元数据和 `minio_key` |

因此，回答“docx 等数据是否存在后端数据库里”：**docx 文件本体没有直接存数据库；数据库只存状态、路径、对象 key 和部分文本内容。**

## 二、项目主链路数据组织

项目主链路由 `AppStore` 管理，当前使用 PostgreSQL 持久化。

核心表：

```sql
CREATE TABLE IF NOT EXISTS projects (
    id VARCHAR(50) PRIMARY KEY,
    payload JSONB NOT NULL,
    updated_at TEXT NOT NULL
)
```

代码位置：

- `code/sewpg-bid-backend/app/services/store.py`

`payload` 是一个较大的 JSON，对应一个项目的完整状态，主要包含：

| 字段 | 用途 |
| --- | --- |
| `files` / `templateFiles` | 前端展示用文件名摘要 |
| `fileRecords` / `templateFileRecords` | 上传文件记录，包含本地路径 |
| `parse_result` | S1 解析结果摘要 |
| `parse_storage` | 解析文本、manifest 等本地路径 |
| `directory_state` | S2 目录生成状态 |
| `outline_state` | S3 目录树和审核状态 |
| `gap_state` | S4/S5 缺口识别、补料提交、审核状态 |
| `review_document_state` | S6 审核文档状态 |
| `fill_state` | S7 初稿生成状态 |
| `document_state` | S9/S10 文档协作和导出状态 |

### 2.1 招标文件上传

招标文件通过接口上传：

```http
POST /api/projects/{project_id}/parse-results/upload-and-run
```

当前实现逻辑：

1. 后端接收 `tenderFiles` 和 `templateFiles`。
2. 文件写入本地目录：

```text
{UPLOADS_DIR}/{project_id}/tender/
{UPLOADS_DIR}/{project_id}/template/
```

3. PostgreSQL `projects.payload` 中记录文件名、大小、content type、本地路径。
4. 随后触发解析，解析文本写入 `parsed` 目录。

相关代码：

- `code/sewpg-bid-backend/app/api/routes/parse.py`
- `code/sewpg-bid-backend/app/services/parsing.py`

### 2.2 解析结果

解析结果不把完整大文本写入项目状态 JSON。

当前处理方式：

| 数据 | 存储位置 |
| --- | --- |
| 每个文件解析文本 | `{PARSED_DIR}/{project_id}/{file_id}.txt` |
| 合并文本 | `{PARSED_DIR}/{project_id}/combined.txt` |
| 解析 manifest | `{PARSED_DIR}/{project_id}/manifest.json` |
| 解析摘要、预览、路径 | PostgreSQL `projects.payload` |

这样能避免项目状态 JSON 中塞入过大的全文内容，但也意味着文件目录和 PostgreSQL 记录必须一起备份，否则解析产物会丢失。

### 2.3 初稿、终稿和 OnlyOffice 文档

项目生成稿由 `onlyoffice_documents.py` 管理。

默认路径：

```text
{DOCUMENTS_DIR}/{project_id}.docx
```

MinIO 对象 key：

```text
documents/{project_id}/draft.docx
```

当前逻辑：

1. 如果本地文档不存在，优先尝试从 MinIO 下载。
2. 如果 MinIO 没有，则用 `document_state.fallback.content` 生成一个 docx。
3. OnlyOffice 回调保存时，后端从 OnlyOffice 提供的 URL 下载新 docx。
4. 下载后的 docx 覆盖本地文件，并尝试同步到 MinIO。
5. PostgreSQL `projects.payload` 中更新文档版本号、保存时间、文件名等状态。

相关代码：

- `code/sewpg-bid-backend/app/services/onlyoffice_documents.py`
- `code/sewpg-bid-backend/app/api/routes/document.py`

## 三、素材库数据组织

素材库是另一套数据链路，目标是 `PostgreSQL + MinIO`。

Docker Compose 中：

- PostgreSQL 使用 `pgvector/pgvector:pg16`
- MinIO 用于对象存储
- 初始化 SQL 在 `code/initdb/01-init.sql`

相关代码：

- `code/sewpg-bid-backend/app/models/materials.py`
- `code/sewpg-bid-backend/app/services/material_store.py`
- `code/sewpg-bid-backend/app/api/routes/materials.py`

### 3.1 原始材料库

原始材料库用于保存上传的原始资料文件，例如 docx、pdf、Excel、图片、压缩包等。

核心表：

| 表 | 用途 |
| --- | --- |
| `raw_folders` | 原始材料目录树 |
| `raw_files` | 文件元数据 |
| `raw_file_versions` | 文件历史版本记录 |

目录层级按业务分为：

```text
标准模板
客户定制/{客户名称}/通用材料
项目定制/{项目ID}/{标书类型}
```

`raw_files` 中保存：

| 字段 | 含义 |
| --- | --- |
| `folder_id` | 所属目录 |
| `name` | 文件名 |
| `size_bytes` | 文件大小 |
| `mime_type` | MIME 类型 |
| `minio_bucket` | MinIO bucket |
| `minio_key` | MinIO 对象 key |
| `version` | 当前版本号 |
| `ext_fields` | 扩展字段，例如 `bidType`、`projectId`、`customerName` |

文件本体写入 MinIO，key 形如：

```text
raw/{folder_path}/{file_name}
```

### 3.2 结构化素材库

结构化素材库用于性能参数、项目业绩、保证值等表格型数据。

核心表：

| 表 | 用途 |
| --- | --- |
| `structured_tables` | 表定义 |
| `structured_rows` | 表数据行 |
| `structured_imports` | 导入记录，当前代码未完整落地 |

`structured_rows.row_data` 使用 JSONB 存每行数据。

示例：

```json
{
  "项目名称": "某风电项目",
  "业主": "某集团",
  "机型": "XXX",
  "容量(MW)": 100,
  "年份": 2025
}
```

当前需要注意：Excel 导入预览和确认仍偏 MVP/stub，尚未形成完整的真实 Excel 解析、校验、导入、错误报告链路。

### 3.3 Wiki 素材库

Wiki 素材库用于段落级、章节级、方案类可复用文本。

核心表：

| 表 | 用途 |
| --- | --- |
| `wiki_nodes` | Wiki 树节点 |
| `wiki_docs` | 节点正文、摘要、标签 |
| `wiki_attachments` | Wiki 附件元数据 |
| `wiki_paragraphs` | 段落向量，表结构已设计 |

`wiki_docs.markdown_content` 保存 Markdown 正文。

Wiki 附件本体写入 MinIO，PostgreSQL 保存附件文件名、大小、MIME、bucket、key。

## 四、前端如何获取素材库信息

前端统一通过 `src/api/index.js` 中的 `materialsAPI` 访问素材库。

代码位置：

- `code/sewpg-bid-frontend/src/api/index.js`

### 4.1 原始材料库页面

页面：

- `code/sewpg-bid-frontend/src/pages/MaterialDB.jsx`

主要调用：

```http
GET /api/materials/raw/tree
GET /api/materials/raw/files
POST /api/materials/raw/upload
POST /api/materials/raw/folders
DELETE /api/materials/raw/folders
PATCH /api/materials/raw/{file_id}
POST /api/materials/raw/move
DELETE /api/materials/raw/{file_id}
GET /api/materials/raw/{file_id}/download
```

加载流程：

1. 页面初始化调用 `materialsAPI.raw.tree()` 获取目录树。
2. 前端根据选中目录确定 `folderPath`。
3. 调用 `materialsAPI.raw.files({ folderPath, keyword, bidType, customerName, projectId, page, pageSize })` 获取文件列表。
4. 上传文件时使用 `FormData` 调用 `/api/materials/raw/upload`。
5. 上传成功后刷新目录树和文件列表。

### 4.2 结构化素材选择

组件：

- `code/sewpg-bid-frontend/src/components/modals/MaterialSelectModal.jsx`

主要调用：

```http
GET /api/materials/structured
```

前端拿到 `items` 后在弹窗内按名称、类型做本地筛选。

### 4.3 Wiki 素材页面

页面：

- `code/sewpg-bid-frontend/src/pages/MaterialWiki.jsx`

主要调用：

```http
GET /api/materials/wiki
GET /api/materials/wiki?nodeId=WIKI-0001
POST /api/materials/wiki
PUT /api/materials/wiki/{node_id}
POST /api/materials/wiki/{node_id}/move
POST /api/materials/wiki/{node_id}/attachments
POST /api/materials/wiki/{node_id}/refresh-summary
```

加载流程：

1. 页面初始化调用 `materialsAPI.wiki.list()` 获取 Wiki 树。
2. 用户选中节点后调用 `materialsAPI.wiki.list({ nodeId })` 获取节点正文、标签、适用类型、附件。
3. 保存节点时调用 `PUT /api/materials/wiki/{node_id}`。
4. 上传附件时使用 `FormData` 调用 `/api/materials/wiki/{node_id}/attachments`。

## 五、当前不够严谨的地方

### 5.1 S5 补料没有真正入素材库

这是当前最重要的问题。

S5 页面上传补料时，前端只把文件名、大小、类型组成 JSON 发给后端，并没有上传文件二进制。

后端 `submit_gap_material` 也只是生成 receipt，写入 PostgreSQL 项目 JSON：

```text
receiptId
projectId
missingId
fileId
fileName
storedPath
traceId
auditId
```

这意味着：

- 补料文件本体没有进入 MinIO。
- `raw_files` 没有新增记录。
- 后续无法从素材库真实下载该补料文件。
- “补录的数据沉淀到素材库，下次项目直接复用”这件事当前没有完整闭环。

### 5.2 MinIO 与数据库提交不是原子事务

原始材料上传流程中，文件先写入 MinIO，再写 PostgreSQL 元数据。

如果 MinIO 上传成功但数据库提交失败，可能留下孤儿对象。

如果数据库提交成功但后续文件操作失败，也可能出现元数据和对象存储不一致。

### 5.3 原始素材版本管理存在覆盖风险

当前同名文件覆盖或版本上传时，MinIO key 仍按目录和文件名生成：

```text
raw/{folder_path}/{file_name}
```

如果新版本继续使用相同 key，旧版本对象可能被覆盖，导致 `raw_file_versions` 里虽然有历史版本记录，但无法可靠取回旧文件内容。

更严谨的方式是每个版本使用不可变 key，例如：

```text
raw/{folder_path}/{file_id}/v{version}/{file_name}
```

### 5.4 上传校验后端不够完整

项目招标文件上传有后端扩展名白名单。

但素材库原始材料上传更多依赖前端白名单，后端主要做大小限制和文件名清洗。正式环境中应在后端补齐：

- 扩展名白名单
- MIME 类型校验
- 文件头校验
- 压缩包安全检查
- 文件名长度和路径约束

### 5.5 PostgreSQL 表初始化依赖部署脚本

应用启动时会确保 MinIO bucket 存在，但不会自动创建核心 PostgreSQL 表。

核心表依赖 `docker-compose` 首次启动时执行：

```text
code/initdb/01-init.sql
```

如果数据库已经初始化过，后续修改 SQL 不会自动迁移。正式化应引入 Alembic 或等价迁移机制。

### 5.6 结构化 Excel 导入仍是 MVP 形态

当前结构化导入接口能返回预览和确认结果，但并未完整实现真实 Excel 解析、字段映射、数据校验、错误报告、导入快照和回滚。

正式化后应补齐：

- Excel 文件真实上传到 MinIO
- 解析工作簿和 sheet
- 字段映射校验
- 必填字段校验
- 类型转换和错误报告
- 成功行写入 `structured_rows`
- 导入记录写入 `structured_imports`

## 六、建议的正式化改造优先级

### P0：补齐 S5 补料真实入库

目标：S5 上传补料后，文件真实进入原始材料库。

建议改造：

1. 前端 S5 补料上传改为 `FormData`，提交文件二进制。
2. 后端 S5 接口接收 `UploadFile`。
3. 后端调用 `material_store.raw_upload()` 写入 MinIO 和 `raw_files`。
4. receipt 中保存真实 `RAW-xxxx` 文件 ID。
5. S6 审核、S7 填充引用真实素材 ID，而不是 mock fileId。

### P1：统一项目文件存储策略

当前项目主链路已经切到 `PostgreSQL + 本地 uploads/documents/parsed`，素材库使用 `PostgreSQL + MinIO`。

可以保留这种混合模式，但需要明确：

- 项目上传原件是否也同步 MinIO。
- OnlyOffice 文档以本地为主还是 MinIO 为主。
- 备份恢复时 PostgreSQL、本地目录、MinIO 的一致性要求。

### P1：补齐对象存储一致性处理

建议增加：

- 上传失败清理 MinIO 对象
- 数据库提交失败清理 MinIO 对象
- 定期扫描孤儿对象
- MinIO key 使用 UUID 或 file_id/version，不直接依赖可变文件名

### P1：补齐数据库约束和迁移

建议增加：

```sql
UNIQUE(raw_folders.path)
UNIQUE(raw_files.folder_id, raw_files.name)
```

同时引入数据库迁移工具，避免依赖一次性 init SQL。

### P2：结构化素材导入真实落地

建议实现完整 Excel 导入链路，并把导入文件、导入记录、错误报告、成功数据建立可追溯关系。

## 七、当前可对外说明口径

如果需要向项目成员或甲方解释，可以使用下面的口径：

> 当前 MVP 不把 Word、PDF、Excel 等文件直接存数据库。系统采用“数据库保存元数据和业务状态，文件系统或 MinIO 保存文件本体”的方式。项目主链路当前使用 PostgreSQL 保存项目阶段状态和文件路径，本地目录保存上传文件、解析文本和生成文档；素材库使用 PostgreSQL 保存目录、标签、结构化数据和 Wiki 正文，MinIO 保存原始文件和附件。当前素材库管理页面已经走真实接口，但 S5 补料上传仍是 MVP 形态，只记录补料回执，尚未把补料文件真实沉淀到原始素材库。正式化前需要优先补齐 S5 文件入库、版本管理、对象存储一致性和数据库迁移机制。
