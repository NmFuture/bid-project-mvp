# 数据存储与素材库数据说明

本文说明当前 MVP 中项目数据、docx 等文件、素材库数据的实际存储方式，以及前端获取素材库信息的数据链路。本文以当前代码实现为准，不等同于后续正式版设计。

> 2026-05-03 更新：技术标主流程已收敛为 `S0-S6`。`S0` 是解析/审核模块；项目阶段条只展示 `S1-S6`。内部字段仍保留 `gap_state`、`review_document_state`、`fill_state` 等历史命名，历史目录名仍保留 `s2_toc_workdir`、`s4_gap_workdir`、`s7_assembly_workdir`，但用户语义分别对应当前 `S1 模板与目录`、`S3 缺口处理`、`S4 生成标书`。缺口处理中的人工上传、选择已有素材和 AI 填写产物已进入项目级真实文件状态；是否进一步沉淀为全局可复用素材库仍需后续设计。

## 一、总体结论

当前系统不是把 `docx`、`pdf`、图片、Excel 等文件二进制直接存入数据库。

实际采用的是“数据库存元数据和状态，文件系统或对象存储存文件本体”的方式：

| 数据类型 | 当前存储位置 | 说明 |
| --- | --- | --- |
| 项目状态、阶段状态、解析结果摘要 | PostgreSQL | 存在 `projects.payload` JSONB 中 |
| 招标文件、模板上传原件 | 本地文件目录 `uploads` | PostgreSQL 只保存文件路径、名称、大小等记录 |
| 设置侧系统默认模板 | PostgreSQL + MinIO | PostgreSQL 保存启用状态和对象 key；MinIO 保存模板文件本体 |
| S0 临时解析缓存 | 本地文件目录 `parsed/{project_id}` | 保存解析运行中的初始文本和附表草稿；确认参与投标后可清理 |
| S0 解析工作区 | 本地文件目录 `documents/{project_id}/technical-workspace/parse` | 保存进入技术标流程后的解析文本、结构化结果和 manifest |
| S1 目录生成工作目录 | 本地文件目录 `documents/{project_id}/technical-workspace/s2_toc_workdir` | `s2_toc_workdir` 是历史内部名；保存最新成功的 `s2_input.json`、`toc.json`、`toc_evidence.json` 和 agent review 输入；旧成功目录归档到 `s2_toc_workdir.runs/` |
| S3 缺口处理工作目录 | 本地文件目录 `documents/{project_id}/technical-workspace/s4_gap_workdir` | `s4_gap_workdir` 是历史内部名；保存 `gap_plan.json`、人工补料、选择素材副本和 AI 填写产物 |
| 正文拼装稿、终稿、OnlyOffice 回写文档 | 本地文件目录 `documents`，并尝试同步 MinIO | PostgreSQL 保存文档状态、文件名、版本等 |
| S4 拼装工作目录 | 本地文件目录 `documents/{project_id}/technical-workspace/s7_assembly_workdir` | `s7_assembly_workdir` 是历史内部名；保存 S1 目录 JSON 副本、Wiki 副本、素材库导出、manifest、拼装计划和报告 |
| 原始素材库文件 | MinIO | PostgreSQL 保存 `minio_key`、目录、文件名、大小等 |
| 结构化素材 | PostgreSQL | `structured_rows.row_data` 使用 JSONB |
| Wiki 节点正文 | PostgreSQL | `wiki_docs.markdown_content` 保存 Markdown |
| Wiki 附件 | MinIO | PostgreSQL 保存附件元数据和 `minio_key` |
| Wiki 自动生成工作区 | 本地文件目录 `parsed/_wiki_build` | 保存 Wiki manifest 和完整 `wiki_blueprint.json`，由 `fastapi` 直接执行技术标 Wiki Skill runner |

因此，回答“docx 等数据是否存在后端数据库里”：**docx 文件本体没有直接存数据库；数据库只存状态、路径、对象 key 和部分文本内容。**

## 二、项目主链路数据组织

项目主链路由 `AppStore` 管理，当前使用 PostgreSQL 持久化。

核心表：

```sql
CREATE TABLE IF NOT EXISTS projects (
    id VARCHAR(50) PRIMARY KEY,
    payload JSONB NOT NULL,
    updated_at TEXT NOT NULL
)
```

代码位置：

- `code/sewpg-bid-backend/app/services/store.py`

`payload` 是一个较大的 JSON，对应一个项目的完整状态，主要包含：

| 字段 | 用途 |
| --- | --- |
| `files` / `templateFiles` | 前端展示用文件名摘要 |
| `fileRecords` / `templateFileRecords` | 上传文件记录，包含本地路径 |
| `parse_result` | S0 解析结果摘要 |
| `parse_storage` | 解析文本、manifest 等本地路径 |
| `directory_state` | S1 目录生成状态 |
| `outline_state` | S2 目录树和审核状态 |
| `gap_state` | S3 缺口识别、处理计划、补料提交、AI 填写、完整性校验和确认状态 |
| `review_document_state` | 缺口处理确认预览文档状态 |
| `fill_state` | S4 标书生成状态、覆盖诊断结果和拼装报告路径 |
| `document_state` | S5/S6 共创和导出状态 |

### 2.1 招标文件上传

招标文件通过接口上传：

```http
POST /api/projects/{project_id}/parse-results/upload-and-run
```

当前实现逻辑：

1. 后端接收 `tenderFiles` 和 `templateFiles`。
2. 文件写入本地目录：

```text
{UPLOADS_DIR}/{project_id}/tender/
{UPLOADS_DIR}/{project_id}/template/
```

3. PostgreSQL `projects.payload` 中记录文件名、大小、content type、本地路径。
4. 随后触发解析，解析文本写入 `parsed` 目录。

相关代码：

- `code/sewpg-bid-backend/app/api/routes/parse.py`
- `code/sewpg-bid-backend/app/services/parsing.py`

### 2.1.1 设置侧系统默认模板

设置页上传的“技术标系统默认模板”和“商务标系统默认模板”不是项目上传文件，也不写入 `projects.payload.templateFileRecords`。它们属于全局模板资产：

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 模板元数据和启用指针 | PostgreSQL `template_assets` | `asset_type=default_template`；`table_key=technical` 或 `business`；同一类型只能有一个当前启用版本 |
| 技术标默认模板文件 | MinIO `bid-templates` | `templates/default/technical/{uuid}-{file_name}` |
| 商务标默认模板文件 | MinIO `bid-templates` | `templates/default/business/{uuid}-{file_name}` |

生成链路只读取“有效模板”，优先级固定如下：

1. 项目上传模板优先，来源是 `{UPLOADS_DIR}/{project_id}/template/`。
2. 项目没有上传模板时，按项目 `bidType` 读取设置页当前启用的系统默认模板。
3. 当前启用的系统默认模板必须是可打开的 `.docx`，并且 MinIO 对象存在、大小正常；无效对象不能进入当前 `S1/S4` 生成 manifest。
4. 如果没有项目模板，也没有有效的同标类系统默认模板，应提示先到设置页上传并启用默认模板；不再静默读取第二层旧兜底模板。

当 `S1/S4` 需要使用设置侧模板时，后端先把 MinIO 中的有效模板下载成项目级临时输入：

```text
{UPLOADS_DIR}/{project_id}/system-default-template/{file_name}
```

这些下载副本只表示“本轮生成的有效输入”，不代表用户在该项目上传过模板，也不应出现在项目上传文件列表中。项目文件列表仍只展示用户真实上传到 `{UPLOADS_DIR}/{project_id}/template/` 的文件。

### 2.2 S0 解析结果

解析结果不把完整大文本写入项目状态 JSON。

当前处理方式：

| 数据 | 存储位置 |
| --- | --- |
| S0 初始缓存 | `{PARSED_DIR}/{project_id}/` |
| 每个文件解析文本 | `{DOCUMENTS_DIR}/{project_id}/technical-workspace/parse/{file_id}.txt` |
| 合并文本 | `{DOCUMENTS_DIR}/{project_id}/technical-workspace/parse/combined.txt` |
| 解析 manifest | `{DOCUMENTS_DIR}/{project_id}/technical-workspace/parse/manifest.json` |
| 解析摘要、预览、路径 | PostgreSQL `projects.payload` |

这样能避免项目状态 JSON 中塞入过大的全文内容，但也意味着 `documents` 工作区和 PostgreSQL 记录必须一起备份，否则解析产物会丢失。`parsed/{project_id}` 只作为 `S0` 运行期临时目录，确认参与投标并提升到技术标工作区后可以清理。

### 2.3 S1 目录生成工作区

`S1 模板与目录` 中的目录生成不直接覆盖上一次成功产物。当前路径仍叫 `s2_toc_workdir`，这是历史内部名。

当前路径策略：

| 路径 | 用途 |
| --- | --- |
| `{DOCUMENTS_DIR}/{project_id}/technical-workspace/s2_toc_workdir.new/` | 新一轮运行的 staging 工作区 |
| `{DOCUMENTS_DIR}/{project_id}/technical-workspace/s2_toc_workdir/` | 最新成功发布的目录生成工作区 |
| `{DOCUMENTS_DIR}/{project_id}/technical-workspace/s2_toc_workdir.runs/` | 旧成功目录和 stale staging 目录归档 |

发布规则：

1. FastAPI 先通过统一模板解析入口取得有效模板：项目上传模板，或设置侧系统默认模板。
2. FastAPI 在 `s2_toc_workdir.new/` 准备招标文件、投标模板、`s2_input.json`、`toc.json`、`toc_evidence.json` 等产物。
3. 投标模板会被复制为本轮 Skill 工作区内的输入文件，并在 `s2_input.json` 的 `templateFile` 中记录路径。
4. futurecode/opencode 调用成功后，后端把旧的 `s2_toc_workdir/` 移入 `s2_toc_workdir.runs/`，再把 `.new` 发布为新的 `s2_toc_workdir/`。
5. 如果本轮失败，旧的 `s2_toc_workdir/` 保持不动，`.new` 留在原处用于排查。
6. `manifestPath` 和 `canonicalManifestPath` 都指向 `s2_toc_workdir/s2_input.json`；不再生成 `{PARSED_DIR}/{project_id}/s2.json` alias。

### 2.4 S4 正文拼装稿、终稿和 OnlyOffice 文档

项目最终可编辑文档由 `onlyoffice_documents.py` 管理，`S4 生成标书` 会把输出 Word 复制到同一个项目文档路径。

默认路径：

```text
{DOCUMENTS_DIR}/{project_id}.docx
```

MinIO 对象 key：

```text
documents/{project_id}/draft.docx
```

当前逻辑：

1. S4 通过同一个模板解析入口取得有效模板，优先级与 S1 一致。
2. S4 在 `{DOCUMENTS_DIR}/{project_id}/technical-workspace/s7_assembly_workdir` 中准备 manifest、S1 目录 JSON 副本、Wiki 副本和导出的素材库 Word；目录名为历史内部名。
3. S4 在 `s7_assembly_input.json` 的 `templateFile` 中记录本轮使用的项目上传模板或系统默认模板副本。
4. S4 调用 `bid-tech-assembler` 生成正文 docx，并复制到 `{DOCUMENTS_DIR}/{project_id}.docx`。
5. 如果本地文档不存在，优先尝试从 MinIO 下载。
6. 如果 MinIO 没有，则用 `document_state.fallback.content` 生成一个 docx。
7. OnlyOffice 回调保存时，后端从 OnlyOffice 提供的 URL 下载新 docx。
8. 下载后的 docx 覆盖本地文件，并尝试同步到 MinIO。
9. PostgreSQL `projects.payload` 中更新文档版本号、保存时间、文件名、S4 拼装状态、覆盖诊断结果等状态。

相关代码：

- `code/sewpg-bid-backend/app/services/onlyoffice_documents.py`
- `code/sewpg-bid-backend/app/services/tech_assembly.py`
- `code/sewpg-bid-backend/app/api/routes/document.py`

## 三、素材库数据组织

素材库是和 `解析 / 技术标 / 商务标 / 审计 / 设置` 同级的一级准备模块，不属于某个项目内步骤。真实使用顺序是：先维护素材库和 Wiki，再进入解析；当 `S0` 确认参与投标并补全项目时，项目会绑定自己的客户素材和项目素材读取范围。

素材库顶层先分 `技术标 / 商务标`。当前只启用技术标，技术标下再分 `通用素材 / 客户素材 / 项目素材` 三档；商务标先保留为空，不上传素材、不生成 Wiki。

素材库是另一套数据链路，目标是 `PostgreSQL + MinIO`。

Docker Compose 中：

- PostgreSQL 使用 `pgvector/pgvector:pg16`
- MinIO 用于对象存储
- 初始化 SQL 在 `code/initdb/01-init.sql`

相关代码：

- `code/sewpg-bid-backend/app/models/materials.py`
- `code/sewpg-bid-backend/app/services/material_store.py`
- `code/sewpg-bid-backend/app/api/routes/materials.py`

### 3.1 原始材料库

原始材料库用于保存上传的原始资料文件，例如 docx、pdf、Excel、图片、压缩包等。

核心表：

| 表 | 用途 |
| --- | --- |
| `raw_folders` | 原始材料目录树 |
| `raw_files` | 文件元数据 |
| `raw_file_versions` | 文件历史版本记录 |

目录层级按业务分为：

```text
技术标/通用素材
技术标/客户素材/{客户名称}
技术标/项目素材/{素材项目ID}
商务标/
```

项目进入后续流程时，`GET /api/projects/{project_id}/materials-path` 会返回统一读取范围：

```text
技术标/通用素材
技术标/客户素材/{客户}
技术标/项目素材/{素材项目ID}
```

`S3 缺口处理` 的“选择已有素材”默认只在这些路径下搜索；`S4 生成标书` 继续用项目身份过滤素材卡片和清洗后的 Word，避免把其他客户或其他项目的文件混入当前项目。

项目补全页的业务文案与存储字段对应如下：

| 页面文案 | 存储/接口字段 | 说明 |
| --- | --- | --- |
| 重要客户 | `materialCustomerId / materialCustomerName` | 来自素材库客户身份选项；用于绑定客户素材读取范围 |
| 普通客户 | `customerName`，后端可生成稳定客户 ID | 不绑定已有重要客户，但仍可形成项目素材范围 |
| 已有项目 | `materialProjectId / materialProjectCode / materialProjectName` | 来自素材库项目身份选项；用于绑定项目素材读取范围 |
| 普通项目 | `materialProjectMode=ordinary`，后端可生成 `MATPRJ-*` | 当前投标工作单没有对应已有项目素材时使用 |

技术标投标机型分两层处理：

- 备选机型不单独保存为静态 JSON。页面打开时调用 `/api/materials/turbine-model-options`，后端从 `raw_files` 中定位投标机型参数表，从 MinIO 读取 Excel 并动态解析候选项。
- 用户选中的机型会随项目保存，写入项目 payload 中的 `turbineModel / selectedTurbineModel / turbineModelLabel`。当前项目表为 `projects(id, payload JSONB, updated_at)`，因此机型参数是项目 JSONB 的一部分，不是独立机型表。

`turbineModel` 典型结构：

```json
{
  "model": "EW10.0-220下置",
  "platform": "X2E-2",
  "layout": "变压器下置",
  "ratedPowerKw": 10000,
  "rotorDiameterM": 220,
  "status": "active",
  "statusLabel": "可投标",
  "source": "parameter_sheet",
  "sourceFileId": "RAW-0437",
  "sourceFileName": "X2平台机型投标参数_20250106.xlsx",
  "aliases": ["EW10.0-220", "W10.0-220"]
}
```

`raw_files` 中保存：

| 字段 | 含义 |
| --- | --- |
| `folder_id` | 所属目录 |
| `name` | 文件名 |
| `size_bytes` | 文件大小 |
| `mime_type` | MIME 类型 |
| `minio_bucket` | MinIO bucket |
| `minio_key` | MinIO 对象 key |
| `version` | 当前版本号 |
| `ext_fields` | 扩展字段，例如 `bidType`、`projectId`、`customerName` |

文件本体写入 MinIO，key 形如：

```text
raw/{folder_path}/{file_name}
```

### 3.3 Wiki 素材库

Wiki 素材库用于段落级、章节级、方案类可复用文本。

当前自动生成口径不是旧的大型知识库，而是给 Agent 读取素材库的最小索引库。`fastapi` 会把素材清单压缩成 manifest 写入共享目录：

```text
{PARSED_DIR}/_wiki_build/bid-wiki-build-*/wiki_build_manifest.json
{PARSED_DIR}/_wiki_build/bid-wiki-build-*/wiki_blueprint.json
```

随后由 `fastapi` 直接执行技术标专用 Wiki Skill runner：

```bash
python opencode/skill/bid-tech-wiki-material-builder/scripts/run_from_manifest.py <wiki_build_manifest.json>
```

runner stdout 只返回小型摘要和 `outputFile`，完整 Wiki 蓝图写入 `wiki_blueprint.json`。后端读取该文件后导入 PostgreSQL，避免大素材库经过 OpenCode 会话时超时，也避免大 JSON 输出被摘要或截断。

自动生成的一级节点固定为：

| 节点 | 用途 |
| --- | --- |
| `01-素材总表` | 快速扫描真实素材、路径、层级、身份、清洗状态和推荐用途 |
| `02-章节映射表` | 把目录/章节需求映射到候选素材卡片，并标记整篇拼接、部分摘取、填表来源或附件引用 |
| `03-素材卡片` | 按 `通用素材 / 客户素材 / 项目素材` 分层，再按主题分组；每张卡保留来源路径、身份字段、用途和 merge 信息 |
| `04-待填写清单` | 标记需要在 `S3 缺口处理` 中确认或填写的项目字段、空表、保证值和来源选择 |
| `05-使用规则` | 约束后续 Agent 的读取顺序、身份过滤和禁止编造事实规则 |

核心表：

| 表 | 用途 |
| --- | --- |
| `wiki_nodes` | Wiki 树节点 |
| `wiki_docs` | 节点正文、摘要、标签 |
| `wiki_attachments` | Wiki 附件元数据 |
| `wiki_paragraphs` | 段落向量，表结构已设计 |

`wiki_docs.markdown_content` 保存 Markdown 正文。

Wiki 附件本体写入 MinIO，PostgreSQL 保存附件文件名、大小、MIME、bucket、key。

### 4.1 原始材料库页面

页面：

- `code/sewpg-bid-frontend/src/pages/MaterialDB.jsx`

入口：


加载流程：

1. 页面初始化调用 `materialsAPI.raw.tree()` 获取目录树。
2. 前端根据选中目录确定 `folderPath`。
3. 调用 `materialsAPI.raw.files({ folderPath, keyword, bidType, customerName, projectId, page, pageSize })` 获取文件列表。
4. 上传文件时使用 `FormData` 调用 `/api/materials/raw/upload`。
5. 上传成功后刷新目录树和文件列表。

当前页面展示方式为左侧 Finder 列表模式：

- 顶层固定为 `技术标 / 商务标`；当前 `技术标` 下固定为 `通用素材 / 客户素材 / 项目素材`，`商务标` 保留为空。
- 目录可以逐级展开，目录下的文件直接显示在同一棵树里。
- 点击已清洗且存在清洗稿的文件，会调用清洗稿预览接口，并在右侧 OnlyOffice 区域打开清洗后的 Word。
- 未清洗、清洗中或清洗失败的文件只显示状态，不进入 OnlyOffice 预览。

## 五、当前不够严谨的地方

### 5.1 缺口处理产物已进入项目级真实文件，但尚未沉淀为全局素材库

这是当前最重要的问题。

统一缺口处理页上传客户资料时，前端会读取文件 Data URL，后端将其转换为项目级 `.docx` 产物并挂回 `gapPlan.resolvedArtifacts`。选择已有素材和 AI 填写也会形成可被标书拼装读取的项目级产物。

仍需注意：旧兼容接口 `submit_gap_material` 仍保留 receipt 形态；更重要的是，缺口处理产物当前主要沉淀在项目工作目录和项目状态中，还没有完整写入全局 `raw_files`/MinIO 素材库复用链路。

```text
gapPlan.resolvedArtifacts[]
documents/{project_id}/technical-workspace/s4_gap_workdir/manual_upload/*
documents/{project_id}/technical-workspace/s4_gap_workdir/selected_material/*
documents/{project_id}/technical-workspace/s4_gap_workdir/ai_fill/*
```

这意味着：

- 标书生成可以读取本项目缺口处理产物。
- 这些产物尚未自动成为全局素材库的可复用原始素材。
- “补录的数据沉淀到素材库，下次项目直接复用”这件事当前没有完整闭环。

### 5.2 MinIO 与数据库提交不是原子事务

原始材料上传流程中，文件先写入 MinIO，再写 PostgreSQL 元数据。

如果 MinIO 上传成功但数据库提交失败，可能留下孤儿对象。

如果数据库提交成功但后续文件操作失败，也可能出现元数据和对象存储不一致。

### 5.3 原始素材版本管理存在覆盖风险

当前同名文件覆盖或版本上传时，MinIO key 仍按目录和文件名生成：

```text
raw/{folder_path}/{file_name}
```

如果新版本继续使用相同 key，旧版本对象可能被覆盖，导致 `raw_file_versions` 里虽然有历史版本记录，但无法可靠取回旧文件内容。

更严谨的方式是每个版本使用不可变 key，例如：

```text
raw/{folder_path}/{file_id}/v{version}/{file_name}
```

### 5.4 上传校验后端不够完整

项目招标文件上传有后端扩展名白名单。

但素材库原始材料上传更多依赖前端白名单，后端主要做大小限制和文件名清洗。正式环境中应在后端补齐：

- 扩展名白名单
- MIME 类型校验
- 文件头校验
- 压缩包安全检查
- 文件名长度和路径约束

### 5.5 PostgreSQL 表初始化依赖部署脚本

应用启动时会确保 MinIO bucket 存在，但不会自动创建核心 PostgreSQL 表。

核心表依赖 `docker-compose` 首次启动时执行：

```text
code/initdb/01-init.sql
```

如果数据库已经初始化过，后续修改 SQL 不会自动迁移。正式化应引入 Alembic 或等价迁移机制。

### 5.6 结构化 Excel 导入仍是 MVP 形态

当前结构化导入接口能返回预览和确认结果，但并未完整实现真实 Excel 解析、字段映射、数据校验、错误报告、导入快照和回滚。

正式化后应补齐：

- Excel 文件真实上传到 MinIO
- 解析工作簿和 sheet
- 字段映射校验
- 必填字段校验
- 类型转换和错误报告
- 成功行写入 `structured_rows`
- 导入记录写入 `structured_imports`

## 六、建议的正式化改造优先级

### P0：补齐缺口处理产物沉淀到素材库

目标：缺口处理中的上传文件、选择素材副本、AI 填写产物，在项目可用之外，也能按规则进入全局原始材料库。

建议改造：

1. 明确哪些缺口处理产物允许沉淀为全局素材，哪些只作为项目临时产物。
2. 后端为允许沉淀的产物调用 `material_store.raw_upload()` 写入 MinIO 和 `raw_files`。
3. `gapPlan.resolvedArtifacts` 保存真实 `RAW-xxxx` 文件 ID、版本和项目来源。
4. 标书生成优先引用真实素材 ID；项目级临时产物继续保留本地路径兜底。
5. 增加重复素材识别、版本管理和人工确认入口。

### P1：统一项目文件存储策略

当前项目主链路已经切到 `PostgreSQL + 本地 uploads/documents/parsed`，素材库使用 `PostgreSQL + MinIO`。

可以保留这种混合模式，但需要明确：

- 项目上传原件是否也同步 MinIO。
- OnlyOffice 文档以本地为主还是 MinIO 为主。
- 备份恢复时 PostgreSQL、本地目录、MinIO 的一致性要求。

### P1：补齐对象存储一致性处理

建议增加：

- 上传失败清理 MinIO 对象
- 数据库提交失败清理 MinIO 对象
- 定期扫描孤儿对象
- MinIO key 使用 UUID 或 file_id/version，不直接依赖可变文件名

### P1：补齐数据库约束和迁移

建议增加：

```sql
UNIQUE(raw_folders.path)
UNIQUE(raw_files.folder_id, raw_files.name)
```

同时引入数据库迁移工具，避免依赖一次性 init SQL。

### P2：结构化素材导入真实落地

建议实现完整 Excel 导入链路，并把导入文件、导入记录、错误报告、成功数据建立可追溯关系。

## 七、当前可对外说明口径

如果需要向项目成员或甲方解释，可以使用下面的口径：

> 当前 MVP 不把 Word、PDF、Excel 等文件直接存数据库。系统采用“数据库保存元数据和业务状态，文件系统或 MinIO 保存文件本体”的方式。项目主链路当前使用 PostgreSQL 保存项目阶段状态和文件路径，本地目录保存上传文件、解析文本、缺口处理产物、标书生成工作目录和生成文档；素材库使用 PostgreSQL 保存目录、标签、结构化数据和 Wiki 正文，MinIO 保存原始文件和附件。标书生成会把素材库中的清洗后 Word、项目缺口处理产物和 AI 填写产物导出到拼装工作目录，再按已确认目录 JSON 拼装正文；覆盖诊断基于拼装计划返回未拼上的素材和未匹配目录项。当前素材库管理页面已经走真实接口，缺口处理产物也能参与本项目拼装；正式化前仍需要补齐“项目补料沉淀到全局素材库”的版本管理、对象存储一致性和数据库迁移机制。
