## 一、总体架构：三进程协作

采纳 **opencode (anomalyco/opencode, MIT)** 作为 agent runtime，与自研业务后端、前端构成三进程架构。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Web 前端（当前基线：React + Vite）                         │
│  ┌─────────────────┐  ┌────────────────┐  ┌──────────────────────────────┐ │
│  │ 业务 UI          │  │ OnlyOffice     │  │ 可选 AI 面板                 │ │
│  │ (目录/素材/审计) │  │ iframe         │  │ (当前 MVP 非必做)           │ │
│  └────────┬────────┘  └────────┬───────┘  └────────────┬─────────────────┘ │
└───────────┼────────────────────┼──────────────────────┼────────────────────┘
            │ REST/WS            │ postMessage           │ opencode SDK
            ▼                    ▼                       ▼
┌───────────────────────────┐  ┌──────────────┐  ┌─────────────────────────┐
│ 业务后端 FastAPI (Python)  │  │ OnlyOffice   │  │ opencode server (Bun/TS)│
│ ─────────────────────────  │  │ DocServer    │  │ ──────────────────────  │
│ · Stage Machine 编排       │  │              │  │ · Agent Runtime         │
│ · 文档处理                  │  │              │  │ · Session 管理          │
│   (python-docx/MinerU/OCR) │  │              │  │ · Plugin 机制注册 tools │
│ · 数据库 / Wiki / MinIO    │  │              │  │ · 多 provider LLM       │
│ · Excel 导入管线            │  │              │  │                         │
│ · OnlyOffice Callback       │  │              │  │                         │
│ · 审计日志                  │  │              │  │                         │
└────────┬──────────────────┘  └──────────────┘  └────────┬────────────────┘
         │                                                 │
         │         ┌──── opencode plugin 内的 tools ────┐  │
         │◀────────│ 每个 tool 通过 HTTP 调 FastAPI    │──┘
         │         │ (业务逻辑在 Python 侧执行)         │
         │         └────────────────────────────────────┘
         │
         ▼
┌──────────────────┐
│ 公司 LLM 网关     │ ← opencode 也通过这里调模型
└──────────────────┘
```

### 1.1 三进程职责分工

| 进程 | 语言 | 职责 |
|---|---|---|
| **Web 前端（当前为 React + Vite）** | TypeScript | 业务 UI + OnlyOffice iframe |
| **FastAPI 业务后端** | Python | 文档处理、数据库、Stage Machine 编排、业务 REST API、OnlyOffice 回调处理 |
| **opencode server** | Bun/TS | Agent runtime、Session、Tool 调度、对 LLM 网关 |

### 1.2 Stage Machine（仍由 FastAPI 驱动）

```
S1 解析 → S2 目录 → [S3 审核目录] → S4 缺口识别 → S5 备料 →
  [S6 审核备料] → S7 填充 → S8 校验 → S9 人机共创 → S10 导出
```

**每个 Stage 的执行方式**：
- 自动化 Stage（S1/S2/S4/S7/S8）：FastAPI 调用 opencode server API 创建 session 发 task → opencode agent 调用已注册 tools → FastAPI 收结果进下一 stage
- 人工 Stage（S3/S5/S6）：FastAPI 暂停流水线，前端进入人机交互 UI
- 共创 Stage（S9）：前端仍通过 FastAPI 获取文档会话与编辑能力；OnlyOffice 事件与保存回写由后端统一承接

### 1.3 设计哲学

- **外层确定性**：阶段顺序、人工审核点、格式应用、导出 —— 全由代码保障，不让 LLM 决定。对应国企合规的硬约束。
- **内层柔性**：阶段内部"怎么找素材、怎么改写段落、怎么回应条款" —— 由 agent 自主决策、调用 skills 完成。对应业务场景的多样性。

这是本方案的**核心架构判断**：纯 workflow 不够灵活，纯 agent 不够可控，两层嵌套才是答案。

## 二、⭐ 深入讨论一：素材检索策略 — LLMWiki vs RAG

### 2.1 RAG（Retrieval-Augmented Generation，向量召回）

**原理**：素材切片 → 嵌入向量 → 向量库索引；查询时用问题向量找 top-k 相似片段 → 喂给 LLM 生成答案。

**适用场景**：
- 开放问答（客服、文档问答）
- 素材规模大（数十万+篇）
- 对召回率敏感、对精度容忍
- 用户会二次验证答案

**在投标场景的致命弱点**：
| 问题 | 具体表现 |
|---|---|
| 相似 ≠ 正确 | 搜"2023 年华能项目业绩" 可能召回华电的类似项目，embedding 分不出来 |
| 追溯弱 | 召回的片段来自哪个原始文档？往往只有向量 ID，追溯到人类可读的文档层级很费劲 |
| 高价值字段易出幻觉 | 金额、日期、机型编号 — LLM 基于相似片段"重新组织"时极易张冠李戴 |
| 控制粒度粗 | 很难指定"只从华能分支找"或"优先 2024 年后的项目"，向量天生无层级结构 |
| 对排版无感 | 原始段落的格式、表格、附件关系在 embedding 中全丢失 |

### 2.2 LLMWiki

**原理**：把素材组织成**有层级、有摘要的目录树**；每层节点带 LLM 生成的摘要；Agent 像图书管理员一样，读摘要决定往下钻、最终读叶子全文。

**类比**：RAG 是"按图书封面相似度推荐"；LLMWiki 是"Agent 根据读者问题，先看分类架，再看书名，再翻目录，最后读章节"。

**投标场景的优势**：
| 优势 | 具体表现 |
|---|---|
| 精度高 | 按"客户 → 项目 → 段落"的业务层级导航，不会把华电的内容当华能的 |
| 决策可审计 | Agent 的导航路径完整可见 — "为了找华能业绩 → 进入 `客户定制/华能/` → 读 `项目合作史` 摘要 → 选中 2023-02 项目" |
| 匹配"每段有出处"硬约束 | 每次产出都带完整路径 `客户定制/华能/甘肃风电/项目介绍段落` |
| 可控粒度 | 可约束 agent 只能在指定子树里找 |
| 冷启动可渐进 | 一级目录先建（客户/机型/专题），叶子摘要按需生成 |

**局限**：
- 冷启动需要建目录与摘要（但只是一次性，且可半自动）
- 目录外的稀有内容找不到
- 叶子段落数量大时，摘要树导航成本上升

### 2.3 对比表

| 维度 | RAG | LLMWiki | 结构化表 |
|---|---|---|---|
| 精度 | 中（依赖 embedding 质量） | **高**（有层级约束） | **极高**（确定性查询） |
| 召回率 | **高**（top-k） | 中（取决于目录完整性） | 低（仅覆盖结构化字段） |
| 追溯能力 | 弱 | **强** | **强** |
| 冷启动成本 | 低 | 中（要建目录） | 高（要设计 schema + 录数据） |
| 维护成本 | 低 | 中 | 中 |
| 适合的素材类型 | 任意文本 | 有业务层级的文档 | 字段明确的数据 |
| 规模适用 | 万+篇最优 | 500–50000 篇甜区 | 任意 |
| 对幻觉的抵抗力 | 弱 | 中 | **强** |

### 2.4 推荐方案：两库三层混合架构

**先讲两库**（与业务语言对齐）：

```
┌─────────────────────────────────┐    ┌──────────────────────────────────┐
│  📊 数据库（结构化）              │    │  📚 文档库 / Wiki（非结构化）    │
│  ─────────────────────────       │    │  ───────────────────────────     │
│  来源：客户 Excel → JSON 存储     │    │  来源：内部积累,三层组织         │
│  内容：机型/项目业绩/人员/证书/   │    │  内容：方案描述/专题/公司介绍/   │
│         资质/功率曲线            │    │         段落级可复用素材         │
│  精度：100%（不允许 LLM 介入）    │    │  精度：高（Agent 按层级导航）    │
│  查询：SQL / 模板占位符           │    │  查询：LLMWiki + pgvector 兜底   │
└─────────────────────────────────┘    └──────────────────────────────────┘
```

**两库分工原则**：
- **数据库**负责"**数字、名称、日期、编号**" — 确定性字段
- **Wiki**负责"**句子、段落、叙事**" — 描述性内容
- 任何字段归属不清时，**优先放数据库**（降低幻觉风险）

**再讲三层查询**（运行时 Agent 如何用）：

```
             ┌─────────────────────────────────────┐
             │   Agent 查询意图（fill_section       │
             │    根据目录节点要点发起）            │
             └──────────────┬──────────────────────┘
                            │
            ┌───────────────┼──────────────────────┐
            ▼               ▼                      ▼
┌────────────────┐  ┌──────────────────┐   ┌──────────────────┐
│ 第一层:         │  │ 第二层:           │   │ 第三层:           │
│ 数据库查询       │  │ LLMWiki 导航      │   │ pgvector 兜底     │
│ (SQL on JSON)  │  │ (目录树 + 摘要)   │   │ (embedding)      │
├────────────────┤  ├──────────────────┤   ├──────────────────┤
│ 机型/项目/人员   │  │ 技术/商务标分支   │   │ 所有叶子段落的    │
│ 资质/证书/金额   │  │ 标准/客户/项目层  │   │ bge-m3 embedding │
│ 确定性字段       │  │ 叙事性内容        │   │                   │
└────────────────┘  └──────────────────┘   └──────────────────┘
        │                  │                      │
        └──────────────────┴──────────────────────┘
                           │
                    ┌──────▼──────┐
                    │ emit_paragraph│
                    │ 带完整证据链  │
                    └─────────────┘
```

**Wiki 按标书类型分支**（技术标 / 商务标 / 通用）：

```
wiki/
├── 标准模板/
│   ├── 公司简介/           [通用]
│   ├── 资质荣誉/           [通用]
│   ├── 技术方案描述/       [技术标]
│   │   ├── 主机/
│   │   ├── 叶片/
│   │   └── 变桨/
│   ├── 专题方案/           [技术标]
│   └── 商务条款模板/       [商务标]
│       ├── 付款方式/
│       └── 质保承诺/
├── 客户定制/
│   ├── 华能/               [通用：合作历史 / 技术标：专题偏好 / 商务标：合同范式]
│   └── ...
└── 项目定制/
    └── [项目ID]/
        ├── 风资源报告/     [技术标]
        ├── 发电量担保函/   [技术标]
        └── 报价明细/       [商务标]
```

Agent 查询时会带 `bid_type` 上下文，`browse_material_wiki` 只返回匹配的分支。

**为什么不用纯 RAG**：投标"精度 > 召回"，且每段要说出处，纯 RAG 满足不了；尤其高价值字段交给 RAG = 主动埋幻觉雷。

**为什么不用纯 LLMWiki**：叶子召回需要保险。

**为什么不用纯结构化表**：非结构化的方案描述、专题内容无法塞进表里。

**甜区判断**：本项目素材规模 500–5000 篇，**正好是 LLMWiki 最发挥的区间**（目录层次合理、摘要成本可控）。

## 三、⭐ 深入讨论二：Agent 架构 — opencode vs dify 真实对比

### 3.1 选型历程（给决策者的上下文）

**第一轮**：对比 dify vs 自研 agent loop，结论选自研。
**第二轮**（本次）：真实调研了 **opencode (anomalyco/opencode, MIT)** 与 **dify (langgenius/dify, Apache 2.0 + 附加条款)** 的最新状态，明确采用 opencode。

### 3.2 Dify 真实情况（基于实际 repo 调研）

**License 关键条款**（2025/10 版本）：
- 基础：Apache 2.0
- 附加条款 a：**禁止多租户服务**，除非书面商业授权
- 附加条款 b：**前端 LOGO / 版权信息不得移除或修改**（除非不使用 dify 前端）

对投标场景的影响：
| 附加条款 | 对我们的影响 |
|---|---|
| 禁多租户 | ✅ 无影响（我们单租户） |
| 禁改 LOGO/版权 | ❌ **国企内部系统通常要求白标（去 Dify 品牌）→ 与条款冲突** |

**部署规模**（实际 `docker/docker-compose.yaml`）：
- 官方 compose 文件定义 29 个 services（vector db 是多选一）
- 精简后最少需要：api / worker / web / redis / sandbox / nginx / 1 个向量库 / minio = **8 个服务**
- 对比 opencode 方案：+1 个 Bun 服务而已

**能力画像**：
- ⭐ 可视化 workflow、Chatflow、Agent、RAG、Dataset
- ⭐ 面向"非开发者搭应用"
- 137k+ stars，生态最活跃

**为什么对我们不合适**：
1. **白标受限**：国企甲方验收时看到 "Powered by Dify" 会问问题
2. **workflow DSL 存 DB**：版本管理、code review 路径不自然
3. **agent 能力是工作流里的一个节点**，不是我们需要的"流水线外层驱动、内层自主决策"的两层嵌套
4. **29 服务的部署复杂度** 对 10-50 人内网项目过重
5. **业务方不需要自助配 workflow** —— dify 最大卖点我们用不上

### 3.3 opencode 真实情况（基于实际 repo 调研）

**License**：**MIT**，纯自由，无附加条款，可白标、可商用、可 fork 修改

**关键架构（实际 `packages/` 验证）**：
| package | 作用 |
|---|---|
| `opencode-ai` | 主 CLI / runtime（Bun） |
| `@opencode-ai/sdk` | Client SDK (openapi.json 自动生成) |
| `@opencode-ai/plugin` | Plugin API，含 `tool({description, args, execute})` |
| `server` | HTTP server，供任何 client 驱动 |
| `web` / `desktop` / `desktop-electron` | 官方已有 web 和 Electron 客户端 |

**对我们的价值**：
- Client/Server 架构 → 适合由 FastAPI 统一驱动
- Plugin tool API → 注册 16+ 业务 skills 的入口
- Provider-agnostic → 接公司 LLM 网关零适配
- Session 持久化 → 多轮共创现成
- Permission 系统 → 敏感 tool 可要求用户批准
- **官方 Desktop (Electron)** → 如果客户要桌面端可直接复用

**关键能力与项目需求映射**：

| 能力 | 对应本项目需求 |
|---|---|
| **Client/Server 架构** | Server 可由 FastAPI 或其他客户端驱动，不限于 TUI |
| **Plugin 机制（`@opencode-ai/plugin`）** | `tool({description, args, execute})` API 可注册自定义 tools → 承载我们 16+ skills |
| **SDK（`@opencode-ai/sdk`）** | 可用于构建客户端能力；当前 MVP 以 FastAPI 调用 server API 为主 |
| **OpenAPI 规范** | `packages/sdk/js/openapi.json` — 接口稳定，可自动生成客户端 |
| **Provider-agnostic** | 对接公司 LLM 网关（OpenAI 协议）只需配置 provider |
| **Session 持久化** | 多轮对话/上下文管理现成，无需自研 |
| **Permission 系统** | 内置 `ask` 机制支持"请求用户批准"，可用于敏感 tool 调用 |
| **Agent 模式（build / plan）** | 可建自定义 agent profile 限制 tool 权限 |

### 3.4 完整三方案对比

| 维度 | dify | 自研 agent loop | **opencode（推荐）** |
|---|---|---|---|
| License | Apache 2.0 + 禁改 LOGO | N/A | **MIT 纯自由** |
| 白标 | ❌ 受限 | ✓ | ✓ |
| 商用 | ✓ | ✓ | ✓ |
| 流程柔性 | workflow 显式图 | 灵活 | **灵活** |
| 业务逻辑位置 | dify plugin (Python) | 自己代码 | **plugin HTTP→FastAPI** |
| 合规可控 | dify runtime 黑盒 | 完全可控 | **可控（开源可审计）** |
| 服务数增量 | +8 服务 | +0 服务 | **+1 服务 (Bun)** |
| 实现工作量 | 中（要适配 plugin） | **高**（agent/session/multi-provider 要自己写 2-3 人月） | **低** |
| Session / 对话 UI | 有 | 需自研 | **SDK 开箱即用** |
| Desktop 客户端 | 无 | 无 | **官方 Electron 可复用** |
| 演进跟随 | 与 dify 强耦合,升级冲击大 | 自己维护负担重 | **跟随社区迭代** |

### 3.5 推荐结论

> **采用 opencode 作为 agent runtime，业务后端保持 Python (FastAPI)，两者通过 HTTP 协作。**

**关键判断**：
1. opencode 已实现我们自研会花 2-3 人月的能力（agent loop、session、plugin、多 provider、permission），**直接用省下最多工作量**
2. MIT 许可可商用、可白标、开源可审计，符合国企合规
3. 它的 client/server 设计让"web 前端 + opencode server"天然契合
4. 业务后端保持 Python 不变 → 文档处理生态优势保留
5. opencode 是活跃开源项目，跟随社区迭代比自己维护更划算

**dify 的不选理由（最关键）**：白标限制在国企项目是硬伤，不是技术问题而是合规/商务问题。

### 3.6 关键架构决策：业务逻辑放哪

**我们的原则**：**opencode 只做 agent 调度，不做业务逻辑**。

```
opencode plugin 内的 tool.execute() {
  → HTTP 调 FastAPI 的对应业务端点
  → 业务逻辑（DB 查询 / 文档处理 / 文件操作）在 Python 侧执行
  → 返回结构化结果给 opencode agent
}
```

**为什么这样分**：
- 文档处理（python-docx / MinerU / PaddleOCR）生态在 Python
- 数据库、MinIO、审计日志的代码都在 Python 侧，集中管理
- opencode plugin 是薄壳（thin wrapper），TS 代码量可控
- 如果未来换 agent runtime，只改壳不改里

## 三 ter、⭐ 素材缺口识别（S4 前置备料机制）

### 3ter.1 为什么重要

如果直接从"目录确认"跳到"章节填充"，一旦某节点需要的素材两库都没有，Agent 要么编造（幻觉）、要么留空（破坏连贯）。**把素材盘点前置到填充之前**，让人工一次性补齐+审核，是保障精度的关键。

### 3ter.2 实现流程（opencode 架构下）

FastAPI 驱动 opencode 执行 `identify_material_gaps` task：

```
FastAPI S4 stage executor:
  ↓ opencode_client.sessions.create(agent_profile="pipeline", ctx={project_id})
  ↓ sessions.send("扫描目录 × 两库,列出缺口")
opencode agent 执行:
  ↓ 调用 tool: list_outline_leaves → FastAPI 返回节点列表
  ↓ 对每个节点调用 tool: analyze_node_requirements → 分析所需素材
  ↓ 对每个需求调用 tool: check_availability → 查两库是否有
  ↓ 缺失项收集 → emit_gap_report
FastAPI 收到结果写入 material_gaps 表
前端渲染缺口清单
```

实际的分析逻辑（`analyze_node_requirements`）仍在 FastAPI 的 Python 侧：

```python
# FastAPI endpoint,由 opencode tool 调用
@router.post("/api/gaps/analyze_node")
async def analyze_node(node_id: str, bid_type: BidType):
    node = get_outline_node(node_id)
    # LLM 分析该节点需要什么
    requirements = await llm.complete(
        prompt=GAP_ANALYSIS_PROMPT.format(node=node, bid_type=bid_type),
        model="mid",
    )
    # 输出结构: [{type: "structured_field", query: "..."},
    #          {type: "wiki_paragraph", topic: "..."},
    #          {type: "attachment", template_id: "..."}]
    return requirements
```

### 3ter.3 数据层

```sql
CREATE TABLE material_gaps (
  id BIGSERIAL PRIMARY KEY,
  project_id BIGINT NOT NULL,
  outline_node_id BIGINT NOT NULL,
  req_type VARCHAR(20),               -- structured_field / wiki_paragraph / attachment
  req_desc TEXT,                      -- "机型 SE-8.0-200 功率曲线"
  suggested_source VARCHAR(200),      -- "数据库 power_curves 表" / "Wiki 客户定制/华能/"
  status VARCHAR(20),                 -- pending / resolved / skipped
  resolved_by BIGINT,                 -- user_id

```

### 3ter.4 前端交互

- 缺口列表页：按节点分组、按优先级排序
- 每项提供"去补录"按钮：
  - **结构化缺失** → 跳转"数据库 Excel 模板下载 + 上传"
  - **Wiki 缺失** → 打开 Wiki 编辑器新建节点
  - **附表缺失** → 提示上传业主附表或确认已有
- "显式跳过" 需填理由（审计记录）
- 全部 resolved/skipped 后 → 进入 **S6 审核备料**
- S6 审核通过后才解锁 S7 填充

### 3ter.5 S6 审核备料实现

**数据模型**（扩展 material_gaps 表）：
```sql

  reviewed_by BIGINT,
```

## 三 quater、⭐ 编辑辅助 Agent（S9 人机共创核心）

生成之后、用户改稿时，AI 继续当辅助角色。在 opencode 架构下有**两条路径**共存：

- **确定性动作**（格式/编号/目录）走 FastAPI 直接处理，低延迟
- **语义动作**（改写/新增/填充）走 opencode session，用户对话式驱动

### 3quater.1 事件驱动架构（双路分流）

```
┌──────────────────┐
│  OnlyOffice      │  onDocumentChange / onSelection / onPaste
│  DocEditor       │─────────┬────────────────────────────────────┐
│  (前端 iframe)    │         │                                    │
└──────────────────┘         │                                    │
         ▲                   ▼                                    ▼
         │      ┌──────────────────────────┐       ┌──────────────────────────┐
         │      │ FastAPI /editor/event    │       │ opencode SDK from web    │
         │      │ (快速路径: 格式/编号/目录)│       │ (慢速路径: AI 对话/改写) │
         │      │ Python 直接处理          │       │ opencode session         │
         │      │ 延迟 < 500ms             │       │ 延迟 2-5s                │
         │      └───────────┬──────────────┘       └────────────┬─────────────┘
         │                  │                                    │
         │                  │                                    │ 调用 opencode tools
         │                  ▼                                    │ (ai_rewrite / ai_fill_new_section)
         │     ┌────────────────────────┐                       │
         │     │  auto_numbering        │                       │
         │     │  refresh_toc           │                       │
         │     │  cleanup_paste         │                       │
         │     │  apply_style_heading   │                       │
         │     │  recompute_coverage    │                       │
         │     │  consistency_scan      │                       │
         │     └────────────┬───────────┘                       │
         │                  │                                    │
         └──────────────────┴────────────────────────────────────┘
                         applyDiff / refreshToc / updateNumbering
```

### 3quater.2 为什么分两路

| 动作类别 | 路径 | 理由 |
|---|---|---|
| **格式/编号/目录/样式** | 直接 FastAPI | 延迟敏感 (<500ms)；规则确定不需要 LLM；避免 opencode 长 session 拖慢 |
| **AI 改写/补段/填充** | 走 opencode session | 需要 LLM；需要多轮对话上下文；用户可看到 agent 思考过程 |
| **清理粘贴污染** | 直接 FastAPI | 正则 + 规则，不需 LLM |
| **覆盖热力图刷新** | 直接 FastAPI | DB 查询，不需 LLM |

### 3quater.3 实时 vs 显式触发的边界

| 动作 | 触发方式 | 路径 |
|---|---|---|
| 自动编号 | 实时（结构变化时） | FastAPI |
| 刷新目录 | 保存触发 | FastAPI |
| 修正标题样式 | debounce 2s | FastAPI |
| 清理粘贴污染 | onPaste 事件 | FastAPI |
| 覆盖热力图刷新 | debounce 3s | FastAPI |
| 项目信息一致性 | 保存/导出前 | FastAPI |
| **AI 改写选中段** | 显式（用户点按钮） | **opencode** |
| **新增章节自动填充** | 显式（用户点按钮） | **opencode** |
| **用户自由对话问 AI** | 在 AI 对话面板 | **opencode** |
| 一键刷格式 | 显式 | FastAPI |

### 3quater.4 冲突处理

- **用户正在输入 → AI 不触发任何自动操作**（WebSocket 反馈 typing 状态）
- **AI 动作范围受限**：FastAPI 路径只动格式/编号/目录/热力图；opencode 路径改语义必须用户确认 diff
- **所有 AI 动作落审计**：可"撤销最近 AI 修改"
- **OnlyOffice 协同模型**：把 FastAPI editor_assist 当作另一个"协同用户"，走同一条 OT/CRDT 通道避免冲突

### 3quater.5 OnlyOffice 集成要点

- OnlyOffice Docs 提供 JavaScript SDK（`DocsAPI.DocEditor`）+ Callback URL
- Callback URL 指向 FastAPI，让后端在文档保存时拿到最新 .docx → 触发格式类处理
- 前端通过 `postMessage` 与 iframe 通信
- 自定义菜单项（"AI 改写"、"AI 填充本节"、"刷格式"）通过 OnlyOffice plugin 机制注入
- AI 相关菜单项当前建议统一走 FastAPI；格式相关菜单项也由 FastAPI 统一承接

**初步推荐社区版，但真实调研后必须改口径**。以下基于 ONLYOFFICE/DocumentServer 官方 Readme 的三版本对比表：

| 属性 | Community | Enterprise | **Developer（推荐）** |
|---|---|---|---|

3. **无法去 OnlyOffice 品牌**：甲方验收看到 ONLYOFFICE LOGO 会问"为什么不是我们自己的品牌"。

**结论修正**：

> **必须采购 ONLYOFFICE Developer Edition 授权**（一年起购）。Developer Edition 的官方定位就是 "for integrators who need to bring document editing to their app users" — 完全契合我们的场景。

| 方案 | 类 Word 还原 | 部署 | 协议 | .docx 无损 | 结论 |
|---|---|---|---|---|---|

| OnlyOffice Community | 极高 | Docker | AGPL + 20 连接上限 | ✓ | ❌ 合规+规模受限 |
| WPS Web Office | 极高 | 易 | 商业授权 | ✓ | 备选：国产优势，但不开源、定制能力弱 |

| Lexical + 自研 | 中 | 难 | MIT | 需自研 | ❌ 成本过高 |

**商务建议**：
- 先用 Community 跑 P0/P1 POC（验证集成可行性）

- 可横向扩展存储

### 6.3 数据库（结构化素材）设计

**核心思路**：**强 schema 的核心字段** + **JSONB 扩展字段**，兼顾查询效率与字段灵活性。

**Excel ↔ 数据库 管线**：

```
┌──────────────┐    ┌────────────────┐    ┌──────────────────┐    ┌─────────────┐
│ 客户 Excel    │ ─→ │ excel-import   │ ─→ │ 映射 + 校验      │ ─→ │ PostgreSQL   │
│ (标准模板)    │    │ Service        │    │ (Pydantic schema)│    │ 核心列 + JSONB│
└──────────────┘    └────────────────┘    └──────────────────┘    └─────────────┘
                         │                                              │
                         ▼                                              ▼
                    每次导入入库前                               JSONB 存扩展字段
                    存快照（可回滚）                             便于灵活扩展
```

**关键实现**：
- 每张核心表（机型/项目/人员）提供一份 **标准 Excel 模板** 下载
- 后端用 `openpyxl` + `pandas` 读 Excel
- 按 Pydantic 模型校验字段类型、必填、唯一性
- 校验失败：返回逐行错误报告，让用户修正后重传
- 成功导入：写入核心列，未知列进 `ext_fields JSONB`
- 导入快照存 `imports` 表，支持回滚到任意版本

**schema 草案（摘要 DDL）**：

```sql
-- 公司
CREATE TABLE companies (
  id BIGSERIAL PRIMARY KEY,
  name VARCHAR(200) NOT NULL,
  est_year INT,
  headquarters VARCHAR(200),
  intro_text TEXT,

  ext_fields JSONB DEFAULT '{}'::jsonb          -- 扩展字段
);

-- 机型（核心）
CREATE TABLE wind_turbine_models (
  id BIGSERIAL PRIMARY KEY,
  model_code VARCHAR(80) UNIQUE NOT NULL,      -- 如 SE-8.0-200
  rated_power_kw INT NOT NULL,
  rotor_diameter_m NUMERIC(6,2),
  hub_height_m NUMERIC(6,2),
  blade_tip_clearance_m NUMERIC(6,2),
  tower_type VARCHAR(80),
  transformer_type VARCHAR(80),
  safety_class VARCHAR(20),
  air_density NUMERIC(5,3),
```

### 7.2 多模型路由（成本/质量平衡）

| 任务 | 模型档位 | 理由 |
|---|---|---|
| 招标解析（结构化抽取） | 大（72B / GPT-4 级） | 精度优先 |
| 目录生成 | 大 | 精度优先 |
| 素材缺口识别 | 中 | 分析成本与精度平衡 |
| 章节填充 | 中（32B / Qwen3-32B 级） | 吞吐优先 |
| 摘要生成（wiki） | 小（7B-14B） | 成本优先 |
| **编辑辅助（实时触发）** | **小** | **延迟优先,高频调用** |
| 格式清洗（判断） | 小 | 成本优先 |

网关支持多模型路由时直接按任务选；若网关固定单模型，预留接口日后切换。

### 7.3 失败与降级

- Celery 任务级重试（指数退避）
- 章节级并行度可配置，网关限速时自动降并发
- LLM 输出格式错误 → 结构化重试 prompt

## 八、文档处理管线

### 8.1 多格式统一入口

```python
def parse(file_path: str) -> StructuredDoc:
    mime = detect_mime(file_path)
    if mime == "docx":
        return DocxParser().parse(file_path)
    elif mime == "pdf":
        if has_text_layer(file_path):
            return PdfPlumberParser().parse(file_path)
        else:
            return MineruParser().parse(file_path)   # 扫描件混合
    elif mime in ("jpeg", "png"):
        return OcrParser().parse(file_path)          # PaddleOCR
```

### 8.2 关键工具选型

| 工具 | 用途 | 理由 |
|---|---|---|
| **python-docx** | .docx 读写 | 标准 |
| **pdfplumber** | 有文本层 PDF 解析 | 对表格还原好 |
| **MinerU** | 复杂 PDF / 扫描件混合 | 当前中文 PDF 解析最好的开源方案 |

### 8.3 附表识别（专用路径）

1. 扫描解析后的文档节点树

3. 保留完整 `table` 节点（表头/行/列结构）
4. 在 Word 内标 `is_owner_attachment=True`（metadata）
5. 填充阶段走 `fill_attachment_table` skill，绝不让 LLM 重写表结构

## 九、格式 100% 合规实现

### 9.1 核心原则：模板 + 代码，绝不让 LLM 碰格式

**为什么**：
- LLM 输出格式不可控（有时写字体、有时不写、写错字号）
- LLM 无法感知 Word 样式体系（`Heading 1`、`TableContent` 这类样式名）
- 格式错误零容忍（"格式合规率 100%"），LLM 容错达不到

### 9.2 标准样式模板

预制 `bid_template.dotx`：
- 内置 `Heading 1–5` 样式，严格按需求文档规范配置字体/字号/段前段后/缩进/多级编号
- 内置 `Normal`、`TableContent`、`TableCaption`、`FigCaption`、`PageHeader`、`PageFooter`
- 页面设置：A4、边距 2.54/3.18、装订线左 0cm
- 页眉占位：logo + 项目名+风机投标文件-技术卷
- 目录域 TOC（3 级、带页码、超链接、可更新）

### 10.1 数据流


```python
@app.middleware("http")
async def audit_middleware(request, call_next):
    user = get_current_user(request)
    before = capture_state(request)
    response = await call_next(request)
    if response.status_code < 400 and is_write(request):
        await log_audit(
            user_id=user.id,
            action=f"{request.method} {request.url.path}",
            resource_type=extract_resource_type(request),
```

## 十三、技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 公司 LLM 网关限速/不稳 | 填充任务卡壳 | Celery 重试 + 章节级并发降级 + LLMClient 抽象便于切换 |
| 附表 OCR 精度不足（扫描件） | 附表准确率 <95% | PaddleOCR + MinerU 双路召回 + 关键字段人工确认 |
| 评分点识别漏抽 | 覆盖校验失效 | 多轮 prompt + 人工抽检 + 建立评测集持续监控 |
| 格式不合规 | 格式合规率失守 | 预制样式模板 + 代码应用 + 导出前校验脚本 + 禁止 LLM 生成格式 |
| **OnlyOffice 授权** | 社区版 AGPL+20 连接限制,国企不可接受 | P0 用 Community 验证集成;P2 采购 Developer Edition 正式上线 |
| 素材库冷启动 | 上线后无内容可填 | 提供批量导入工具 + 交付"素材库初始化手册" + 示范项目预置 |
| **Excel 字段不规范** | 导入失败或数据脏 | 强校验 Pydantic + 逐行错误报告 + JSONB 扩展字段兜底 |
| **缺口识别漏判** | 填充时仍发现缺素材 | 评测集 + 填充阶段再做一次 precheck 作为二道关 |
| **编辑辅助 AI 与用户打架** | 体验差 | typing 状态互斥 + AI 动作范围限定格式类 + 撤销栈 |
| **opencode 版本升级破坏兼容** | plugin/SDK 接口变化 | 锁定次版本号 + 升级前评测集回归 + 把 HTTP 调用保持在 plugin tool 层,业务逻辑不受影响 |
| **opencode 产品方向偏离** | 社区聚焦 coding 场景,非我们领域需求 | plugin 层是薄壳,换 runtime 成本可控；关键路径有评测集保证 |
| **opencode <-> FastAPI 联调复杂** | 开发周期长 | P0 先跑通最小闭环(1 个 tool 端到端)；OpenAPI 代码生成减少手工联调 |
| **双进程故障排查** | 出问题难定位 | 统一请求 trace id (FastAPI ↔ opencode ↔ tool) + 集中日志 |
| **Bun 运行时国企陌生** | 运维技能缺口 | 文档化 Bun 常见命令; Bun 本质是 Node 替代,排查路径相似 |
| LLM 对企业数据窃取 | 合规 | 全链路内网 + 网关对接企业侧管控 |
| Agent 失控长循环 | 资源浪费 / 成本 | agent loop 硬性 max_steps 上限 + timeout + 工具调用频控 |
| 项目信息不一致 | 响应规则违反 | 统一 fact table + 禁止硬编码 + 全文扫描校验 |
