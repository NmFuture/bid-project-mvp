## 一、背景与现状

事实表 v2（148 清单 spec 骨架 + 专项抽取器 + 七态模型）已合入本地分支 `feature/project-fact-table-20260723`（rebase 至 origin/Dev 33a13c0），PRJ-0007 实测：

- 字段数 133→141，其中 88 个自动提取、9 个待人工确认、9 个已确认
- 35 个字段未提取，全部为"清单-招标文件"类（可利用率、招标单机容量、塔筒型式等）

当前痛点：

1. **触发靠人工/外部 AI**：素材入库、点按钮、修数据都是手动动作，正常流程不应依赖
2. **招标文件类字段无自动通道**：S1 解析白名单只覆盖约 10 个 fieldKey，剩余 35 个每项目都要手填
3. **抽取值存在脏数据**：如"年平均风速"被抽成 `7.36/6.86/7.20 风电场保证年上网电量(MWh)`（表格跨列串行），目前只能靠人工复核兜底

已修复（本分支）：`technical_gap_service.build_facts/save_facts` 事件循环内同步构建导致素材查询被静默吞掉的 bug（改 `asyncio.to_thread` + 异常日志）；素材 tier 元数据与目录不一致导致项目范围查不到。

## 二、目标与原则

- 正常项目流程零手工触发：**传素材 → 自动构建 → 人工复核 → AI 填写**
- 确定性工作（建骨架、路由、抄数）留在代码，不交给 LLM
- LLM 只做需要判断力的三件事：长尾字段补抽、脏数据清洗、口径歧义建议
- AI 产出一律 `pending_confirmation`，**confirmed 只能由人工在界面点出**（现有硬门禁不变）

## 三、方案 A：代码自动触发（确定性链路）

### A1. 触发点

| 触发事件 | 挂接位置 | 动作 |
|---|---|---|
| 缺口识别完成 | `technical_gap_service.py` 中 `recognitionStatus` 置 `completed` 处（约 line 179） | 后台任务执行一次 `build_facts` |
| 项目定制素材入库 | `technical.py` 素材写操作完成后：raw 上传（line 671）、移动（line 823）、批量移动、文件夹移动 | 对该素材所属 project 触发 `build_facts`（防抖合并，见 A3） |
| 事实表 spec 更新 | `POST /api/settings/technical-fact-specs` 上传成功后 | 提示"受影响项目需重建"，不自动全量重建（避免惊扰已确认结果） |

### A2. 后台执行

- 复用现有 worker/后台任务机制（参考 OCR 任务异步模式），不在请求线程内跑构建
- 构建失败显式记录到 gap_state（`factBuildError`），前端可见，不静默

### A3. 防抖与重入

- 同一 projectId 60 秒内多次触发只跑一次（批量上传/移动会连发）
- 构建期间再次触发 → 标记 `pendingRebuild`，本次完成后补跑一次

### A4. 完整率反馈（前端）

事实表弹窗顶部加汇总条（数据已有：`summary.specTotal / unextractedCount` 等）：

```
清单 128 字段：已提取 88 · 待确认 9 · 未提取 35
未提取按来源分组提示：
  清单-招标文件 25 → "将由事实表维护 Skill 补抽"（方案 B 落地后）
  清单-项目定制材料 10 → "缺素材：请上传 风资源报告 / …"（按 spec.referenceFile 提示）
```

## 四、方案 B：OpenCode Skill `bid-tech-fact-curator`（事实表维护）

### B1. 定位

技术标事实表的"AI 复核员"，在自动构建之后、人工确认之前运行。遵循 `opencode/skills/STAGES.md` 的阶段约定，目录 `opencode/skills/bid-tech-fact-curator/`。

### B2. 职责（三件事）

1. **长尾补抽**：对 `unextracted` 且 `sourceKind=tender` 的字段（当前 35 个，如可利用率、招标单机容量、塔筒型式），读招标文件解析产物/原文找值，产出候选值 + 证据出处
2. **脏数据清洗**：对 `extracted` 字段做合理性校验（单位、量纲、数值范围、串行文本如"7.36/6.86/7.20 风电场保证年上网电量"），拆错列、改错值的给出修正建议
3. **口径建议**：15 条 `needsConfirmation` 字段读原文给出建议答案（如承诺函版本保证值/考核值），附引用页码

### B3. 输入/输出契约

- 输入 manifest：projectFactTable（全量字段 + spec 元数据）、招标文件解析产物路径、相关素材路径，由后端组装（复用 `technical_gap_ai_fill.py` 注入 fact table 的模式）
- 输出：逐字段 `{fieldKey, suggestedValue, unit, evidence, confidence, action: fill|fix|confirm-advice}`
- 后端回收后一律置 `pending_confirmation` 并写 sourceRefs（type: `factCurator`），**不直接写 confirmed**；人工在界面逐条确认或改值

### B4. 边界（写进 SKILL.md）

- 只处理 manifest 给定的字段和文件，禁止全库搜索、禁止编造事实
- 找不到值 → 保持 `unextracted` 并在 notes 写原因，不硬填
- frontmatter：`description` 中文触发条件式；`allowed-tools: [Read, Bash, Write]` 按需收敛；SKILL.md 控制在 100~200 行，细则拆 `references/`

## 五、整体时序

```
用户上传项目素材 ──► 素材写操作完成 ──► [A1 防抖] ──► 后台 build_facts
缺口识别完成 ──────────────────────────┘              │
                                                       ▼
                                        事实表：骨架 + 自动提取（代码）
                                                       │
                                          [B] bid-tech-fact-curator
                                                       ▼
                                  补抽/清洗/口径建议 → pending_confirmation
                                                       │
                                          人工界面逐条确认（硬门禁）
                                                       ▼
                                     整表 confirmed → AI 填写放行（现有链路）
```

## 六、任务拆分

| # | 任务 | 改动点 | 验收 |
|---|---|---|---|
| T1 | build_facts 后台化 + 防抖 | `technical_gap_service.py`、任务调度 | 连续触发 3 次只构建 2 次（首次+补跑） |
| T2 | 缺口识别完成自动触发 | `technical_gap_service.py` line 179 附近 | 识别完成后无需点按钮事实表即生成 |

| T5 | `bid-tech-fact-curator` skill | `opencode/skills/bid-tech-fact-curator/`、`opencode_client.py` 加 `run_bid_tech_fact_curator_with_trace` | 35 个 tender 字段补抽命中率 ≥ 70%，产出全为 pending_confirmation |

## 八、风险与边界

- 已 confirmed 字段在自动重建中不可被覆盖（现有 reconcile 已保证，T1~T3 必须回归验证）
- 整表插入类（工程量表、弯矩表 75 行）不走事实表，仍走 table-filler 同形表移植，不在本方案
- spec 更新只走设置页上传 + 人工触发重建，不自动全量重建
- 事实表 spec 的"清单-认证证书"4 字段依赖证书 PDF 文本层/OCR，命中率另行评估
