# 技术标 S1 解析异步化改造方案

> 日期：2026-07-19 ｜ 状态：**已实施**（P0–P3 全部落地，见 §6 实施记录与 §7 验证结果）
> 配套链路图：`docs/20260719-技术标S1解析链路-现状.html`（现状）与 `docs/20260719-技术标S1解析链路-异步改造.html`（目标），可并排打开对比。
> 事实来源：sewpg-bid-backend / sewpg-bid-frontend 代码走查（结论均带 文件:行号）。

## 1. 诉求与目标

- 长时间解析改为**后台异步运行**：页面切换不中断解析，用户无需停留等待。
- 前端能看到**后端进行到哪一步**：进度展示 + 用户摘要信息（真实信息为主、安慰剂文案兜底）。

## 2. 现状关键事实（调研结论）

### 2.1 执行模型：请求内同步

- `/parse/technical` 页面对应 `TechnicalTenderReview.jsx`（routes.jsx:27-29），「上传并解析」调 `POST /api/technical/projects/{id}/parse-results/upload-and-run`（technical.py:171）。
- `upload_and_parse`（bid_parse_service.py:2003-2060）在请求协程里保存文件后 `await asyncio.to_thread(parse_tender_documents)`（bid_parse_service.py:60-75）——**HTTP 请求挂到解析结束才返回**。无队列、无后台任务。
- 前端请求 5 分钟超时、不重试（api/index.js:366-373）；超时后进入 2 分钟恢复轮询（technicalParseUploadRecovery.js:168-217），仍不完提示「解析仍在后台运行」。
- 客户端断开只 abort HTTP 等待，解析线程继续跑（TechnicalTenderReview.jsx:763-765）；重进页面可恢复轮询（:661-668）。**但进程重启线程即丢失**，只剩 stale 标记，无续跑。

### 2.2 进度机制（已较完善，可整体保留）

- 进度状态 `parse_progress` 挂在项目 JSONB 上（bid_parse_state.py:112），前端 1s 轮询（TechnicalTenderReview.jsx:797）。
- 分段映射：extract 8→24/42%、local_structure 24→34%、appendix 34→62%、prepare 62→68%、structured 68→96%、finalize 96→100%（bid_parse_service.py:302-319）。
- 心跳 10s（parsing.py:359-393 / opencode_client.py:21）；阶段超时无心跳判 `stale`；前后端双单调不回退；事件日志保留最近 80 条。
- **成本点：每次进度事件都整行 JSONB upsert Postgres（bid_parse_service.py:1816）。**

### 2.3 失败重试（现状薄弱）

- opencode 层：首次失败后用「恢复重试」prompt 重试 1 次（parsing.py:6224-6274）；技术标再失败降级本地兜底，商务直接抛错。session 创建对 429/5xx 最多重试 6 次（opencode_client.py:24-25,45-54）。
- **任务级重试：无。** Redis worker 对目录/正文任务也是失败即置 failed，不重试（redis_worker.py:92-95）。

### 2.4 可复用的异步基建（已存在，S1 解析未接入）

- `job_queue.py`：Redis 队列（list `bid:jobs` + 状态 hash `bid:job:{id}` + 项目锁 `bid:lock:{type}:{project}` + in-flight 登记 + `reclaim_stale_inflight_jobs` 崩溃回收），Redis AOF 持久化（docker-compose.yml:297）。
- `redis_worker.py`：独立容器 `sewpg_bid_worker`，BLPOP 消费 + 心跳续锁。
- `local_job_executor.py`：Redis 不可用时本地单线程串行兜底。
- 已接入：directory_generation、fill_generation、material_cleaning（job_queue.py:19 `KNOWN_JOB_TYPES`）。**扩展路径现成：注册新类型 + worker 加分支。**

### 2.5 并发缺陷

- 同项目解析**无锁**：仅靠前端按钮 disabled，多标签/竞态会并发覆盖同一项目状态。
- opencode 并发=1 是进程内信号量（opencode_client.py:23），多 worker 下无全局约束（当前默认单 worker，可接受）。

### 2.6 彭维锋相关代码盘点（用户点名核查）

## 3. 改造方案

总体思路：**解析引擎（parsing.py 六个阶段、进度协议 bid_parse_state.py）一行不动，只把「触发方式」从请求内同步改为入队**，复用 job_queue 三件套，与目录/正文生成统一范式。

### 3.1 后端改动

| # | 改动 | 位置 |
|---|---|---|
| 1 | `KNOWN_JOB_TYPES` 注册 `s1_parse` | job_queue.py:19 |
| 2 | worker 增加 `s1_parse` 分支：调 `parse_tender_documents`（带 cancel_check / progress_callback） | redis_worker.py `_run_job` |
| 3 | `upload_and_parse` 改为：保存文件 → 加锁 → 入队 → 返回 202 `{jobId, status:"queued"}`；锁冲突返回 **409「解析进行中」** | bid_parse_service.py:2003 |
| 4 | `run_without_upload` 同样改为入队；**商务标补齐 `parse-results/run` 端点** | bid_parse_service.py:1931、business.py |
| 5 | 进度写库节流：跨阶段/终态必写 Postgres，阶段内 ≥1s 且百分比变化 ≥1 才写；内存态保持实时（前端轮询无感） | bid_parse_service.py:1816 附近 |
| 6 | job 级重试：可重试错误（opencode 429/5xx、连接错误、DB 瞬断）退避 ≤2 次（30s/120s），attempt 写入 `bid:job:{id}` 与 parse_progress；确定性错误（文件损坏/格式不支持）直接 failed + 用户可读 summary | redis_worker.py / job_queue.py |
| 7 | 崩溃恢复：复用 `reclaim_stale_inflight_jobs`（worker 每 300s 回收残留置 failed） | redis_worker.py:27 |

说明：保存上传文件必须留在请求内（文件流不可转移给 worker），这部分秒级完成，用户无感。

### 3.2 前端改动

| # | 改动 | 位置 |
|---|---|---|
| 1 | 上传请求改为短超时（只覆盖上传+入队）；拿到 202 后进入既有 1s 轮询（`shouldPollParseProgress` 已覆盖 queued/running，technicalParseUploadRecovery.js:127-133） | api/index.js:366、TechnicalTenderReview.jsx |
| 2 | 解析进行中允许自由切换页面：全局顶条「技术标解析进行中 · N%」；重进页面自动恢复（复用 loadCurrentProject 逻辑） | AppShell / 项目上下文 |
| 3 | 完成/失败 toast；失败给「重新解析」按钮（调 `parse-results/run`，前端目前未接线） | TechnicalTenderReview.jsx |
| 4 | **进度摘要卡**（见 §3.3） | 解析进度区 |

### 3.3 进度展示与「安慰剂」摘要

- 真实信息层（数据均已存在于 progress payload / events）：
  - 阶段进度条（phaseLabel + 百分比，单调不回退）；
  - 当前处理对象（文件名 / 第几个附表）；
  - 阶段产出计数：已识别附表 N 个、清单已解读 N/58 条（opencode parts 计数已在 `_opencode_progress_from_payload` 用于进度估算）；
  - 已耗时 + 预计剩余（按阶段区间或历史均值估算，标注为预估）。
- 安慰剂层（无细分信号阶段，如 AI 解读期）：
  - 心跳微推进（沿用现有 heartbeat credit 算法，不回退）；
  - 按阶段预置的轮播安心文案（如「AI 正在逐条核对技术要求…」「正在追溯『详见第三卷』引用来源…」）——**只描述阶段动作，不编造数据**；
  - 明确提示「解析在后台进行，可随时离开本页」。

### 3.4 分步实施

- **P0**：注册 `s1_parse` 入队 + 项目锁 + 409 + 202 返回 + worker 分支（核心异步化）。
- **P1**：job 级退避重试 + 进度写库节流 + inflight 崩溃回收验证。
- **P2**：前端摘要卡 + 全局进度条 + 「重新解析」按钮接线。
- **P3**：商务标对齐（补 `parse-results/run` 端点、同一套异步链路）。

## 4. 新旧对比

| 维度 | 现状 | 改造后 |
|---|---|---|
| 执行模型 | HTTP 请求内同步（to_thread 挂起） | Redis 队列 + worker，202 立即返回 |
| 用户等待 | 需停留；5min 超时后提示割裂 | 随时离开，全局进度条 + 完成通知 |
| 任务持久化 | 无（线程随进程死亡，仅 stale 标记） | Redis AOF + inflight 崩溃回收 |
| 同项目并发 | 无锁，可并发覆盖 | `bid:lock:s1_parse:{project}` + 409 |
| 失败重试 | 仅 opencode 内层 1 次 | 内层 1 次 + job 层退避 ≤2 次 |
| 进度写库 | 每事件整行 JSONB upsert | 节流（≥1s 且变化 / 跨阶段 / 终态） |
| 进度展示 | 阶段进度条 | 进度条 + 摘要卡（产出计数/耗时预估/安心文案） |
| 商务标 | 无 run 端点、无重新解析入口 | 补齐端点，同一套异步链路 |

## 5. 风险与注意点

- **opencode 并发**：解析移入 worker 后，与目录/正文生成共用 worker 内 opencode 信号量（=1），AI 阶段仍是全局串行点；吞吐量瓶颈在 AI 而非队列，可后续按 worker 数调。
- **本地兜底无持久化**：Redis 不可用时 submit_local_job 纯内存，进程重启丢任务——与目录/正文生成现状一致，接受。本地兜底模式下 `is_generation_locked` 返回 False（无锁），同项目并发防护退化为与原同步链路一致。
- **取消链路需回归验证**：worker 模式下 cancelRequested 经 Postgres 项目状态传递，心跳/阶段边界检查不变，需测「取消→opencode abort_session」全链路。
- **与彭维锋代码的协调**：改动集中在他的解析线模块，且 pwf 分支（92d37b6）刚合入、fdcd177 有附表入库新改动——动手前 rebase 最新 Dev，PR 拉他 review。
- **范围外**：技术标缺口识别（technical.py:308 同步路由）、OCR、证书增量扫描等也是请求内同步长任务，可后续按同模式推广，不在本次范围。
