## 0. 一句话总览

技术标素材库维护一份 **动态重建的三级目录 JSON 索引**（`technical_material_index.json`）。
它是整套系统的 **地基/约定层**：素材一变，索引自动重建；下游的「解析弹窗候选」「Wiki 目录树」「标签」全部以它为唯一来源。

```
                    ┌─────────────────────────────────────────┐
   上传/移动/删除素材 → │  technical_material_index.json (地基)     │
   (结构真值=Postgres)  │  tiers → folders → files，schemaVersion=2 │
                    └───────────────┬─────────────────────────┘
                                    │ 所有下游都读这份 JSON
              ┌──────────────────┬──┴───────────────┬──────────────────┐
              ▼                  ▼                  ▼                  ▼
        解析弹窗候选        技术标 Wiki 目录树      标签 (tag)         项目解析等
     (客户/机型下拉)     (确定性镜像三级结构)    (真值就在 JSON)
```

## 1. 地基：三级目录 JSON 索引

### 1.1 它是什么

- **结构**：一级=档位（tier），二级=三级目录（folder），三级=文件（file）。
- **结构真值在 Postgres**（`raw_folders` / `raw_files`），文件字节在 MinIO。**这份 JSON 只是结构的快照/索引**，不存原始字节。
- **确定性生成**：从数据库实时重建，**不走 LLM**。
- 当前 `schemaVersion = 2`：从 v2 起 **标签(tag) 的真值也落在这份 JSON 里**（见第 4 节）。

### 1.2 它在哪

| 项 | 值 |
|---|---|
| 容器内路径 | `/data/documents/_runtime/materials/technical_material_index.json` |
| 所在卷 | Docker named volume `documents`（`DOCUMENTS_DIR=/data/documents`） |
| 代码常量 | `app/services/technical_material_index.py` → `TECHNICAL_MATERIAL_INDEX_PATH` |
| 只读接口（推荐） | `GET /api/technical/materials/index`（空则即时重建再返回） |

> ⚠️ 这是数据卷里的运行期产物，**宿主机源码目录下看不到**。要直接看文件：
> ```bash
> docker exec sewpg_bid_fastapi cat /data/documents/_runtime/materials/technical_material_index.json
> ```

### 1.3 JSON 结构（schemaVersion = 2）

```jsonc
{
  "bidType": "技术标",
  "schemaVersion": 2,
  "tagsSourceOfTruth": "index",          // ← 标记：tag 真值在本 JSON
  "generatedAt": "2026-06-19 10:30:00",  // 重建时间，可据此判断新鲜度
  "stats": { "tierCount": 3, "thirdLevelFolderCount": 8, "fileCount": 526 },

  "tiers": [                             // 2 级档位数组，固定 3 档
    {
      "name": "标准文件",                 // 2 级目录真实名（见第 3 节）
      "tier": "standard",                // 归一后的档位：standard|customer|project
      "path": "技术标/标准文件",
      "folderId": "...",                 // 档位级 tag 认领键
      "fileCount": 324,
      "tags": [],                        // ① 档位级 tag
      "folders": [                       // 3 级目录数组（动态）
        {
          "name": "EW5.0-220",
          "path": "技术标/标准文件/EW5.0-220",
          "tier": "standard",
          "folderId": "...",             // 目录级 tag 认领键
          "customerName": "",            // customer 档才有值
          "projectId": "",               // project 档才有值
          "customerId": "", "projectCode": "", "description": "",  // 占位，恒空，勿依赖
          "fileCount": 12,
          "updatedAt": "2026-06-19 10:30:00",
          "tags": [],                    // ② 目录级 tag
          "files": [
            {
              "id": "RAW-0369",          // 文件级 tag 认领键

              "path": "技术标/标准文件/EW5.0-220/专题/.../发电机位移监测分析系统.docx",  // 完整路径
              "ext": "docx",
              "cleanStatus": "cleaned",  // cleaned|pending|original_only|failed
              "tags": [],                // ③ 文件级 tag（真值在此 JSON）
              "preview": {               // AI 内容预览（仅 docx、生成成功时才有，见第 5 节）

  ]

## 2. 动态更新：素材一变，JSON 怎么自动刷新

这是整套系统的核心机制。**任何改素材结构的操作完成后，钩子会自动重建索引，无需手动触发。**

### 2.1 触发时机（写盘时机）

| 触发方式 | 说明 |
|---|---|
| **自动（主路径）** | 素材库任何**改结构**的操作——上传、移动/删除目录、移/删文件、拆分、改名、项目 bootstrap——完成后，钩子 `TechnicalMaterialStore._refresh_index` 自动重建。 |
| **兜底** | 调只读接口 `GET .../index` 时若文件为空，即时重建一次再返回（保证「拿到的一定是最新」的标准做法）。 |

### 2.2 重建是怎么做的（merge-preserve）

重建 = **结构从 DB 实时取 + tag/预览从旧 JSON 贴回**：

1. **结构**（有哪些档位/目录/文件、谁移动了）→ 每次从 **数据库** 实时读，保证结构永远是最新。
2. **tag** → 从 **旧 JSON** 按认领键贴回新树（文件认 `RAW-id`、目录认 `folderId`，与 path 无关 → 改名/移动不丢 tag）。
3. **AI 预览** → 从 DB 缓存（`ext_fields.techWikiPreview`）按内容指纹增量注入（见第 5 节）。
4. **原子写 + 进程锁**：先写 `.tmp` 再 `os.replace`；rebuild 与「人工打 tag」串行，避免并发写丢数据。

### 2.3 `preview_mode` 三态（决定重建时要不要调 LLM）

重建时通过 `preview_mode` 控制是否生成 AI 预览，这是「快」与「慢」解耦的关键：

| 模式 | 行为 | 用在哪 |
|---|---|---|
| `none` | 完全跳过预览，只重建结构 + 认领 tag | **结构变更钩子**（上传/移动/删除，很频繁） |
| `cached` | 只读 DB 已生成预览注入，**不调 LLM（秒级）** | 重建/刷新 Wiki、人工打 tag 兜底重建 |
| `generate` | 增量调 LLM 补齐缺失预览（慢） | **后台预览任务**（见第 5 节） |

> 即：日常上传/删除走 `none`（秒级、不烧钱），点「重建 Wiki」走 `cached`（秒级），真正调 LLM 的重活只在后台任务里 `generate`。

### 2.4 深层文件归并规则（重要）

- 4 级及更深目录里的文件，会被**归并到所属的 3 级祖先目录** 的 `files[]` 下（贯彻「3 级为基准」），但每个 file 的 `path` 保留**完整原始路径**，不丢深层信息。需要还原层级时解析 `file.path`。
- 直接挂在 2 级目录下（无 3 级祖先）的散落文件**不出现在任何 folder 的 `files[]`**，也不计入 `fileCount`。
- `stats.fileCount` = 所有 3 级目录文件数之和（已归并的有效文件）。

## 3. 三个档位（tier）的语义 ⚠️ 下游务必读 tier 字段

技术标 2 级目录的**真实命名**与直觉不同，**判档请读已归一的 `tier` 字段**，不要靠中文目录名硬判：

| 2 级目录真实名 | `tier` 值 | 含义 | 3 级目录名的含义 | 回填字段 |
|---|---|---|---|---|
| `标准文件` | `standard` | 通用/平台标准素材 | 机型号或分类（如 EW5.0-220） | — |
| `客户定制` | `customer` | 按客户区分 | **客户名** | `customerName` |
| `项目定制` | `project` | 按项目区分 | **项目标识** | `projectId` |

- `tier` 由后端 `normalize_material_tier()` 归一，覆盖「标准文件/客户定制/项目定制」及历史别名「通用素材/客户素材/项目素材」。
- `customerId` / `projectCode` / `description` **恒为空字符串**（占位待回填），**下游不要依赖它们**；要客户/项目身份就用 `customerName` / `projectId`。

## 4. 以 JSON 为地基（一）：标签 tag

### 4.1 原则

> **每级节点（档位/目录/文件）各挂一个 `tags` 数组，记录“这一级自己的标签”。不向上聚合、不向下继承。** tag 的**真值 = 这份 JSON 自身**（`tagsSourceOfTruth: "index"`）。

| 层级 | tag 字段 | 认领键（rebuild 时靠它贴回） |
|---|---|---|
| 档位 tier | `tags` | `folderId`（数字字符串） |
| 三级目录 folder | `tags` | `folderId` |
| 文件 file | `tags` | `id`（`RAW-xxxx`） |

### 4.2 怎么读/写 tag

- **写**：`PUT /api/technical/materials/index/tags`，body `{ "targetId": "<节点>", "tags": ["标签1","标签2"] }`。
  - `targetId`：`RAW-xxxx` → 文件；数字 folderId 或目录 path → 档位/三级目录。
  - `tags` 经 `normalize_material_tags` 规整（去重去空、单条≤40字、≤20个；也支持传 `"a,b,c"` 字符串自动切分）。
  - 传空数组 `[]` = 清除该节点 tag。
- **读**：直接读 `GET .../index`，tag 就在每级节点的 `tags` 字段里。

> ⚠️ 数据库 `raw_files.ext_fields.tags` **已不再是 tag 真值**（只在首次迁移时当种子灌一次）。**技术标 tag 一律走 JSON 索引接口**，不要直接写 DB 的 `ext_fields.tags`（写了不进索引 = 没生效）。
> 仍读/写旧 DB tag 的历史点（暂未改、用到时注意）：`material_raw_file_filter.py`、`wiki_generation.py`（读）、`material_update_metadata.py`、`material_tag_import*.py`（写）。

### 4.3 改名/移动会不会丢 tag

不会（认领键稳定即可）：文件改名/移动 → 认 `RAW-id`，tag 跟随 ✅；目录改名/移动 → 认 `folderId`，tag 跟随 ✅；文件真删 → tag 随之消失（合理）；新上传/新建 → tag 默认空 `[]`。

## 5. 以 JSON 为地基（二）：技术标 Wiki 目录树

### 5.1 Wiki = 索引的确定性镜像

技术标 Wiki（`/workspace/tech/materials/wiki`）的目录树 **严格等于** 三级目录 JSON 索引，**不经过 LLM 编排结构**：

```
技术标Wiki（自动生成）              ← 根节点
├── 01-标准文件 (standard)          ← 一级 = 档位 tier
│   └── EW5.0-220                   ← 二级 = 3 级目录（机型号/分类）
│       └── 发电机位移监测分析系统.docx   ← 三级 = 文件卡片
├── 02-客户定制 (customer)          ← 二级目录名 = 客户名
└── 03-项目定制 (project)           ← 二级目录名 = 项目标识
```

档位固定顺序 standard → customer → project（脚本 `TIER_ORDER` 控制）。Wiki 在 DB 里是三张表：`wiki_nodes`（树，`parent_id` 自引用）、`wiki_docs`（节点 Markdown 正文）、`wiki_attachments`（附件，MinIO key）。

> **唯一用到 LLM 的地方**：给每个 docx 文件卡片生成「内容预览」（导读/要点/关键参数/检索提示），是可选增强，失败只降级成纯目录卡片，不影响树生成。

### 5.2 生成链路（四步，第 ③ 步不碰 DB / 不调 LLM）

```
POST /api/technical/materials/wiki/bootstrap
  │  generate_platform_wiki → 技术标短路到 _generate_technical_wiki
  ▼
① 重建索引 JSON  rebuild_technical_material_index(preview_mode="cached")  ← 秒级，不调 LLM
  ▼
② 写 manifest  _write_technical_index_manifest()  （把索引包成临时构建文件）
  ▼
③ 镜像脚本生成 blueprint  run_from_manifest.py (subprocess，纯模板)
     索引 JSON → {summary, rootTitle, nodes[三层树]}，每个 file → 一张 Markdown 卡片
  ▼
④ 导入 DB  _mirror_technical_index_to_wiki / _import_generated_wiki_blueprint
     mode=replace：删同名旧根整棵树重建；refresh：只换自动生成子节点保留根
```
返回 `generation.generator = technical_index_mirror`，`summary` 给「N 档位 / M 目录 / K 文件」。

### 5.3 两个按钮

- **重建 Wiki**（修树用，`mode=replace`）：按当前素材库三级结构重新镜像。**秒级返回**（走 `cached`，不等 LLM）。
- **刷新 Wiki**（`mode=refresh`）：只替换自动生成子节点，保留根。

> 素材库目录变动后点「重建 Wiki」即可对齐。命令行：
> ```bash
> curl -s -X POST http://localhost/api/technical/materials/wiki/bootstrap \
>   -H 'Content-Type: application/json' -d '{"mode":"replace","bidType":"技术标"}'
> ```

### 5.4 文件卡片的 AI 预览（异步后台生成）★ 当前口径

**重建 Wiki 秒级返回，不在请求里跑 LLM**；预览由独立后台任务增量补齐，避免 HTTP 超时（历史上 500+ 文件 ×15s 同步跑会超时丢预览，已改异步）：

```
①「重建Wiki」秒级返回（preview_mode="cached"，缺预览的 docx 先降级为纯目录卡片）
②  前端自动触发后台任务  POST /api/technical/materials/wiki/previews/generate  → Redis 队列
③  worker 后台增量生成（preview_mode="generate"，不受 HTTP 超时约束）
       命中内容指纹缓存的不重算；进度落盘；前端 3s 轮询 GET .../wiki/previews/status
④  全部跑完 → 用 _mirror_technical_index_to_wiki(mode="replace") 重镜像 → 前端轮到 completed 自动 reload
```

预览机制要点：
- **增量缓存**：缓存在 DB `ext_fields.techWikiPreview`，按内容指纹（文件名+Heading+正文摘录）判定，内容没变就复用。实测首次约 15s/文件、命中缓存约 0.4s。
- **任务全局单例**：Redis job 锁（`job_type=technical_wiki_preview`），同一时刻只跑一个；前端首屏探测在跑的任务自动续上轮询。
- **best-effort 降级**：非 docx / 超 30MB / 解析失败 / LLM 超时 → 退回纯目录卡片，不阻断镜像。

**卡片对比**：无预览只有「文件定位/所属档位/索引说明」；有预览时卡片顶部多一段「## 内容预览（AI 生成）」（导读 + 要点 + 关键参数表 + 检索提示）。

### 5.5 怎么读 Wiki（API）

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/technical/materials/wiki` | 取整棵树（只有结构 `id/title/icon/expanded/children`，正文不在树里） |
| `GET` | `/api/technical/materials/wiki?nodeId=WIKI-xxx` | 取单节点 `selectedNode.markdownContent`（前端渲染这个） |
| `POST` | `/wiki/bootstrap` | 生成/重建整棵 Wiki |
| `POST/PUT/DELETE` | `/wiki`、`/wiki/{id}`、`/wiki/{id}/move` | 手动建/改/删/移节点 |
| `POST` | `/wiki/previews/generate` ｜ `GET` `/wiki/previews/status` | 触发/轮询后台预览任务 |

典型读取：先 `GET wiki` 拿树 → 用户点节点 → `GET wiki?nodeId=xxx` 拿 markdown → 前端渲染。
商务标把 `technical` 换成 `business`，接口一致（但商务标走 **LLM 编排** 树，不在本索引体系内）。

## 6. 以 JSON 为地基（三）：解析弹窗候选项

页面 `/parse/technical` 的「新建/完善技术标项目」弹窗（`TechnicalProjectWizardModal`），两个下拉**实时从 JSON 索引派生**：

| 下拉 | 候选来源 | 末尾固定追加 |
|---|---|---|
| **客户** | `tier==='customer'` 各 folder 的 `customerName`（回退 `name`） | 「其他」手动输入 |
| **风机机型** | `tier==='standard'` 各 folder 的 `name`（机型号） | 「其他」手动输入 |

- 数据源：`GET /api/technical/materials/index`（前端 `technicalMaterialsAPI.index()`），**每次挂载实时拉取**。
- 派生纯函数（`src/workspaces/shared/projectInfoOptions.js`）：`deriveCustomerOptionsFromIndex` / `deriveTurbineModelOptionsFromIndex` / `OTHER_OPTION_LABEL`，保证「其他」恒为最后一项且只出现一次。
- **兜底**：接口失败 → 回退静态常量 `STATIC_CUSTOMER_OPTIONS` / `STATIC_TURBINE_MODEL_OPTIONS`，弹窗仍可用。
- **编辑/草稿恢复**：已存的客户/机型若不在最新候选内，自动进入「其他」态显示原值，不丢数据。
- 前端 Vite 改动热更新即生效（本块未触碰后端，无需 rebuild docker）。
