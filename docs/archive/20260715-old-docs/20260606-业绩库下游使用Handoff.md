# 业绩库下游使用 Handoff

## 1. 结论先行

当前业绩库有两条链路，需要下游区分使用：

| 链路 | 数据表 | 主要用途 | 下游建议 |
| --- | --- | --- | --- |
| 新业绩包链路 | `performance_categories`、`performance_items`、`performance_attachments`、`performance_item_attachments` | 汇总表导入、合同包上传、项目级合同拆分、按项目明细引用 | 后续主推使用 |
|              |                                                              |                                                        |              |

下游如果要拿“业绩分类、明细行、项目级合同附件”，优先调用：

```text
GET /api/materials/performance/categories
GET /api/materials/performance/categories/{categoryId}
GET /api/materials/performance/categories/{categoryId}/items/{itemId}/attachments/{attachmentId}
```

业务路由下也有同等包装：

```text
GET /api/business/materials/performance/categories
GET /api/business/materials/performance/categories/{categoryId}
GET /api/business/materials/performance/categories/{categoryId}/items/{itemId}/attachments/{attachmentId}
```

建议下游通过 API 下载附件，不直接拼 MinIO 地址。MinIO 的 bucket/key 会随环境变量变化，接口会统一读取并以流式响应返回。

## 2. 新业绩包链路怎么用

### 2.1 用户侧流程

```text
上传业绩汇总表
-> 预览解析结果
-> 导入为业绩分类和明细行
-> 上传合同包
-> 系统拆分成项目级合同附件
-> 下游按分类/明细/附件引用
```

对应接口：

| 动作 | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 分类列表 | `GET` | `/api/materials/performance/categories` | 列出业绩分类，支持关键词、机型、年份、标签、状态等筛选 |
| 汇总表预览 | `POST` | `/api/materials/performance/categories/preview` | 只解析上传的 `.docx` 汇总表，不落库 |
| 汇总表导入 | `POST` | `/api/materials/performance/categories/import` | 创建分类、明细行，并把汇总表作为附件存入对象桶 |
| 分类详情 | `GET` | `/api/materials/performance/categories/{categoryId}` | 返回分类、明细行、分类附件、项目级附件；会触发懒加载拆分 |
| 上传分类附件 | `POST` | `/api/materials/performance/categories/{categoryId}/attachments` | 上传合同包或其他附件；合同包会触发项目级合同拆分 |
| 下载分类附件 | `GET` | `/api/materials/performance/categories/{categoryId}/attachments/{attachmentId}` | 下载汇总表、原始合同包或其他分类附件 |
| 下载项目附件 | `GET` | `/api/materials/performance/categories/{categoryId}/items/{itemId}/attachments/{attachmentId}` | 下载拆分后的单项目合同 |

### 2.2 推荐下游调用方式

#### 场景 A：拿可筛选的业绩分类

```http
GET /api/materials/performance/categories?keyword=海上&turbineModel=EW8.0&operationYear=2024&page=1&pageSize=20
```

常用筛选参数：

| 参数 | 含义 |
| --- | --- |
| `keyword` | 分类名、场景、功率段、摘要、明细行项目名、客户、机型、原始行字段模糊搜索 |
| `scene` | 场景，例如海上、陆上 |
| `powerRating` | 功率段 |
| `turbineModel` | 机型 |
| `timeKeyword` | 原始时间文本或时间事实模糊搜索 |
| `contractYear` | 合同年 |
| `deliveryYear` | 交货年 |
| `operationYear` | 投运年 |
| `tag` | 分类标签 |
| `status` | `enabled` 或 `disabled`，默认 `enabled` |

返回的 `items[]` 是分类摘要，不包含全部明细行。常用字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 分类 ID，形如 `PERCAT-0011` |
| `name` | 分类名 |
| `scene` | 场景 |
| `powerRating` | 功率段 |
| `summary` | 汇总表里推断出的摘要 |
| `fieldSchema` | 汇总表字段结构 |
| `turbineModels` | 分类下聚合出的机型 |
| `contractYears` | 分类下聚合出的合同年 |
| `deliveryYears` | 分类下聚合出的交货年 |
| `operationYears` | 分类下聚合出的投运年 |
| `tags` | 分类标签 |
| `scope` | 范围，`standard`、`customer`、`project` |
| `status` | 启用状态 |
| `itemCount` | 明细行数量 |
| `attachmentCount` | 分类附件数量 |
| `contractAttachmentCount` | 原始合同包数量 |
| `itemContractAttachmentCount` | 项目级合同附件数量 |
| `summaryFileName` | 最近一份汇总表附件名 |
| `contractFileName` | 最近一份合同包附件名 |

#### 场景 B：拿一个分类下的明细行和项目合同

```http
GET /api/materials/performance/categories/PERCAT-0011
```

返回结构：

```json
{
  "item": {},
  "rows": [],
  "attachments": []
}
```

`item` 是分类摘要；`attachments` 是分类级附件；`rows` 是明细行。每条 `rows[]` 会带自己的 `attachments`：

```json
{
  "id": "PERITEM-0268",
  "categoryId": "PERCAT-0011",
  "rowIndex": 1,
  "projectName": "华电新疆喀什 2x66 万千瓦",
  "customerName": "华电",
  "turbineModel": "11-230",
  "turbineModels": ["11-230"],
  "contractQuantity": "2",
  "deliveryOrOperationTime": "2024",
  "contractYear": null,
  "deliveryYear": 2024,
  "operationYear": 2024,
  "timeFacts": {},
  "values": {},
  "attachments": []
}
```

注意：

- `values` 是汇总表原始行字段，保留了上传表格里的完整列。
- `turbineModel / turbineModels / contractYear / deliveryYear / operationYear / timeFacts` 是后端从 `values` 派生出的核心筛选字段。
- `GET 分类详情` 会调用懒加载逻辑：如果合同包已上传但项目级合同附件不存在，或旧附件 `format_version` 低于当前版本，会尝试重拆。

#### 场景 C：下载项目级合同附件

先从分类详情拿到：

```json
{
  "id": "PERITEMATT-0118",
  "categoryId": "PERCAT-0011",
  "itemId": "PERITEM-0268",
  "attachmentType": "contract_item",
  "fileName": "001-华电新疆喀什 2x66 万千瓦_合同.docx"
}
```

再调用：

```http
GET /api/materials/performance/categories/PERCAT-0011/items/PERITEM-0268/attachments/PERITEMATT-0118
```

接口返回文件流，响应头里带下载文件名。下游不需要知道 MinIO key。

## 3. 字段存储在哪里

先说清楚存储方式：业绩库字段整体是存 PostgreSQL，也就是 SQL 表结构；不是把整份业绩数据存成一个 JSON 文件。

但表里有几列是 PostgreSQL 的 `JSONB` 类型，用来保存“字段数量不固定”或“数组/对象结构”的内容。可以理解为：

```text
SQL 表负责固定主结构
+ JSONB 列负责可变字段和数组
```

例如：

| 存储内容 | 存储方式 | 说明 |
| --- | --- | --- |
| 分类名、场景、功率段、状态、创建时间 | 普通 SQL 列 | 固定字段，便于查询和排序 |
| 汇总表表头结构 `field_schema` | SQL 表里的 `JSONB` 列 | 表头列可能每份汇总表不同 |
| 分类标签 `tags` | SQL 表里的 `JSONB` 列 | 数组，例如 `["海上", "8MW及以上"]` |
| 明细行原始字段 `row_values` | SQL 表里的 `JSONB` 列 | 保存汇总表每一行的完整原始列 |
| 拆分后的机型数组 `turbine_models` | SQL 表里的 `JSONB` 列 | 数组，例如 `["EW8.0-230", "EW8.5-230"]` |
| 时间解析详情 `time_facts` | SQL 表里的 `JSONB` 列 | 保存从原始时间文本里解析出的辅助信息 |

下游通过 API 看到的 JSON 是后端把 SQL 行转换后的响应格式，不代表底层是 JSON 文件存储。

### 3.1 分类表：`performance_categories`

用途：保存一个业绩分类，例如“海上 8MW 及以上业绩”或“陆上 11MW 业绩”。

| 字段 | API 字段 | 含义 |
| --- | --- | --- |
| `id` | `id` | 数字主键；API 格式化为 `PERCAT-0001` |
| `name` | `name` | 分类名称 |
| `scene` | `scene` | 场景，如海上、陆上 |
| `power_rating` | `powerRating` | 功率段 |
| `summary` | `summary` | 汇总说明 |
| `field_schema` | `fieldSchema` | 汇总表表头结构 |
| `tags` | `tags` | 分类标签，JSONB |
| `scope` | `scope` | 范围，`standard`、`customer`、`project` |
| `status` | `status` | 启用状态，`enabled`、`disabled` |
| `review_status` | `reviewStatus` | 审核状态，`draft`、`reviewed`、`disabled` |
| `created_at` | `createdAt` | 创建时间 |
| `updated_at` | `updatedAt` | 更新时间 |

### 3.2 明细表：`performance_items`

用途：一行汇总表数据对应一条业绩明细。

| 字段 | API 字段 | 含义 |
| --- | --- | --- |
| `id` | `id` | 数字主键；API 格式化为 `PERITEM-0001` |
| `category_id` | `categoryId` | 所属分类 |
| `row_index` | `rowIndex` | 汇总表里的行序 |
| `project_name` | `projectName` | 项目名 |
| `customer_name` | `customerName` | 客户/业主 |
| `turbine_model` | `turbineModel` | 原始机型文本 |
| `turbine_models` | `turbineModels` | 拆分后的机型数组，JSONB |
| `contract_quantity` | `contractQuantity` | 合同台数 |
| `trial_operation_quantity` | `trialOperationQuantity` | 试运行台数 |
| `commissioned_capacity_mw` | `commissionedCapacityMw` | 投运容量 |
| `delivery_or_operation_time` | `deliveryOrOperationTime` | 原始交货/投运时间文本 |
| `contract_year` | `contractYear` | 合同年 |
| `delivery_year` | `deliveryYear` | 交货年 |
| `operation_year` | `operationYear` | 投运年 |
| `time_facts` | `timeFacts` | 时间解析详情，JSONB |
| `contact_info` | `contactInfo` | 联系信息 |
| `row_values` | `values` | 汇总表原始行字段，JSONB |

下游取业务事实时，优先读 `row_values / values` 保留原始字段；需要筛选时用派生字段 `turbineModels`、`contractYear`、`deliveryYear`、`operationYear`。

举例：如果汇总表原始行是：

```json
{
  "项目名称": "某海上风电项目",
  "买方": "某业主单位",
  "型号和规格": "EW8.0-230 EW8.5-230",
  "交货期/投运时间": "2024"
}
```

那么底层存储大致是：

```text
performance_items.project_name = "某海上风电项目"       -- 普通 SQL 列
performance_items.customer_name = "某业主单位"          -- 普通 SQL 列
performance_items.turbine_model = "EW8.0-230 EW8.5-230" -- 普通 SQL 列
performance_items.turbine_models = ["EW8.0-230", "EW8.5-230"] -- JSONB 列
performance_items.operation_year = 2024                 -- 普通 SQL 列
performance_items.row_values = {...完整原始行字段...}    -- JSONB 列
```

## 4. 附件存储在哪里

附件文件存在 MinIO，默认 bucket 是：

```text
settings.minio_buckets["materials"]
默认环境变量：MINIO_BUCKET_MATERIALS=bid-materials
```

数据库只保存 bucket、key、文件名、大小、MIME 等元数据。

### 4.1 分类附件表：`performance_attachments`

用途：保存分类级附件，包括原始汇总表、原始合同包、其他附件。

| 字段 | API 字段 | 含义 |
| --- | --- | --- |
| `id` | `id` | API 格式化为 `PERATT-0001` |
| `category_id` | `categoryId` | 所属分类 |
| `attachment_type` | `attachmentType` | `summary_table`、`contract_bundle`、`other` |
| `file_name` | `fileName` | 原始文件名 |
| `minio_bucket` | `minioBucket` | 对象桶，默认 `bid-materials` |
| `minio_key` | `minioKey` | 对象 key |
| `mime_type` | `mimeType` | MIME |
| `size_bytes` | `sizeBytes` | 文件大小 |

当前 key 规则：

```text
汇总表：
performance-categories/PERCAT-{categoryId}/summary/{fileName}

合同包或其他分类附件：
performance-categories/PERCAT-{categoryId}/{attachmentType}/{fileName}
```

示例：

```text
bid-materials/
  performance-categories/PERCAT-0011/summary/陆上11MW业绩_汇总表.docx
  performance-categories/PERCAT-0011/contract_bundle/陆上11MW业绩_合同.docx
```

### 4.2 项目级附件表：`performance_item_attachments`

用途：保存从合同包拆出来的单项目合同。

| 字段 | API 字段 | 含义 |
| --- | --- | --- |
| `id` | `id` | API 格式化为 `PERITEMATT-0001` |
| `category_id` | `categoryId` | 所属分类 |
| `item_id` | `itemId` | 所属明细行 |
| `source_attachment_id` | `sourceAttachmentId` | 来源合同包附件 |
| `attachment_type` | `attachmentType` | 当前为 `contract_item` |
| `file_name` | `fileName` | 拆分后的项目合同文件名 |
| `minio_bucket` | `minioBucket` | 对象桶，默认 `bid-materials` |
| `minio_key` | `minioKey` | 对象 key |
| `mime_type` | `mimeType` | MIME |
| `size_bytes` | `sizeBytes` | 文件大小 |
| `format_version` | 暂未直接返回 | 拆分输出格式版本，当前代码常量为 `3` |
| `match_confidence` | `matchConfidence` | 合同块与明细行匹配置信度 |
| `match_method` | `matchMethod` | `project_name` 或 `row_order` |
| `source_title` | `sourceTitle` | 来源合同块标题 |
| `source_block_start` | `sourceBlockStart` | 来源块起点 |
| `source_block_end` | `sourceBlockEnd` | 来源块终点 |

当前 key 规则：

```text
performance-categories/PERCAT-{categoryId}/item-contracts/PERITEM-{itemId}/SRC-{sourceAttachmentId}-{fileName}
```

示例：

```text
bid-materials/
  performance-categories/PERCAT-0011/item-contracts/PERITEM-0268/SRC-0118-001-华电新疆喀什_合同.docx
```

## 5. 合同拆分和懒加载行为

合同包上传时：

```text
POST /api/materials/performance/categories/{categoryId}/attachments
attachmentType=contract_bundle
```

如果上传的是 `.docx` 合同包，后端会：

1. 保存原始合同包到 `performance_attachments`。
2. 调用合同拆分逻辑生成合同块。
3. 按项目名称优先匹配明细行。
4. 项目名置信度不足时按明细行顺序兜底。
5. 把单项目合同写入 MinIO。
6. 把项目级附件元数据写入 `performance_item_attachments`。

分类详情读取时：

```text
GET /api/materials/performance/categories/{categoryId}
```

后端会检查合同包是否已有最新项目级附件。如果没有，或已有附件 `format_version` 低于当前版本，会尝试从原始合同包重新拆分。这意味着下游读取详情接口时，可能触发一次补拆。

## 6. 旧单条业绩记录链路

旧链路表是 `performance_records`，接口是：

```text
GET    /api/business/materials/performance
POST   /api/business/materials/performance
PUT    /api/business/materials/performance/{recordId}
DELETE /api/business/materials/performance/{recordId}
POST   /api/business/materials/performance/{recordId}/word
GET    /api/business/materials/performance/{recordId}/word
```

它保存的是一条业绩记录和一个 Word 附件：

| 字段 | 含义 |
| --- | --- |
| `name` | 业绩名称 |
| `customer_name` | 客户 |
| `project_type` | 项目类型 |
| `scale` | 规模 |
| `location` | 地点 |
| `started_at` / `completed_at` | 起止时间 |
| `amount` | 金额 |
| `turbine_model` | 机型 |
| `tags` | 标签 |
| `applicable_bid_types` | 适用标类 |
| `scope` | 范围 |
| `word_object_key` | Word 附件 MinIO key |
| `cleaned_object_key` | 清洗稿 key，当前链路里只存字段 |
| `review_status` | 状态 |

Word 附件 key 规则：

```text
performance/PERF-{recordId}/{fileName}
```

现有商务标缺口识别会通过 `performance_library_service.list_match_candidates()` 把 `performance_records` 转成素材候选：

```json
{
  "sourceType": "performance_library",
  "candidateType": "performance_record",
  "businessMaterialKind": "performance",
  "businessMaterialKindLabel": "共用业绩"
}
```

如果下游当前接的是商务标素材匹配候选，要注意它读的是旧 `performance_records`，不是新业绩包四表。后续如果要让素材匹配使用项目级合同，需要把候选生成逻辑改到新业绩包链路。

## 7. 给下游的推荐接法

### 7.1 只展示/筛选业绩

用分类列表接口：

```text
GET /api/materials/performance/categories
```

按 `turbineModel`、`contractYear`、`deliveryYear`、`operationYear`、`keyword` 做筛选。

### 7.2 要拿项目级合同

先取分类详情：

```text
GET /api/materials/performance/categories/{categoryId}
```

再从 `rows[].attachments[]` 找 `attachmentType=contract_item`，拿 `categoryId / itemId / attachmentId` 调下载接口。

### 7.3 要做标书附件拼接

推荐使用以下数据：

| 数据 | 来源 |
| --- | --- |
| 选中的分类 | `performance_categories` / 分类详情 `item` |
| 选中的业绩明细 | `performance_items` / 分类详情 `rows[]` |
| 原始汇总字段 | `rows[].values` |
| 筛选字段 | `rows[].turbineModels`、`contractYear`、`deliveryYear`、`operationYear` |
| 单项目合同 | `rows[].attachments[]` + 项目附件下载接口 |
| 匹配质量 | `matchConfidence`、`matchMethod`、`sourceTitle` |

不要直接用原始合同包做最终拼接，除非业务明确要整包附件。

### 7.4 要做素材匹配

当前代码里的素材匹配候选仍会读旧 `performance_records`。如果要改成新业绩包，需要新增候选生成逻辑：

- 从 `performance_items` 生成候选条目。
- 用 `projectName / customerName / turbineModels / values / tags` 生成关键词。
- 把 `performance_item_attachments` 作为可引用附件。
- 候选 `sourceType` 建议区别于旧链路，例如 `performance_package`。

## 8. 注意事项

- 下游优先走 API，不直接读数据库或拼 MinIO key。
- `GET 分类详情` 可能触发懒加载拆分，首次调用可能比普通查询慢。
- 项目级附件存在 `matchMethod=row_order` 时，说明是按顺序兜底匹配，人工审核时要重点确认。
- `row_values / values` 是原始事实来源；派生字段用于筛选，不应覆盖原始字段。
- 删除分类会级联删除 DB 记录，并尝试删除 MinIO 中分类附件和项目级附件。
- `performance_records` 是旧兼容链路；新业绩包不要再用 `PERF-` 作为项目级合同引用 ID。

## 10. 下游最小接入清单

1. 用 `GET /api/materials/performance/categories` 获取可筛选业绩分类。
2. 用 `GET /api/materials/performance/categories/{categoryId}` 获取明细行和项目级合同附件。
3. 从 `rows[].values` 读取原始业务字段。
