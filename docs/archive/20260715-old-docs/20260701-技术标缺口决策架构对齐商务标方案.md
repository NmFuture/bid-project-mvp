# 技术标缺口决策架构 — 对齐商务标「候选≠决策」方案

## 0. 一句话

技术标现在是"匹配到候选就直接判定决策"，商务标是"候选只是候选，选中/处理完才算数"；把技术标的决策计算改成商务标这套两层架构（初判 + 运行时终审），顺带修掉一个因此被牵出来的分类 bug（非附表的"待填写"素材匹配被误判成"素材匹配"而不是"AI填写"）。

## 1. 结论先行（边界）

- **只改 decision 的计算方式和归类条件，不改召回算法本身**（A/B/C 层的证据片段召回、主题弱关联召回全部保留，2026-06-29 那份方案的产出不动）。
- **不新增素材类型规则表**（商务标的 `task_mapping_table.json` 是它自己的第一层初判，技术标已经有等价的第一层——章节主素材/附表规则/文件级候选匹配/主题召回，不重造）。只迁移商务标的**第二层：运行时终审**（`recompute_task_states` 的思路）。
- **前端"素材匹配"这个 UI 概念保留**（用户已经确认过要复用商务标的候选卡片交互），不是要把技术标改成商务标那种"选完才出现标签"的极简展示；只是让"素材匹配"背后对应的 `decision` 值，从"系统认为已经可以走了"变成"待用户确认，选完才真正算数"。
- 涉及文件：`opencode/skills/bid-tech-gap-planner/scripts/run_from_manifest.py`（不改，只新增一个终审函数）、`app/services/technical_gap_planner.py`（挂载终审）、`app/services/technical_gap_domain.py`（summary 口径，字段已存在不用改 schema）、`app/services/technical_gap_service.py`（`ai_fill_all` 的过滤条件要跟着调整）、前端 `TechnicalGapRecognition.jsx`（`isAppendixFillItem`/`technicalActionMode`）。

## 2. 现状：两条线的决策逻辑到底差在哪

### 商务标（`bid-business-gap-planner/scripts/run_from_manifest.py`）

两层：
1. **初判**：`task_mapping_table.json` 按标题关键词把任务分到 `ready`/`fill_required`/`material_required`/`ai_draft_required`/`review_required` 五种里的一种。
2. **终审 `recompute_task_states`**（1704-1740 行，每次都会重跑，是最终结果）：
   - 有**确认过**的 `resolvedArtifacts` → `decision=ready`
   - 有**未确认**的 `resolvedArtifacts` → `review_required`
   - 有 `templateCandidates`（未确认模板候选）→ `review_required`
   - 有 `candidateMaterials`（哪怕只是算法自动召回、用户还没选）→ `review_required`
   - 以上都没有 → 退回初判结果原样（`fill_required`/`material_required` 保持不变，只是 `status` 变成 `needs_input`）

前端 `taskActionMode`（`BusinessGapRecognition.jsx:345-365`）判的不是 `decision`，是**已经落地的产物**（`resolvedArtifacts`/`handlingMode`）——没处理完之前不打"固定素材/AI填写/人工补充"这种具体标签，只显示通用的 `review_required`/`needs_input`。

**本质**：候选素材永远不能单独把任务判定成"可以走了"，必须要么被用户选中确认、要么走完 AI 填写产出产物，否则一律算"待复核"。

### 技术标（`bid-tech-gap-planner/scripts/run_from_manifest.py`）

只有一层，`build_gap_plan` 里一次性算完 `decision`，不会再终审：

```
candidate_materials 非空:
  pick_material 选出最优 matched_material
  ├─ material_requires_fill(matched_material) 为真（选中的是"待填写-XXX.docx"模板）
  │    → decision=fill_required, usage=section_fill, fillTasks=[build_material_fill_task(...)]
  │    → gapReason: "需要先由 AI 填写后再进入 S4 合并"
  └─ 否则（选中的是已经写好的现成文件）
       → decision=ready, usage=matched_material.usage（通常是 section_merge）
candidate_materials 为空:
  主题弱关联召回命中 → decision=fill_required, usage=section_fill, 无 fillTasks（纯候选，供人工选一个）
  否则 → decision=material_required
```

前端 `technicalActionMode`（`TechnicalGapRecognition.jsx:136-146`）直接读 `decision`：

```js
if (decision === 'fill_required') return isAppendixFillItem(item) ? 'ai_table_fill' : 'material_match'
```

`isAppendixFillItem` 只看 `appendixTasks.length > 0`（`TechnicalGapRecognition.jsx:131-134`）。

**问题 1（架构对不齐）**：只要 `decision=fill_required` 且没有 `appendixTasks`，不管候选是"用户还没选的弱关联召回"还是"系统已经很确定的现成候选"，一律显示成 `material_match`，候选一出现就等于"这条已经有着落了"——不像商务标那样把"有候选但未确认"单独打成待复核。

**问题 2（分类 bug，本次一并发现）**：`fillTasks` 不只在附表分支（`appendixTasks` 非空）才有——非附表分支里，如果字面匹配到的是一份"待填写-XXX.docx"模板（`material_requires_fill=True`），同样会生成 `fillTasks`（`build_material_fill_task`），需要走 `ai_fill_word`。但因为它没有 `appendixTasks`，`isAppendixFillItem` 判它为 false，前端把它归到 `material_match`，**详情面板只渲染"候选素材匹配"选择区，完全不渲染"AI填写"按钮区块**（`TechnicalGapRecognition.jsx:1292` 的 `selectedIsAppendixFill` 判断为 false）。用户在这种条目上点"选择"，只是把这份"待填写"模板原文件直接标记为 `resolved`，从未真正触发过 `bid-tech-word-placeholder-filler` 填写——选中的其实是一份没填过的空表。

## 3. 目标架构

### 3.1 决策计算改两层

**第一层（不动）**：`build_gap_plan` 里现有的章节主素材/附表/文件级候选/主题召回逻辑，产出的 `decision`/`usage`/`candidateMaterials`/`fillTasks` 全部保留，作为"初判"。

**第二层（新增）**：`_recompute_technical_gap_decisions(plan)`，作为 Route B 后处理挂在 `technical_gap_planner.py` 里（`_attach_evidence_segments_to_plan`/`_attach_topic_recall_to_plan` 之后，与它们同一批"确定性后处理"），对每个 item 按优先级终审：

```
1. resolvedArtifacts 非空（已选定/已上传/AI填写已完成产物）
     → decision=ready, status=resolved（已经是现在 register_technical_existing_gap_material /
       ai_fill 完成后的行为，这条本来就成立，终审只是显式声明，不改变现状）
2. fillTasks 非空 且未全部 completed
     → decision=fill_required（不管有没有 appendixTasks，都保持 fill_required，
       对应"需要 AI 处理过才能 merge"——这条是关键：不再受"有没有 candidateMaterials"影响，
       避免像商务标那样误把 AI 草拟类任务也扫进 review_required）
3. candidateMaterials 非空（且不落入规则 2，即没有待完成的 fillTasks）
     → decision=review_required（这是新增的活分支，此前只在 schema 里占位、
       从未被真正赋值过；对应"系统给了候选，但没人确认选哪个"）
4. structural（结构性目录项）
     → decision=ready 不变
5. 都没有
     → decision=material_required 不变
```

`status` 同步刷新：`ready`→`resolved`/`matched`（沿用现有区分），`review_required`→`needs_input`（保持 `blockingCount` 统计口径不变，不新增会拉高"卡住"计数的新状态；只是 decision 层面区分出"待复核"）。

### 3.2 前端跟着改两处

- `isAppendixFillItem` 的判定从 `appendixTasks.length > 0` 改成 `fillTasks.length > 0`（附表任务本来就会生成 `fillTasks`，这个条件是原条件的超集，不会影响附表分支，只会把非附表的"待填写模板匹配"也正确纳入"AI填写"展示，修掉问题2）。
- `technicalActionMode` 里 `decision === 'review_required'` 映射到 `material_match`（保留现有候选卡片 UI 和"选择"交互，用户不需要重新学一套操作；只是内部决策字段和统计口径对齐商务标）。

### 3.3 下游消费点要跟着调整

- `technical_gap_service.py:461`（`ai_fill_all` 批量 AI 填写的过滤条件）：`decision != "fill_required"` 就跳过——这条不用改，因为规则 2 保证"需要 AI 填写"的条目 `decision` 始终是 `fill_required`，不会被终审改成别的。
- `technical_gap_domain.py` 的 `summarize_technical_gap_plan`：`reviewRequiredCount` 字段已经存在（读 `decision_counts.get("review_required", 0)`），不用改 schema，之前一直是死统计，改造后会自然出现非零值。
- 前端"待处理"合计（`TechnicalGapRecognition.jsx:1113`，目前是 `material_match + manual_upload + manual_select`）：`material_match` 桶的口径变化（present-but-unconfirmed 候选也算进来，此前它们已经在这个桶里，所以这条统计口径实际不变）。

## 4. 影响评估：三种情况分别怎么变

| 情况 | 现状 decision | 现状 UI | 改造后 decision | 改造后 UI | 变化 |
|---|---|---|---|---|---|
| 字面匹配到现成完整文件 | ready | 固定素材 | ready（不变，仍在规则5之前就被第一层判定） | 固定素材 | 无变化 |
| 字面/主题候选存在，需人工选一个（无 fillTasks） | fill_required | 素材匹配 | review_required | 素材匹配（UI 不变） | decision 字段变了，统计口径从"已确定走这条路"变成"待复核"；选中后走 `register_technical_existing_gap_material` 直接终审成 ready，和商务标一致 |

| 无候选无匹配 | material_required | 人工补料 | material_required（不变） | 人工补料 | 无变化 |

## 6. 风险与边界

- **不改附表/来源矩阵路径**：`appendixTasks`/`sourceRouting` 全程不碰，规则 2 明确保留"有 fillTasks 就是 fill_required"，附表分支的 `fillTasks` 恒非空，行为不变。
- **不新增新的"卡住"计数**：`review_required` 的 `status` 映射到已有的 `needs_input`，不引入新的 blocking 状态值，避免下游审计/完整性检查（`check_technical_gap_integrity`）因为多出一个陌生 status 而误判。
- **风险点**：问题2 的修复（`isAppendixFillItem` 判定条件改变）理论上会让此前从未被用户走过"AI填写"流程、但已经被误选成 `resolved` 的历史条目产生新的期望行为差异——但这属于本来就该被修的 bug，不属于本次架构改造引入的新风险；需要在验证阶段确认 PRJ-0010 现有已选中条目不会被这次改动影响（新增的是"未来新生成的 gap plan"如何分类，不回溯改写已经写入 `resolvedArtifacts` 的历史选择）。

## 8. 附带修复：素材匹配按项目机型布局（上置/下置）过滤

做完决策终审后，候选卡片第一次完整展示，暴露出一个更早就存在的机型过滤缺陷：
PRJ-0010 锁定投标机型 `EW10.0-220上置`，但候选里混进了大量 `EW10.0-220下置` 目录下的素材
（同一份通用模板按机型变体各存一份，如"待填写-标方案优势说明"上置/下置各一份）。

**根因**：`app/services/turbine_models.py::material_model_fit` 的机型匹配用的是别名子串包含。
项目型号 `EW10.0-220上置` 会派生出一个"去布局别名" `EW10.0-220`（本意是让只写基础型号的
素材也能命中），而 `EW10.0-220` 是 `EW10.0-220下置` 的子串，于是下置素材被误判成 `match`，
逃过了 `technical_material_store.raw_files` 里 `fit != "conflict"` 的过滤。且 `MODEL_PATTERN`
正则不会把 `上置/下置` 纳入 token，光比对 token 也识别不出布局差异。

**修复**：`material_model_fit` 增加布局感知——项目布局（取 `layout` 字段，否则从型号串推断）
存在时，若素材全文（含 folderPath）只出现相反布局词、且不含当前布局词，直接判 `conflict`。
这样：
- 下置目录、文件名无布局 → conflict（过滤掉，主修复目标）。
- 文件名显式带（上置）但误放进下置目录 → 保留（文件名布局优先，属素材库归档不一致，非漏网）。
- 项目本身未锁布局（型号无上置/下置）→ 上置下置都保留，不误伤。

**边界**：`material_model_fit` 仅被技术标 `technical_material_store` 使用；商务标只用
`project_turbine_model` 读项目机型，不碰此函数，不受影响。

**验证**：
- 单测 `tests/test_turbine_material_layout_fit.py`（6 例：同布局 match / 相反布局 conflict /
  无布局通用素材 match / 无型号 token generic / layout 字段驱动 / 不同基础型号 conflict）。
- 容器内重跑 PRJ-0010：修复前 54 个纯下置候选（文件名和路径均无上置），修复后 0 残留；
  规则路径计数不变（ready 31 / appendixTaskCount 83 / sourceRouting 50 / material_required 10 /
  review_required 8）。唯一保留的 `自动消防系统（上置）.docx`（误放进下置目录）符合"文件名布局
  优先"预期，非漏网。

## 8bis. 附带修复：主题召回到「待填写模板」应走 AI 填写，不能当现成素材

决策终审 + 候选卡片完整展示后，暴露出主题召回分支的一个遗漏：GAP-0008「投标方案优势说明」
召回到 `待填写-标方案优势说明.docx`（一个待填写模板），却被判成 `material_match`（选择即合并），
点"选择"会把一个没填过的空模板直接合入——错误。

**根因**：字面候选分支（`elif candidate_materials:`）已用 `material_requires_fill` 区分
「待填写模板→AI填写」与「现成素材→固定/素材匹配」，但主题召回分支（`else:` 及 Route-B 的
`_attach_topic_recall_to_plan`）没做这个区分，把所有召回素材一律当 material_match。

**对齐商务标**：商务标把「待填写模板」（`templateCandidates`）与「现成素材」（`candidateMaterials`）
分成两个列表——模板走 `assemblyMode=template_fill_docx`（AI 填充），现成素材才「选择合并」，两者
不混在同一个可选列表里（`bid-business-gap-planner/run_from_manifest.py::recompute_task_states`）。

**修复**（两条路径同改：本地 `run_from_manifest.py` else 分支 + Route-B `_attach_topic_recall_to_plan`）：
1. 主题召回的最相关素材是待填写模板 → 生成 fillTask（`bid-tech-word-placeholder-filler`），
   decision=fill_required、终审保持 fill_required → 前端 AI填写。
2. 最相关是现成素材 → material_match，且从「选择即合并」候选列表里剔除待填写模板
   （模板只应通过 AI 填写处理），避免用户误选空模板。

**验证（容器内 PRJ-0010）**：
- GAP-0008 从 material_match 修正为 AI填写（fillTasks=1，skill=bid-tech-word-placeholder-filler）。
- 全量扫描：所有 review_required（素材匹配）项的可选候选里，待填写模板残留数 = 0。
- 受影响的 GAP-0015/0043/0046 过滤模板后仍保留现成素材候选，未变空。
- reviewRequiredCount 8→7，fillRequiredCount 94→95，其余规则路径不变。
- 单测 `tests/test_technical_topic_recall_template_routing.py`（2 例：待填写→AI填写、现成→review_required）。

## 8ter. 附带修复：候选卡片对齐商务标打分版式 + 左右栏独立滚动

用户对比两条线后指出「技术标交互和商务标没统一」——技术标候选卡片信息稀疏、没有可读的匹配度打分。

**候选卡片对齐商务标**（`TechnicalGapRecognition.jsx`）：
- 新增 `technicalMatchScore`，口径复用商务标 `numericMatchScore`（`score/matchScore/similarity/confidence`，
  兜底 `topicRelevance`；值 >1 视为百分制）。技术标 `matchScore` 是 `material_score` 的无上界原始排序分
  （全标题命中 +120 等），显示时钳到 **100% 上限**（否则出现 107% 这种）。排序仍用原始分保留区分度。
- 卡片按商务标版式展示：`匹配度 X% · 召回原因`、素材类型 badge（通用/客户/项目素材）、`清洗：{状态} 清洗稿可用`、
  路径、匹配证据片段（去掉原来每段的原始分 badge——整体匹配度已在头部，段落只留标题/摘要/页码，对齐商务标 Wiki依据）。
- 候选列表按匹配度降序排。

**左右栏独立滚动**：外层 grid 由 `min-h-[720px]`（会被 210 项长列表撑高、整页联动）改为固定视口高度
`h-[min(78vh,900px)] overflow-hidden`，左右两栏各自 `overflow-auto` 独立滚动。
