# 解析进度条细化方案

版本日期：2026-07-09

本文记录技术标解析进度条的当前落地方案，并作为后续商务标解析同步细化时的参考。当前方案以 Word/PDF 两类文件的真实解析链路为基础，目标是让用户看到“正在做什么、已经执行多久、没有卡死”，同时避免把内部实现词暴露到前端。

## 1. 展示原则

前端解析进度区域保持三块信息：

| 区域 | 展示内容 | 要求 |
| --- | --- | --- |
| 左侧第一行 | 当前任务阶段 | 只显示阶段，例如 `PDF 处理中`、`结构化解析中`。 |
| 左侧第二行 | 当前具体任务 | 一句话说明正在做的事，可包含已执行时长。 |
| 右侧徽标 | 状态和百分比 | 保持现有样式，例如 `解析中 · 95%`。 |

明确约束：

- 左侧只展示两行，不再展示第三行 `current / total · 阶段 xx%`。
- 用户可见文案不出现 `AI`、`Opencode`、`S1`、`Skill`、`manifest`、`输出片段`、`sessionId`、`heartbeat`。
- 进度条不倒退。后端运行态和前端展示态都要做单调保护。
- 完成前不伪造到 `100%`。长耗时阶段用“已执行 X 分 X 秒”证明仍在运行。
- 97% 到 99% 的写入和资产阶段通常很快，轮询可能直接从 96% 看到 100%，不为展示效果人为加延时。

## 2. 技术标阶段权重表

| `62%-68%` | 准备结构化解析中 | 整理结构化解析输入，准备进入长耗时结构化阶段。 |

## 4. 进度单调性规则

### 4.1 后端规则

后端 `parse_progress` 是前端展示的唯一进度事实来源。运行态更新时：

- `percentage` 取 `max(existing_percentage, requested_percentage)`。
- 同一 `phaseKey` 内的 `phasePercent` 取 `max(existing_phase_percent, requested_phase_percent)`。
- `completed`、`failed`、`cancelled` 等终态按终态规则覆盖。
- 每次有效进度更新都刷新 `heartbeatAt`，供 stale 判断使用。

这样可以避免异步事件乱序、结构化解析输出片段波动、轮询旧快照导致进度倒退。

### 4.2 前端规则

前端所有进度入口都走单调合并：

- 上传解析轮询。
- 上传超时后的恢复轮询。
- 详情页加载后的进度刷新。
- 手动同步最新项目状态。

运行态中，如果新快照百分比小于当前展示百分比，保留当前百分比；同一阶段的 `phasePercent` 也同理。摘要和阶段标题可以采用新快照，以便“已执行 X 分 X 秒”持续刷新。

## 5. 长耗时阶段规则

### 5.1 PDF 处理中

PDF 处理中可能由 Docling 或同类文档引擎执行，耗时可能达到数分钟。当前策略：

- `PDF 处理中` 区间为 `8%-42%`。
- 每隔约 10 秒发送一次心跳。
- 心跳根据已执行时长推进阶段内百分比，当前上限为阶段内 `95%`，对应主进度约 `40%`。
- 如果引擎提供 `currentPage/totalPages/tableCount`，第二行可以显示 `已处理 x / y 页`、`已识别 n 个表格`；没有真实数据时只显示已执行时长。

真实链路观察：2026-07-07 使用 `招标文件-技术规范.pdf` 上传解析，PDF 处理阶段从 13% 平滑推进到 40%，经过 21% 时第二行持续刷新已执行时长，没有出现长时间无反馈。

### 5.2 结构化解析中

结构化解析是另一个长耗时阶段：

- 主区间为 `68%-96%`。
- 第二行显示 `正在识别招标文件中的技术要求和原文依据，已执行 X 分 X 秒。`
- 用户可见标题固定为 `结构化解析中`。
- 完成前不展示内部执行工具、会话、输出片段和原始调试内容。
- 如果阶段达到 96% 后仍在运行，继续刷新已执行时长，不继续伪造 97%-99%。

真实链路观察：2026-07-07 使用 `招标文件-技术规范.pdf` 上传解析，结构化阶段从 86% 到 96% 未倒退；96% 后持续刷新已执行时长，最终完成为 100%。

## 7. 商务标同步建议

商务标不要直接照搬技术标阶段名，应先按商务标实际链路重新命名，但可以复用同一套展示与单调性规则。

建议阶段：

| 建议区间 | 阶段 | 具体任务 |
| --- | --- | --- |
| `0%-8%` | 上传文件中 | 保存或复用商务招标文件。 |
| `8%-30%` 或按文件类型拆分 | 文档处理中 | 读取 Word/PDF 文本与表格。PDF 长耗时同样需要心跳。 |
| `30%-45%` | 整理文档线索中 | 整理章节、正文、表格和原文位置。 |
| `45%-62%` | 识别商务附件模板中 | 识别投标函、承诺函、商务附件模板等。 |
| `62%-68%` | 准备结构化解析中 | 整理商务结构化解析输入。 |
| `68%-96%` | 结构化解析中 | 识别商务要求、模板要求和原文依据，持续显示已执行时长。 |
| `96%-98%` | 写入解析结果中 | 同步商务解析结果到项目状态。 |
| `98%-99%` | 生成结果资产中 | 生成商务附件、承诺函等结果资产。 |
| `100%` | 解析完成 | 商务解析结果可展示和消费。 |

商务标同步时必须检查：

- 用户可见文案不出现内部词。
- 长耗时 PDF 处理和结构化解析都有心跳。
- 前端只显示两行文字，右侧徽标不改。
- 前后端都做单调保护。
- 真实上传至少覆盖一个 Word 样本和一个 PDF 样本。

## 8. 验证要求

调整技术标或同步商务标时，至少验证：

- 后端阶段权重测试覆盖 Word/PDF 两套区间。
- 前端摘要测试覆盖两行展示，`detail` 为空。
- 前端测试覆盖进度不倒退。
- 后端测试覆盖结构化解析已执行时长。
- `git diff --check` 通过。
- 真实上传链路采样确认：
  - 主进度无倒退。
  - 同阶段进度无倒退。
  - 长耗时阶段第二行持续刷新已执行时长。
  - 最终状态为 `completed`，最终百分比为 `100`。

## 10. 后续注意事项

- 进度条负责诚实反馈，不负责掩盖耗时。
- 如果要减少 PDF `40%` 或结构化 `96%` 附近的停留时间，需要解析引擎或结构化解析过程提供更细的真实里程碑。
- 不建议为展示观感加入假延时；快速阶段被轮询跳过是可接受的。
- 商务标同步前，应先用真实商务标 Word/PDF 样本记录链路，再确定最终权重表。
