# 代码结构梳理

## 1. 总体边界

```text
code/
  docker-compose.yml
  sewpg-bid-frontend/   # React + Vite 前端
  sewpg-bid-backend/    # FastAPI、服务层、队列、OnlyOffice、OpenCode/Skill
  sewpg-bid-api/        # 接口说明目录，不是运行时代码
```

当前运行主链是：前端页面 -> `src/api/index.js` -> FastAPI route -> `app/services/*` -> PostgreSQL / MinIO / 本地工作区 / Redis worker / OpenCode 或 Skill runner。

## 2. 页面清单

前端入口在 `code/sewpg-bid-frontend/src/App.jsx`。未登录时不走独立路由，直接渲染 `Login`；登录后进入 `AppShell`，再挂载公共页面、技术标页面、商务标页面。

### 2.1 公共页面

| 路由 | 页面 | 功能 |
| --- | --- | --- |
| `/dashboard` | `pages/Dashboard.jsx` | 项目总览、工作台入口、状态概览。 |
| `/settings` | `pages/Settings.jsx` | 用户、LLM 网关、OCR、默认模板、系统健康检查。 |

结论：页面已经按技术标、商务标拆开，不应该再写成“一个通用页面通过删字段适配两类标”。

## 3. API 设计与实现

### 3.1 前端 API 封装

前端统一从 `code/sewpg-bid-frontend/src/api/index.js` 调用后端，不在页面里拼散乱请求。主要分组：

| API 分组 | 对应能力 |
| --- | --- |
| `authAPI`、`dashboardAPI`、`settingsAPI` | 登录、看板、系统设置。 |
| `technicalProjectsAPI`、`businessProjectsAPI` | 项目 CRUD、素材范围、默认模板。 |
| `technicalParseAPI`、`businessParseAPI` | 招标文件解析、进度、附件/承诺函/评分确认、模板上传。 |
| `technicalDirectoryAPI`、`businessDirectoryAPI` | 目录生成状态与触发。 |
| `technicalOutlineAPI`、`businessOutlineAPI` | 目录读取、保存、确认、技术标重新生成。 |
| `technicalGapsAPI`、`businessGapsAPI` | 缺口、事实库、素材选择、AI 填写/草稿、复核。 |
| `technicalGenerateAPI`、`businessGenerateAPI` | 填写/生成任务状态与触发。 |
| `technicalDocumentAPI`、`businessDocumentAPI` | 协同编辑、保存、格式处理、最终文件。 |
| `technicalMaterialsAPI`、`businessMaterialsAPI` | 原始素材库、Wiki、附件、摘要刷新。 |
| `technicalAuditAPI`、`businessAuditAPI` | 审计日志。 |

项目列表接口支持 `reviewDecision` 查询参数。项目总览页传 `participate`，避免把解析阶段临时承载项目展示成正式投标项目；解析页不传该参数，用于恢复仍处于待判断状态的解析记录。

### 3.2 后端 API 路由

后端入口在 `code/sewpg-bid-backend/app/api/router.py`，挂载：

| 路由文件 | API 前缀/功能 |
| --- | --- |
| `routes/auth.py` | `/api/auth/*`，登录、当前用户、退出、客户选项。 |
| `routes/dashboard.py` | `/api/dashboard`，工作台总览。 |
| `routes/settings.py` | `/api/settings/*`，用户、LLM、OCR、默认模板、健康检查。 |
| `routes/technical.py` | `/api/technical/*`，技术标项目、解析、目录、缺口、生成、文档、素材、Wiki、审计。 |
| `routes/business.py` | `/api/business/*`，商务标项目、解析、目录、生成、文档、素材、Wiki、审计。 |
| `routes/business_gaps.py` | `/api/business/projects/{project_id}/business-gaps/*`，商务缺口接口；因接口数量和任务模型更复杂，单独拆文件。 |
| `routes/system.py` | `/healthz`、`/api/healthz`、`/api/root`。 |

### 3.3 后端实现方式

小白版理解：

- `routes/*.py` 像前台窗口：接收前端请求，做少量参数处理，然后交给 service。
- `services/*_service.py` 像业务负责人：负责一个页面或一段流程。
- `services/*_state.py` 像状态表模板：规定项目当前处于什么状态、进度怎么记录。
- `services/*_flow.py` 像长流程调度器：负责排队、跑任务、更新进度。
- `services/*_store.py` 像资料柜：负责素材、Wiki、附件的读写和范围校验。
- `services/*_domain.py` 像业务规则手册：放判断规则、状态计算、字段规范。
- `services/*_planning.py`、`*_assembly.py`、`*_generation.py` 更接近“跑 Skill/脚本生成结果”的执行层。

技术标和商务标不是两套完全割裂的后端。共同能力放在 `bid_*`、`material_*`、`workspace_*` 这些共享文件；技术标专属逻辑放在 `technical_*` 和 `tech_assembly.py`；商务标专属逻辑放在 `business_*`。调用时通常是：

```text
技术标页面 -> /api/technical/... -> technical_* service -> 共享 bid_* / material_* 底座 -> 技术标 Skill/脚本
商务标页面 -> /api/business/...  -> business_* service  -> 共享 bid_* / material_* 底座 -> 商务标 Skill/脚本
```

下面所有服务表统一按“文件 / 干什么 / 技术标怎么用 / 商务标怎么用”四列写；同类服务尽量上下相邻，方便直接对比技术标和商务标差距。

#### 3.3.1 项目主流程服务

| 文件 | 干什么 | 技术标怎么用 | 商务标怎么用 |
| --- | --- | --- | --- |
| `bid_type.py` | 统一规范 `技术标`、`商务标` 这两个标类。 | 技术标服务用它校验类型。 | 商务标服务用它校验类型。 |
| `bid_project_service.py` | 项目 CRUD 的统一服务，创建项目、更新项目、删除项目、查素材范围。 | 实例化成 `technical_project_service`，只处理技术标项目。 | 实例化成 `business_project_service`，只处理商务标项目。 |
| `bid_project_state.py` | 定义项目长什么样、默认状态是什么、阶段怎么更新，并支持按 `reviewDecision` 过滤项目列表。 | 创建技术标项目时初始化技术标解析、目录、缺口、文档状态；项目总览只展示 `participate`。 | 创建商务标项目时初始化商务标解析、目录、缺口、文档状态；项目总览只展示 `participate`。 |
| `bid_project_repository.py` | 项目数据读写的仓储层。 | 被技术标 project service 间接使用。 | 被商务标 project service 间接使用。 |
| `bid_runtime_state.py` | 从已有文件恢复运行态，避免重启后项目状态丢失。 | 恢复解析、目录生成、目录大纲等通用状态；如果数据库状态缺失但项目目录里已有技术标 S2 产物 `toc.json`，会用它重建页面目录树。 | 恢复解析、目录生成、目录大纲等通用状态；如果数据库状态缺失但项目目录里已有商务标 S2 产物 `toc.json`，会用它重建页面目录树。 |
| `project_stage_flow.py` | 定义项目阶段流转。 | 技术标页面阶段条使用。 | 商务标页面阶段条使用。 |
| `workspace_project_access.py` | 项目标类校验，防止技术标接口读商务标项目。 | 要求项目 `bidType=技术标`。 | 要求项目 `bidType=商务标`。 |
| `store.py` | 上层 store 门面，屏蔽底层项目数据来源。 | 技术标项目读写会经过它。 | 商务标项目读写会经过它。 |
| `dashboard_service.py` | 工作台总览数据。 | 汇总技术标项目。 | 汇总商务标项目。 |

本小节 Skill 使用：

| 标类 | Skill | 简单说明 |
| --- | --- | --- |
| 技术标 | 无 | 项目创建、状态恢复、阶段流转、权限校验都是后端基础服务，不调用 Skill。 |
| 商务标 | 无 | 和技术标共用同一套项目底座，只是绑定商务标项目类型。 |

#### 3.3.2 S1 招标文件解析服务

| 文件 | 干什么 | 技术标怎么用 | 商务标怎么用 |
| --- | --- | --- | --- |
| `bid_parse_service.py` | 解析页面的服务入口：上传文件、查进度、取解析结果、预览附表。 | `technical_parse_service` 使用 `/api/technical/projects` 前缀。 | `business_parse_service` 使用 `/api/business/projects` 前缀，并多处理承诺函、商务评分确认。 |
| `bid_parse_state.py` | 解析进度状态。 | 记录技术标解析进度。 | 记录商务标解析进度。 |
| `parse_profiles.py` | 定义技术标/商务标解析 profile、schema、Skill 名称和 workspace。 | 指向技术标 schema 和技术标解析 Skill。 | 指向商务标 schema 和商务标解析 Skill。 |
| `parsing.py` | 真正解析招标文件：抽文本、OCR 兜底、提取结构化要求、附表、承诺函。 | 使用 `TECHNICAL_PARSE_PROFILE`，目标是评分细则、风机参数、性能保证、专题方案、附表等。 | 使用 `BUSINESS_PARSE_PROFILE`，目标是商务评分、资格业绩、承诺事项、商务附表/空表等。 |
| `bid_ocr_service.py` | OCR 任务服务。 | 技术标扫描件/PDF 可走 OCR。 | 商务标扫描件/PDF 可走 OCR。 |
| `ocr_service.py` | 更底层的 OCR 调用封装。 | 被解析和素材清洗间接使用。 | 被解析和素材清洗间接使用。 |
| `business_parse_assets.py` | 商务解析后的附件、承诺函、评分确认资产。 | 不走这套。 | 商务标专用，用于承诺函、商务附件、评分项确认。 |

解析过程会先生成本地结构化结果和 `s1_parse_manifest.json`；是否再通过 OpenCode 调用 `s1parse` Skill，由 `S1_PARSE_OPENCODE_ENABLED` 控制。关闭时使用本地解析结果；开启时走 `OpencodeClient.generate_tender_parse_with_trace()`，失败则回退本地结果。

前端产品口径是“上传招标文件并解析”，不是“先新建项目”。短期实现里，`TechnicalTenderReview.jsx` 和 `BusinessTenderReview.jsx` 在用户点击上传解析时，可静默调用对应项目 API 创建临时承载；解析完成后人工选择参与投标才进入正式项目推进，不参与则删除临时承载并回到上传态。

本小节 Skill 使用：

| 标类 | Skill | 简单说明 |
| --- | --- | --- |
| 技术标 | `bid-tech-tender-structured-parser` | 把技术标招标文件解析成结构化 JSON，重点提取评分细则、技术要求、风机参数、性能保证、专题方案、附表。 |
| 商务标 | `bid-business-tender-structured-parser` | 把商务标招标文件解析成结构化 JSON，重点提取商务评分、报价、符合性审查、资格业绩、承诺事项、商务附件和空表。 |

#### 3.3.3 S2 目录/大纲服务

| 文件 | 干什么 | 技术标怎么用 | 商务标怎么用 |
| --- | --- | --- | --- |
| `bid_directory_flow.py` | 目录生成长任务：排队、更新进度、保存目录状态。 | 被 `technical_directory_service.py` 包一层后调用，最终交给 `outline_generation.py` 执行。 | 被 `business_directory_service.py` 包一层后调用，最终交给 `outline_generation.py` 执行。 |
| `technical_directory_service.py` | 技术标目录 API 的薄包装；和商务标目录服务结构相同，只是绑定 `technical_project_service` 和 `/api/technical/projects` 前缀。 | 技术标页面 `/template-directory` 调用。 | 不用。 |
| `business_directory_service.py` | 商务标目录 API 的薄包装；和技术标目录服务结构相同，只是绑定 `business_project_service` 和 `/api/business/projects` 前缀。 | 不用。 | 商务标页面 `/template-directory` 调用。 |
| `bid_outline_state.py` | 目录/大纲状态：生成、保存、确认、证据。 | 保存技术标目录树。 | 保存商务标目录树。 |
| `outline_generation.py` | S2 目录生成执行器：准备 manifest、调用 OpenCode、读取 Skill 输出；OpenCode 不可用时直接跑 Skill 目录下的 `scripts/run_from_manifest.py` 兜底。 | 技术标目录走 `bid-tech-outline-generator`。 | 商务目录走 `bid-business-outline-generator`。 |

本小节 Skill 使用：

| 标类 | Skill | 简单说明 |
| --- | --- | --- |
| 技术标 | `bid-tech-outline-generator` | 根据招标文件、模板和历史资料生成技术标目录树，输出前端使用的 `toc.json`。 |
| 商务标 | `bid-business-outline-generator` | 学习商务模板和历史目录，生成商务标 `outline.json`，后端再转成页面兼容的 `toc.json`。 |

| `services/business_assembly.py` | `bid-business-assembler`、`bid-business-format-cleaner`。 | S5 商务标正文装配和格式清理：把商务任务、附件模板、草稿和证据装成 Word，并清理格式。 |
| `services/wiki_generation.py` | `bid-tech-wiki-material-builder`、`bid-business-wiki-material-builder`。 | 素材库 Wiki 构建兜底：根据素材生成技术标或商务标 Wiki 蓝图。 |
| `services/bid_document_flow.py`、`material_cleaning.py` | 文档转换、素材清洗等本地命令，不属于 OpenCode 主链。 | 文件处理类确定性操作：保存/转换文档、清洗素材文本，通常不需要 AI 判断。 |

结论：当前不是“全部功能都由 OpenCode 生成”。OpenCode 主要用于语义判断、规划、草稿和可追踪的 AI 调用；确定性装配、格式处理、文件转换、清洗、部分填表是后端直接跑脚本或本地服务。

## 5. 素材库、模板、Wiki 的存储与范围

### 5.1 存储位置

配置在 `code/sewpg-bid-backend/app/core/config.py`：

| 类型 | 默认位置/桶 | 内容 | 技术标/商务标怎么区分 | 释放/清理方式 |
| --- | --- | --- | --- | --- |
| 上传临时区 | `.localdata/uploads` | 招标文件、项目模板上传、默认模板下载副本。 | 按项目 ID 分目录：`{project_id}/tender`、`{project_id}/template`、`{project_id}/system-default-template`；标类靠项目元数据区分，不在目录名里直接写技术标/商务标。 | 当前没有定时释放；上传失败会删除半成品，默认模板副本按需下载/覆盖。项目删除时还没有统一清这个目录，后续应补 TTL 或项目删除清理。 |
| 解析区 | `.localdata/parsed` | S1 解析中间产物、Wiki 构建临时区。 | 按项目 ID 分目录；解析 profile 里区分技术标/商务标。正式工作产物会进入对应 `technical-workspace` 或 `business-workspace`。 | 参与投标后会把解析产物提升到文档工作区并清理解析临时目录；放弃投标或删除项目也会清理项目解析临时目录。 |
| 文档工作区 | `.localdata/documents` | 项目工作目录、目录、缺口、生成 Word/PDF、OnlyOffice 文件。 | 项目内明确分为 `{project_id}/technical-workspace` 和 `{project_id}/business-workspace`；OnlyOffice 草稿文件按项目 ID 保存。 | 当前作为项目长期工作区保留，没有定时释放；项目删除时也没有完整清理文档工作区，后续应补项目删除级清理。 |
| 素材对象 | MinIO `bid-materials` | 原始素材、清洗稿、Wiki 附件等文件对象。 | 桶共用；原始素材 key 里带路径，如 `raw/技术标/...`、`raw/商务标/...`；清洗稿 key 按 `RAW-id` 存，但通过素材元数据里的 `bidType` 归属。 | 删除素材文件/文件夹会删除对应 MinIO 对象；删除项目会删除对应 `技术标/项目素材/{project_id}` 或 `商务标/项目素材/{project_id}`。 |
| 生成文档对象 | MinIO `bid-documents` | OnlyOffice 草稿、复核稿等文档对象。 | 桶共用；key 主要是 `documents/{project_id}/draft.docx`、`review.docx`，靠项目 ID 和项目标类隔离，不直接在 key 里写技术标/商务标。 | 保存文档时覆盖/同步；当前没有独立 TTL 或项目删除级对象清理。 |
| 默认模板对象 | MinIO `bid-templates` | 系统默认模板和模板版本。 | 默认投标模板按 `templates/default/technical/...`、`templates/default/business/...` 分开；其他 dotx/excel 模板按模板类型和表类型分。 | 上传新默认模板会把同类型旧模板置为非激活，但旧对象不自动删除；当前没有定时释放。 |
| 结构化元数据 | PostgreSQL | 项目、素材元数据、Wiki 节点、附件、审计、设置。 | 项目、素材、Wiki、模板记录里保存 `bidType`、`templateType` 或路径范围。 | 随业务接口更新/删除；没有统一的过期清理任务。 |

项目工作区按标类拆分：

```text
.localdata/documents/{project_id}/technical-workspace/
.localdata/documents/{project_id}/business-workspace/
```

解析结果会先进入 `.localdata/parsed/{project_id}`，再提升到对应 workspace 的 `parse/` 目录。默认模板通过 `template_store.py` 管理，项目使用时下载到 `.localdata/uploads/{project_id}/system-default-template/`。

### 5.2 素材路径规范

素材库根路径只允许两类：

```text
技术标/
商务标/
```

每类下面按身份范围分三层：

```text
技术标/通用素材
技术标/客户素材/{客户名}
技术标/项目素材/{project_id}

商务标/通用素材
商务标/客户素材/{客户名}
商务标/项目素材/{project_id}
```

项目创建后，`build_project_material_scope()` 会生成 `readableScopes`：通用素材一定可读；有客户名则加客户素材；有项目 ID 则加项目素材。缺口规划、事实库、AI 填写、正文装配都应从这个范围取素材，不能全库乱扫。

### 5.3 Wiki 路径与权限

Wiki 和原始素材共用标类范围：

| 技术标 | 商务标 |
| --- | --- |
| `technical_material_store.py` 只允许 `技术标` 路径、技术标文件、技术标 Wiki 节点和附件。 | `business_material_store.py` 只允许 `商务标` 路径、商务标文件、商务标 Wiki 节点和附件。 |

平台 Wiki 构建在 `services/wiki_generation.py`：先在 `.localdata/parsed/_wiki_build` 生成中间结果，再导入素材/Wiki 存储。前端访问时 URL 会被重写成 `/api/technical/materials/...` 或 `/api/business/materials/...`，避免跨工作区暴露。

### 5.4 当前判断

- 路径规范基本合理：`技术标/商务标 + 通用/客户/项目` 可以支撑素材复用和项目隔离。
- 调用范围基本合理：项目侧通过 `readableScopes` 取素材，不应该跨标类、跨客户、跨项目。
- 后端标类隔离已有：`workspace_project_access.py`、`technical_material_store.py`、`business_material_store.py` 都在做校验。
- 需要补齐：把业务 API 的登录态、角色权限、工作区权限做成统一 route dependency；否则只靠前端 `WorkspaceAccess` 不够。
