# 技术标解析与目录生成交接契约

版本日期：2026-06-22

本文定义技术标 S1 结构化解析与 S2 目录生成的交接边界、产物契约、接口契约和后续开发注意事项。目标是让后续同事在开发 S3 缺口识别、素材匹配、AI 填写、S4 成稿或前端审核体验时，能够直接消费当前阶段产物，而不是重复猜测招标文件位置、解析状态、目录来源和证据映射。

## 1. 交接范围

当前已完成的主链路包括：

- 技术标招标文件上传与解析，生成固定技术解读清单结果。
- 技术标解析结果展示，支持按大类查看解读状态、结论和证据。
- 技术标附表/空表产物识别与预览、确认。
- 技术标目录生成，基于投标模板主目录和招标文件证据生成可审核目录。
- 技术标目录审核、人工调整、确认，并进入后续阶段。

本文只约定 S1 解析和 S2 目录生成的交接契约，不展开 S3 缺口识别、S4 文档生成、格式清洗和最终导出的内部实现。后续阶段只能把本文约定的 `published/confirmed` 状态和稳定产物作为正式输入。

## 3. S1 技术标解析契约

### 3.1 触发接口

| 动作 | 方法与路径 | 说明 |
| --- | --- | --- |
| 查询解析结果 | `GET /api/technical/projects/{projectId}/parse-results` | 前端读取当前 S1 结构化结果。 |
| 查询解析进度 | `GET /api/technical/projects/{projectId}/parse-results/progress` | 上传解析超时恢复和轮询使用。 |
| 已有文件重跑解析 | `POST /api/technical/projects/{projectId}/parse-results/run` | 不重新上传，使用项目已记录文件重跑。 |
| 上传并解析 | `POST /api/technical/projects/{projectId}/parse-results/upload-and-run` | 表单字段为 `tenderFiles` 和可选 `templateFiles`。 |
| 上传模板文件 | `POST /api/technical/projects/{projectId}/template-files/upload` | 供后续目录生成使用投标模板。 |
| 附表预览 | `GET /api/technical/projects/{projectId}/parse-results/appendices/{appendixId}/preview` | OnlyOffice 预览配置。 |
| 附表确认 | `POST /api/technical/projects/{projectId}/parse-results/appendices/{appendixId}/approve` | 标记单个附表产物可进入后续。 |
| 批量确认附表 | `POST /api/technical/projects/{projectId}/parse-results/appendices/approve` | 批量确认附表产物。 |

### 3.2 工作区与产物路径

技术标解析 profile 固定为：

```text
schemaVersion: bid-tender-structured-v1
skillName: bid-tech-tender-structured-parser
workspaceDirname: technical-workspace
```

容器内默认工作区：

```text
${DOCUMENTS_DIR}/{projectId}/technical-workspace/
  parse/
    combined.txt
    manifest.json
    s1_parse_manifest.json
    s1_structured_result.json
    parse-result.workspace.json
    s1_nav.sqlite
  appendices/
    APPX-*.docx
```

`parse_storage` 至少应保留这些路径：

| 字段 | 指向 |
| --- | --- |
| `projectDir` | `${DOCUMENTS_DIR}/{projectId}/technical-workspace` |
| `parseDir` | `${DOCUMENTS_DIR}/{projectId}/technical-workspace/parse` |
| `combinedTextPath` | `parse/combined.txt` |
| `structuredResultPath` | `parse/s1_structured_result.json` |
| `manifestPath` | `parse/manifest.json` |
| `skillManifestPath` | `parse/s1_parse_manifest.json` |
| `documents[]` | 每个源文件的 `sourcePath`、`textPath`、`textLength` 等。 |

后续阶段不要自行拼历史临时目录路径，应优先从项目状态里的 `parse_storage` 读取。

### 3.3 结构化结果字段

`s1_structured_result.json` 的顶层结构：

```json
{
  "schemaVersion": "bid-tender-structured-v1",
  "items": [],
  "structured": {}
}
```

`structured` 内稳定可消费字段：

| 字段 | 说明 |
| --- | --- |
| `schemaVersion` | 技术标解析 schema，当前为 `bid-tender-structured-v1`。 |
| `sourceDocuments[]` | 招标文件来源摘要。 |
| `technicalInterpretation` | 固定 58 条技术解读清单，是当前技术标解析的核心交接结果。 |
| `workflow` | skill 运行方式、阶段、session、校验和追踪信息。 |
| `fieldGroups` | 兼容旧展示的项目基础信息、风机参数、性能保证、环境适应等字段组。 |
| `scoringCriteria` | 技术、报价、度电成本、符合性审查等评分/审查项。 |
| `requirementPresence` | 专题方案、供货范围、考核条款等存在性判断。 |
| `coverage` | 覆盖情况汇总。 |
| `appendices[]` | 技术标附表/空表产物。即使为空，也应保留空数组。 |
| `categoryCounts` | 前端概览计数使用。 |
| `opencodeOutput` | skill 输出追踪，供排查使用。 |

`technicalInterpretation` 是后续最可靠的字段，结构如下：

```json
{
  "schemaVersion": "technical-interpretation-v1",
  "checklistVersion": "excel-technical-2026-06-16",
  "categories": [],
  "items": [],
  "summary": {
    "total": 58,
    "found": 0,
    "partial": 0,
    "missing": 0,
    "needs_spec": 0
  }
}
```

每条 `technicalInterpretation.items[]` 必须按 58 条固定清单补齐，关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` / `rowNo` | 清单项唯一标识和原始行号。 |
| `displayGroup` | 前端展示大类。 |
| `primaryCategory` / `secondaryCategory` | 原始一级、二级分类。 |
| `specificContent` | 该清单项具体内容。 |
| `status` | 只能是 `found`、`partial`、`missing`、`needs_spec`。 |
| `conclusion` | 给业务人员看的判断结论。 |
| `evidenceSummary` | 一句话证据摘要。 |
| `neededSourceName` | `needs_spec` 时必填，必须使用招标文件原文名称。 |
| `evidenceRefs[]` | 已物化证据，前端展开证据和后续追溯使用。 |

`evidenceRefs[]` 的稳定字段：

| 字段 | 说明 |
| --- | --- |
| `id` | `s1_nav.sqlite` 中的证据编号。 |
| `sourceDocumentId` | 源文件 ID。 |
| `sourceFile` | 源文件名。 |
| `section` | 证据所在标题路径。 |
| `evidenceLocation` | 证据位置描述。 |
| `text` | 原文证据片段。 |

后续开发不要只依赖 `evidenceIds`，因为对前端和下游来说，`evidenceRefs` 才是可直接展示、可审计的证据对象。后端 `GET /parse-results` 会从 `s1_nav.sqlite` 物化证据；如果改动证据结构，要同步更新物化逻辑和前端展示工具。

### 3.4 状态判断规则

技术解读状态语义：

| 状态 | 语义 | 后续处理 |
| --- | --- | --- |
| `found` | 当前文件中有明确、直接的原文依据。 | 可作为已覆盖要求进入后续引用。 |
| `partial` | 找到部分依据，但未覆盖全部子要求或细节。 | 后续缺口识别应把未覆盖部分转为补充材料任务。 |
| `missing` | 当前文件包中未找到直接依据。 | 后续可以作为缺口候选，但不应编造要求。 |
| `needs_spec` | 当前文件明确指向某个缺失来源。 | 必须提示补充 `neededSourceName` 对应文件或附件。 |

`found` 和 `partial` 必须有证据；`needs_spec` 必须有 `neededSourceName`。这是 skill 校验规则，也是后续开发必须遵守的契约。

## 4. S2 技术标目录生成契约

### 4.1 触发接口

| 动作 | 方法与路径 | 说明 |
| --- | --- | --- |
| 查询目录生成状态 | `GET /api/technical/projects/{projectId}/directory-generation` | 返回 `directory_state`，含任务、事件、opencode 输出和证据摘要。 |
| 监听目录生成进度 | `GET /api/technical/projects/{projectId}/directory-generation/stream` | SSE，前端用于实时更新进度。 |
| 触发目录生成 | `POST /api/technical/projects/{projectId}/directory-generation/run` | 异步启动，重复运行时会做并发保护。 |
| 查询审核目录 | `GET /api/technical/projects/{projectId}/outline` | 返回 `outline_state` 和招标文件预览信息。 |
| 保存审核目录 | `PUT /api/technical/projects/{projectId}/outline` | 保存人工调整后的 `nodes`。 |
| 重新生成目录 | `POST /api/technical/projects/{projectId}/outline/regenerate` | 从当前状态重新生成草稿目录。 |
| 确认目录 | `POST /api/technical/projects/{projectId}/outline/confirm` | 将 `reviewStatus` 置为 `confirmed`，推进阶段。 |
| 目录证据文件预览 | `GET /api/technical/projects/{projectId}/outline/tender-files/{fileId}/file` | 供 OnlyOffice 打开招标文件并定位证据。 |

### 4.2 生成前置条件

触发 S2 前必须满足：

- S1 已完成并能读取 `parse_storage.combinedTextPath`。
- `combined.txt` 非空。
- 项目已上传可读取的投标模板文件。
- 招标文件记录仍能从项目输入记录中找到。

如果缺少 `combined.txt`，目录生成会报“请先完成解析”；如果缺少投标模板，会报“请先上传可读取的投标模板文件”。

### 4.3 工作区与产物路径

目录生成使用技术标工作区：

```text
${DOCUMENTS_DIR}/{projectId}/technical-workspace/
  s2_toc_workdir.new/
    s2_input.json
    toc.json
    toc_evidence.json
  s2_toc_workdir/
    s2_input.json
    toc.json
    toc_evidence.json
  s2_toc_workdir.runs/
    <archived-runs>/
```

发布规则：

- 新一轮生成先写入 `s2_toc_workdir.new`。
- 生成和路径重写成功后，再移动为正式 `s2_toc_workdir`。
- 如果已有成功版本，会归档到 `s2_toc_workdir.runs`。
- 如果新一轮失败，旧的 `s2_toc_workdir` 必须保留。
- `s2.json` 旧别名不再作为正式产物使用。

`s2_input.json` 关键字段：

| 字段 | 说明 |
| --- | --- |
| `projectId` / `projectCode` / `projectName` | 项目信息。 |
| `bidType` | 必须是技术标。 |
| `workDir` | 当前 S2 工作区。 |
| `tenderFiles[]` | 招标文件副本列表。 |
| `templateFile` | 投标模板文件。 |
| `attachFile` | 可选附件模板。 |
| `outputFile` | `toc.json` 输出路径。 |
| `evidenceFile` | `toc_evidence.json` 输出路径。 |
| `reviewBudget` | 目录审核压缩预算。 |

### 4.4 目录产物结构

`toc.json` 使用：

```text
schema_version: bid-toc-json-v1
```

关键字段：

| 字段 | 说明 |
| --- | --- |
| `items[]` | 扁平目录项，后端会转换为前端树形 `nodes`。 |
| `summary` | 总数、来源等概览。 |
| `outputFile` / `evidenceFile` | 发布后的正式路径。 |

每个 `items[]` 稳定字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 目录项 ID。 |
| `number` / `tocNumber` | 目录编号。 |
| `title` | 目录标题。 |
| `level` | 目录层级。 |
| `annotation` | 目录项说明，如模板来源或新增副表。 |
| `required_status` / `requiredStatus` | 必要性状态，常见为“必要”“可选”“待确认”。 |
| `source` | 来源，技术标目录只应来自 `template` 或 `tender`。 |
| `source_refs[]` | 可追溯证据。 |
| `material_refs[]` | 技术标 S2 不使用素材库，当前应为空数组。 |

`source_refs[]` 稳定字段：

| 字段 | 说明 |
| --- | --- |
| `type` | `template` 或 `tender`。 |
| `role` | 常见为 `basis`。 |
| `fileId` / `fileName` | 来源文件。 |
| `path` | 源文件路径。 |
| `paragraphIndex` | 段落索引。 |
| `basisText` | 依据原文。 |
| `searchText` | OnlyOffice 搜索定位文本，尽量保持原文写法。 |

`toc_evidence.json` 使用：

```text
schema_version: bid-toc-evidence-v1
engine: bid-tech-outline-generator
```

它包含模板目录、招标文件候选、Agent 决策和规则配置。前端和后续阶段优先消费 `directory_state.ruleEvidence` 中压缩后的摘要；只有排查问题或人工深查时才读取完整 `toc_evidence.json`。

### 4.5 目录状态结构

目录生成完成后，项目会写入 `directory_state`：

```json
{
  "status": "completed",
  "percentage": 100,
  "summary": "...",
  "generatedAt": "...",
  "output": {
    "fileName": "项目名_目录.docx",
    "fileType": "docx",
    "chapterCount": 0
  },
  "opencodeOutput": {},
  "ruleEvidence": {},
  "events": [],
  "tasks": []
}
```

稳定状态：

| 状态 | 语义 |
| --- | --- |
| `idle` | 尚未开始。 |
| `running` | 后台生成中。 |
| `completed` | 已生成并发布到 `s2_toc_workdir`。 |
| `failed` | 本轮失败，旧成功产物如果存在应保留。 |

`opencodeOutput` 稳定字段：

| 字段 | 说明 |
| --- | --- |
| `engine` / `skill` | 技术标应为 `bid-tech-outline-generator`。 |
| `status` | `waiting`、`received`、`failed` 等运行态。 |
| `workDir` | 正式 `s2_toc_workdir`。 |
| `manifestPath` / `canonicalManifestPath` | 正式 `s2_input.json`。 |
| `tocJsonPath` | 正式 `toc.json`。 |
| `evidencePath` | 正式 `toc_evidence.json`。 |
| `parts[]` | 流式输出的尾部片段，最多保留尾部片段。 |

生成完成后还会写入 `outline_state`：

```json
{
  "outlineVersion": 1,
  "reviewStatus": "draft",
  "generatedAt": "...",
  "summary": {
    "totalNodeCount": 0
  },
  "nodes": []
}
```

`reviewStatus` 流转：

| 状态 | 语义 | 后续处理 |
| --- | --- | --- |
| `draft` | 已生成或已人工编辑，但未确认。 | 只能作为审核草稿。 |
| `confirmed` | 人工确认完成。 | 后续 S3/S4 可以正式消费。 |

## 5. S1 到 S2 的数据依赖

S2 目录生成依赖 S1 的最小集合：

- `parse_storage.combinedTextPath`：招标文件合并文本，用于确认 S1 已完成并提供招标文本输入。
- `parse_storage.documents[]`：用于复制招标文件到 S2 工作区，保留文件 ID 和文件名。
- 项目上传的模板文件：作为目录主骨架来源。
- 项目信息：`projectId`、`projectCode`、`projectName`、`bidType`。

S2 不直接依赖 `technicalInterpretation.items[]` 生成目录。技术解读清单服务于需求解读、缺口识别和证据展示；目录生成服务于投标文件结构搭建。后续如果要把 S1 解读清单反向影响目录，必须显式增加契约字段，不能在现有字段里隐式复用。

## 6. 前端消费契约

解析页消费：

- `technicalParseAPI.uploadAndRun` 负责上传并解析。
- `technicalParseAPI.progress` 用于超时恢复和轮询。
- `technicalParseAPI.results` 读取 `structured.technicalInterpretation`、`fieldGroups`、`scoringCriteria`、`appendices`。
- `technicalInterpretation.js` 负责把 58 条清单按展示大类分组，并生成证据展开行。

目录页消费：

- `technicalDirectoryAPI.status` 读取 `directory_state`。
- `technicalDirectoryAPI.run` 触发生成。
- `technicalDirectoryAPI.stream` 监听 SSE。
- `technicalOutlineAPI.get` 读取 `outline_state`。
- `technicalOutlineAPI.save` 保存人工调整后的 `nodes`。
- `technicalOutlineAPI.confirm` 确认目录并推进阶段。

`TechnicalOutlineReview.jsx` 对目录证据的兼容读取规则：

- 优先读 `node.sourceRefs`。
- 兼容读 `node.source_refs`。
- 证据定位优先使用 `searchText`，其次 `basisText`、`rawText`、`title`。

后续前端改动要保持 camelCase 和 snake_case 的兼容，除非同步完成后端、测试和历史数据迁移。

## 7. 后续开发边界

后续阶段可以依赖：

- S1：`structured.technicalInterpretation.items[]` 的 58 条全量清单和 `evidenceRefs[]`。
- S1：`structured.appendices[]` 中已确认的技术附表产物。
- S2：`outline_state.reviewStatus == "confirmed"` 的目录树。
- S2：`directory_state.opencodeOutput.tocJsonPath` 和 `evidencePath` 对应的正式产物。
- S2：目录节点中的 `sourceRefs/source_refs` 和 `requiredStatus/required_status`。

后续阶段不要依赖：

- `s2_toc_workdir.new`，它只是 staging 目录。
- `s2.json` 旧别名。
- `opencodeOutput.parts[]` 的完整性，它只保留尾部片段。
- `toc_evidence.json` 的全量候选结构作为业务主数据。
- S1/S2 运行中的临时 stdout 文本。
- 未确认的 `outline_state.reviewStatus == "draft"` 作为正式目录。

如果需要新增字段，必须遵守：

- 后端落盘 JSON、API 返回、前端读取、测试样例同步更新。

- 对同一语义同时存在 snake_case 和 camelCase 时，读端必须保持兼容。
- 证据字段必须能回查到源文件、段落或导航证据编号。

## 10. 常见风险

- 技术解读清单是固定 58 条，不能因为某次文件缺失就减少 `items[]`。
- `needs_spec` 不是失败状态，它表示原文指向了当前文件包外的资料来源。
- 目录生成以投标模板为主骨架，招标文件证据只补充依据和必要副表，不应随意把素材库内容写入 S2 目录。
- 新一轮 S2 生成失败时，不能破坏上一轮成功的 `s2_toc_workdir`。
- 前端目录证据跳转依赖 `searchText/basisText`，后端清洗时不要过度改写原文。
- S1 解析和 S2 目录是两个阶段，不能把 S1 的 `technicalInterpretation` 当作目录树，也不能把 S2 的 `toc.json` 当作需求解读清单。
