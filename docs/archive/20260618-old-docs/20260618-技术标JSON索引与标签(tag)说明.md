# 技术标三级目录 JSON 索引 —— 位置、使用方式与标签(tag)嵌套说明

> 给协作同事的说明文档。读完你能知道：这份 JSON **在哪、谁生成、怎么读、怎么写**，以及 **tag 是怎么一层层嵌在里面的、真值在哪、改名移动会不会丢**。

---

## 1. 这是什么

技术标素材库维护一份**动态重建的三级目录结构 JSON 索引**，作为「Wiki 构建 / 项目解析 / 标签标注」共同依赖的**约定层**。

- 它**镜像素材库的目录结构**：一级=档位（标准文件/客户定制/项目定制），二级=三级目录（机型号/客户名/项目标识），三级=文件。
- 结构是**确定性生成**的（从数据库实时重建，不走 LLM）。
- **从 v2 起，它还承载标签(tag)**，并且 **tag 的真值就在这份 JSON 里**（详见第 4 节）。

当前版本：`schemaVersion = 2`。

## 2. 存放位置（生成/落盘的位置）

| 项 | 值 |
| --- | --- |
| **容器内磁盘路径** | `/data/documents/_runtime/materials/technical_material_index.json` |
| **所在卷** | Docker named volume `documents`（`DOCUMENTS_DIR=/data/documents`） |
| **代码常量** | `app/services/technical_material_index.py` → `TECHNICAL_MATERIAL_INDEX_PATH` |

> ⚠️ **重要**：这是数据卷里的运行期产物，**宿主机源码目录下看不到**。要直接看文件，得进 `sewpg_bid_fastapi` 容器：
> ```bash
> docker exec sewpg_bid_fastapi cat /data/documents/_runtime/materials/technical_material_index.json
> ```

### 谁生成它（写盘时机）

- **自动**：素材库任何**改结构**的操作（建/删/移目录、移/删文件、上传、拆分、改名、bootstrap）完成后，钩子 `TechnicalMaterialStore._refresh_index` 会**自动重建**这份索引。
- **手动/兜底**：调只读接口时若文件为空，会即时重建一次再返回。
- 写盘是**原子写 + 进程锁**：先写 `.tmp` 再 `os.replace` 换名，且 rebuild 与「人工打 tag」串行，避免并发写丢数据。

## 3. 使用位置（在哪读、在哪写）

### 3.1 只读接口（取整份索引）

```
GET /api/technical/materials/index
```
- 返回整棵三级树（含每级的 tags）。
- 若索引尚未生成或被清空，会即时 rebuild 再返回。

### 3.2 写 tag 接口（给某个节点打标签，v2 新增）

```
PUT /api/technical/materials/index/tags
Content-Type: application/json

{ "targetId": "<目标节点>", "tags": ["标签1", "标签2"] }
```

`targetId` 的取值规则：

| targetId 形如 | 命中节点 | 例 |
| --- | --- | --- |
| `RAW-xxxx`（以 `RAW-` 开头） | **文件** | `"RAW-0182"` |
| 数字（folderId） | **档位(tier)或三级目录(folder)** | `"120"` |
| 目录 path | 同上（folderId 的备选） | `"技术标/项目定制/xxx项目"` |

- `tags` 会经 `normalize_material_tags` 规整：**去重、去空白、单条≤40字、最多20个**；也支持传字符串（如 `"AI填写,固定素材"` 会按逗号/分号/换行切分）。
- 返回：成功 `{ "ok": true, "node": {…该节点…} }`；定位失败 `{ "ok": false, "error": "未在索引中找到节点：xxx" }`。
- **设空 tag** = 清除：`{"targetId":"120","tags":[]}`。

### 3.3 代码内调用（后端/脚本）

```python
from app.services.technical_material_index import (
    load_technical_material_index,    # 读已落盘索引，无则返回 {}
    rebuild_technical_material_index, # 重建并写盘（async，best-effort）
    set_tags_for_node,                # 给某节点打 tag（async，真值落 JSON）
)
```

### 3.4 下游消费方

- **技术标 Wiki**（`/workspace/tech/materials/wiki`）：目录树严格镜像这份索引，tag 字段会随索引透传，无需改镜像逻辑。
- **客户/机型候选弹窗**、**项目解析**等：直接 import 这份 JSON 作为三级结构基准。

## 4. 标签(tag) 是怎么嵌在 JSON 里的 ★

这是本文档的重点。

### 4.1 一句话原则

> **每一级节点（档位 / 三级目录 / 文件）都各自挂一个 `tags` 数组，记录“这一级自己的标签”。不向上聚合、不向下继承——目录的 tag 属于目录，文件的 tag 属于文件，互不串味。**

所以从最粗的档位到最细的文件，每一层都能就地打标签并被记录。

### 4.2 结构示意（节选真实数据，tags 已就地标注以作演示）

```jsonc
{
  "bidType": "技术标",
  "schemaVersion": 2,
  "tagsSourceOfTruth": "index",      // ← 标记：tag 真值在本 JSON，不在数据库
  "generatedAt": "2026-06-18 09:20:42",
  "stats": { "tierCount": 3, "thirdLevelFolderCount": 8, "fileCount": 526 },

  "tiers": [
    {
      "name": "项目定制",
      "tier": "project",
      "path": "技术标/项目定制",
      "folderId": "119",             // ← 档位级的 tag 认领键
      "fileCount": 45,
      "tags": ["重点档位"],          // ← ① 档位级 tag（挂在 tier 上）
      "folders": [
        {
          "name": "华能赤峰…120万千瓦风电项目北区",
          "path": "技术标/项目定制/华能赤峰…",
          "tier": "project",
          "folderId": "120",         // ← 目录级的 tag 认领键
          "customerName": "",
          "projectId": "华能赤峰…",
          "fileCount": 28,
          "tags": ["重点客户", "资质"], // ← ② 目录级 tag（挂在三级目录上）
          "files": [
            {
              "id": "RAW-0182",       // ← 文件级的 tag 认领键
              "name": "待填写-供货范围概述.docx",
              "path": "技术标/项目定制/华能赤峰…/待填写-供货范围概述.docx",
              "ext": "docx",
              "cleanStatus": "cleaned",
              "tags": ["AI填写"]      // ← ③ 文件级 tag（挂在 file 上）
            }
          ]
        }
      ]
    }
  ]
}
```

三处 `tags` 各自独立：①档位、②目录、③文件，谁也不影响谁。

### 4.3 每级的 tag 字段一览

| 层级 | 节点字段 | tag 字段 | 认领键(rebuild 时靠它把 tag 贴回) |
| --- | --- | --- | --- |
| 档位 tier | tiers[] | `tags` | `folderId`（数字字符串） |
| 三级目录 folder | tiers[].folders[] | `tags` | `folderId` |
| 文件 file | …folders[].files[] | `tags` | `id`（`RAW-xxxx`） |

### 4.4 tag 的真值在哪（关键，务必理解）

- **tag 的真值 = 这份 JSON 索引自身**（顶层 `tagsSourceOfTruth: "index"` 即为标记）。
- 数据库 `raw_files.ext_fields.tags` **不再是 tag 真值**——它只在「首次迁移」（旧索引不存在或 `schemaVersion < 2`）时，被当作种子灌进 JSON 一次；之后改 tag 一律改 JSON。
- 因此：**要给技术标素材打/改 tag，请走 `PUT /api/technical/materials/index/tags`**，不要再直接写数据库的 `ext_fields.tags`（那样不会进索引，等于没生效）。

### 4.5 结构变更 / 改名 / 移动时，tag 会不会丢？

不会（在认领键稳定的前提下）。rebuild 是 **merge-preserve**：

- **结构**（有哪些目录/文件、谁移动了）每次从**数据库**实时取；
- **tag** 从**旧 JSON** 按认领键贴回新树：文件用 `id`(`RAW-xxxx`)、目录用 `folderId`。

由此：

| 操作 | tag 表现 |
| --- | --- |
| 文件改名 / 移动到别的目录 | **tag 跟随**（认 `RAW-id`，与 path 无关）✅ 已实测 |
| 目录改名 / 移动 | tag 跟随（认 `folderId`）✅ |
| 文件被真正删除 | 该文件的 tag 随之消失（合理）✅ |
| 上传新文件 / 新建目录 | tag 默认空 `[]` ✅ |

## 6. 注意事项（连带影响，给后端同事）

迁移到「JSON 唯一真值」后，以下**仍在读/写数据库 `ext_fields.tags` 的旧点不再是准的**，目前未改，后续要用到技术标 tag 时需注意：

- 读 DB tag（结果可能过期）：`material_raw_file_filter.py`（按 tag 过滤素材列表）、`wiki_generation.py`（Wiki 卡片 tag）。
- 写 DB tag 的旧入口：`material_update_metadata.py`、`material_tag_import*.py`——它们写的 tag **不会进索引**。
- 结论：**技术标的 tag 读写,统一以 JSON 索引为准**（读 `GET .../index`，写 `PUT .../index/tags`）。

> 本次仅技术标。商务标走的是另一条 LLM 精修链路，不在此索引范围。
