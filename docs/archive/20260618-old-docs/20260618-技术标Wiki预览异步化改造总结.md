# 技术标 Wiki 内容预览改造：从同步阻塞到异步后台任务

> 工作总结 ｜ 编写日期：2026-06-18
> 关联文档：《技术标 Wiki 架构与使用指南》（本次改造让该文档第 4 节描述的「同步生成预览」链路过时，以本文为准）

---

## 1. 背景与现象

用户在 `http://localhost/workspace/tech/materials/wiki` 点「重建 Wiki」后反馈两个问题：

1. **点了重建半天没响应**（最终超时报错）。
2. **大量文件卡片信息量不足**——只有「文件定位 / 所属档位 / 本卡片仅为三级目录结构索引」这种纯目录壳，没有内容预览卡片。

用户贴出的样例（`螺栓在线监测分析系统（钢塔）.docx`，RAW-0583）就是一张退化成纯索引的空壳卡。

---

## 2. 排查与根因（已用线上数据实测确认）

### 2.1 链路追踪

```
前端「重建Wiki」按钮 (TechnicalMaterialWiki.jsx)
   └─ POST /api/technical/materials/wiki/bootstrap   (前端超时 10 分钟)
        └─ generate_platform_wiki → _generate_technical_wiki
             └─ rebuild_technical_material_index(enrich_preview=True)   ← 同步阻塞
                  └─ _enrich_previews：为每个 docx 调 LLM 生成预览
```

整条链路是**全同步阻塞**：HTTP 响应必须等到所有 docx 的 LLM 预览跑完才返回。

### 2.2 实测数据（改造前）

| 检查项 | 结果 |
|---|---|
| 索引文件总数 | 526（其中 docx 324、应生成预览的 docx 511） |
| **实际带预览的卡片** | **0** |
| DB `ext_fields.techWikiPreview` 状态分布 | `completed: 2`，`NONE: 554`（绝大多数压根没被处理） |
| RAW-0583（样例文件） | `techWikiPreview = None`（从没被处理过） |
| 单文件预览耗时（实测 RAW-0583） | 解析 0.5s + **LLM 15.1s**，内容质量很好 |

### 2.3 根因结论

**不是逻辑缺失，而是量级 × 同步 × 超时三者叠加：**

- 511 个文件 × ~15s ÷ 并发 4（`PREVIEW_CONCURRENCY=4`）≈ **32 分钟**。
- 前端 bootstrap HTTP 超时只有 **10 分钟**。
- 结果：请求必然在 10 分钟时超时断开 → 连接一断，`_enrich_previews` 那批协程的 `session.commit()` 还没走到 → 只有零星几个先写进 DB（所以 `completed` 只有 2）。
- 镜像脚本（`run_from_manifest.py`）对没有 `preview` 字段的文件**自动降级成纯目录卡片** → 用户看到的就是空壳卡。

**一句话**：500+ 个文件 ×15 秒的 LLM 调用塞进了一个 10 分钟超时的同步 HTTP 请求里，跑不完就被掐断，预览全丢、卡片集体降级。

---

## 3. 改造方案：重建秒级返回 + 预览异步后台增量生成

核心思路是**解耦**：把「快的结构镜像」与「慢的 LLM 预览生成」拆成两条独立链路。

```
①「重建Wiki」（秒级返回）
    rebuild_technical_material_index(preview_mode="cached")
    → 只读 DB 已缓存预览注入，不调 LLM
    → 缺预览的 docx 先降级为纯目录卡片
    → 立即返回结构树

② 重建成功后，前端自动触发后台任务
    POST /api/technical/materials/wiki/previews/generate
    → 丢进 Redis 队列（job_type = technical_wiki_preview）

③ worker 后台增量生成（不受 HTTP 超时约束）
    → preview_mode="generate"：调 LLM 补齐缺失预览（命中指纹缓存的不重算）
    → 进度落盘，前端 3s 轮询 GET .../previews/status
    → 全部跑完后用 _mirror_technical_index_to_wiki(mode="replace") 重镜像
    → 带预览的卡片落到 Wiki 树上

④ 前端轮到 completed → 自动刷新 Wiki，卡片更新
```

### 3.1 `preview_mode` 三态

把原来的布尔 `enrich_preview` 升级为三态 `preview_mode`，语义更清晰：

| 模式 | 行为 | 用在哪 |
|---|---|---|
| `none` | 完全跳过预览，只重建结构 + 认领 tag | 结构变更钩子（上传/移动/删除，很频繁） |
| `cached` | 只读 DB 已生成（completed）预览注入，**不调 LLM（秒级）** | 重建/刷新 Wiki、人工打 tag 兜底重建 |
| `generate` | 增量调 LLM 补齐缺失预览（慢） | 后台预览任务 |

## 7. 设计要点与注意事项

- **预览缓存仍按内容指纹增量**（DB `ext_fields.techWikiPreview`）：文件没变 / 已生成的不会重复调 LLM，所以后续重建只补齐新增/变更文件，很快。
- **best-effort 原则保持不变**：预览生成失败不阻断结构镜像，最坏情况退化为纯目录卡片。
- **任务全局单例**：用 Redis job 锁（`job_type=technical_wiki_preview`，`project_id` 固定为 bidType）保证同一时刻只跑一个预览任务；前端首屏会探测在跑的任务并自动续上轮询。
- **递归 7 天自动过期不涉及**（这是定时任务概念，本任务是一次性 enqueue，不冲突）。
- **实测速度比预估快很多**：单文件串行测试是 15s，但实跑 472 个文件在数十秒内完成——opencode 后端有并发/批处理优化，且大量命中指纹缓存。即便如此，异步化仍是正确方案——它彻底摆脱了 HTTP 超时这一硬约束，文件再多也不会失败。
