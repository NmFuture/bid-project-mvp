# 技术标 Wiki 架构与使用指南

> 面向同事的入门介绍：Wiki 是什么、数据怎么组织、怎么生成、怎么读取。
> 编写日期：2026-06-18 ｜ 适用：技术标 Wiki（商务标走另一条 LLM 链路，本文末尾简述差异）

---

## 1. 一句话理解

**Wiki 是素材库的"知识树视图"**：把技术标素材库里的文件，按 `档位 → 3 级目录 → 文件` 的三层结构，自动镜像成一棵可浏览的文档树。每个节点是一张 Markdown 卡片。

- **结构真值在数据库素材库**（raw_files / raw_folders）。
- **Wiki 树是它的确定性镜像**——技术标 Wiki **不经过 LLM 编排树结构**，目录树严格等于素材库三级结构。
- **唯一用到 LLM 的地方**：给每个 docx 文件卡片生成一段「内容预览」（导读/要点/关键参数/检索提示），这是可选增强，失败也不影响树生成。

---

## 2. 三层结构长什么样

```
技术标Wiki（自动生成）              ← 根节点
├── 01-标准文件 (standard)          ← 一级 = 档位 tier
│   └── EW5.0-220                   ← 二级 = 3 级目录（机型号/分类）
│       └── 发电机位移监测分析系统.docx   ← 三级 = 文件卡片
├── 02-客户定制 (customer)          ← 二级目录名 = 客户名
└── 03-项目定制 (project)           ← 二级目录名 = 项目标识
```

三个档位（tier）固定顺序：**标准文件 → 客户定制 → 项目定制**。

> ⚠️ **深层归并**：素材库里 3 级以下还有更深的子目录（如上例 `EW5.0-220/专题/数字化智慧风场专题/智能传感系统/xxx.docx`），这些文件会被**归并到所属的 3 级目录**下平铺展示，完整原始层级保留在卡片的「完整路径」字段里。

---

## 3. 数据怎么存（数据库）

Wiki 在数据库里是三张表（`app/models/materials.py`）：

| 表 | 作用 | 关键字段 |
|---|---|---|
| `wiki_nodes` | 树节点 | `id`、`parent_id`（自引用建树）、`title`、`tier`、`path`、`bid_types[]`、`sort_order` |
| `wiki_docs` | 节点正文（1:1） | `node_id`、`markdown_content`、`ai_summary`、`tags[]` |
| `wiki_attachments` | 节点附件（1:N） | `doc_id`、`file_name`、`minio_key`、`minio_bucket` |

- **树靠 `parent_id` 表达**：`parent_id IS NULL` 是根节点。
- **节点正文是 Markdown**：存在 `wiki_docs.markdown_content`，前端直接渲染。
- **附件存 MinIO**，表里只存 key。

## 4. 生成链路（从素材到 Wiki）

技术标 Wiki 的生成入口是 `_generate_technical_wiki`（`app/services/wiki_generation.py`），四步：

```
POST /api/technical/materials/wiki/bootstrap
        │
        ▼
① 重建三级目录索引 JSON  rebuild_technical_material_index(enrich_preview=True)
   - 从 DB 实时读素材结构
   - 为每个 docx 增量生成 AI 预览（见 §6）
   - 落盘到 /data/documents/_runtime/materials/technical_material_index.json
        │
        ▼
② 写 manifest  _write_technical_index_manifest()
   - 把索引 JSON 包成 manifest 丢到临时构建目录
        │
        ▼
③ 镜像脚本生成 blueprint  run_from_manifest.py（subprocess 跑，纯模板，不调 LLM）
   - 读索引 JSON → 渲染成 {summary, rootTitle, nodes[...]}
   - 每个 file → 一张文件卡片 markdown
        │
        ▼
④ 导入数据库  _import_generated_wiki_blueprint(mode="create")
   - mode=create：删掉同名旧根节点整棵树，重建
   - 递归创建 wiki_nodes + wiki_docs
```

**关键点**：第 ③ 步的镜像脚本只读「索引 JSON」，它**不碰数据库、不调 LLM**，纯粹把 JSON 翻译成 Markdown 树。所有"智能"都在第 ① 步预生成好写进 JSON。

---

## 5. 数据源：三级目录索引 JSON

`technical_material_index.json`（落盘在 `/data/documents/_runtime/materials/`）是 Wiki 的中间数据源，`schemaVersion = 2`，结构 `tiers → folders → files`：

```jsonc
{
  "bidType": "技术标",
  "schemaVersion": 2,
  "tagsSourceOfTruth": "index",
  "generatedAt": "2026-06-18 10:30:00",
  "stats": { "tierCount": 3, "thirdLevelFolderCount": 8, "fileCount": 526 },
  "tiers": [
    {
      "tier": "standard", "name": "标准文件", "path": "技术标/标准文件",
      "folderId": "...", "fileCount": 324, "tags": [],
      "folders": [
        {
          "name": "EW5.0-220", "path": "技术标/标准文件/EW5.0-220",
          "tier": "standard", "folderId": "...", "fileCount": 12,
          "tags": [],                          // ← 目录级 tag（人工打）
          "files": [
            {
              "id": "RAW-0369",
              "name": "发电机位移监测分析系统.docx",
              "path": "技术标/标准文件/EW5.0-220/专题/.../发电机位移监测分析系统.docx",
              "ext": "docx",
              "cleanStatus": "cleaned",
              "tags": [],                      // ← 文件级 tag（人工打，真值在此 JSON）
              "preview": {                     // ← AI 内容预览（仅 docx、生成成功时才有）
                "lead": "一句话导读 ≤80字",
                "points": ["要点1","要点2","要点3"],
                "keyParams": [{"label":"轮毂高度","value":"160m"}],
                "retrievalHints": ["混塔","160米"]
              }
            }
          ]
        }
      ]
    }
    // customer 档：folder 带 customerName；project 档：folder 带 projectId
  ]
}
```

### 两个"真值"要分清

| 数据 | 真值存哪 | 怎么改 |
|---|---|---|
| **结构**（哪些档位/目录/文件） | 数据库素材库 | 上传/移动/删除文件 → 钩子自动刷新索引 |
| **tag**（标签） | **index JSON 自身** | `PUT .../index/tags`（`set_tags_for_node`），按节点 id 认领，改名/移动不丢 |
| **AI 预览** | **数据库 `raw_files.ext_fields.techWikiPreview`** | 生成 Wiki 时增量生成（带内容指纹缓存） |

## 6. AI 内容预览（文件卡片的"导读"）

这是最近新增的功能。**默认情况下文件卡片只有目录索引信息**（material_id / 路径 / 档位 / 清洗状态）；开启预览后，卡片顶部会多一段 AI 生成的内容导读。

### 卡片对比

**无预览（旧 / 非 docx / 解析失败时降级）：**
```markdown
# 发电机位移监测分析系统.docx
## 文件定位
- material_id: RAW-0369
- 完整路径: `技术标/标准文件/EW5.0-220/专题/.../发电机位移监测分析系统.docx`
- 扩展名: docx
- 清洗状态: 已清洗 (cleaned)
## 所属档位
- tier: standard (标准文件)
- 3 级目录: EW5.0-220
> 本卡片仅为三级目录结构索引，不承载文件正文。
```

**有预览（docx 生成成功，tags 多一个「AI预览」）：**
```markdown
# 混塔计算结果简要说明.docx

## 内容预览（AI 生成）
> 本文件为国电投河北邢台50MW项目混塔结构计算结果说明，用于技术标塔架方案章节。

**要点**
- 采用160m混塔方案
- 适配6.25MW机型
- 含强度与疲劳校核结论

**关键参数**
| 参数 | 值 |
|---|---|
| 轮毂高度 | 160m |
| 适用机型 | 6.25MW |

**检索提示**: 混塔 · 塔架计算 · 160米 · 邢台50MW

---
## 文件定位
- material_id: RAW-0220
...（下方索引字段不变）
```

### 预览的机制要点

- **何时生成**：只有 Wiki 生成（bootstrap）时才调 LLM（`enrich_preview=True`）；频繁的上传/删除钩子**不会**触发 LLM。
- **增量缓存**：缓存在 DB，按内容指纹（文件名 + Heading + 正文摘录）判定。内容没变就复用，不重复烧钱。实测：首次约 15s/文件，命中缓存 0.4s。
- **内容来源**：用素材已抽取的 Heading + 最多 10 段正文摘要，不读完整正文。
- **降级**：非 docx / 超 30MB / 解析失败 / LLM 超时 → 自动退回纯索引卡片，不阻断 Wiki 生成。
- **并发**：首次全量生成时最多 4 个文件并发调 LLM。

> 📌 **现状提醒**：当前线上 Wiki 是在预览功能上线前生成的，文件卡片**还没有**预览区。要让预览出现，需要**重新跑一次 bootstrap**（见 §8）。当前库有约 324 个 docx，全量首次生成约 15~20 分钟。

## 7. 怎么读取 Wiki（API）

技术标前缀 `/api/technical/materials/wiki`，商务标把 `technical` 换成 `business` 即可，接口一致。

### 读取类（同事最常用）

**① 取整棵树**
```
GET /api/technical/materials/wiki
```
返回：
```jsonc
{
  "tree": [                         // 树（懒加载内容，只有结构）
    {
      "id": "WIKI-3032",
      "title": "技术标Wiki（自动生成）",
      "icon": "...",
      "expanded": true,
      "children": [
        { "id": "WIKI-3033", "title": "01-标准文件", "children": [...] }
      ]
    }
  ],
  "selectedNode": { ... },          // 默认选中节点的详情
  "tagOptions": [...],              // 可选 tag 列表（供筛选）
  "applicableTypeOptions": [...]
}
```
> 树节点只含 `id / title / icon / expanded / children`，**正文不在树里**，要单独取。

**② 取单个节点的正文卡片**
```
GET /api/technical/materials/wiki?nodeId=WIKI-3035
```
返回 `selectedNode`：
```jsonc
{
  "id": "WIKI-3035",
  "title": "发电机位移监测分析系统.docx",
  "markdownContent": "# ...\n## 内容预览（AI 生成）\n...",  // ← 卡片正文，前端渲染这个
  "aiSummary": "...",
  "tags": ["技术标","文件卡片","标准文件","docx"],
  "applicableTypes": ["技术标"],
  "path": "...",
  "pathText": "...",
  "updatedAt": "...",
  "attachments": []
}
```

**典型读取流程**：先 `GET wiki`（拿树）→ 用户点某节点 → `GET wiki?nodeId=xxx`（拿该节点 markdownContent）→ 前端用 Markdown 渲染。

### 写入/管理类

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/wiki/bootstrap` | **生成/重建整棵 Wiki**（body 可空 `{}`） |
| `POST` | `/wiki` | 手动新建节点（`{parentId, title, ...}`） |
| `PUT` | `/wiki/{node_id}` | 改节点标题/正文/tag |
| `DELETE` | `/wiki/{node_id}` | 删节点及其子树 |
| `POST` | `/wiki/{node_id}/move` | 移动节点（`{targetId, mode}`） |
| `POST` | `/wiki/{node_id}/attachments` | 上传附件 |
| `GET` | `/wiki/attachments/{id}/content` | 下载附件 |
| `POST` | `/wiki/{node_id}/refresh-summary` | 重新生成节点 AI 摘要 |
| `PUT` | `/api/technical/materials/index/tags` | 给索引节点打 tag（tag 真值落 JSON） |
| `GET` | `/api/technical/materials/index` | 直接读三级目录索引 JSON |

---

## 8. 实操：重新生成带预览的 Wiki

```bash
# 触发生成（首次约 15~20 分钟，含全量 LLM 预览；之后增量重建命中缓存会很快）
curl -X POST http://<backend>/api/technical/materials/wiki/bootstrap \
     -H 'Content-Type: application/json' -d '{}'
```
返回里 `generation` 字段会带统计（档位数/目录数/文件数）。生成完成后，前端打开 Wiki 页面、点开任意 docx 文件卡片，即可看到「## 内容预览（AI 生成）」区块。

前端也有"生成/刷新 Wiki"按钮（页面 `TechnicalMaterialWiki.jsx`），点击即调上面的 bootstrap 接口。

| 页面 | 路径 |
|---|---|
| 技术标 Wiki | `sewpg-bid-frontend/src/workspaces/technical/pages/TechnicalMaterialWiki.jsx` |

## 10. 技术标 vs 商务标（差异）

| | 技术标 | 商务标 |
|---|---|---|
| 树结构 | **确定性镜像**素材三级目录，不经 LLM | **LLM 编排**（按素材语义分组） |
| 生成主路径 | `run_from_manifest.py` 镜像脚本 | LLM 调 `wikibuild` + 语义精修 |
| 回退 | 无需回退（脚本即主路径） | LLM 失败 → 本地脚本骨架 → 确定性蓝图 |
| 文件卡片预览 | ✅ 本文 §6 的 AI 预览 | 走自己的 OCR/摘要逻辑 |
| 入口 | `_generate_technical_wiki` | `generate_platform_wiki` 商务标分支 |
