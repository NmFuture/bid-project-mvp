# 怎么使用 Codex 和 Claude Code 重构前端 UI

> 来源：X/Twitter @leon7hao · 2026-05-26
> 声明：作者非设计师/专业前端，分享的是 vibe coding 方式做大范围 UI 和架构重构的经验。

## 背景

Lody 由于底层技术栈和人力原因，完全使用 Web 统一构建网页端、桌面端和移动端。最初只做了网页端，后续慢慢添加桌面端和移动端，且几乎全程 vibe coding。

问题：移动端 UI 到处使用 `isMobile()` 判断，整体布局只是将桌面端变窄并添加 sidebar。交互别扭、字体过小、按钮过小。

**重构目标**：
1. 多端通用部分组件化，构建新的移动端入口，与旧布局解耦
2. 完全重新设计移动端的 UI 和交互

---

## 核心工作流

### 1. 干活之前了解模型特点

每个模型在当前阶段有不同的擅长领域，差异不是 80 vs 90，而是**能用 vs 不能用**。

| 模型 | 擅长 | 不擅长 |
|------|------|--------|
| GPT (Codex) | 架构梳理；生成图像；找 bug 真实原因；复杂后端/业务逻辑 | 写前端；写简洁文档 |
| Opus (Claude Code) | 写前端；理解交互；中小任务；写文档总结 | 复杂且需不断深入的任务；不能遗漏细节的任务 |

> 每次模型更新都需要重新试探边界，这也是异构 multi-agent 能提升生产力的原因。

### 2. 把绝大部分时间花在文档/Spec 上

- 先让 Codex 整理代码库中所有与移动端耦合的地方（约 40 个文件）
- 根据 Codex 写的重构文档调整细节：文件分隔、命名、移动端路由方式、组件等
- 与 Codex 进行一次对齐，确保理解真实需求
- 最终产出近 1000 行的计划文档

### 3. 让 AI 拆分大任务

让 Codex 将大需求拆分为不同阶段的需求和实现方案文档，放到 `docs/` 下统一管理：

| 阶段 | 内容 |
|------|------|
| 0 | 再次搜索确认耦合位置，固化共享/分端的维护边界 |
| 1 | 拆出纯移动端使用、没有耦合的组件 |
| 2 | 较大重构：拆出 chat/session/settings/archive 等核心 feature 的移动端布局 |
| 3 | 评估新的移动端组件、手势、询问新的 UI 设计方案 |
| 4 | 测试可访问性、设备矩阵和渐进发布 |

每个阶段的文档通过 comment 讨论几轮，前一阶段实现完再讨论下一轮。Codex 做重构的同时，可以去设计新版 UI。

## 不是设计师怎么设计 UI

1. **先不考虑美不美**，为功能服务，让人能看过去，规规矩矩是第一要务
2. **看好的软件**，主动分析为什么会这样设计
3. **带入用户视角**：一进来希望看到什么？最热路径是什么？哪些功能最快被触达？哪些可以增加层级做更明确的区分？
4. **iPad 手稿**：把所有主要界面和组件画出来
5. **Codex 生图**：把手稿发给 Codex，告诉它想要的风格，生成模拟真机渲染图
6. 不断调整 prompt、抽卡，直到获得想要的视觉效果

## 怎么向 AI 描述想要的交互

### 学习组件名称

去 shadcn/ui 或其他组件库官网，把所有组件看一遍。拿着渲染图上不知道怎么描述的组件，挨个去比对、点击，记住组件名称。

**反例**（冗长描述）：
> "我想要一个问题和答案的列表，默认只展示问题，点击之后可以在下面显示答案，点击别的问题时已展开的需要自动收起..."

**正例**（使用组件名）：
> "使用 Accordion 组件，Trigger 和 Content 分别是 Question A, Answer A..."

> 日常浏览网站时看到专业名词就记下来，不但节省 tokens，而且 AI 理解更清楚。

### 复原渲染图

从上到下描述当前图上所有组件：它是什么、它的功能是什么、希望的交互效果是什么。

第一遍 AI 只能复现个大概，先看架构和主题风格是否正确，然后有出入的地方一点一点磨。

## 善用 Storybook 便于走查

组件编码完成不代表生命周期结束——AI 随时可能把已设计好的样式或交互搞坏。

**推荐**：在 `AGENTS.md` 中添加规则——新增组件必须创建枚举所有状态的 Storybook（正常态、空态、加载态、错误态、禁用态等）。

好处：
- 不需要每次都端到端测试组件样式
- 不会忽略空状态、异常状态
- Storybook 不依赖真实接口，非常适合同屏展示所有可能状态

## 磨 UI UX 时 Web 技术栈的优势

- Codex 的预览模式
- Cursor 的 design 模式
- Lody 的预览模式（甚至可以在手机上给对应组件直接评论发送给 Agent）
- Web 可以 HMR 热更新，改完就能看到效果

## 关键经验总结

1. **先了解模型**：不同模型擅长不同任务，事半功倍
2. **文档先行**：把时间花在 spec 上，AI 做 plan 写 doc
3. **任务拆分**：大需求拆成阶段文档，逐阶段 comment 讨论
4. **组件化描述**：学会专业组件名称，大幅节省 tokens 且 AI 理解更准
5. **Storybook 兜底**：防止 AI 破坏已有组件，枚举所有状态
6. **异构 multi-agent**：Codex 做架构/重构，Opus 写前端，各司其职
