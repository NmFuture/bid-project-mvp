# 商务标素材库与 Wiki 库设计说明

> 用途：统一商务标素材库、Wiki 库、项目运行期附表/附件产物之间的边界，作为后续产品、后端、前端和 Skill 设计的评审底稿。
> 状态：方案稿，待评审。
> 更新日期：2026-05-07

## 1. 设计目标

本说明解决四个问题：

1. 商务标原始素材库应该如何分层、分目录、分主题。
2. 商务标 Wiki 库为什么需要存在，以及应该承载什么信息。
3. 商务标项目运行期解析出来的附件/空表/评分表，和全局素材库是什么关系。
4. 新资料上传后，清洗、索引、Wiki 更新应该如何闭环。

一句话原则：

> 原始素材库按“材料类型”组织，Wiki 库按“模板模块如何消费这些材料”组织，项目解析产物单独留在项目工作区，不直接混入全局素材库。

## 2. 商务标与技术标的核心差异

商务标不应简单照抄技术标 Wiki 结构的含义。

技术标的核心任务偏向：

- 长篇正文拼接
- 整章素材覆盖
- 段落摘录融合
- 技术附表填写

商务标的核心任务偏向：

- 附件模块映射
- 证据材料挂载
- 报价/资质/业绩/授权/承诺等表单化填写
- 合规与否决项响应
- 评分索引回填

因此商务标设计时应坚持：

- 少谈“整章拼接”
- 多谈“模块挂载”“证据卡片”“待确认变量”“风险规则”

## 3. 商务标原始素材库设计

### 3.1 顶层结构

保持与技术标一致的三层身份边界：

```text
商务标/
  通用素材/
  客户素材/{客户名称}/
  项目素材/{素材项目ID}/
```

说明：

- `通用素材`：适合多数商务标项目复用的标准材料。
- `客户素材`：只对某个客户或某类业主有效的专属材料。
- `项目素材`：只对某一具体项目有效，或强依赖某项目事实的材料。

### 3.2 原始素材库结构

目录模块设计遵循两个原则：

- 上传人看到目录名，应能一眼判断这份材料该放在哪里。
- AI 读取路径时，应能直接推断这份材料更可能映射到哪个 Wiki 模块和模板模块。

因此原始素材库不按文件形态划分，而按商务标业务语义划分。

#### 通用素材库

| 目录 | 主要内容 | 属性与管理逻辑 |
|---|---|---|
| `01-资质合规库` | 营业执照、开户行信息、股权结构、行业资质、ISO 体系认证、信用中国/失信/经营异常截图、银行资信证明、纳税信用等级 | 跨项目复用的基础资质与合规材料；建议重点维护有效期、查询日期、颁发机构等字段。 |
| `02-企业能力库` | 组织架构、公司/工厂简介、生产能力、服务能力、质量管理、荣誉奖项、专利证书 | 跨项目复用的企业能力和背书材料；建议按对外版本、年度版本管理。 |
| `03-业绩资产池` | 合同扫描件、中标通知书、240h 试运行报告、验收报告 | 作为业绩证明资产池长期维护；建议按业务线、容量等级、客户、年份等标签化管理。 |
| `04-财务资料库` | 各年度审计报告、财务报表 | 周期性更新的年度财务材料；建议按年度归档。 |
| `05-专题证书库` | 机型认证证书、大部件型式认证证书 | 高频复用的专题证书材料；建议单独维护证书编号、适用机型、有效期。 |
| `06-通用模板底稿库` | 投标函空白模板、授权书空白模板、廉洁协议空白模板、附件空白底稿 | 只存通用底稿，不存项目填写成稿；作为客户层和项目层的模板来源。 |

建议目录树：

```text
商务标/
  通用素材/
    01-资质合规库/
    02-企业能力库/
    03-业绩资产池/
    04-财务资料库/
    05-专题证书库/
      01-机型认证证书/
      02-大部件型式认证证书/
    06-通用模板底稿库/
```

#### 客户素材库 / 项目素材库

客户素材库与项目素材库使用同构结构。

两者区别仅在于：

- `客户素材`：服务重点客户长期经营与反复投标。
- `项目素材`：服务某一具体项目的最终响应与复盘沉淀。

| 目录 | 主要内容 | 属性与管理逻辑 |
|---|---|---|
| `01-客户关系与专项证明` | 战略协议、框架协议、评价信、优秀供应商证明、示范应用证明 | 更偏客户经营与专项背书；客户层沉淀长期关系资产，项目层可沉淀本项目实际采用版本。 |
| `02-商务响应文件` | 投标函、授权书、廉洁承诺、投标专用章效力说明、投标价格表、开标价格表、规格表、商务偏差表、供货范围表、保证金回单、保函、履约承诺、附件9、否决项响应、其他说明 | 这是最核心的成稿响应目录；凡是“本次投标如何响应”的正式文件，优先放这里。 |
| `03-模板底稿与过程文件` | 客户常用模板、项目整理底稿、二次整理空表、过程说明文件等 | 用于存放定制底稿和过程整理文件；不与最终成稿混放。 |

建议目录树：

```text
商务标/
  客户素材/{客户名称}/
    01-客户关系与专项证明/
    02-商务响应文件/
    03-模板底稿与过程文件/

  项目素材/{素材项目ID}/
    01-客户关系与专项证明/
    02-商务响应文件/
    03-模板底稿与过程文件/
```

### 3.3 分层口径说明

#### 通用素材适合放什么

- 公司级长期复用材料
- 周期性更新但跨项目复用的材料
- 可作为资产池反复筛选的业绩和证书
- 通用空白模板和底稿

#### 通用素材不建议放什么

- 本项目成稿的投标函、授权书、廉洁承诺
- 本项目投标价格表、开标价格表、偏差表、规格表
- 本项目保证金回单、保函、履约承诺
- 本项目附件 9、否决项响应、其他说明

#### 客户素材适合放什么

- 重点客户长期复用的战略关系材料
- 重点客户常用模板、底稿、过程整理文件
- 面向重点客户沉淀的常用响应版本

#### 项目素材适合放什么

- 本项目最终采用的商务响应文件
- 本项目二次整理的底稿和过程材料
- 本项目最终实际采用的客户关系和专项证明版本

### 3.4 原始素材库与 Wiki 模块的主映射关系

| 原始素材库模块 | 更可能服务的 Wiki 模块 |
|---|---|
| `01-资质合规库` | `资格证明文件模块（附件7）`、合规类评分点 |
| `02-企业能力库` | 企业介绍相关模块、`商务评分索引表` |
| `03-业绩资产池` | `业绩情况表模块（附件7I）`、业绩类评分点 |
| `04-财务资料库` | `资格证明文件模块（附件7）`、财务资信类评分点 |
| `05-专题证书库` | `资格证明文件模块（附件7）` |
| `06-通用模板底稿库` | 各模板模块的底稿来源 |
| `01-客户关系与专项证明` | `供应链协同模块`、`其他说明与承诺模块（附件9）`、商务评分索引表 |
| `02-商务响应文件` | `投标函与授权模块`、`投标价格表模块`、`货物规格一览表模块`、`商务偏差表模块`、`投标保证金模块`、`履约保证承诺模块`、`其他说明与承诺模块（附件9）`、`否决项与符合性响应模块` |

### 3.5 原始素材库应维护的关键元数据

建议每份商务标原始素材至少维护以下字段：

| 字段 | 作用 |
|---|---|
| `bidType` | 固定区分为 `商务标` |
| `materialTier` | `standard / customer / project` |
| `customerId / customerName` | 客户身份过滤 |
| `projectId / projectCode / projectName` | 项目身份过滤 |
| `businessCategory` | 所属主题分类，按所在层级目录定义 |

## 4. 商务标 Wiki 库设计

### 4.1 总体原则

商务标 Wiki 不按“长篇正文知识库”设计，而按“模板模块如何消费材料”设计。

保留 5 个一级节点，但重新定义每个节点的含义：

```text
商务标Wiki（自动生成）
  01-素材总表
  02-模板模块映射表
  03-证据卡片
  04-待填写与待确认清单
  05-使用规则
```

### 4.2 一级节点详细说明

#### `01-素材总表`

回答的问题：

> 当前商务标素材库里到底有什么材料。

建议记录：

- 文件名
- 素材层级
- 主题分类
- 证据形式
- 清洗状态
- 适用模板模块
- 身份范围
- 关键标签，例如年份、机型、容量、客户、合同类型

这是给 AI 和人工都能快速扫库的总入口，不承担复杂决策。

#### `02-模板模块映射表`

回答的问题：

> 商务标模板中的某个模块，优先应该找哪些类型的材料，以及怎么使用。

这里不建议继续沿用“章节映射表”命名理解，而应视作“模板模块映射表”。

建议的模块层级如下：

```text
02-模板模块映射表
  01-商务评分索引表
  02-投标函与授权模块
  03-投标价格表模块
  04-货物规格一览表模块
  05-商务偏差表模块
  06-投标保证金模块
  07-履约保证承诺模块
  08-资格证明文件模块（附件7）
  09-业绩情况表模块（附件7I）
  10-开标价格表模块
  11-其他说明与承诺模块（附件9）
  12-否决项与符合性响应模块
  13-供应链协同模块
```

### `02` 的映射原则

商务标 Wiki 的模块映射不建议只靠单一来源判断，而应由三层共同决定：

1. `路径语义规则`
- 原始素材库路径先提供粗分类方向。
- 例如：
  - `通用素材/01-资质合规库` 优先指向 `资格证明文件模块（附件7）`
  - `通用素材/03-业绩资产池` 优先指向 `业绩情况表模块（附件7I）`
  - `客户/项目素材/02-商务响应文件` 优先指向投标函、报价、偏差、保证金、附件9等模块

2. `AI 阅读素材内容判断`
- AI 基于文件名、清洗后文本、关键字段、图片/OCR 结果细化模块归属。
- 例如同样位于 `02-商务响应文件` 下的文件，AI 需要进一步区分它到底是投标函、开标价格表还是附件9响应。

3. `人工纠偏/确认`
- 对低置信度映射、敏感模块映射和异常文件，允许人工确认或覆盖。

因此：

- 路径负责粗分类
- AI 负责细分类
- 人工负责纠偏

### `02` 的风险兜底策略

映射表不应成为唯一入口，否则一旦映射遗漏，就会导致“素材明明存在，但 AI 找不到”。

建议固定采用三层检索顺序：

1. `先查映射表`
- 优先使用 `02-模板模块映射表` 中已经明确建立的候选关系。

2. `目录级回退搜索`
- 如果映射表未命中，则按原始素材库目录做回退搜索。
- 例如：
  - `附件7` 回退搜索 `01-资质合规库 / 04-财务资料库 / 05-专题证书库`
  - `附件7I` 回退搜索 `03-业绩资产池`
  - 投标函、报价、偏差、保证金、附件9 回退搜索 `客户/项目素材/02-商务响应文件`

3. `全卡片检索兜底`
- 若目录级回退仍未命中，则允许在当前项目可读范围内，对全部证据卡片按关键词、标签、关键字段做搜索。

建议在检索结果里记录来源：

- `mapped`
- `directory_fallback`
- `global_card_search`

这样后续可以反向评估映射表质量。

### `02` 每一行建议长什么样

建议将 `02-模板模块映射表` 设计成“一个模块可对应多行候选关系”的表结构。

每一行建议至少包含：

| 字段 | 说明 |
|---|---|
| `module_name` | 模板模块名称，例如 `资格证明文件模块（附件7）` |
| `module_code` | 稳定编码，例如 `module_attachment_7` |
| `source_path_prefix` | 推荐优先搜索的素材库路径前缀 |
| `business_category` | 推荐优先使用的业务分类 |
| `candidate_card_ids` | 该行直接命中的候选证据卡片 ID 列表 |
| `usage_mode` | 推荐使用方式 |
| `mapping_source` | `path_rule / ai_inferred / manual_confirmed` |
| `confidence` | 当前行映射置信度，建议 `0-1` |
| `needs_human_confirm` | 是否必须人工确认 |
| `mapping_reason` | 为什么这样映射，例如“路径命中 + 标题含投标函” |
| `fallback_scope` | 映射失败时允许回退搜索的范围 |
| `missing_hint` | 找不到材料时如何提示缺料 |

### `02` 的使用方式枚举

这里的“使用方式”建议标准化为：

- `attach_whole`：整件挂载
- `extract_fields`：字段抽取
- `extract_image`：摘图/截图
- `fill_table`：表格填充
- `reference_only`：只做证明引用

### `02` 的示例行

| module_name | source_path_prefix | business_category | usage_mode | mapping_source | confidence | needs_human_confirm | fallback_scope |
|---|---|---|---|---|---:|---|---|
| `资格证明文件模块（附件7）` | `通用素材/01-资质合规库` | `资质合规库` | `attach_whole` | `path_rule` | 0.90 | `false` | `01-资质合规库;04-财务资料库;05-专题证书库` |
| `业绩情况表模块（附件7I）` | `通用素材/03-业绩资产池` | `业绩资产池` | `fill_table` | `path_rule` | 0.88 | `true` | `03-业绩资产池` |
| `投标保证金模块` | `项目素材/{项目ID}/02-商务响应文件` | `商务响应文件` | `extract_fields` | `ai_inferred` | 0.76 | `true` | `客户素材/02-商务响应文件;项目素材/02-商务响应文件` |

#### `03-证据卡片`

回答的问题：

> 某份商务材料具体怎么被模板使用。

这层是商务标 Wiki 的核心。

建议结构：

```text
03-证据卡片
  通用素材
    01-资质合规库
    02-企业能力库
    03-业绩资产池
    04-财务资料库
    05-专题证书库
      01-机型认证证书
      02-大部件型式认证证书
    06-通用模板底稿库
  客户素材
    {客户名称}
      01-客户关系与专项证明
      02-商务响应文件
      03-模板底稿与过程文件
  项目素材
    {项目代号}
      01-客户关系与专项证明
      02-商务响应文件
      03-模板底稿与过程文件
```

这里故意让 `03-证据卡片` 和原始素材库的真实目录口径保持一致。

原因是：

- `通用素材` 是标准资产池，重点是资质、能力、业绩、财务、专题证书和通用底稿。
- `客户素材` 和 `项目素材` 采用更粗粒度的定制包结构，便于上传和复盘。
- `客户素材` 与 `项目素材` 的区别不在目录名，而在身份过滤和使用优先级。

每张证据卡建议至少包含：

### `03` 的设计原则

商务标卡片不再是“正文内容卡片”，而是“证据用途卡片”。

它主要回答：

- 这份材料服务哪个模块
- 这份材料怎么用
- 这份材料能提取什么字段
- 这份材料适用于谁
- 这份材料有什么风险
- 这份材料是否仍然有效

尤其对于证书、资信证明、回单、截图、保函等材料，**时效状态** 是证据卡片必须承接的能力。

### `03` 最终字段清单

建议将证据卡片字段分成 6 组：

#### A. 基础定位字段

| 字段 | 说明 |
|---|---|
| `card_id` | 证据卡片 ID |
| `material_id` | 原始素材 ID |
| `title` | 卡片标题 |
| `path` | 原始素材路径 |
| `cleaned_file_name` | 清洗后的标准文件名 |
| `material_tier` | `standard / customer / project` |
| `business_category` | 所属业务分类 |
| `evidence_type` | `docx / pdf / image / excel / scan` |

#### B. 身份范围字段

| 字段 | 说明 |
|---|---|
| `identity_scope` | `general / customer / project` |
| `customer_id` | 客户 ID |
| `customer_name` | 客户名称 |
| `project_id` | 项目 ID |
| `project_code` | 项目编号 |

#### C. 使用决策字段

| 字段 | 说明 |
|---|---|
| `applicable_modules` | 适用的模板模块列表 |

| 字段 | 说明 |

### `03` 字段使用重点

- `applicable_modules`：用于告诉系统“它能服务哪些模块”

- `risk_notes`：用于告诉系统“能不能自动用，还是必须人工确认”

#### `04-待填写与待确认清单`

回答的问题：

> 本项目还缺哪些变量、证据版本选择和人工确认项。

建议下沉为 4 类：

```text
04-待填写与待确认清单
  01-项目基础变量
  02-金额与时效变量
  03-证据选择与版本确认
  04-合规与页码确认
```

### `04` 的设计原则

这一节不只是“列缺什么”，而是要形成**可执行的待办清单**。

因此它既要让人能看，也要让系统能驱动后续动作，例如：

- 提醒人工确认
- 生成缺口处理任务
- 阻断高风险自动生成
- 驱动页码回填、版本选择、字段确认

### `04` 每一行建议长什么样

建议将 `04-待填写与待确认清单` 设计成逐条任务表，每一条代表一个需要处理的变量、确认项或缺口项。

| 字段 | 说明 |
|---|---|
| `todo_id` | 待办项 ID |
| `todo_type` | `project_basic / amount_time / evidence_selection / compliance_review / pagination_review` |
| `field_name` | 待确认字段名，例如 `保证金金额` |
| `module_name` | 所属模板模块 |
| `expected_value_type` | `text / date / number / enum / boolean / card_select / page_range` |
| `current_value` | 当前已识别值 |
| `suggested_value` | 系统建议值 |
| `candidate_sources` | 候选来源卡片 ID、候选值或候选文件 |
| `is_required` | 是否必填 |
| `status` | `pending / suggested / confirmed / waived / blocked` |
| `needs_human_confirm` | 是否必须人工确认 |
| `blocking_level` | `high / medium / low` |
| `reason` | 为什么会出现在待确认清单 |
| `owner` | 默认责任角色，例如 `商务人员 / 审核人 / AI` |

### `04` 的分类字段建议

#### A. `01-项目基础变量`

典型内容：

- 项目名称
- 招标编号
- 投标日期
- 投标人名称
- 法定代表人
- 授权代理人

#### B. `02-金额与时效变量`

典型内容：

- 投标有效期
- 供货期
- 保证金金额
- 保证金到账日期
- 开标价格版本

#### C. `03-证据选择与版本确认`

典型内容：

- 本次入选业绩表条目
- 本次使用哪份营业执照
- 使用哪一年度财报
- 使用哪份资信证明
- 使用哪套合作协议或协同案例
- 使用哪张机型认证证书

#### D. `04-合规与页码确认`

典型内容：

- 否决项是否逐条响应
- 附件 9 承诺条款是否齐全
- 商务评分索引是否已回填章节和页码
- OCR 提取结果是否已人工复核

### `04` 的状态流转建议

建议状态固定为：

- `pending`：尚未处理
- `suggested`：系统已给出建议值
- `confirmed`：人工已确认
- `waived`：经人工确认可忽略
- `blocked`：当前无法继续，需要补料

### `04` 的示例行

| todo_id | todo_type | field_name | module_name | current_value | suggested_value | status | needs_human_confirm | blocking_level |
|---|---|---|---|---|---|---|---|---|
| `TODO-0001` | `amount_time` | `保证金金额` | `投标保证金模块` | `` | `500000` | `suggested` | `true` | `high` |
| `TODO-0002` | `evidence_selection` | `本次入选业绩` | `业绩情况表模块（附件7I）` | `` | `CARD-BIZ-0012,CARD-BIZ-0048` | `pending` | `true` | `high` |
| `TODO-0003` | `compliance_review` | `否决项逐条响应完整性` | `否决项与符合性响应模块` | `部分缺失` | `` | `blocked` | `true` | `high` |

#### `05-使用规则`

回答的问题：

> 商务标生成和取证时，系统应按什么规则裁决。

建议至少拆成下面几部分：

```text
05-使用规则
  01-身份过滤规则
  02-证据优先级规则
  03-模块使用方式规则
  04-合规与否决项规则
  05-OCR与图片处理规则
  06-页码索引回填规则
```

### `05` 的设计原则

这一节不应只写自然语言说明，而应尽量沉淀为“机器可执行 + 人可审阅”的规则表。

也就是说：

- 人能读懂规则
- 系统能按规则做判断
- 审计时能说明“为什么这样选材”

### `05` 每一行建议长什么样

建议每条规则至少包含：

| 字段 | 说明 |
|---|---|
| `rule_id` | 规则 ID |
| `rule_group` | 所属规则组 |
| `rule_name` | 规则名称 |
| `condition` | 触发条件 |
| `action` | 系统动作 |
| `priority` | 规则优先级 |
| `enabled` | 是否启用 |
| `severity` | `info / warn / block` |
| `human_readable_note` | 人类可读说明 |

### `05` 的规则组建议

#### `01-身份过滤规则`

核心规则：

- 项目素材优先于客户素材
- 客户素材优先于通用素材
- 身份不命中的材料禁止使用

#### `02-证据优先级规则`

核心规则：

- 同一模块多份候选时，优先最新、最完整、身份最匹配版本
- 同一证据存在 Word、PDF、扫描件时，优先结构化可读版本
- 已过期证据不得高于有效证据排序

#### `03-模块使用方式规则`

核心规则：

- 报价、保证金、授权、资质证书优先 `attach_whole` 或 `extract_fields`
- 业绩证明优先 `fill_table + attach_whole`
- 合作协议和协同案例优先 `reference_only` 或 `extract_image`

#### `04-合规与否决项规则`

核心规则：

- 否决项和符合性条款必须逐条可追溯
- 不允许仅用摘要代替正式响应条款
- 未确认的关键承诺不得自动发布为最终稿

#### `05-OCR与图片处理规则`

核心规则：

- OCR 结果默认低一档置信度
- 证书图片、扫描件、回单等提取结果必须人工确认
- 低于置信度阈值的 OCR 结果不得直接作为最终字段

#### `06-页码索引回填规则`

核心规则：

- 商务评分索引属于后处理模块
- 仅在正文/附件结构稳定后回填页码和章节
- 页码回填后如附件顺序变化，应重新校验

### `05` 的示例规则行

| rule_id | rule_group | rule_name | condition | action | priority | severity |
|---|---|---|---|---|---:|---|
| `RULE-001` | `identity_filter` | `项目素材优先` | `candidate.material_tier == project` | `rank_boost(+30)` | 100 | `info` |
| `RULE-002` | `identity_filter` | `身份不命中禁止使用` | `candidate.identity_match == false` | `exclude_candidate` | 1000 | `block` |
| `RULE-003` | `validity_check` | `过期证书降级` | `candidate.validity_status == expired` | `rank_drop(-100)` | 900 | `warn` |
| `RULE-004` | `ocr_guard` | `低置信度OCR禁止直出` | `candidate.ocr_confidence < 0.75` | `force_human_confirm` | 950 | `block` |
| `RULE-005` | `pagination` | `页码后处理` | `module == 商务评分索引表` | `defer_until_final_layout` | 500 | `info` |

### `05` 的建议实现口径

第一阶段可以先在 Wiki 中用 Markdown + 表格表达规则。

第二阶段建议逐步把高价值规则结构化，优先抽成：

- 身份过滤规则
- 过期证据规则
- OCR 阈值规则
- 关键模块人工确认规则

## 5. 商务标 Wiki 与原始素材库的关系

可以用一句话总结：

- 原始素材库：存“文件本体”
- Wiki 库：存“文件如何被用”

对应关系如下：

| 层 | 作用 | 是否存文件本体 |
|---|---|---|
| 原始素材库 | 归档、上传、版本管理、身份边界 | 是 |
| Wiki 素材总表 | 盘点素材、展示索引 | 否 |
| Wiki 模块映射表 | 建立模板模块到证据候选的关系 | 否 |
| Wiki 证据卡片 | 记录某份材料的用法与限制 | 否 |
| 项目工作区 | 存本项目解析附表、生成产物、处理中间件 | 是 |

## 6. 商务标新资料上传后的推荐流程

### 6.1 建议流程

```text
上传原始文件
  -> 写入商务标原始素材库
  -> 自动入清洗队列
  -> 生成清洗后 Word 或证据归一化产物
  -> 更新素材元数据
  -> 触发商务标 Wiki 重建任务
  -> 发布新的商务标 Wiki
```

### 6.2 清洗目标建议

商务标不建议只有一种清洗目标。

建议分成两类：

#### A. `docx_cleaned`

适用对象：

- Word
- Excel
- 可结构化 PDF

目标：

- 统一转换为标准 `docx`
- 便于抽取标题、表格、段落、字段
- 便于 OnlyOffice 预览

#### B. `evidence_normalized`

适用对象：

- 扫描件
- 图片
- 合同扫描 PDF
- 证书照片
- 回单截图

目标：

- 提取证据类型
- 提取 OCR 文本
- 提取关键字段
- 记录页数、图片数、可裁图区域
- 标记是否适合整件挂载、摘图或字段抽取

### 6.3 Wiki 更新建议

建议商务标比技术标更严格地做自动重建：

- 新增文件 -> 入队重建
- 修改文件 -> 入队重建
- 删除文件 -> 入队重建
- 重建失败 -> 保留上一个已发布版本，并给出审计日志

不建议继续维持“手工想起来再点一次创建 Wiki”的弱触发方式。

## 7. 商务标不建议直接照搬技术标的部分

以下能力不建议直接从技术标复制：

1. 不以“整章大 Word 拼接”为主线。
2. 不以“段落摘取融合”为主线。
3. 不把 `skeleton_section` 当成唯一核心字段。
4. 不把“章节映射”理解成“正文目录映射”。

商务标更适合的主线是：

1. 模板模块识别
2. 证据候选定位
3. 字段抽取或整件挂载
4. 待填写项确认
5. 合规和否决项复核
6. 页码与索引后处理

## 8. 第一阶段实施建议

如果按 MVP 方式推进，建议先做下面四件事：

1. 开放商务标原始素材库上传，采用本说明的目录结构。
2. 开放商务标 Wiki bootstrap，先生成 `01-05` 五个一级节点。
3. 首批只重点打通三类模块：
   - 资格证明文件（附件 7）
   - 业绩情况表（附件 7I）
   - 其他说明与承诺（附件 9）
4. 首批只重点结构化三类素材：
   - 业绩表与业绩证明
   - 资格资质与认证
   - 财务与资信

原因：

- 这三类最值钱
- 也是商务标自动化最容易形成闭环的部分
- 报价和页码索引可以放在下一阶段收口

## 9. 审核重点

本方案评审时建议重点看以下问题：

1. 原始素材库二级主题是否覆盖主要商务材料类型。
2. 商务标模板模块划分是否符合真实投标文件结构。
3. 证据卡片字段是否足够支撑“整件挂载 / 摘图 / 抽字段 / 填表”。
4. 待填写与待确认清单是否覆盖商务标运行期高频变量。
5. 哪些商务产物允许回灌全局素材库，哪些必须只留在项目工作区。
6. 商务标是否需要单独的 `business-workspace`，还是先复用现有项目工作区结构。

## 10. 当前结论

当前版本的推荐设计可以简化成一句话：

> 商务标原始素材库按“材料类型 + 身份范围”建库，商务标 Wiki 按“模板模块 + 证据用途 + 待确认变量”建索引，项目解析出来的附件和评分表只留项目工作区，不直接沉淀为全局素材。
