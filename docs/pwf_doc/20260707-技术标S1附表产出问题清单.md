# 技术标 S1 附表产出问题清单

> 面向 S1 解析线（pwf）。基于华能翁牛特旗北区（PRJ-0010）金标反评发现，S1 产出的
> `structured.appendices[]` 存在边界识别与元数据问题，导致下游 S4 缺口决策
> （gap-planner）无法为部分必填附表生成正确的填写任务。

## 背景与触发场景

S4 缺口决策消费 S1 解析产出的 `structured.appendices[]`（每条含 `id / title /
rowCount / contentBlocks / docxPath`）来生成"附表填写任务"。下游按 `title` 里的
附表编号与投标目录项匹配——契约中 appendices 条目**没有显式关联目录项的外键**，
只能靠编号。

金标反评发现：**技术附表I（技术条款偏差表，投标人必填）在界面上"没有表可填"**。
追查到 S1 产出的 appendices 数据存在以下三类问题。

## 问题清单

### P1　技术附表I 边界越界：吞掉了文档剩余全部内容

- **现象**：`APPX-0080「技术附表I 技术条款偏差表」` 的 `contentBlocks` 有 **1921 项
  （119 张表 + 1802 段）**，把偏差表之后的所有内容——"附件一 中国华能集团陆上风电
  工程设备监理大纲""见证表""数据点表""验收标准"等——全部圈进了这一个 APPX。
- **实际**：技术附表I 本体只是一张 **14 行 × 5 列** 的偏差表（序号 / 招标文件 /
  投标文件），到下一个标题为止。后面的"附件一 监理大纲…"是独立内容，不属于它。
- **影响**：下游即使匹配到 APPX-0080，拿到的也是一张被污染的巨型表，无法使用。
- **代码定位**（`app/services/parsing.py`）：附表内容边界由
  `content_blocks = _slice_content_blocks(blocks, index, next_heading_index)`（约 4672 行）
  决定，`next_heading_index = _next_appendix_heading_index(...)`（4217 行）**只把"附表X"
  当边界**——`_is_appendix_heading` 默认 `include_attachments=False`，不认"附件X"。
  技术附表I 是全文最后一个附表，其后全是"附件"标题，找不到下一个"附表"标题 →
  返回 `len(blocks)` → 内容一路切到文档末尾。
- **期望 / 修复建议**：边界判定应把"附件X 标题"及文档结构性大标题也作为截断点
  （尤其对最后一个附表），或对该 lookahead 传 `include_attachments=True`。

### P2　rowCount 元数据不可信

- **现象**：80 张附表里 **14 张 `rowCount=0`，其中 11 张 `contentBlocks` 里实际有
  内嵌表格**。例：
  - APPX-0080（技术附表I）：`rowCount=0`，实际 contentBlocks 含 119 张表；
  - APPX-0004（附表B.1 供货范围清单）：`rowCount=0`，实际有可填表格。
  - 反向：APPX-0003 / APPX-0016（技术附表B/C）：`rowCount=44 / 41`，但
    `contentBlocks` 为空（见 P3）。
- **影响**：下游无法用 `rowCount` 判断附表是否有可填内容。
- **代码定位**（`app/services/parsing.py`）：两处叠加——
  (a) 主表匹配窗口只看附表标题后 8 个 block（约 4663 行 `min(len(blocks), index + 8)`），
  说明段落多的附表（如技术附表I 标题与偏差表间隔多段）主表落窗外 → 走
  `table_index == -1` 分支（4696 行）`rows=[]` → `rowCount=0`；
  (b) 即便匹配到表，`rowCount = len(rows)`（3373 / 4734 行）**只数顶层 `rows`**，不数
  `contentBlocks` 里 `type=table` 的内嵌表格。
- **期望 / 修复建议**：主表匹配窗口放宽到 `next_heading_index`；`rowCount` 统计
  `contentBlocks` 内表格行数，与产物保持一致。

### P3　技术附表B/C 数据自相矛盾：contentBlocks 空 + docx 16MB 巨物

- **现象**：`APPX-0003（技术附表B）`、`APPX-0016（技术附表C）` 是**分组容器标题**
  （真实投标文件里它们下面直接是 附表B.1 / C.1 子表，自身无独立表格），但 S1 产出：
  - `contentBlocks = 0`（空）
  - `rowCount = 44 / 41`（非 0）
  - docx 产物 **约 16 MB**（对比正常单表 APPX-0004 仅 37 KB）
  - 三处数据互相矛盾，docx 疑似吞了整个 B 组 / C 组内容。
- **影响**：下游无法区分"分组容器标题"和"独立表"。
- **代码定位**（`app/services/parsing.py`）：技术标切割 `keepEnd = table_body_index`
  （4738 行，即匹配到的主表位置），当容器标题（技术附表B）匹配到的主表落在很远
  （跨整个 B 组）时，docx 会把标题到那张表之间**整段切进来** → 16 MB；而
  `contentBlocks` 因下一个附表标题（附表B.1）紧邻、`next_heading_index` 很近而为空。
- **期望 / 修复建议**：分组容器标题（技术附表B / C / F）**要么不作为独立 appendix
  产出**，要么显式标记为容器（如 `isContainer=true`）；技术标 `keepEnd` 宜取"下一个
  附表标题前一个 body_index"（`_last_body_index_before`，商务分支已用
  `slice_end_body_index`），而非主表 `table_body_index`，避免跨组切割。

## 契约增强建议（可选，长期）

appendices 条目目前只能靠 `title` 里的编号与目录项匹配，纯字母章级附表（如
"技术附表I"）编号无数字，正则容易漏。建议补充：

- `tocNumber` / 规范化附表编号（含纯字母 "I"）：下游直接按编号关联，不必正则猜。
- `isContainer`：标识分组容器标题。
- 明确 `rowCount` / `contentBlocks` 语义，并保证 **docx 产物边界与 contentBlocks 一致**。

## 下游（gap-planner）已做的兜底

已在 `code/sewpg-bid-backend/opencode/skills/bid-tech-gap-planner/scripts/run_from_manifest.py`
加了纯字母附表匹配 + 容器排除（`pure_letter_appendix_code` /
`appendix_container_letters`），让"技术附表I"这类纯字母章级附表能被识别成可填附表、
同时排除 B/C/F 容器。

但这只解决"**能不能选到**"。技术附表I 填出来是否干净，仍取决于 S1 对 **P1（边界越界）**
的修复——目前它指向的 APPX-0080 是吞了全文的脏表。**P1/P3 需 S1 侧根治。**
