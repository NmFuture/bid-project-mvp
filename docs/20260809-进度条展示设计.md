耗时文案在 `src/utils/progressDuration.js`，六处共用：
`formatProgressDuration(秒)` 出「x 分 y 秒」，`progressElapsedLine(秒, {finished})`
出「已运行 …」/「总耗时 …」。终态一律「总耗时」，包括失败。

## 3. 三套进度语义

### 3.1 目录（场景 1、2）

**数据来源最好，是另外两处的模板。** 后端在判定阶段回传真实计数，
所以明细行是可核对的数字而不是形容词：

> 已判定目录条款 12/54 项 · 技术附表 3/83 项

`technicalDirectoryProgress.js` 关键位置：

| 位置 | 作用 |
| --- | --- |
| `normalizeDecisionProgress` | 解析后端 `decisionProgress`，`total<=0` 直接判空，不编造分母 |
| `directoryDisplayPercentage` | **锚点 + 爬升**：后端 percentage 是锚点，锚点之间按 `CREEP_PERCENT_PER_SECOND = 0.05`（每秒 0.05%）慢爬，单次最多爬 `CREEP_MAX_PERCENT = 6`，运行期封顶 `RUNNING_DISPLAY_CAP = 96` |
| `mergeMonotonicDirectoryProgress` | 跨轮询保单调：百分比、阶段、判定计数都不许回退；同时给锚点盖时间戳 `percentageUpdatedAt` 供上面那个爬升用 |
| `directoryElapsedSeconds` | 起点 `startedAt`（缺失时退回最早一条 event），终态冻结在完成/失败时刻 |
| `summarizeDirectoryProgress` | 出 `tone` 和明细文案；`internalDirectoryTextPattern` 过滤 futurecode/opencode/S2/session 等内部名词 |

调快慢 → 改 `CREEP_*` / `RUNNING_DISPLAY_CAP`。
调文案 → 改 `decisionDetailText` / `visibleFailureSummary`。

### 3.2 正文（场景 3、4）

后端 `percentage` 的原始锚点**不能直接当进度用**。PRJ-0004 实测：

| 事件 step | 时刻 | 本段耗时 | 后端 percentage | 占总时长 |
| --- | --- | --- | --- | --- |
| `bootstrap` | 12:39:50 | 64 秒 | 5 → 30 | 22.9% |
| `inputs_ready` | 12:40:54 | 1 秒 | 30 → 60 | 0.4% |
| `assembly_waiting` | 12:40:55 | **168 秒** | 60 → 85 | **60.0%** |
| `assembling` | 12:43:43 | 2 秒 | 85 → 90 | 0.7% |
| `format_cleaning` | 12:43:45 | 44 秒 | 90 → 96 | 15.7% |
| `format_done` | 12:44:29 | 1 秒 | 96 → 100 | 0.4% |

即：**1 秒内跳 30 个点，然后 168 秒只走 25 个点**。这就是「前 60% 一分钟、
后 40% 好几分钟」的来源。

`technicalGenerationProgress.js` 的处理是按实测耗时占比重排区间，
`STAGES` 表以事件 `step` 为键：

```
bootstrap                3 → 23   预计 65 秒
inputs_ready            23 → 25   预计  3 秒
assembly_waiting        25 → 82   预计 170 秒   ← 最长的一段，给最宽的区间
assembling              82 → 85   预计  5 秒
format_cleaning         85 → 97   预计 45 秒
format_done             97 → 100  预计  3 秒
```

阶段内用 `easeWithinStage` 渐进逼近区间末端（`tau = 预计/2.5`，走到预计耗时时
约到 92%），慢于预期也不会越界，所以**不会卡死也不会提前打满**。

**组装段有真实计数时以计数为准。** 后端逐条回传 `assemblyProgress: {done, total, updatedAt}`，
明细行变成：

> 已组装目录项 27/54 项

此时百分比 = `25 + 57 × done/total`，两次计数之间只在「下一条目录项的刻度」以内
小步平滑，绝不越过。计数缺失（历史数据、商务标）时自动退回上面的阶段估算，
再退不动就用 `PERCENTAGE_ANCHORS` 把后端 percentage 映射到同一套刻度。

后端这条链路（改计数口径走这里）：

```
merger.py  merge()  正文遍历循环，逐条 progress_callback(i, total)
   ↓
runner.py  _throttled_merge_progress()   按秒节流，收尾那次必报
   ↓
tech_assembly.py  _run_assembler_manifest → _run_local_assembler
   ↓
bid_generation_flow.py  _handle_fill_progress("assembling_progress")
   ↓
bid_fill_generation_state.py  update_fill_generation_state(assembly_progress=...)
   → fill_state.assemblyProgress
```

两个约束别破坏：

- **不写 event**。`events` 是 `[-20:]` 环形缓冲，逐条写会把 `bootstrap` 和阶段历史挤掉，
  耗时基线和阶段判断都会跟着废掉。所以另记了 `fill_state.startedAt`。
- **按秒节流**。每次上报都要落库，逐条写库会把耗时算到进度汇报本身上。
- 顺带：`_is_fill_generation_stale` 已把 `assemblyProgress.updatedAt` 算进心跳，
  否则长组装会被 60 分钟无进展的自动收口误判。

### 3.3 素材匹配（场景 5）

**这处没有真实进度可查，是当前五处里唯一的估算。**
`POST /gaps-detection/run` 是一次性阻塞请求（内部跑纯脚本缺口识别，不调 LLM），
返回前没有任何中间态可轮询。改造前这里写死 `running ? 68 : 100`，是个假数字。

现在的口径写在 `MaterialMatchProgressModal.jsx`：

- 计时真实：起点是点击确认的时刻，终点是接口返回的时刻，由页面记账
  （`materialMatchProgressState.js` 的 idle/started/finished 三个取值，技术标商务标共用）。
- 百分比是估算：`EXPECTED_SECONDS = 60`，渐进逼近 `RUNNING_CAP = 92` 后停住等真实结果，
  **不封顶到 100**——没拿到返回就不许显示完成。
- 明细里的目录项数量是真的，来自当前目录 `countNodes(nodes)`。

**想让它变成真进度**，得先把这个接口改成「起任务 + 轮询状态」，
参考正文那条链路的形状：起一个后台 job、把中间计数写进项目状态、前端轮询。
在那之前，别把这里的估算当成真实进度看。

### 3.4 招标文件解析（场景 6）

后端 `TECHNICAL_PROGRESS_PHASES`（`bid_parse_service.py`）把刻度这样分：

```
extract (8,24)  local_structure (24,34)  appendix_scan (34,40)
appendix (40,62)  prepare (62,68)  structured (68,96)
```

即 **AI 结构化解析只分到 68→96 共 28 个点**。PRJ-0003 实测（总 475 秒）：

| 区段 | 实际耗时 | 占总时长 | 后端刻度 |
| --- | --- | --- | --- |
| 提取 → 附表 → 准备 | 113 秒 | **23.8%** | 0 → 68（68 点） |
| AI 结构化解析 | 360 秒 | **75.8%** | 68 → 96（28 点） |

和正文那处一个病，而且更极端：四分之一的时间走完三分之二的条，剩下四分之三的时间只走
28 个点——所以截图会长时间停在 68%。

`parseDisplayPercentage`（`technicalParseUploadRecovery.js`）按实测耗时占比做分段线性
重映射，仍以后端百分比为唯一输入，不另造进度：

```
后端  0 →   0        68 →  30   ← 结构化解析开始
      8 →   2        96 →  96   ← 结构化解析拿到 66 个点
     24 →  10       100 → 100
     34 →  14
     40 →  17
     62 →  26
```

**为什么折算放在前端**：那张表由技术标和商务标共用（`BusinessParseService` 继承
`BidParseService`，走同一个 `_progress_callback`），改后端刻度会同时改掉商务标解析的进度。
与正文那处同一个理由。要改成后端折算，得先把两条线的 phase 表拆开。

**心跳不写 event。** 结构化解析每两三秒回一次心跳，而 `events` 是 **80 条**环形缓冲——
改造前实测一次 8 分钟的解析，80 条事件全是「仍在执行」，上传/提取/附表的阶段记录被挤得
一条不剩。现在只有真正推进（`completedShards` / 已返回片段数变化）才落一条事件，
文案也从「还活着」改成「已完成 3/7 个分片」。心跳照常刷新百分比、摘要和 `heartbeatAt`——
**卡死检测看的是 `parse_progress.heartbeatAt`，不看 events**，所以这样改不影响 stale 判定。
这条同样作用于商务标解析（共享回调），但不改任何百分比语义。

明细行的量化数据优先级：`opencodeOutput.totalItems/completedItems`（「已解析条款 41/64 项」）
→ 分片计数（「已完成 3/7 个分片」）→ 阶段文案。前两者都是后端给的真值。

技术标已全部接入。**商务标一处都没接**，5 个位置如下：

`materialMatchProgressState`、`progressDuration`，外加后端 `_progress_callback` 与
`TECHNICAL_PROGRESS_PHASES`。**改这几个要同时确认商务标。**

`TechnicalGapRecognition.jsx:689/2736` 的占比条与填写完成度、`StageProgress.jsx` 的步骤条宽度、
`JobMonitor.jsx:135` 的耗时分布图——这些是「计量条」不是「任务进度条」。
`MaterialPipelineProgress.jsx` 是有意做成行内窄条的素材流水线，保留现状。
