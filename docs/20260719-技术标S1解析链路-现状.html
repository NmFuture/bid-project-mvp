二、伴随机制（与主链路并行）

进度跟踪

  • 前端 1s 轮询 GET .../parse-results/progress
  • 进度存项目 JSONB，每次事件整行 upsert Postgres
  • 心跳 10s；阶段超时无心跳 → stale「可能中断」
  • 前后端双单调保护，进度不回退

取消

  • POST .../parse-results/cancel → 置 cancelRequested + opencode abort_session
  • 解析线程在心跳/阶段边界协作式抛 ParseCancelledError

断连行为

  • 页面切换只 abort HTTP 等待，后端解析线程继续跑；重进页面可恢复轮询
  • 但进程重启 → 线程丢失，只剩 Postgres 里的 stale 标记，无续跑

并发

  • 同项目解析无锁：仅靠前端按钮 disabled，多标签/竞态会并发覆盖同一项目状态
  • opencode 进程内信号量=1：所有 AI 调用（解析/目录/生成/gap）串行排队

三、现状痛点（改造动因）

① 同步长请求

用户体验是「必须停留等待」；5 分钟超时后提示割裂，实际任务还在跑。

② 重启即丢任务

解析线程随进程死亡，无恢复/续跑，只剩 stale 标记。

③ 无解析锁

重复点击/多标签可并发解析同一项目，互相覆盖状态。

④ 进度写放大

每次进度事件都整行 JSONB upsert Postgres，高频小写。

⑤ 两套异步范式

目录/正文生成已走 Redis 队列 + worker，S1 解析仍是请求内同步，架构不一致。

⑥ 重试薄弱

仅 opencode 层 1 次恢复重试；无任务级重试；商务标连「重新解析」端点/入口都没有。
