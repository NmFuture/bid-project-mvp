# 技术标 Wiki 预览：PDF 全文提取与 AI 摘要补充方案

日期：2026-08-03
状态：一期已实施（2026-08-03）
关联：PR #130（恢复 PDF/XLSX→Word 转换链，已合入 Dev）、PR #59（后台深度解析）、62760f3（收窄素材范围，删除转换链）

## 1. 背景与问题

技术标 Wiki 文件卡片的 AI 摘要只认 docx 正文：

- `_should_generate_preview`（`technical_wiki_preview_generation.py:94-101`）对非 docx 直接终态 fallback「非 docx，无可解析正文」，页面显示"本地摘要"（本地 TLDR，仅由文件名/路径等元数据拼成）。
- 实测一轮生成：330 个素材中 42 个落入本地 TLDR，绝大多数是 PDF（证书、报告类素材）。
- 62760f3 删除的 `pdf_to_word.py` 转换链也只是把 PDF 每页渲染成 PNG 嵌进 docx，**全程没有文字提取**，恢复后 LLM 仍只能看到标题。

结论：**当前 Wiki 构建环节对 PDF 类文件没有任何 OCR / 文本提取工作**。缺口匹配对 PDF 素材同样零召回。

## 2. 现状资产盘点（可复用件）

| 资产 | 位置 | 能力 | 复用评估 |
| --- | --- | --- | --- |
| OCR 服务 | `app/services/ocr_service.py` | `recognize_text_for_parse(file_name, content, mime_type)`（:576），字节入参；PDF 逐页转 PNG 送多模态模型（`_ocr_pdf` :770-805）；DB 表队列 + 并发 8 + 重试 2 + fencing（:120-262）；模型配置走系统设置 ocr 项 | **直接复用**。按页调用，绕开整本 maxTokens 限制 |
| 文字层抽取模式 | `material_certificate_time.py:1099-1120` | 先 PyMuPDF 抽 PDF/DOCX 文字层，不够再调 OCR | **复用该判定模式** |
| 深度解析框架 | `material_deep_parse.py` | 任务入队/状态回写/产物画像（`deepParseProfile` ext field，`{schemaVersion, sourceKey, profile}`） | **扩展新 kind**，框架不动 |
| 预览缓存/签名 | `technical_wiki_preview_generation.py:52-62` | 签名含 headings+paragraphs+tableCount，产物就绪后自动重算升级 | **天然兼容**，无需改缓存机制 |
| docling worker | `docling_worker.py` / `docling_engine.py` | markdown 产物、RapidOCR 兜底 | **不直接复用**：强绑 S1 父任务锁、输出共享卷、不接 MinIO/DB，解耦成本高；作为远期选项保留 |

## 3. 方案设计

### 3.1 总体链路

```
PDF 素材入 Wiki 预览闸口
   │
   ├─ 有 deepParseProfile(extract 产物) → 走现有 LLM 预览 → AI 摘要卡片（可展开全文）
   │
   └─ 无产物 → enqueue_deep_parse_job(kind="extract")，卡片置 retryable「已排队后台全文提取」
                    │
                    ▼
        extract 作业（material_deep_parse 扩展）
          1. PyMuPDF 逐页抽文字层
          2. 文字层不足的页（扫描页）→ OCR recognize_text_for_parse 按页补齐
          3. 合并全文 → 写 MinIO  parsed/RAW-xxx/v<n>/fulltext.md
          4. 生成同构 profile {headings, paragraphs(摘录), tableCount} 回写 ext_fields
                    │
                    ▼
        下次刷新自动升级为正式 AI 预览（现有签名机制触发重算）
```

设计要点：

- **文字层优先、OCR 兜底**。数字版 PDF（多数报告、导出件）文字层免费且准确，零 OCR 成本；仅扫描页消耗 OCR 调用。判定沿用证书台账的既有模式。
- **不动 docling**。docling 与 S1 任务锁耦合深，本方案用 OCR 服务 + PyMuPDF 即可闭环；若未来商务标也要素材全文，再评估 docling 解耦。
- **产物与 #130 的关系**：本方案的 extract 产物（全文文本）在 Wiki 场景下优于 #130 的图片 docx（无文本）。若 #130 已合入，PDF 在闸口优先消费 extract 产物；convert 产物仅作为"原件版式查看"用途。两者不冲突，但建议 Wiki 链只依赖本方案。

### 3.2 后端改动点

1. `material_deep_parse.py`
   - `raw_file_deep_parse_kind` 增加 PDF → `"extract"`（XLSX 留到二期，见 §5）。
   - 新增 `_run_extract_job(file_id)`：文字层抽取 + OCR 兜底 + 全文落 MinIO + profile 回写。
   - 页数护栏：`TECH_WIKI_EXTRACT_MAX_PAGES`（默认 80），超限只处理前 N 页并在 profile 标注 `truncated: true`。
2. `technical_wiki_preview_generation.py`
   - `_should_generate_preview`：PDF 若有 extract 画像则放行；无画像则入队并返回 retryable「已排队后台全文提取，完成后自动补全预览」。
   - `_docx_profile_for_raw_file` 泛化为 `_profile_for_raw_file`，接受 extract 画像（`sourceKey` 匹配全文 MinIO key）。
3. 摘录截断策略（防签名/prompt 膨胀）
   - paragraphs 摘录：最多 20 段、每段 ≤200 字、总量 ≤4000 字，采样取首段+尾段+含关键词中段。
   - headings：PDF 无样式信息，用启发式（短行、编号前缀、全大写等）提取，抽不到则以文件名作为唯一 Heading。
4. 新 API：`GET /api/technical/materials/{file_id}/fulltext`——返回 MinIO 全文（或分页片段），供前端"查看全文"。
5. 配置项（安全默认值，5090 实测值只写 `docker-compose.5090.yml`）：
   - `TECH_WIKI_PDF_EXTRACT_ENABLED=true`
   - `TECH_WIKI_EXTRACT_MAX_PAGES=80`
   - `TECH_WIKI_EXTRACT_OCR_PAGE_CONCURRENCY=4`（OCR 服务自身并发 8，留出余量给证书识别）

### 3.3 前端改动点（`TechnicalMaterialWiki.jsx`）

- 状态徽标复用现有映射：extract 排队中 →「待重试」琥珀条；extract 失败 →「解析失败」+ 失败原因。
- 卡片新增「查看全文」入口（仅 extract 产物存在时显示）：抽屉/弹窗展示 fulltext.md，顶部标注页数与是否截断。
- 本地 TLDR 的提示文案补充引导：「PDF 全文提取排队中，完成后自动升级」替代现在的纯原因陈述。

## 4. 验证计划

- 单测：
  - 文字层 PDF → 零 OCR 调用、profile 正确生成；
  - 扫描版 PDF（mock OCR）→ 仅无文字层页触发 OCR；
  - 超页数护栏 → truncated 标记；
  - 摘录截断 → 签名稳定、prompt 体积受限；
  - 闸口：无产物入队 retryable、有产物放行、失败计数达上限转终态。
- 对拍：用 QA 现成的真实证书 PDF（如上述 CGC 证书）跑 extract → 检查全文完整度与 OCR 页准确率。
- 回归：商务标闸口行为不变（非 docx 终态跳过），跑 `test_material_deep_parse.py`、wiki 预览相关测试。
- `git diff --check` 干净。

## 5. 分期与遗留

- 一期（本方案）：PDF extract + Wiki 预览升级 + 前端全文查看。
- 二期候选：
  - XLSX extract（pandas 读表 → 文本化 → profile），替代/补充 #130 的 excel_to_word；
  - OCR 页增量缓存（按页 sha256），重复刷新不重打；
  - docling 解耦后作为 PDF 结构化提取（表格/版面）的升级引擎；
  - 缺口匹配（gap service）消费 extract 全文，解决 PDF 素材零召回。
- 已知限制：OCR 走云端 SiliconFlow，扫描页有 API 成本与 maxTokens 约束（按页调用已规避）；5090 本地 vLLM OCR 就绪后可切换 `DEFAULT_OCR_BASE_URL` 降本。

## 6. 一期实施记录（2026-08-03）

已按 §3 落地，两处与设计稿的有意偏差：

- **profile 信封 `sourceKey` 记原始 minio_key**（而非设计稿写的全文 MinIO key）：与既有 `deep_parse_profile_for` 过期语义一致——素材被替换/重传后产物自动失效重排；全文位置由 profile 内 `fulltextBucket`/`fulltextKey` 承载。
- **fulltext 路由按现有约定落在 `/api/technical/materials/raw/{file_id}/fulltext`**（设计稿漏了 `raw/` 段）。

落地清单：

- `material_deep_parse.py`：`raw_file_deep_parse_kind` PDF → `"extract"`；`_run_extract_job`（PyMuPDF 文字层 → 缺字页渲染 PNG 按页 OCR，并发受 `TECH_WIKI_EXTRACT_OCR_PAGE_CONCURRENCY` 限制）→ 全文写 MinIO `parsed/RAW-xxx/v<n>/fulltext.md` → 同构 profile 回写；失败计数 `deepParseFailCount`（成功清零）。
- `technical_wiki_preview_generation.py`：`_docx_profile_for_raw_file` 泛化为 `_profile_for_raw_file`，PDF 有画像放行 / 无画像 `deepParsePending` 入队 retryable「已排队后台全文提取，完成后自动补全预览」；extract 连续失败 ≥3 次转终态并展示失败原因；`pdfFulltext`（页数/字数/截断）随负载透传到文件卡片。
- `run_from_manifest.py`：有 `pdfFulltext` 的卡片打 `全文已提取` tag。
- 前端 `TechnicalMaterialWiki.jsx`：卡片头部「查看全文」按钮（仅 `全文已提取` tag 时显示）+ 弹窗展示全文（页标记转分页标题，顶部标注页数/字数/截断）。
- 测试：`test_material_deep_parse.py` 覆盖文字层零 OCR、扫描页按页 OCR、页数护栏截断、失败计数、闸口终态、fulltext 服务、摘录截断与 Heading 启发式；相关回归 95 项全绿。

**上线后修复（2026-08-03 同日）**：存量 PDF 的预览缓存是历史版本写的终态 fallback（"非 docx"，retryable=False），而签名只含 headings/paragraphs/tableCount——extract 排队与否不改变签名，旧缓存永远命中，堵死 extract 排队。修复：`_preview_signature` 在 `deepParsePending` 时把该标记并入签名（仅 pending 时加入，存量 completed 缓存签名不变、全部保留）。回归测试 `test_pdf_stale_terminal_cache_does_not_block_extract` 覆盖。

**与 #130 的合并（2026-08-03 同日）**：#130 合入 Dev 后 `material_deep_parse` 新增 convert 分支（PDF/XLSX 无清洗稿 → 后台转 Word）。按 §3.1 的既定关系合并：PDF 优先 extract（`raw_file_deep_parse_kind` 中 extract 分支在 convert 之前，不采信 convert 链的图片 docx）；XLSX 走 convert；`TECH_WIKI_PDF_EXTRACT_ENABLED=false` 时 PDF 回落 convert 链。闸口入队统一带 `allowConvert: True`（extract 作业按 kind 分发，不消费该标记）。

**真实链路对拍（2026-08-03，本地 Dev）**：330 个素材刷新两轮。第一轮 23 个 PDF 全部排队 extract，作业零失败（文字层优先生效：122 页报告仅 2 页触发 OCR；页数护栏生效：80/122 截断标注）；第二轮 AI 成功 288 → 311、待重试 23 → 0。CGC 变流器证书（RAW-0366）OCR 5 页、全文 10,580 字，卡片标签 `AI预览成功 + 全文已提取`，fulltext API 返回完整证书文本。剩余 19 个本地 TLDR 为 xlsx（二期）与纯表格模板 docx（无 Heading/正文摘录，符合预期）。
