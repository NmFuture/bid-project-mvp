# 技术标目录生成:决策粒度降到二级

> 状态:**已实施**(2026-07-30,分支 `codex/tech-directory-level2-decision`)。
> 本文前半是方案,末尾"实施结果"记录实际落地情况。
> 只改技术标线:`bid-tech-outline-generator` Skill 及其 scripts,商务标 outline-generator 不动。

## 背景与目标

现状:`bid-tech-outline-generator` 对模板 **level≤3 全部节点**逐个决策(保留/建议删除),
超大章还按二级小节拆决策子树,并叠加逐招标章节强制阅读、evidence 阅读基线、全局查漏阅读门禁等
多重程序性约束,流程冗长。

目标:**决策粒度收敛到 level≤2(一级章根 + 二级节点)**,三级节点不再独立决策,
完全跟随其二级父节点;最终产物仍是完整三级目录。同时重写 SKILL.md,
让流程简洁清晰、以 opencode 自主判断为主,并保证建议增加/删除是有效、可定位的建议。

## 核心决策(已与架构师确认)

1. **决策目标 = level≤2**:一级章根也参与决策(承接整章不适用、无二级子节点的叶子章两种场景);
   二级节点逐个决策。三级节点从决策目标中移除。
2. **决策下沉**:二级节点(或整章删除时的一级节点)的 decision/reason/evidence
   在 compose 阶段冗余传播到其全部三级子节点——保留则子树全保留,建议删除则子树全部标建议删除。
   前端标签、理由、定位原文全部跟随二级父节点,**前端组件不改**(数据驱动,后端把字段落到子节点即可)。
3. **建议增加允许 L1 章和 L2 节点**,不允许直接新增三级节点。
4. **evidence_id / reason 的定位是前端展示契约,不是阅读门禁**:
   有 evidence_id → 前端标签可点击跳转招标原文;没有 → 展示 reason。
   服务端保留 evidence_id 有效性校验(必须是真实读到过的证据),
   但**取消**逐招标章节强制阅读、阅读次数/基线门禁等程序性约束,信任 opencode 自主安排阅读。
5. **保留一轮轻量全局查漏**:全部章决策完成后,从招标侧按二级粒度扫一遍遗漏,
   可提交少量修正,但不设强制新阅读基线门禁。这一环节是"有效建议增加"的质量保障,不能砍。

## 改造范围

全部位于 `code/sewpg-bid-backend/opencode/skills/bid-tech-outline-generator/`:

### 1. `scripts/decision_workflow.py`

- `_annotated_items` 过滤条件 `level<=3` → `level<=2`,决策目标只剩章根 + 二级节点。
- 决策单元简化为**一章一批**(章根 + 该章全部二级节点)。超大章按二级小节拆子树的逻辑
  (`_decision_units` 中 `MAX_DECISION_UNIT_ITEMS` 分支)可整体删除。
- 提交校验调整:additions 的 parent 只能是章根(新增 L2)或顶层(新增 L1),拒绝三级新增。
- 删除逐节强制阅读、阅读事件基线等程序性门禁;保留 evidence_id 真实性校验
  (提交的 evidenceId 必须来自受控阅读返回过的证据)。
- 全局查漏(`review-*`)保留,但去掉"必须发生新阅读才能 review-complete"的门禁,
  改为一轮自主复核 + 可选修正提交。

### 2. `scripts/outline_composer.py`

- 决策应用逻辑:suggest_delete 作用于二级节点时收拢(collapse)整个子树;
  retain 时子树全保留。
- **新增决策下沉**:compose/report 输出中,三级节点冗余携带其二级父节点的
  action/reason/evidence(basis)字段,并可加 `inherited_from` 标记来源节点(备用,前端暂不用)。
- `build_level_three_report` 及 compose 校验中按"逐三级节点决策"假设写的校验,
  改写为按二级决策 + 下沉后的一致性校验。

### 3. `scripts/run_from_manifest.py` / `scripts/review_workflow.py`

- 跟随上述接口调整:decision-next 返回结构、submission_contract 文案、
  review 流程门禁同步简化。涉及被删门禁的状态字段一并清理,不留死代码。

### 4. `SKILL.md` 重写(重点)

目标:简洁、流程线性清晰、自主决策为主。建议结构:

1. 准备(prepare)。
2. 通读模板目录(到二级即可)与招标全目录。
3. 按章决策:每章一批,对章根 + 二级节点做三类判断(保留/建议删除),外加建议增加(L1/L2)。
   判断原则保留现有"专家判断原则"的精髓但**收敛到二级粒度**:
   - 是否适用本项目、是否与其他二级节点语义重复、是否值得作为独立二级单元表达;
   - 建议增加须来自招标实际要求或完整响应单元,带已读 evidence_id;
   - 建议删除须指出具体结构问题与内容归属,不能只写"招标未提及"。
   - 明确说明:决策二级即决策其整个子树,删除一个二级节点意味着其下三级全部建议删除,
     判断时要考虑子树整体内容,可用 template-headings 查看子树再判断。
4. 附表判断(appendix 流程基本不动)。
5. 一轮全局查漏(轻量,可提交修正)。
6. compose / finalize。

篇幅控制在 100~150 行;frontmatter 的 description、allowed-tools 规范照旧。

### 5. 前端

预期**零改动**:`OutlineActionTag` 与目录页按节点上的 action/basis/reason 渲染,
后端下沉字段后三级节点自然显示父节点的标签与理由。执行时做一次页面冒烟确认即可;
若发现前端有按"节点必有独立决策"假设的校验逻辑,再最小化调整。

## 实施结果

### 与方案的差异

- **`_apply_add` 的层级限制放在决策协议层,不放在 compositor。** `decision_workflow`
  新增 `_addition_level()`,按父节点层级推导新增节点层级并拒绝 >2;
  `outline_composer._apply_add` 仍允许三级(它是共用合成引擎,层级三报表逻辑依赖该能力)。
- **`decision-next` 取消 `--max-items`。** 决策单元固定为"一个一级章的章根 + 全部二级节点",
  只有超出 24000 字节响应预算时才自动裁剪,剩余节点下一轮继续。原先按二级小节拆超大章的
  `_decision_units()` 整体删除。
- **`retain` 允许同时给 `evidence_id` 和 `reason`**(原先"二选一")。这是前端展示契约:
  有 `evidence_id` 可点击跳转原文,`reason` 同时作为说明展示。
- **决策状态 schema 升到 v7**,v6 进 `LEGACY_STATE_SCHEMAS`。旧工作区会明确报
  "目录决策协议已升级,请重新生成目录",而不是在集合比对处给出费解的错误。
- **新增一级章会插到"技术附表"根节点之前**(`_apply_add`),避免全局查漏阶段补章
  破坏 `finalize` 的"技术附表必须是最后一个根节点"约束。

### 移除的程序性门禁

`decision-batch` 的"每单元至少一次新受控阅读"基线、`review-corrections` 与 `review-complete`
的"必须新增阅读"基线全部删除(连同 `_evidence_read_event_count`、
`_arm_global_review_if_ready`、`global_review_read_baseline` 状态字段)。
保留的校验:evidence_id 必须来自受控阅读(`resolve_tender_basis`)、
`suggest_delete` 必须给 reason、附表 `missing` 必须 exclude、全局复核仍是 `decisions` 的前置。
