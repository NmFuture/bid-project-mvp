一、主链路（上传 → 入队 → Worker 执行 → 轮询进度）

1用户上传并触发解析 前端 TechnicalTenderReview.jsx
同现状：选择文件点「上传并解析」→ POST .../parse-results/upload-and-run。 差异：请求只需覆盖「上传 + 入队」，秒级返回；前端随即进入既有 1s 轮询。
▼
2保存文件 + 入队，立即返回 202 请求不再挂起
  • 保存上传文件（必须在请求内完成，文件流不可转移）——同现状
  • 加项目锁 bid:lock:s1_parse:{projectId}（已存在则 409「解析进行中」，杜绝并发覆盖）
  • RPUSH bid:jobs（job_type=s1_parse，注册进 KNOWN_JOB_TYPES）+ 登记状态 hash
  • 立即返回 202 { jobId, status: "queued" }
  • Redis 不可用时降级 submit_local_job 本地串行线程（与目录/正文生成同一兜底）
▼
3redis_worker 消费执行 独立容器 sewpg_bid_worker
BLPOP bid:jobs → 登记 in-flight → 心跳线程续锁 → 执行解析。进程重启不再丢任务：Redis AOF 持久化 + reclaim_stale_inflight_jobs 周期（300s）把崩溃残留任务显式置 failed，用户可一键重跑。
▼

  • 新增 job 级重试：可重试错误（opencode 429/5xx、连接/DB 瞬断）退避重试 ≤2 次（30s / 120s），attempt 写入状态；文件损坏等确定性错误直接 failed，给出用户可读摘要

二、进度展示与「安慰剂」摘要卡（前端新增）

真实信息层（有信号时）

  • 阶段进度条：phaseLabel + 百分比（复用现有分段映射，单调不回退）
  • 当前处理对象：文件名 / 第几个附表（progress payload 已有）
  • 阶段产出计数：当前处理对象（文件名 / 第几个附表）与 current/total 进度对；清单解读 N/58 条产出计数列为后续增强（opencode parts 计数已具备数据基础）
  • 已耗时 + 预计剩余（按阶段区间或历史均值估算）

安慰剂层（无信号时）

  • AI 解读等无细分信号阶段：心跳驱动的微推进（沿用现有 heartbeat credit 算法，不回退）
  • 轮播安心文案：「AI 正在逐条核对技术要求…」「正在追溯『详见第三卷』引用来源…」（按阶段预置，非编造数据）
  • 最近事件流（进度 events 已保留最近 80 条）摘 1 条人性化展示
  • 明确可离开提示：「解析在后台进行，可随时离开本页」

三、失败处理分层

层机制说明
内层（现状保留）opencode 恢复重试 1 次 → 技术标本地兜底parsing.py:6224-6274，带首次失败原因的恢复 prompt
Job 层（新增）退避重试 ≤2 次（30s / 120s）仅网络 / 429 / 5xx / DB 瞬断等瞬时错误；确定性错误不重试
崩溃恢复（复用）reclaim_stale_inflight_jobs 周期回收worker 崩溃残留任务 300s 内置 failed，前端「重新解析」一键重跑
兜底（复用）Redis 不可用 → submit_local_job 本地串行线程与目录 / 正文生成同一降级路径
