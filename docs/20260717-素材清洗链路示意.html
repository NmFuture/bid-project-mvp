素材文件清洗链路

上传即触发、Redis 异步执行、由 skill 内置的确定性脚本完成清洗 —— 线上链路没有 AI 参与判断，输出稳定可复现。清洗范围已收束：只清洗 .docx，其他格式一律保留原件。

触发时机

（含覆盖 / 新版本上传）

异步消费，不阻塞上传
实现载体
skill 目录里的脚本

产物为清洗稿 + cleaning_manifest.json

01主流程：从上传到清洗稿入库

六步链路，前两步在上传请求内同步完成，其余全部在后台 worker 中异步执行。

用户上传素材，先过滤再按后缀分流 material_upload_operations.py · material_taxonomy.py

快捷方式与空文件先被过滤、不入库，其余文件写入 MinIO raw/ 路径并建库记录，同时按后缀给出初始清洗状态：

.lnk / .url / .webloc / .desktop、0 字节文件→过滤 无实质内容不入库，响应里逐个提示文件名和原因
.docx→pending 等待清洗规范化 Word
.pdf / .xls* / .doc / 图片 / .md→original_only 原件直接保留，不清洗
白名单以外后缀→拒绝 整批报 400（RAW_FILE_TYPE_NOT_ALLOWED）
清洗任务入队 material_raw_object_operations.py

上传事务提交后，对每个 pending 文件调用 enqueue_cleaning_job，往 Redis 塞一个 material_cleaning 任务。覆盖 / 新版本上传会先删旧清洗稿，再重新入队。队列故障只告警、不阻断上传。

后台 worker 消费任务 workers/redis_worker.py

worker 取出 material_cleaning 任务，执行 clean_material_file_sync。非 .docx 任务（含历史遗留 pending）直接改标 original_only 结束；.docx 置为「cleaning · 正在清洗 Word 素材」。

下载原件，subprocess 调用 skill 脚本 services/material_cleaning.py

从 MinIO 下载原件到临时目录，然后直接以子进程运行 opencode/skills/bid-material-format-cleaner/scripts/driver.py（固定带 --no-feishu，默认 30 分钟超时）。skill 定位是「AI 编排 + 确定性脚本」，但后端这条线跳过 AI 编排，直接跑脚本。

driver 执行 Word 规范化 driver.py → word 事务

线上只会收到 .docx，driver 走 Word 规范化分支（详见下节），产物为标准 .docx 清洗稿，并写出结构化清单 cleaning_manifest.json。原始文件全程只读，绝不修改。

清洗稿回传 MinIO，状态写入素材元数据 services/material_cleaning.py

清洗稿上传到 cleaned/RAW-xxxx/，manifest 里的状态、日志尾部、cleanNeedsHumanReview（需人工复核）、cleanUsableForRetrieval（可否检索）等写进素材 ext_fields，供商务 Wiki 和素材匹配等下游使用。前端通过 /materials/raw/{id}/cleaned/preview·content 查看清洗稿。

02清洗只做一件事：Word 规范化

剥离封面、目录、前言等无用内容，只保留正文及其标题层级、图片和排版。PDF / Excel 转 Word 分支仍保留在 skill 脚本里，但线上链路不再触发。

Word 规范化（唯一线上分支）

.docx
  • 「单临时副本事务 + 预检快路径」：先探针判断正文起点
  • 有封面 / 目录 / 前言 / 审批页 → 最多一次 trim 切掉
  • normalize：标题去前置数字编号，保留或补齐 Heading 层级
  • 验证失败最多纠偏一次，仍异常则标 REVIEW，不做无上限试错

其他格式：保留原件

.pdf / .xlsx / .xls / .xlsm / .doc / 图片 / .md
  • 上传即标 original_only，不入清洗队列
  • 前端预览 / 下游检索直接使用原件
  • skill 内的 PDF / Excel 转换能力暂时下线，后续需要时可重新接回

03清洗结果四态

进入清洗的 .docx 由 driver 固定归入四种状态之一，状态与详情随 manifest 回写到素材元数据；非 docx 素材不进入四态，停留在 original_only。

OK已清洗

完成转换 / 切割并规范化，清洗稿可直接使用。

SKIP无需切割

前部已是正文，跳过 trim，只做规范化 + 验证。

REVIEW需人工复核

已完成事务内处理，但结果不确定，标记 cleanNeedsHumanReview。

FAIL硬失败

依赖缺失、文件损坏等，不产出清洗稿，错误信息进报告。

05目前的边界

没有手动「重新清洗」接口。路由里只有查看清洗稿的 GET 接口，触发全靠上传自动入队。清洗失败后想重试，目前只能通过覆盖上传（overwrite / version）重新触发；如需人工重触发能力，需要单独加接口。
