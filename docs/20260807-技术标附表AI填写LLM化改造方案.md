# 技术标附表 AI 填写 LLM 化改造方案

日期：2026-08-07 ｜ 状态：PR-1/PR-2 已实现，待试点对拍 ｜ 范围：技术标附表填写（bid-tech-table-filler），正文占位符填写不在本期

## 1. 背景与目标

现状：附表「AI 填写」实际由确定性脚本 `run_from_manifest.py`（约 5000 行）完成全部工作——
词典/相似度打分决定取值、结构判据定位单元格、python-docx 写回。OpenCode 会话里的 LLM
只转发一次 `s4fill <manifest>` 命令，不参与任何判断（脚本异常时后端还会静默回退本地脚本，
LLM 可整体旁路）。

瓶颈：取值决策靠同义词典 + 字符串相似度，字段名对不上词典、取值需要理解段落语义时填不准；
词典维护成本随附表类型线性增长。

目标（产品裁决 2026-08-07）：**判断类工作全部交给 AI**——读空表理解待填位置、读素材/事实表/
招标文件决定取值；脚本只保留「安全的执行手」：保格式写回、校验、报告。文件格式操作不交给
LLM（操作 XML 只有损坏风险，没有智能含量）。

## 2. 总体架构

```
后端 technical_gap_ai_fill.py（基本不变）
  └─ 准备 manifest（素材下载/OCR sidecar/事实表/招标文件，全部保留）
  └─ OpenCode 会话（agent 真正做判断）
       ① s4fill --prepare <manifest>   → fill_brief.json（待填字段清单+素材清单）
       ② agent 自由阅读素材（Bash cat，共享卷 /data/documents 路径一致）
       ③ agent 写 fill_plan.json（.tmp 原子改名，逐格：坐标+值+证据+置信）
       ④ s4fill --apply <manifest>     → 脚本校验计划 → 保格式写回 → fill_report
          校验失败 → 返回错误清单，agent 修计划重试（上限 N 轮）
  └─ 后端回收结果，落 artifact（含 opencode trace）
  └─ OpenCode 不可用/失败 → 回退现有纯脚本路径（行为不劣化，trace 标注回退原因）
```

先例对齐：本方案与 `bid-tech-fact-curator` 的分工契约同构（脚本机械准备、agent 判断、
JSON 落盘、后端校验），不是新发明。

## 3. 详细设计

### 3.1 runner 新增两个子命令（`bid-tech-table-filler/scripts/run_from_manifest.py`）

**`--prepare`：产出填写简报 fill_brief.json**（复用现有检测/抽取函数，零判断改动）

- `blankDocxPath`、`outputFile`、`planFile`（约定 plan 落盘路径）、`title/appendixId`
- `targetFields[]`：现有 `extract_target_fields` / 清单型 `_extract_list_fields_from_table` 的输出
  增强——每字段带 `targetFieldId`、`tableIndex/rowIndex/valueCol/unitCol`（现有 AppendixSpec
  坐标三元组）、字段名、行标签/列标签（清单型）、`requirementValue`（招标要求值）、`unit`、`group`
- `materials[]`：每份素材 `{id, name, route（referenceMaterial/tenderDocument/...）, path,
  ocrTextPath, originalPath(xlsx), 摘要建议}`；路径直接用共享卷绝对路径，agent 可自行 cat
- `factTableFields[]`：项目事实表 confirmed/extracted 字段（label/value/unit/status）
- `parseFields[]`、`projectTurbineModel`：原样透传
- `rules`：填写铁律（不编造、不确定写待人工补充、单位换算规则、机型只写英数型号等）

**`--apply`：校验并执行填写计划**

- 读 `fill_plan.json`，逐格校验（全部复用现有函数）：
  - 坐标存在性：`(tableIndex, rowIndex, valueCol)` 必须在 blank docx 内且是待填空位
    （`cell_needs_fill`）；清单型按列区分多格（现有去重逻辑）
  - **证据可溯源（防幻觉核心校验）**：`evidence.excerpt` 必须能在其声明的 `sourcePath`
    文件文本中原样找到（脚本 grep）；找不到 → 该格降级 `manual` 并在报告标注"证据未命中"
  - 值合法性：`usable_value`、单位换算 `normalize_value_for_field`、冲突检测 `find_conflict`
  - `action=manual` → 写死 `[待人工补充：{字段名}]`（现有 marker 契约不变）
- 校验全过 → 调现有 `fill_doc`/`set_cell` 保格式写回 → `write_sidecar_reports` 出报告
- 校验失败 → **不写文件**，stdout 返回 `{validationErrors: [{field, error}...]}`，
  agent 修正后重跑 `--apply`；SKILL.md 限定最多 3 轮，超出按失败冒泡
- 报告增强：`fillReport` 增加 `fillMode: "llm-plan"`、`model/sessionId`（后端补）、
  每格 `evidence`（来源+excerpt）进 `filledFieldDetails/evidenceRefs`（结构沿用现有字段）

### 3.2 填写计划 schema（`bid-tech-table-fill-plan-v1`）

```jsonc
{
  "schemaVersion": "bid-tech-table-fill-plan-v1",
  "fills": [
    {
      "targetFieldId": "A1-T0R3C2",        // 与 brief 逐字一致
      "tableIndex": 0, "rowIndex": 3, "valueCol": 2, "unitCol": null,
      "field": "塔架基础工程量",
      "action": "fill",                     // fill | partial | manual
      "value": "...", "unit": "",
      "confidence": 0.9,
      "evidence": {
        "sourceRoute": "referenceMaterial", // 或 tenderDocument / factTable / parseFields
        "sourcePath": "/data/documents/.../塔架与基础工程量.docx",
        "sheet": null, "row": null, "column": null,
        "excerpt": "原文原句（脚本将按此 grep 溯源）"
      },
      "reason": "为什么取这个值"
    }
  ],
  "notes": "整体说明（可选）"
}
```

decision 结构与 runner 现有 `map_fields` 输出同构，`fill_doc` 消费零改动。

### 3.3 SKILL.md 改写（`bid-tech-table-filler/SKILL.md`）

从「只调用一次命令」改为「agent 负责全部判断」，契约对齐 fact-curator：

- 流程：`s4fill --prepare` → 读 brief → 自由阅读素材 → 写 plan（`.tmp` 原子 `mv`）→
  `s4fill --apply` → 有 validationErrors 就修 plan 重试（≤3 轮）→ stdout 只回摘要 JSON
- 铁律：
  - 素材范围锁定 manifest 给定的 referenceMaterials +（规则要求时）tenderDocuments +
    事实表/parseFields；**禁止**读 manifest 外文件、禁止重新搜全库（与前端"勾选锁定唯一
    素材范围"产品裁决一致）
  - 每格必须带 evidence.excerpt 且为原文原句；找不到依据的格子 `action=manual`，禁止编造
  - 值只写数值不写单位（单位列由脚本写）；机型只写英数型号编码（AGENTS.md 既有规则）
  - 要求值（requirementValue）优先直抄
- 上下文控制（本地/弱模型友好）：一次只处理一张附表；brief 已含字段清单，素材按需 cat，
  大文件先看 OCR sidecar 文本；不要求 agent 一次读完所有素材

### 3.4 后端改动（`app/services/technical_gap_ai_fill.py`、`opencode_client.py`）

- `_build_table_filler_prompt` 重写：指向新 SKILL 流程（prepare → 判断 → apply）
- 回收方式：LLM 路径多轮读写，**不用** `early_tool_command="s4fill"` 提前收口，改为
  fact-curator 同款——等会话结束，校验 stdout 摘要 + 检查 outputFile/fill_plan.json 存在
  （`early_tool_command` 仅保留给回退路径）
- 超时：LLM 路径会话明显变长，`S4_LLM_FILL_TIMEOUT_SEC`（新环境变量，本地默认沿用
  `OPENCODE_TIMEOUT_SEC`=1800；5090 实测取值只写 `docker-compose.5090.yml`）
- 回退策略（保留但显式化）：OpenCode 建会话/执行失败 → 落回现有纯脚本 `s4fill` 路径，
  artifact 的 opencodeOutput 标注 `fallbackReason`，不再静默
- 开关：`S4_TABLE_FILL_MODE=llm|script`（默认 `script`，试点项目显式开 `llm`；评估达标后
  再切默认）——代码默认值必须是本地安全值（AGENTS.md 配置分层规则）

### 3.5 不改的部分

- manifest 组装、素材下载/OCR sidecar 准备（backend 职责，与 LLM 化无关）
- 写回保格式、`[待人工补充]` 黄高亮（FFF2CC）、fill_report sidecar、前端复核流程
- 现有纯脚本路径整体保留（回退 + 对照基线）
- 正文占位符填写（word-placeholder-filler 已是清单定位直填，无取值难题）

## 4. 测试方案

- 单测（确定性，CI 可跑）：
  - `--prepare`：对金标空表产出的 targetFields 与现状检测一致
  - `--apply` 校验器：伪造 plan 覆盖 坐标越界 / excerpt 不在来源文件 / 单位换算 /
    manual 标记 / 清单型多列 五类用例
  - 端到端：手写一份正确 plan → apply → 输出 docx 与金标对拍（复用
    `eval_fill_vs_golden.py` 的对拍机制）
- LLM 路径（非 CI）：试点附表（建议从清单型供货清单或机型参数表起步，结构规整、
  现有脚本基线明确）用真实素材跑 LLM 路径，与脚本路径结果对拍，指标：
  **人工修改率**（复核时改了几格）、证据命中率、单表耗时
- 词典/打分逻辑改动仍须跑 `eval_fill_vs_golden.py`（SKILL.md 既有纪律延续）

## 5. 试点与推广

1. PR-1：runner `--prepare`/`--apply` + 校验器 + 单测（无行为变化，纯增量）
2. PR-2：SKILL.md 改写 + 后端 prompt/回收/开关，默认 `script`
3. 试点项目开 `llm` 跑真实附表，对拍调优（prompt/素材切片策略；5090 模型与超时取值
   由发布负责人在 5090 配置层实测）
4. 达标后切默认 `llm`，脚本路径保留一个版本周期作为回退

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| LLM 编造值 | excerpt 原文 grep 校验，命中不了强制 manual；报告标注证据未命中 |
| 本地/网关模型能力弱 | 一次一张表、brief 预切片、严格 JSON schema；输出走现有 `_repair_json_payload` 修复会话 |
| 会话变长、超时 | 独立超时环境变量；素材按需读取而非全文喂入；5090 实测调并发/超时 |
| 坏格式 | LLM 不碰文件，写回只用现有 `fill_doc`/`set_cell`（保格式已验证） |
| OpenCode 故障 | 显式回退纯脚本路径并在 artifact 标注，行为不劣化 |
| 上下文超长 | brief 只给字段清单+素材路径，agent 按需 cat；超大素材优先 OCR sidecar 文本 |
