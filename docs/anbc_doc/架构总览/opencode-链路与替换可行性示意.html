先说结论

可行，且改造半径比想象中小。 后端对 opencode 的全部依赖收敛在 OpencodeClient（约 2700 行）一个类里；业务侧只认「建会话 → 发 prompt → 拿 JSON / 读产物文件」这套语义。 只要抽象出一个 AgentEngine 接口（create_session / send / stream_events / abort），Codex 和 Pi 都能作为第二个实现接入，上层 S1~S4 各阶段 service 与 prompt 内容基本不用动。

我们实际依赖 opencode 的 5 个能力（替换时必须对齐的接口面）

  • 常驻 server + REST 会话模型：POST /session、/message、/abort，多会话并存。
  • 消息流轮询：GET /session/{id}/message 拿到增量输出，用于进度推流、idle 监管、以及 early completion（检测到 s1parse-finalize 这类终止 bash 命令完成后直接收割产物，不等 LLM 复述大 JSON）。
  • Skill 加载机制：prompt 第一句「Use the bid-xxx skill.」依赖 .opencode/skills/ 的发现与注入。
  • provider/model 每次请求可指定：payload 里带 {providerID, modelID}，配合系统设置的自定义 LLM。
  • bash 工具 + 共享文件系统：CLI 包装命令（s1parse 等）和 /data 卷 —— 这部分与引擎无关，任何带 shell 工具的 agent 都能跑。

候选引擎对比

维度opencode（现状）OpenAI Codex CLIPi（pi-mono / pi-coding-agent）
非交互/服务化 ● opencode serve 常驻 HTTP server，正是我们现在用的形态 ● codex exec 一次性 headless 进程（支持 resume 续会话、JSON 事件流）；也有 app-server / MCP server 形态，但生态不如 exec 成熟 ● 四种模式：interactive / print·JSON / RPC（JSON-over-stdio 常驻服务） / SDK，RPC 模式与 opencode serve 最神似
会话模型映射 多 session REST ● 一个 session ≈ 一个 exec 进程，abort=杀进程；进度=解析事件流（比轮询更实时） ● RPC 进程按 JSON 命令驱动，事件流推送，多会话要起多进程
early completion 收割 轮询消息里找已完成的 bash 工具输出 exec 事件流是结构化的，识别「finalize 命令完成」反而更容易 RPC 事件流同理，bash 工具调用有结构化事件
Skill 体系迁移 .opencode/skills/*/SKILL.md 需转成 AGENTS.md / prompt 注入；SKILL.md 内容本身可复用，但「Use the xxx skill」的发现机制要重写 加载 AGENTS.md/CLAUDE.md + 自定义 SYSTEM.md；Skill 发现同样要适配一层
模型/Provider 任意 OpenAI 兼容 provider，按请求指定 OpenAI 系为主；config 可配自定义 provider/base_url，但按请求动态切 provider 需验证 多 provider 设计就是它的卖点之一，切换灵活
许可/可控性 开源，已锁定 1.18.2 自用 开源（Rust），迭代快，跟随 OpenAI 策略 开源，极简（4 个工具），作者个人项目色彩浓
主要风险 —（现状基线） 没有官方常驻 REST server 语义，需用进程编排补齐 session 池；事件协议版本变动要跟进 社区与生产验证少；edge case（超长会话、工具输出污染）需自己趟
接入工作量估计 — 中：引擎适配层 + session 进程管理 + Skill 注入适配，核心链路 1~2 个冲刺可见 demo 中偏小：RPC 协议简单直接，但周边（重试、监管）要自己补齐

注：Codex 能力依据 codex exec 官方 headless 文档与 DeepWiki 源码导览；Pi 依据 pi-mono 仓库 docs/rpc.md 及作者设计文章。两者均以 2026 年中的公开资料为准，落地前建议各做一个 1 天级 PoC 复核。

建议的迁移路径（不动业务代码）

  • 第 0 步：把 OpencodeClient 的公开方法抽成 AgentEngine 协议（Python Protocol/ABC），现有实现改名 OpencodeEngine，全量测试保持绿 —— 纯重构，无行为变化。
  • 第 1 步（PoC）：选 S1 分片会话（run_tender_parse_shard_with_trace）做 Codex/Pi 的试点 —— 它不依赖 finalize 提前收割、不解析业务 JSON，是依赖最少的一条链路。
  • 第 2 步：补 early completion 的等价物（解析引擎事件流里的 bash 工具完成事件），再迁移 S1 finalize、S2 目录这类强依赖收割的链路。
  • 第 3 步：Skill 注入适配层 —— 把「Use the xxx skill」翻译成目标引擎的指令注入方式；CLI 包装命令和 /data 卷原样保留。
  • 第 4 步：引擎做成配置项（AGENT_ENGINE=opencode|codex|pi），5090 实测取值仍只落 5090 专属配置层，符合仓库的发布分工约束。
最大的隐藏工作量不在「调起来」，而在语义对齐：idle 超时、abort 后产物回收、工具输出不是 JSON 时的修复重解析（_repair_json_payload）、以及 S2 接力会话这类多会话编排，都是围绕 opencode 行为调出来的。换引擎后这批监管逻辑要用真实长任务重新验证一轮。
