# 技术标正文素材匹配 — 证据片段召回方案

## 0. 一句话

技术标缺口里**附表（表格）走来源矩阵规则已通**；但**非附表的正文/专题类缺口**目前只有"目录号 + 标题关键词"的粗粒度召回，召回粒度是整份 docx、且对近半数缺口召不回素材。本方案把商务标已验证的 **evidenceSegments（段落级证据片段）+ LLM-free 打分召回** 移植到技术标的"非附表"分支，**不触碰附表的规则路径**。

## 1. 结论先行（边界）

判定分叉点已存在于 planner（`bid-tech-gap-planner/scripts/run_from_manifest.py` 的"是否附表"分支），本方案只在"非附表"一侧增强：

| 缺口类型 | 判定 | 召回方式 | 本次是否改动 |
| --- | --- | --- | --- |
| 固定素材 | `decision = ready` | 不匹配，直接用 | 否 |
| **附表 → AI 填表** | `fill_required` + 有 `appendixTasks` | **来源矩阵 `sourceRouting` 规则路由** | **否（保持规则）** |
| **正文 → 素材匹配** | `fill_required` + 无 `appendixTasks` | **evidenceSegments + 打分召回** | **是（本次新增/增强）** |
| 人工补料 | `decision = material_required` | 人工上传入口 | 否 |

核心原则：**能走规则的（附表）就走规则；走不了规则的（正文）才用打分召回机制。**

## 2. 现状证据（PRJ-0010 实测，2026-06-27 识别）

143 个目录项，按处理方式分桶：

| 处理方式 | 数量 | 说明 |
| --- | --- | --- |
| ① 固定素材 (`ready`) | 31 | 不用匹配 |
| ② 附表 → AI 填表 | 81 | 走规则；其中 50 项已挂来源矩阵 `sourceRouting` |
| ③ **正文需匹配 (`material_match`)** | **13** | 走打分召回 ← 本次目标 |
| ④ 人工补料 (`material_required`) | 18 | 留人工入口 |

关键问题：③ 的 13 项里，**6 项 `candidateMaterials` 为空**——现有"目录号 + 关键词"召回对接近一半的正文缺口召不回任何素材。这正是粒度过粗（只到文件、不到段落）导致的。

数据来源：`GET /api/technical/projects/PRJ-0010/gaps` 的 `gapPlan.items`，逐项按 `decision` / `appendixTasks` / `candidateMaterials` 统计。

## 3. 根因（不在匹配算法，在被匹配的料）

| 维度 | 技术标 Wiki（现状） | 商务标 Wiki（现状） |
| --- | --- | --- |
| 生成方式 | **确定性镜像**三级目录树（`technical_wiki_generation.py`），只补"AI 内容预览卡片" | LLM 精修 + OCR 抽字段 + **段落切分** |
| 证据片段 | **无 `evidenceSegments`** | 生成时预切：`segmentId / title / sourcePages / summary / keywords` |
| 缺口消费 | 仅按 `skeleton_section` 目录号做**结构匹配**，召回整份文件 | 召回到段落，带相关度/有效期/可用模块 |
| 打分 | 内部排序分（标题匹配 +520 等），**无对外 matchScore** | LLM-free 算法分（相关度 + 机型覆盖 + 负向惩罚） |

结论：技术标缺的不是匹配算法，而是**段落级证据片段**。没有它，正文缺口只能拿"文件 ID + matchReason 文本"去配，且无法定位"该用这份素材的哪一段"。

参考商务标已验证实现：`app/services/business_gap_planning.py:659-872`（三级切分：Wiki 卡片内嵌段落 → 清洗 Word 自动切片 → 文件级兜底）。

## 8. 三分边界（实测后确认）

正文缺口不是一刀切都走打分召回。按"库里有没有对应素材"分两类，加上表类，共三分：

| 缺口类型 | 判定 | 处理 | 本次 |
| --- | --- | --- | --- |
| 表（附表/空表） | `fill_required` + 有 `appendixTasks` | 来源矩阵 `sourceRouting` 规则路由 | 不动 |
| 正文·库里有料 | `fill_required` + 无附表 + 匹配到候选 | 候选 + `evidenceSegments` 打分召回 | 增强 |
| 正文·项目特定无料 | 文件级召回为空 → `material_required` | 人工补料/上传 | 不动（系统正确兜底） |

要点：证据片段是叠加在"已召回候选"之上的精度增强，**救不了也不该救"零候选"缺口**。
试验监造、考核指标、项目验收、交货进度等高度项目特定的内容，库里本无现成素材，
系统判为 `material_required`（人工补料）是预期行为；硬塞通用素材召回反而会误导填写。

## 9. 回归结论（PRJ-0010）

### 9.1 本地离线复跑（逻辑链路）

方法：导出容器内 PRJ-0010 的 manifest/toc/parse_result/来源矩阵到本地，用改后 planner
复跑，对比容器基线 `gap_plan.json`。

- **零回归**：①固定 31 / ②附表 81 / ③正文 13 / ④人工补料 18，与基线逐项一致；
  附表项 81、带 `sourceRouting` 50 项也逐项一致。
- **正文召回（链路验证）**：注入片段后，6 个有候选的正文缺口成功挂上 `recalledSegments`。

### 9.2 端到端（容器内，真实 docx 片段）

方法：重建 fastapi/worker 镜像 → 触发 Wiki 预览任务（异步切真实 docx 片段，1438/1934
文件切出 evidenceSegments）→ 重跑 PRJ-0010 识别（走 opencode agent 主路径）。

- **零回归**：①31 / ②81 / ③13 / ④18、附表 81、sourceRouting 50，与基线逐项一致。
- **正文召回增强（真实生效）**：7 个有候选的正文缺口（GAP-0002/0033/0034/0036/0044/0048/0052）
  全部挂上真实 `recalledSegments`，带 `matchScore`。
- **6 个无料缺口（GAP-0053~0057/0140）**：候选 0、片段 0，正确归为人工补料，见 §8。

## 9bis. 关键架构发现：agent 主路径绕过本地 planner（路线 B）

调研期把 `run_from_manifest.py` 当成主执行路径，**有误**。实测 `technical_gap_planner.py`
的 `run_technical_gap_planner_skill` **优先走 opencode agent**（`providerId: opencode`），
本地脚本仅为 agent 失败时的 fallback。因此只改 `run_from_manifest.py` 时，agent 路径
**不会执行**段落召回，生产环境拿不到片段。

修正方案（路线 B，已落地）：在 `build_technical_gap_plan_for_project` 拿到 plan 之后
做一道**确定性后处理** `_attach_evidence_segments_to_plan`——无论 plan 由 agent 还是
本地脚本产出，都统一按 `material_index` 的片段对候选做打分召回并回填。职责切分：
**agent 管「召回哪些素材」，确定性后处理管「挂段落级证据 + 打分」**，符合 §6 的 LLM-free 原则，
两条执行路径都能拿到片段。
